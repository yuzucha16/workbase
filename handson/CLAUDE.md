# ai-handson: AI活用ハンズオンの設計と育成

このディレクトリで、AI活用の小さなタスクを「ハーネス6要素」の表に落とし込み、実装しながら育てる。
Claudeは、以下の進め方とルールに従って作業する。

## ディレクトリ構成

- `CLAUDE.md`: このファイル。進め方とルール(毎セッション自動で読まれる)
- `templates/task-template.md`: 新しいタスクを作るときの記入テンプレート
- `templates/changelog.md`: テンプレート自体の改訂ログと、抽象化タスクの依頼文
- `tasks/`: 1タスク1ファイル。育成中のタスクはすべてここに置く
  - 記入例: `tasks/comms-digest.md`

## 作業の基本

- 新しいタスクを作るときは、`templates/task-template.md` を読み、`tasks/<タスク名>.md` を作る
- 既存タスクを更新するときは、`tasks/` の該当ファイルを直接編集する
- テンプレートは勝手に書き換えない。改訂案を提示し、承認を得てから `templates/task-template.md` と `templates/changelog.md` を更新する

## 進め方

1. 人間から「タスクの前提」を受け取る。不足があれば、答えないと表が埋まらない点だけを質問する(1回につき1つ)
2. 6要素の表を埋める。**v0は最小構成**にし、最初から作り込まない
3. 実装順を提案する(目安: ツール層 → コンテキスト管理 → 権限 → 状態 → 検証 → 制御フック。フックは失敗パターンが見えてから足す)
4. 人間が実装して失敗ログを持ち帰ったら、「落とし穴」「v1」の列を更新する
5. 学びがテンプレート自体に影響しそうなら、通常の回答とは別に「テンプレ改訂案」を出す

### ルール

- 確認していない仕様(製品の機能や制限)は断定せず、「要確認」と明記する
- 権限は最小(読み取りのみ、書き込み先は限定)から始め、必要になってから広げる
- 完了条件は、人間が実際に確認できる形で書く
- 6要素すべてを厚くしない。今回のタスクで効くところだけ具体化し、他は1行で済ませてよい

### 実装担当の判別

表の「実装担当」列に、次の3区分のどれかを書く。

| 区分 | 対象 | 例 |
|---|---|---|
| AIが実装 | ローカルのファイルや設定、コード、Markdown。テキストで完結し、差分を確認でき、元に戻せるもの | settings.json、スクリプト、Markdown |
| 人間が実装 | 自分の資格情報やテナント権限が必要なもの、共有設定や権限付与など外部に影響する操作 | Power Automate、SharePoint、Copilot Studioの設定 |
| AIが下書き、人間が実行 | 中身はAIが作れるが、設定作業は人間が行うもの | エージェントの指示欄の文面、フローの設計手順、式、命名 |

判別の問い(上から順に確認する):

1. 自分の権限や資格情報がないと触れないか → はい: 人間、または下書き止まり
2. 誤ったときに外部へ影響するか、元に戻せないか → はい: 人間
3. AIが結果を確認・差分レビューできるか → いいえ: 人間

迷ったら人間側に倒す。失敗ログで実態と合っていたかを見直し、区分の基準を更新する。

## 6要素の観点(何を問う要素か)

| 要素 | 問い |
|---|---|
| ツール層 | AIは何を呼び出せて、何をトリガーに動くか |
| コンテキスト管理 | AIに何を、どの形で渡し続けるか(指示書、参照データ) |
| 権限とサンドボックス | AIに何を許し、何を禁じ、どこまでしか書き込めないか |
| 制御フック | 実行の前後・失敗時に、何を自動で挟むか(スケジュール、リトライ、検知) |
| 状態と永続化 | 実行をまたいで、何をどこに残すか |
| 接点(UI)と検証 | 人間はどこで結果を見て、どう正しさを確かめるか |
