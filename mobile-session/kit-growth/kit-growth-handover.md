# 引き継ぎ: workflow-kit の育て方（改善の経路）

- 作成: 2026-10-15（モバイルのセッションでの検討）。
- 状態: 方向は合意済み。**着手は、PC2 で並行中の AI の見せる範囲（ai-workspace-boundary）の話が終わってから。** 順番は「`mobile-session/` → `topics/` の改名（別の話題で決定済み）→ この経路の整備」。

## 前提（ユーザーが明示）

| # | 内容 |
|---|---|
| 1 | PC1（実務。projects / areas を使う）と PC2（workbase を改善する）は別の端末 |
| 2 | PC1 は GitHub が使えず、ローカルのリポジトリにコミットする。workbase は pull のみ |
| 3 | PC2 は works と workbase の両方を push / pull してよい |
| 4 | PC1 → workbase のオンラインの改善の経路は無い。PC1 で使った印象を、帰り道にモバイルで壁打ちしてメモにし、取捨選択・優先づけして大事なものをトピックにする。家に着いてから PC2 で直す |
| 5 | 運び方は今のままで足りる（忘れて落ちるものは無い） |
| 6 | exmem もあまり使われていない（2026-10-14 に少し使った程度） |

## 現状の kit の約束とのずれ

kit の約束（各フックの改善案 → `improvements.md`、週1の `review` が `events`/`sessions` を読む、自動採用）は、PC1 の記録を PC2 で読める前提で、実際の経路に乗っていない。`improvements.md` の新規は 2026-10-08 以降1行だけ。

## 決まったこと（ユーザーの合意。2026-10-15）

| # | 内容 |
|---|---|
| 1 | 改善の受け皿は workbase の `topics/` に置く（モバイルと PC2 の両方から届くため。PC2 の works には置かない） |
| 2 | workbase の改善を Area 型のトピック（例: `topics/kit-growth/`）にし、壁打ちで出た印象はその inbox に入れる。育った話は Project 型の子トピックに切り出し、PC2 で直して close する |
| 3 | 今の仕組み（トピックの docs 型、open / close、review）を流用して改善の経路をつなぐ。足すより畳む |

## 次にやること（案。PC2 で、上の順番が来たら）

1. `topics/kit-growth/` を作る（`topics/` の型に従う）。
2. `review` の入力を、PC1 の記録の代わりに、kit-growth の inbox と動いているトピックに変える（30日動かないトピック、終わったのに残るトピック、inbox の未選別を見る）。
3. `improvements.md` は追記をやめて凍結する。`hook-common.md` の「改善」の「1行足す」を「トピックの decisions に書く」に変える。
4. フックの改善案は残す（PC1 で出た分は壁打ちで inbox へ）。
5. 自動採用は 2026-11-08 の判定で畳む方向。

kit の変更は、従来どおりユーザーの承認を得てから行う。
