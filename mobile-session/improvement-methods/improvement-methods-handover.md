# 引き継ぎ: 作業の進め方の型（やり方集・取扱説明書・start のモード）

- 作成: 2026-10-14（モバイルのセッションでの検討の終了時）。
- 読む順: この文書 → [[improvement-methods-next-steps]]。詳細は `exmem/inbox/` の6本（下の表）。
- 状態: inbox の6本と、`start` のモード（kit の変更）まで反映済み。**点検スクリプトは未実行**（モバイルの環境に `pwsh` が無い）。型の実測はこれから。

## 目的

ユーザーが自分の型をやり方集に明文化し、セッションの進め方をこの型で進める。きっかけは、開始インタビュー（`start`）がうまく機能していなかったこと。ユーザーの仮説は「進め方の整合を前もってAIとそろえていないから」。ユーザー自身が第三者レビューで磨くことを望んでいる。

## 決まったこと（ユーザーが明示）

| # | 内容 |
|---|---|
| 1 | 「問題解決のやり方」と「改善のやり方」は別系列。やり方集と、AI の取扱説明書は分ける |
| 2 | 改善1: 現状を数値にし、10%・20%・30% の固定の刻みで選択肢を比べる。刻みは実現難易度を数値で表すため。バッチ内は同じ測り方で、実行後に測り直す |
| 3 | 問題解決2: 前提を書き戻して、決定に差し戻す。差し戻しは最大3回（全体4回）。上限は実測ではなく適当な数字 |
| 4 | 改善2: 想定と実際のズレを仮説にして修正する。仮説は AI に伝えない（AI は肯定に寄るため）。期待と実際だけを渡す |
| 5 | 取扱説明書には、ユーザーの悪い面も書く。public になっても許容する（人物特定できないため） |
| 6 | セッションをA（ゴールを決める）とB（達成する）に分け、開始時に確定型か探索型かを1問で決める |
| 7 | `start` のモード追加（差分は承認済み）。ユーザーは「まずはやってみます」 |

## 注意（推測を含む点）

- 取扱説明書の「やらないことを先に決める」「引き継ぎ前提で終える」は、AI の推測（仮説）。確認が要る。
- モードの目安（成果物の合否を事前に書けるか）と、4回の上限は、実測の裏づけが無い。
- 改善1の実例（性能改善）の、リスク・影響・難易度の表の中身は未記録。実例2（定例会）の採用理由は記録済み。
- start-hook から型のノートを指していない。型は inbox にあり、整理すると消えるため。lessons へ統合した後に、参照を足すかを決める。
- `events` の `kind` の定義は呼び出し元（作業側）の `AGENTS.md` にあり、このリポジトリに無い。`goal_change` の追記が PC 側で要る。
