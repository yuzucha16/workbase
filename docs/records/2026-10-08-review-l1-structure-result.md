## 前提として置いた仮定

- 仮定A: 「常時読み込み 約8万字」は、`start` などの開始時に、作業ログ全文・判断記録全文・運用規則・作業側 AGENTS をエージェントが読む合計である。
- 仮定B: Claude Code は、親ディレクトリの CLAUDE.md を起動時に読み、サブディレクトリ（例: `resources/` 配下）の CLAUDE.md は、そこのファイルに触れたときに追加で読む。したがって知識を1件読むと、共有側 AGENTS（4KB）と知識置き場 AGENTS（8KB）も一緒に読まれうる。Codex・Copilot の読み込み範囲はこれと異なりうる。
- 仮定C: 旧リポジトリの clone は、ワークスペースの配下（エージェントの検索範囲内）にある。
- 仮定D: `exmem/contexts/` には、モバイルやクラウドで行った**業務の**作業状態が入りうる。
- 仮定E: 作業側の「非公開の remote」は、ユーザーの個人アカウントにある。クラウドのセッションから clone してよいかは、会社の規程上まだ決まっていない。
- 仮定F: 手順書の利用者は、実質ユーザー1人（の複数の PC とクラウド）。第三者が共有側を単独で使う予定は、当面ない。

## 指摘（重大度順）

### 高

**1. 常時読み込みの8割は、構造ではなく「作業ログと判断記録を毎回全文読む」設計から来ている**
- 根拠（事実）: 常時読み込み約8万字のうち、作業ログ約5万字＋判断記録約1.4万字＝約6.4万字（8割）。作業ログは 94KB で、退避の規則が無い。
- 放置した場合: ログは追記で単調に増え、開始のたびにコストが増える。長い文脈の中で、AGENTS の規則（安全規則を含む）が相対的に埋もれ、読み落としが増える（一般的な傾向。仮定）。案 A〜E のどれを選んでも、この部分を変えない限り削減は小さい。
- 最小の対策: 作業ログを2つに割る。「現在状態・次にやること」だけの短いファイル（上書き。上限 3KB 程度）を開始時に読み、経緯の追記ログは開始時に読まない（必要なときに検索する）。判断記録も開始時の読み込みから外す。

**2. 共有側（公開されうる側）が、作業側の構造を前提にしている**
- 根拠（事実）: 手順書8本が、作業側の指標 CSV の列や記録ファイル名を名指ししている。共有側 AGENTS は「単独で clone しても自己完結する」と書いており、記述と実態が矛盾している。知識置き場の AGENTS にも、作業側の `転記待ち` や終了処理の記述がある。
- 放置した場合: 共有側を公開したとき、作業側の運用の内部構造が外に出る。また、作業側を変えるたびに共有側の手順書も直す必要があり、参照の方向が実質的に双方向になる（「共有側から作業側へのリンク禁止」は、リンクとしては守られていても、依存としては破られている）。
- 最小の対策: 依存の向きを逆転させる。手順書側に「作業ディレクトリに期待するもの」を1枚の**契約**として書き（例: 「AGENTS.md と、現在状態のファイルがあること」程度）、手順書は契約の名前だけを使う。作業側固有の記録（指標の列など）は手順書から出し、作業側の AGENTS か作業側のスクリプトに置く。L0 で指標を縮小したので、消せる記述も多いはず。

**3. 呼び出し表の写しが5か所にあり、既に2か所がずれている**
- 根拠（事実）: 作業側 AGENTS、共有側 AGENTS、手順書置き場 README、ひな形 AGENTS、個別リポジトリの AGENTS。共有側と個別リポジトリは旧名のまま。旧名の案内ファイルで、たまたま動いている。
- 放置した場合: 合言葉や手順書を変えるたびに、写しの更新漏れが起きる。エージェントが旧い写しを正と誤読し、旧い手順を実行する。
- 最小の対策: 呼び出し表の正本を手順書置き場の1ファイル（例: `hooks.md`）に置き、ほかの場所は「合言葉を受けたら、手順書置き場の `hooks.md` を読む」の1行だけにする。ひな形も1行にする。旧名の案内ファイルは、写しを直した後に消す（別名は正本の表に残す）。

**4. `exmem/contexts/`（引継ぎコンテキスト）が、公開されうる側にある**
- 根拠（事実＋仮定D）: 引継ぎコンテキストは「作業側から見えない場所の作業の現在状態」。固定の制約は「作業側の機密・会社固有の情報を共有側に出さない」。業務の作業状態は、会社固有の情報を含みやすい。消化する手段も未定。
- 放置した場合: 業務の文脈が、意図せず公開可能な場所に溜まる。消化されないまま、古い状態が残り、誤読される。
- 最小の対策: 共有側を公開する前に、`contexts/` の置き場所を決め直す。業務の文脈を含みうるなら、非公開側（作業側の非公開 remote か、別の非公開リポジトリ）へ移す。仮定Eの規程を確認するまでは、共有側の公開を保留する。

### 中

**5. 規則を書く場所に、正本の線引きが無い**
- 根拠（事実）: 規則が、AGENTS（毎回）、手順書（呼ばれたとき）、README（50KB。人間向けとエージェント向けが混在）、判断記録（経緯）に分散している。最も読まれた「運用規則」（約9千字）は、AGENTS とは別に「始める前に必ず読む」と指示されている。
- 放置した場合: 同じ規則が複数箇所に書かれ、矛盾したとき、どれが正か判定できない。
- 最小の対策: 3層に固定する。(1) **憲法**＝AGENTS（毎回読む。安全規則・恒久前提・手順書への入口だけ）、(2) **手順**＝手順書（合言葉で呼ばれたときだけ読む）、(3) **案内**＝README（人間向け。エージェントには読ませない）。判断記録は規則の置き場にしない（規則に昇格したら手順書か AGENTS に移し、判断記録には根拠とリンクだけ残す）。運用規則9千字は、憲法に入れる分（数百字）と手順に回す分に分解する。

**6. 手順書の変化が速く、付随文書が本体より大きい**
- 根拠（事実）: 版が1日に5回上がった日がある。README 50KB、改善記録 42KB に対し、手順書本体は31ファイル 247KB（README と改善記録で約4割）。承認なしで変えられる「自動採用の規則」節がある。
- 放置した場合: 手順が安定せず、複数 PC 間で「どの版で動いたか」がずれる。L0 で指摘した「整備の本業化」が、構造として固定される。
- 最小の対策: 案Cを採る。版番号の運用をやめて git のコミット（必要ならタグ）で代える。変更履歴と改善記録は git の履歴と `archives/` へ移す。README は数KBの案内にする。「自動採用の規則」節は凍結する。

**7. 知識化の経路（判断記録 → inbox → 統合 → 台帳 → 転記済）が、効果に比べて重い**
- 根拠（事実）: 判断記録の各項目に5種類以上の状態があり、人手の Markdown で遷移させている。台帳 `integrated.md` は、その確定の根拠。一方、知識42件のうち業務側で読まれたのは5件（L0）。
- 放置した場合: 状態の更新漏れが溜まり、`転記待ち` が増え続ける。これを解消する作業自体が見直しの時間を奪う。
- 最小の対策: 構造化（YAML・CSV 化）ではなく、**簡素化**する。状態は「済／未」の2つにするか、状態を持たずに「知識化したら判断記録にリンクを1行足す」だけにする。台帳は git の履歴で代える（凍結）。昇格の起点は、L0 の `again`（繰り返し言ったこと）を最優先にする。

**8. 手順書の場所を、固定パスで各 AGENTS に書いている**
- 根拠（事実）: `$HOME\works\resources\workflow-kit` と WSL のパスが、各ディレクトリの指示ファイルに書かれている。クラウドのセッションでは、どちらのパスも存在しない。
- 放置した場合: パスの写しも、呼び出し表と同じくずれる。クラウドでは、毎回「読めない」で止まる。
- 最小の対策: パスの定義を**マシンごとに1か所**にする。各 PC のユーザー全体の指示ファイル（Claude Code のユーザー設定の CLAUDE.md など）に、共有側の場所を1行書き、dotfiles で管理する。各ディレクトリの AGENTS からパスを消す。クラウドでは、共有側を clone した場所を、そのセッションの最初に1行で伝える（または clone 先を規約で固定する）。環境変数は、エージェントによっては読む手順が増えるので、主にはしない（仮定B：エージェントごとの読み込み範囲の差は要確認）。

**9. 知識を1件読むと、運用の規則も一緒に読まれうる**
- 根拠（仮定B）: 知識置き場の AGENTS（8KB）に、台帳や作業側の手順の記述がある。知識に触れると、それが読み込まれうる。
- 放置した場合: 知識を読むコストが不必要に高くなり、「読めば分かることを聞かれない」の妨げになる。
- 最小の対策: 知識置き場の AGENTS を、「知識の書き方（見出し・frontmatter・タグ）」だけに縮める（目安 1〜2KB）。統合の手順は手順書へ移す。あわせて、知識の索引（1件1行の要約。数KB）を置き、エージェントは索引から探す。

**10. 旧リポジトリの clone が、検索範囲に残っている**
- 根拠（事実＋仮定C）: 旧構成の完全な写しで、旧名のファイルを含む。
- 放置した場合: エージェントが検索したとき、旧い規則や旧い知識を拾って誤用する。
- 最小の対策: ワークスペースの外へ移すか、消す（remote に残っていれば再 clone で戻せる）。

### 低

**11. 検査スクリプトが PowerShell で、クラウドで動かない**
- 根拠（事実）: クラウドのセッションに PowerShell が無い。
- 放置した場合: クラウドで知識を書いたとき、検査を飛ばすことになる。
- 最小の対策: 検査を最小限に絞ったうえで、どこでも動く言語（Python や POSIX sh）に寄せるか、「検査は PC でだけ行う」と割り切って明記する。詳細は L5 で扱う。

**12. 周辺物（チートシート・ハンズオン。約90KB）が共有側に同居している**
- 根拠（事実）: 本運用と関係が薄い。
- 放置した場合: 検索のノイズと、責務の説明の複雑化。実害は小さい。
- 最小の対策: 別リポジトリにするか、`archives/` に移す。急がない。

**13. 指標（`docs/metrics/` 約150KB）が PC ごとに閉じている**
- 根拠（事実）: CSV とスクリプトが PC ごと。L0 で、計測は `again` の件数などに縮小済み。
- 放置した場合: PC 間で集計が合わないが、L0 の方針では影響は小さい。
- 最小の対策: 縮小後の指標（`again` の件数など）は、作業側の判断記録か週の見直しの記録に1行で残せば足り、CSV の仕組みは凍結してよい。

## 責務の1文（推奨後の姿）

| 単位 | 責務（1文） |
|---|---|
| 作業側リポジトリ | 機密を含みうる、この仕事の現在状態と経緯を持つ（非公開）。 |

| ユーザー全体の指示（PC ごと。dotfiles 管理） | そのマシンでの共有側の場所を持つ。 |

## データ構造の診断

| データ | 正本 | 寿命・退避・上限 | 推奨 |
|---|---|---|---|
| 作業ログ | 1つ（各作業ディレクトリ） | **規則なし**。開始時に全文 | 「現在状態」（上書き・3KB 上限・開始時に読む）と「経緯ログ」（追記・月ごとに分割・開始時に読まない）に分ける |
| 判断記録 | 1つ | 規則なし。状態5種以上 | 開始時に読まない。状態は2値か廃止。規則に昇格したら移す |
| 知識 | 1つ | 上限なし。42件 519KB（1件平均約12KB） | 索引（1件1行）を追加。3か月読まれないものは L0 の基準でアーカイブ |
| 未整理メモ（inbox） | 1つ | 統合で削除 | 現状でよい。作成時の版は、コミットの識別子で代える |
| 台帳 | 1つ | 追記のみ | git の履歴で代え、凍結 |
| 引継ぎコンテキスト | 1つ | **消化手段なし** | 置き場所を非公開側へ（指摘4）。`start` で読んで現在状態に統合し、消す手順にする |
| 手順書 | 1つ（ただし呼び出し表は5写し） | 版が頻繁 | 呼び出し表を1か所に。版は git で |
| 指標 | PC ごと | 規則なし | 凍結。縮小後の件数だけ見直し記録に残す |

人手の Markdown で持っている状態遷移は、**構造化より削減**を推奨する。1人・数十件の規模では、YAML や CSV にしても、それを保つスクリプトと規則が増え、L0 の規模凍結に反する。

## 指示ファイルの縮小（サイズ予算の目安）

| 対象 | 現状 | 目安 | 出すもの → 行き先 |
|---|---|---|---|
| 開始時の常時読み込みの合計 | 約8万字 | **1万字以下** | 作業ログ全文・判断記録全文 → 開始時に読まない |
| 作業側 AGENTS | 約8KB（箇条約13項目） | 3KB 程度 | 指標の記録手順 → 凍結。`start` `review` `wrap` の細則 → 手順書。push の許可リストと安全規則 → 残す（先頭に置く） |
| 運用規則（必ず読む指示） | 約9千字 | 憲法に入る数百字＋残りは手順書 | 分解して廃止 |
| 共有側 AGENTS | 4KB | 1〜2KB | 呼び出し表 → `hooks.md` への1行 |
| 知識置き場 AGENTS | 8KB（104行） | 1〜2KB | 台帳・作業側の手順 → 手順書 |
| ひな形 AGENTS | 28行 | 10行程度 | 呼び出し表とパス → 1行のポインタ |
| 手順書置き場 README | 50KB | 数KB | 変更履歴・改善記録 → git と archives |

読み落としとサイズの関係について: 正確な数値は示せない（仮定）。一般に、指示が長く、項目が多いほど、個々の規則の遵守は下がりやすく、中ほどにある規則ほど落ちやすい。目安として、毎回読む「必ず守る」規則は十数項目以内にし、安全規則を先頭に置くことを推奨する。

|---|---|---|---|---|---|---|
| (a) 言わない | △ | × | △ | × | ◎（`again` で直接昇格） | ◎ |
| (a) 聞かれない | △ | × | ○（手順が読みやすい） | × | ○ | ○（知識の索引も） |
| (a) 最短 | △ | × | ○ | △ | △（引継ぎの手順が薄い） | ○ |
| (b) 常時読み込みの削減 | △（重複分、数KB） | ×（0） | ○（運用規則の分解） | ×（0〜増） | ○〜◎（手順を畳めば） | **◎（8万字 → 1万字以下）** |
| (c) 移行コスト | ◎ 小 | △ 中（clone とパスが1つ増え、全写しを直す） | ○ 中 | △ 中 | ◎ 小 | ○ 中（段階的に分割可） |
| (d) 可逆性 | ◎ | ○ | ◎（git で戻せる） | ○ | ◎ | ◎（各ステップが小さい） |

| (f) クラウド・複数 PC | △（固定パス・PowerShell が残る） | △（clone 対象が増える） | ○ | ○（自己完結）だがずれる | ◎ | ○ |

要点:
- **B と D は推奨しない。** B は、本当の問題（共有側が作業側に依存していること）を解かずに、リポジトリを増やすだけ。D は、写しのずれという今起きている問題を、仕組みとして固定する。
- A〜E のどれも、常時読み込みの8割（作業ログと判断記録の全文読み込み）に直接触れていない。削減効果は、構造の切り直しより、**ログの読み方を変える**ほうが桁違いに大きい。
- E は L0 の目的に最も直接効くが、単独では引継ぎ（核3）と、手順書の依存問題（指摘2）が残る。

## 推奨案: F（C＋E＋境界の修正＋作業ログ分割）

### 内容

- リポジトリは**2つのまま**（作業側＝非公開、共有側＝公開可）。境界の主軸は「性質（公開範囲）」。新設・分割はしない。
- 作業ログを「現在状態（開始時に読む）」と「経緯（読まない）」に分け、判断記録も開始時に読まない。
- 規則の置き場を、憲法（AGENTS）・手順（手順書）・案内（README）の3層に固定する。呼び出し表とパスは、それぞれ1か所だけにする。
- 手順書は、作業ディレクトリへの**契約**だけを前提にし、作業側固有の記述を持たない。
- 手順書を薄くし（C）、版は git で代える。昇格は `again` を起点にする（E）。

### 理由

- L0 の3つの目標と、常時読み込みの上限の両方に、最も効く。
- 大きく作り直さずに済み、各ステップを独立に戻せる。
- 公開されうる側から作業側の前提を抜くので、固定の制約（機密を出さない）を構造で守れる。

### 移行の順序

| # | ステップ | 可逆か | 壊しうるもの（と戻し方） |
|---|---|---|---|
| 0 | 両リポジトリに移行前のタグを打ち、常時読み込みの字数を記録する | 可逆 | なし |
| 1 | 旧リポジトリの clone をワークスペースの外へ移す（または消す） | 可逆（再 clone） | 旧パスを参照するリンク。事前に旧リポジトリ名で検索して確認 |
| 2 | 作業ログを「現在状態」（上書き・3KB 上限）と「経緯」（月ごと・開始時に読まない）に分ける。`start` の読み込み対象を差し替え、判断記録を読み込みから外す | 可逆 | エージェントが過去の経緯を自動で見なくなる → 必要なとき検索する一文を `start` に入れる。1週間試し、手戻りが増えたら戻す |
| 3 | 呼び出し表の正本を `hooks.md` 1か所にし、5か所の写しを1行のポインタに置き換える。写しを直した後、旧名の案内ファイルを消す | 可逆 | 旧い合言葉で呼んだときの動作 → 正本の表に別名として残す |
| 4 | 手順書の場所の定義を、各 PC のユーザー全体の指示ファイル（dotfiles 管理）に1か所化し、各 AGENTS からパスを消す | 可逆 | Codex・Copilot がユーザー全体の指示を読まない場合（仮定B） → 作業側 AGENTS にだけ1行残す |
| 5 | 作業側 AGENTS を3KB 程度に縮め、運用規則を分解して廃止する（安全規則は先頭に残す） | 可逆 | 細則の読み落とし → 該当する手順書に移したことを確認してから消す |
| 6 | 手順書に「契約」を1枚置き、作業側固有の記述（指標の列・記録ファイル名）を手順書から抜く | 可逆 | 指標の自動記録 → L0 で縮小済みなので、`again` の記録だけ作業側に残す |
| 7 | 手順書を薄くする: README を数KBの案内に、変更履歴・改善記録を git と `archives/` へ、版の運用を git で代える、「自動採用の規則」節を凍結する | 可逆 | inbox メモの「作成時の版」 → コミットの識別子に置き換え |
| 8 | 知識側を整える: 知識置き場 AGENTS を書き方だけに縮める、索引を追加する、判断記録の状態を2値か廃止にする、台帳を凍結する | 可逆 | `転記待ち` の項目の扱い → 移行時に一度だけ棚卸しする |
| 9 | `contexts/` の置き場所を決め直す（非公開側へ移すか、業務の文脈を書かない規則にする）。**共有側の公開は、これが済むまで保留** | 可逆 | モバイルからの引継ぎ → 新しい置き場所を `start` の手順に書く |
| 10 | 周辺物（チートシート・ハンズオン）を別の置き場へ | 可逆 | 既存のリンク → 移動先を検索で確認 |

1週目に 0〜3、2週目に 4〜6、3〜4週目に 7〜10 を目安にする。各ステップは単独で戻せる。

### やらないこと

- 手順書を独立リポジトリにする（案B）。
- 手順書の写しを各ディレクトリに持つ（案D）。
- 判断記録の状態遷移を、YAML・CSV・データベースに構造化する。
- 合言葉の統合（8個 → 4個程度）は、ここでは決めない。L3（プロセス）で扱う。
- 検査スクリプトの書き直しは、ここでは決めない。L5（運用・統制）で扱う。
- 新しい手順書・指標・規則の追加（規模凍結の継続）。

## 見落としているリスク

- **移行作業そのものが本業化する**: 上の10ステップは、それ自体が整備。L0 の「整備時間の自己判定」を、移行期間中も続ける。2週連続で「元が取れていない」なら、ステップ 7 以降を止める。
- **規則同士の矛盾**: 移行の途中で、旧い場所と新しい場所の両方に規則が残る期間がある。各ステップで、旧い記述を消すまでを1単位にする。
- **エージェント間の差**: Claude Code・Codex・Copilot で、指示ファイルを読む範囲が違う（仮定B）。Claude Code で動くことを基準にし、ほかのエージェントでは「作業側 AGENTS だけで最低限動く」ことを確認する。
- **安全規則の読み落とし**: 常時読み込みを減らすと、むしろ安全規則は目立つようになるが、縮める途中で誤って消すリスクがある。安全規則は、縮小の対象から機械的に外す（先頭の節にまとめ、その節は触らない）。

## 確認したいこと

1. 「常時読み込み 約8万字」は、`start` のたびに実際に全文を読んでいるか（仮定A）。それとも上限つきで読んでいるか。
2. `exmem/contexts/` の7件に、業務の内容（会社固有の情報）が入っているか（仮定D）。
3. 作業側の「非公開の remote」はどこにあり、クラウドのセッションから clone してよいか（仮定E）。これにより、引継ぎの置き場所の選択肢が変わる。
4. 共有側を、実際に公開する予定はあるか。予定が無ければ、指摘2・4の優先度は下がる（ただし、制約として「公開されうる前提で書く」を続けるなら、優先度は変わらない）。
5. Codex・Copilot を、実際にどの程度使っているか。ほとんど使わないなら、互換性の配慮を減らせる。
6. 旧リポジトリの clone は、ワークスペースの配下にあるか（仮定C）。
7. 知識42件のうち、業務の知識と環境構築の知識の内訳。業務側で読まれた5件が環境構築に偏っているのは、業務の知識が少ないためか、探しにくいためか。
