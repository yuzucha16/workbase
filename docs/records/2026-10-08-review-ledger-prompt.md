# 第三者レビュー依頼文: 転記の台帳方式の時系列整合（別モデル向け。2026-10-08）

用途: 別のモデルに、下の「依頼」以降を貼って、設計の穴を指摘してもらう。自己完結（ほかのファイルを見せなくてよい）。固有名・機密は含めていない。回答は、`docs/decisions.md` の該当項目の「未決」の検討に使う（採否はユーザーが決める）。

---

## 依頼

あなたは、ファイルベースの運用設計のレビュアーです。次の設計の、時系列整合（順序・古さ・競合）の穴を、批判的に指摘してください。褒めは不要です。実装はしないでください。

### 背景

個人が、AI エージェントと一緒に作業しています。構成は2つの git リポジトリです。

- **作業側**（ローカル専用の個人リポジトリ。複数ある）: 作業の判断を `docs/decisions.md` に項目として書く。各項目は、行き先の状態を持つ。
- **共有側**（共有リポジトリ。`inbox/` と `knowledge/` を持つ）: 作業側の項目から、一般化した知識メモを作って `inbox/` に置く。後で `knowledge/` に統合して、メモを削除する。

項目の行き先の状態:

| 状態 | 意味 |
|---|---|
| `未仕分け` | まだ判断していない |
| `転記待ち（→ inbox/<メモ名>）` | 一般化したメモを `inbox/` に置いた。統合は未確認 |
| `転記済（日付 → <統合先>）` | 統合先に到達したことを確認した。このとき、汎用の本文を作業側から外す（正本を共有側の1つにする） |
| `local` `滞留` `破棄` | 転記しない |

### 従来のやり方（手間が大きい）

メモを作る（作業側が `転記待ち` にする）→ 共有側で統合する（エージェントが `knowledge/` に統合し、メモを削除する）→ 作業側で、`転記待ち` の項目ごとに、統合先に根拠と却下案が欠けなく写っているかを突き合わせ、一覧をユーザーに示して承認を得て、`転記済` にし、本文を外す。最後の工程が、手間の中心です。過去の実測では、突き合わせた5件すべてに、統合先の欠落や誤り（元に無い却下案を AI が補っていた、など）がありました。

### 新しい設計（台帳方式。今回のレビュー対象）

1. **台帳**: 共有側に `integrated.md`（追記のみ）を置く。統合のたびに、統合するエージェントが、メモを削除する前に1行足す: `| 日付 | メモ名 | 統合先のファイル |`。作業側の固有情報（項目名、パス）は書かない。
2. **見直し（週1回を目途。作業側で実行）** が、`転記待ち（→ inbox/<メモ名>）` の各項目を、台帳で引く。
   - 台帳に無ければ何もしない（未統合、または捨てられた）。
   - 台帳にあれば、次の3つを機械的に確認する。すべて満たしたものだけ、`転記済（日付 → 統合先。本文残し）` に進める。本文は外さない。
     1. 台帳に統合先のファイルが書かれている。
     2. 統合先のファイルが実在し、項目の見出し（または太字の先頭の1文）が、統合先に含まれている。
     3. 項目の最終更新日が、メモの作成日以前である。満たさなければ、`転記待ち` のままにして、再度ナレッジ化する候補として報告する。
   - **前回までに `本文残し` にした項目**は、次の見直しで本文を外す。外す前に、統合先に根拠と却下案が欠けなく写っているか（元に無い記述が混ざっていないか）を、本文で確認する。怪しければ外さず、ユーザーに聞く。
   - ユーザーに聞く例外: 確認 2・3 を満たさない項目、統合先の欠落や混入が疑われる項目。それ以外は、事後報告だけ。
3. 台帳に記録が無い過去の統合は、従来の方式で確定する。台帳を共有できない隔離環境（社用 PC など）は、対象外。

### 制約・前提

- ユーザーは1人。複数の PC とモバイル（クラウドのセッション）から作業するので、共有側への書き込みが並行しうる。
- 作業側の項目は、後から改訂・撤回される。
- 項目の最終更新日は、人が書く日付ではなく、`git log`（またはファイルの更新時刻）から取る想定。
- 統合は AI が解釈して書き直すので、項目と統合先の文言は一致しない。

### 観点（これに限らず、追加してよい）

1. 時系列の穴: 台帳の記載、項目の改訂、メモの作成、統合、見直しの順序が入れ替わったり、重なったりして、誤って `転記済` や本文外しに進む（または、進むべきなのに戻る）筋書き。
2. 3つの確認（台帳、見出しの実在、最終更新日）が、検出できない誤り。特に、見出しが残っているのに中身が古い・欠けている場合。
3. 本文外しの2段階（本文残し → 次回に外す）が、何を防ぎ、何を防げないか。1回の見直しの間隔（約1週間）は妥当か。
4. 並行（複数端末・クラウドの書き込み）での台帳の競合。追記のみの台帳は十分か。
5. 項目の最終更新日の取り方（`git log` ほか）が壊れる場面（リネーム、整形だけの変更、日付の粒度が日単位）。
6. 台帳の改ざん・誤記・訂正（「追記のみ。訂正は行を足す」）の扱いの穴。
7. もっと単純で安全な代替案があるか（ある場合は、1〜2案を短く）。

### 出力の形

- 指摘は、重大度（高・中・低）の順に、番号つきで。各指摘に、「再現する筋書き（順序つき）」「想定される結果」「最小の対策案」を、1〜3文ずつ。
- 最後に、「この設計をこのまま試験運用（2週間）に進めてよいか」を、はい・条件つきではい・いいえ、のどれかで答え、条件があれば列挙してください。
- 分からないこと・仮定したことは、「仮定」と明記してください。
