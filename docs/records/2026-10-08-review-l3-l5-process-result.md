## 指摘（重大度順）

### 高

**1. 規則を生む流量が、見直す流量を大きく上回っている**
- 根拠（事実）: 改善案の承認 89件中88件が採用、修正・補足0（ゲートとして情報量なし）。自動採用が 2026-10-08 に追加。一方、`review` 0回、見直し記録0行、規則の働いた記録0行。
- 放置した場合: 凍結（1つ足すなら1つ畳む）は、畳む側を決める場（`review`）が動いていないので守れない。手順書と規則は増え続け、L1 で削った読み込み量が戻る。
- 最小の対策: 改善案の**生成**を絞る。`wrap` の段階9（改善案）を外し、改善案は週1の見直しでだけ、最大1件出す（出すなら、畳む案と対にする）。自動採用は、凍結期間中は停止する。承認をなくすのではなく、承認に来る量を減らす。

**2. `wrap` の読み込みと工程が、開始時の削減分を食いつぶしている**
- 根拠（事実）: L1 で開始時の読み込みは約6.2千字になったが、`wrap` 1回で `docs-rules`＋`wrap`＋`stock` の約2.4万字を読む。9段階のうち、目的に直接効くのは一部（下表）。
- 放置した場合: セッションの終わりが重くなり、`wrap` を省くか、終わりの品質が落ちる。引継ぎ（核3）が `wrap` に依存しているので、`wrap` が省かれると引継ぎが壊れる。
- 最小の対策: `wrap` を3段階に絞る（現在状態の上書き、昇格1行、コミットと push）。ナレッジ化（`stock`）・棚卸し・統合待ちの報告・改善案を `wrap` から外す。目安は手順書 2千字以下、読み込み合計 5千字以下。

- 根拠（事実）: `start` は毎セッション、ゴール・完了条件・制約を聞き取る。L0 の目標は「調べれば分かることを聞かれない」。

**8. 検査の機械化は、黙って効かなくなる経路がある**

- 放置した場合: 機械化したつもりで、クラウドや新しい PC では検査が無いまま push される。
- 最小の対策: 検査を POSIX sh の1スクリプトにまとめ、リポジトリに版管理して置く。(1) pre-push フックから呼ぶ、(2) `wrap` の手順からも明示的に呼ぶ、の**二重**にする（フックが未設定でも `wrap` で動く）。対象は安全規則だけに絞る（push 先が許可リストか、remote が非公開か、機密のパターンが無いか）。書式の点検は対象にしない。

## 推奨案: E（核4つに合わせた4合言葉＋安全だけの機械検査＋改善案の流量制限）

### 内容

- 合言葉は4つ: `start`（`open` を統合）、`wrap`（`close` を任意の追加段階として統合）、`stock`（知識化。`integrate` は共有側の作業として、その下位の手順に）、`review`（核4の中身に置き換え）。`init` は合言葉から外す。日本語の別名は、呼び出し表の正本1か所にだけ残す（廃止しない。記憶負担を下げているため）。
- `wrap` は3段階（現在状態の上書き、昇格1行、コミット・push）＋報告（終了時の1問）。
- 転記の仕組みは「リンクの有無」だけにし、6状態・ハッシュ・台帳・照合を畳む。
- 人の承認は、安全・決定の記録・週1の判断の3か所に絞る。改善案は週1、最大1件、畳む案と対で。自動採用は停止。
- 検査は、安全規則だけを POSIX sh の1スクリプトにし、pre-push フックと `wrap` の両方から呼ぶ。安全規則の正本は作業側 AGENTS の先頭。
- 指標は `again` と終了時の1問だけを手で残す。自動抽出は月1の診断用。

### 理由

- L0 の核4つと、合言葉が1対1で対応する（指示ファイル＝常時、昇格＝`wrap` の1行と `stock`、引継ぎ＝`start`・`wrap`、見直し＝`review`）。
- 肥大化の源（改善案の流量、転記の仕組み、手で書く指標）を、生成側で止める。
- 安全規則は、毎回読む場所と機械の両方で守り、縮小の影響を受けない。
- クラウドでも Codex でも、sh とファイルの読み書きだけで回る。

### 畳む・残す・足す

| 区分 | 対象 |
|---|---|
| **畳む** | `open`（`start` へ統合）、`close`（`wrap` の任意段階へ）、`init` の合言葉（手順書は案内から参照）、`wrap` の段階4・5・7・9、改善案の個別承認、自動採用（凍結期間中）、行き先の6状態、本文ハッシュ、台帳、`integrate` の照合承認、`check-docs` の状態点検（PowerShell）、手で書くイベント記録・セッション記録・規則の働いた記録、試験運用の判定日 10-22（11-08 に統合） |
| **残す** | 安全規則（正本を作業側 AGENTS の先頭へ）、決定の記録の原則、push の許可リスト、`start` `wrap` `stock` `review`、日本語の別名（正本1か所）、`again` の記録、終了時の1問、会話履歴からの自動抽出（月1の診断用）、凍結、判定日 10-15（読み落とし点検）と 11-08 |
| **足す（畳むものと対）** | 安全の検査スクリプト（POSIX sh）＋ pre-push フック ↔ `check-docs`（PowerShell）を畳む／`start` の「見直しから7日超なら一度提案」の1行 ↔ `review` の自動採用見直し・転記確定を畳む／判断記録の「→ 知識」リンク1行 ↔ 6状態・ハッシュ・台帳を畳む |

### 試験運用の判定基準（既定は「畳む」）

| 項目 | 残す条件（11-08 時点） |
|---|---|
| `review`（核4の中身） | 4回中3回以上実施され、少なくとも1回「直す・畳む」の判断に使われた。満たさなければ、見直しの仕組みでなく、開催のきっかけ（リマインドの置き場所）を見直す。核4自体は畳まない |
| `start`（`open` 統合後） | 開始時に、現在状態にあることを聞き直した事例が0〜1件 |
| `wrap` の `close` 段階 | 実際に Project を閉じた回数が1回以上。0回なら手順を畳み、手作業に戻す |
| ログ分割 | 終了時の1問で「大きく遠回り」の原因が、経緯を読まなかったこととされた事例が0件 |
| `docs-rules` の開始時読み込み廃止 | 10-15 の読み落とし点検で、安全規則の違反が0件 |
| 検査スクリプト（新設） | 誤検知で push が止まり、ユーザーが手で回避した回数が月2回以下 |

### やらないこと

- 検査を git フックだけに頼ること（クラウドや新しい PC で黙って効かなくなる）。
- 書式・状態の点検の機械化（仕組みごと畳むため）。
- 判断記録の状態の構造化（YAML・CSV・データベース）。
- 承認の全面撤廃（安全・決定・週1の判断には残す）。
- 別名の廃止。
- 新しい合言葉・指標の追加（凍結の継続）。

## 見落としているリスク

- **畳んだ仕組みを、改善案として再提案する**: エージェントが過去の経緯から「台帳があると便利」などを提案し直す。判断記録に「畳んだ理由」を1項目で残し、`review` で再提案が来たらそれを参照する。
- **終了時の1問への慣れ**: 毎回「なし」と答えるようになり、情報量が落ちる。週1の見直しで、`again` の事例と突き合わせて矛盾がないかを見る（`again` があったのに「なし」が続くなど）。
- **安全の検査の誤検知による回避の習慣化**: 誤検知が多いと、検査を飛ばす操作が日常になり、本当に危ないときも飛ばす。誤検知の回避回数を判定基準に入れたのは、このため。
- **Codex での動作差**: Codex が呼び出し表や作業側 AGENTS をどこまで読むかは、Claude Code と違いうる。安全規則は機械検査で守られるので、Codex では「手順は最低限、安全は機械」で割り切る。
- **移行そのものの本業化**: L0・L1 と同じ。移行のステップ 9 は、余力が無ければやらない。
