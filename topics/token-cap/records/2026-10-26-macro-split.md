# Excel マクロの全面実装を、役割分割で軽くする案

2026-10-26。叩き台（実装なし）。背景: 今月の 90% の主因は、ee が書けない Excel マクロを AI にフル実装させていること。ee の仮説（人と AI の工程分割。境界は基準文書。`exmem/lessons/change-method.md`）を当てはめる。

## なぜ重くなるか（推測。PC1 の集計で確かめる）

1. 大きなマクロを 1 つの会話で書き、直し続けるため、会話が大きくなる（量は「会話の大きさ × 応答数」）。
2. 直すたびに全文を出力する（出力が重い）。
3. Windows で実行して失敗 → 報告 → 直す、の往復が多い（`room-windows-balance` の「ラリー」。環境の違いが主因）。
4. 仕様が会話の中で育つので、手戻りが出る。

## 役割分割の案

| 工程 | 人（ee） | AI | 機械（スクリプト・Excel） |
|---|---|---|---|
| 要件 | 業務ルールと、**入力例 → 出力例**（ダミーのシート）を書く。これが基準文書 | 抜け・矛盾を質問し、ID つきの要件と検証項目に整える | |
| 設計 | 承認 | 部品に分ける（1 部品 = 1 モジュール、目安 150 行以下）。共通部品（エラー処理、ログ、シートの読み書き）を先に決める | |
| 実装 | | **部品ごとに別の短い会話**で書く。渡すのは、基準文書と該当モジュールだけ | 構文・規約の機械チェック（`Option Explicit`、名前の規約など。スクリプト化できる） |
| 検証 | 実行して、結果を**定型の報告**で返す | 原因を絞る | ダミー入力 → 期待出力の突き合わせ（Excel 側で自動比較する検証用シート） |
| 修正 | | **該当プロシージャの差分だけ**を出す（全文を出さない） | |

## 効きそうなこと（量の見立ては PC1 の集計後）

- **部品化 + 別の会話**: 会話が小さく保たれる。1 部品の会話は 5 万以下で終わる見込み。
- **差分だけ出す**: 出力トークンが減る。
- **共通部品のライブラリ化**: 毎回書かせない。VBA の定番（エラー処理、ログ出力、範囲の取得）を `exmem/lessons/` に蓄え、`triggers` で引き当てる。
- **エラー報告の型**: 番号、メッセージ、発生した手順、直前のシートの状態を定型にして、聞き返しを減らす（`room-windows-balance` の診断ログ案と合流）。
- **VBA を使わない選択肢の確認**: Power Query、動的配列の数式、Office スクリプトなどで済む部分は、VBA より短く、直しやすい。勤務先の環境で使えるか次第。
- **作業の分担 haiku / sonnet**: 定型の部品（入出力の整形、シート操作）は軽いモデルでも書ける可能性。量で数える上限では数は減らないので、重み付けが分かってから。

## ee に聞きたいこと

1. マクロの規模（モジュール数、総行数）、実装済みの割合、残り。
2. 実行する PC（PC1 のみか）。開発タブで AI が出したコードを貼る運用か。
3. VBA 以外（Power Query、数式、Python）が使える環境か。
4. 失敗のとき、どんな情報を AI に返しているか（エラー文、画面、ファイル）。
