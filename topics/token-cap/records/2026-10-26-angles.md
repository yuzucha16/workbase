# 勤務先の利用上限に向けた見直しの角度（叩き台）

作成: 2026-10-26。探索型。実装はしていない。材料は同じフォルダの既存ノート（principles、cut-and-narrow、top4-coverage-matrix、cache-and-batch、cache-experiment-result、hook-read-cost、zed-session-cost、cache-insights）と、workbase の `exmem/lessons/ai-work-metrics.md`、`guides/explain/claude-code-cost-session-size.md`、`guides/howto/claude-usage-report.md`、`workflow-kit/tools/usage_report.py`・`heavy_sessions.py`、`workflow-kit/token-matrix.md`。数値の目安は暫定（実測で直す）。

前提: 勤務先の接続は LLM ゲートウェイ + OIDC（`guides/explain/llm-gateway-oidc.md`）。Claude Desktop、Claude Code、Zed から使う。実務は PC1。

## 0. 先に決めること: 上限の「単位」で優先順位が入れ替わる

月「約2万トークン」は、トークン数そのものとしては小さすぎる。新しい会話の土台だけで約2.4万トークンある（`claude-code-cost-session-size.md`）。単位は次のどれかの可能性が高い。

| 単位の候補 | 数え方 | 効く角度が変わる点 |
|---|---|---|
| U1 トークン数（キャッシュ読みも含む。例: 2万「千トークン」=2,000万） | 量で数える。実記録では量の約96%がキャッシュ読み | 会話の大きさ × 応答数がほぼすべて。**切る・土台を減らす・サブエージェントを控える**が最優先。モデルやキャッシュの単価は効かない |
| U2 金額（例: 2万円、$200） | 単価で数える。費用は読み約3割・書き込み約4割・出力約3割 | 既存ノートの結論がそのまま使える。**間（TTL）・モデル選択・切る**が効く。手順書の字数削減は金額では小さい（cache-insights 2-6） |
| U3 勤務先独自のクレジット・リクエスト数 | ゲートウェイの集計しだい | リクエスト数なら、**往復の回数**（ツール呼び出しの多さ、細切れの指示）が効く |

確かめ方: 勤務先の案内（ポータルの使用量の表示）で単位を見る。PC1 で `usage_report.py --by month --prices ...` を出し、「90%」に当たる量が、総トークン・入出力だけ・金額のどれと合うかを突き合わせる。

## 1. 角度の一覧

効果: 大・中・小（U1 と U2 で違うときは両方）。済み度: 既存の資料・仕組みでどこまで済んでいるか。

| # | 角度 | 中身 | 済み度 | 効果 U1 / U2 | 手間 | ee の判断が要る点 |
|---|---|---|---|---|---|---|
| A | 計測（何が食ったか） | PC1 で今月の内訳を出す: 上位の会話、作業ディレクトリ別、Desktop の分 | 道具はある（`usage_report.py`、`heavy_sessions.py`）。PC1 での実行は未 | 前提（効果は他の角度を選ぶため） | 小 | 上限の単位。Desktop の分は jsonl に無いので、ポータルの表示で見るか |
| B | 土台（ベーストークン）を減らす【ee の案1】 | 毎回載るもの: ハーネスの指示・ツール定義・MCP、`AGENTS.md` の連鎖、triggers の出力、`log.md`。フック1回の読み込み（約0.9〜1.9万トークン） | 字数の予算と読む順番は厚い（top4 の③）。MCP・skills の整理は未。PC1 側の areas/projects の `AGENTS.md` は未確認 | 大 / 小 | 中 | 土台の大半はハーネス側（約2.4万のうち、workbase 直下の開始時の読み込みは約5千）。MCP を外すのは dotfiles・PC 側。どこまで kit で削るか |
| C | 会話を短く切る | 10万を超えたら区切る、`wrap` 後に同じ会話で続けない、間が空いたら切る | 規則と道具は済み（`hook-common.md`、`session-handoff.md`、`heavy_sessions.py`）。守られているかは未計測 | 特大 / 大 | 小 | 目安の数値を上限に合わせて下げるか（例: 10万→5万） |
| D | 人と AI の線引き【ee の案2】 | AI に渡さない作業を決める: 機械的な集計・点検はスクリプト、読むだけ・転記は人、AI は判断と下書きに寄せる | 考え方はある（工程分割と基準文書の仮説、cache-insights の S5）。作業の棚卸しは未 | 大 / 大 | 中〜大 | どの作業を AI から外すか（棚卸しの粒度と、品質との兼ね合い） |
| E | 間（キャッシュの TTL） | 5分を超えて間が空くと、同じ作業が約3倍（実測 n=1）。ゲートウェイ経由は API と同じ扱いで5分の可能性が高い | 実験済み（cloud）。勤務先の接続の TTL は未確認 | 小 / 大 | 小 | `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` が勤務先のゲートウェイで効くか、使ってよいか |
| F | モデルと effort | 定型は軽いモデル・低い effort、設計判断だけ上位 | 原則だけ（principles 8）。比較は未（S6） | 小〜中 / 大 | 小 | 勤務先で選べるモデル。品質の下限 |
| G | 往復と手戻りを減らす | 最初の依頼を完備する、計画で合意してから実装 | 原則だけ。`briefed` の試行はやめた（2026-10-26） | 中 / 中 | 小 | 依頼の型を作り直すか |
| H | 読み方・ツール出力を絞る | 大きいファイルは節だけ、出力は要約と件数 | ほぼ済み（`docs-rules.md` の読み方、点検スクリプト） | 中 / 小 | 小 | なし（守られているかを A で見る） |
| I | 財布を分ける | workbase の改善や学習は個人の契約（PC2・cloud）で行い、勤務先の枠は実務だけに使う | 線は PC1/PC2 で実質できている。勤務先の枠を何に使ったかは未確認 | A しだい（大の可能性） | 小 | 勤務先の規程で、何に勤務先の枠を使ってよいか |
| J | 予算の配分と見張り | 月の枠を日・週に割り、残りを見て使い方を変える。50%・75% で知らせる | 仕組みは無い（週次の `review` に「重い会話」はある） | 中（再発防止） | 小〜中 | 月の途中での配分（例: 1営業日あたり約5%） |
| K | Desktop の使い方 | 添付ファイル（xlsx・pptx・PDF）や長いチャットを Desktop で回すと大きい | 未確認 | A しだい | 小 | Desktop をどの作業に使うか |
| L | 出力を短くする | 報告の型、長い説明はファイルへ | 済み（フックの報告の型） | 小 / 小〜中 | 小 | なし |

## 2. 角度ごとの補足

- **A 計測**: 今月は 26 日で 90% なので、残り 5 日で 10%。来月の対策を決める材料として、今月の内訳が最も価値がある。PC1 の jsonl は PC1 にしかない（PC2 には自動で届かない）ので、ee が PC1 で実行し、集計の表（上位10件と合計）だけを持ち帰る形になる。会話の中身は持ち帰らない。
- **B 土台**: U1 なら、土台 × 応答数が効く。2.4万の土台で 50 応答なら、それだけで 120万。削れる場所は、(1) 使わない MCP サーバーとツール定義、(2) 自動で載る `AGENTS.md` / `CLAUDE.md` の連鎖（PC1 の areas/projects の `AGENTS.md` を含む）、(3) 依頼ごとの triggers の出力、(4) フック本体（`docs-rules.md` のコミット節 約4.9千字を wrap・integrate・review が毎回読む）。U2 なら、字数を削る価値は小さい（cache-insights 2-6）。
- **C 切る**: 実記録では 100k 以上の会話が応答の 44%、費用の 56%（`claude-code-cost-session-size.md`）。U1 でも U2 でも最も効く。規則はあるので、残りは「守れているか」と「目安の数値」。
- **D 線引き**: ee の仮説（工程分割、境界は基準文書）に沿うなら、AI の工程を「判断と下書き」に絞り、前後の機械的な工程（集計、点検、転記、整形、変換）を人かスクリプトに寄せる。棚卸しは、A の上位の会話から「その会話で AI がしていた作業」を見て、外せるものに印を付けるのが手早い。U1 では、サブエージェントも土台を新しく読むので、重い探索の隔離（principles 6）は逆に高くつく場合がある。
- **E 間**: U2 で効く。勤務先の接続の TTL は、`claude -p "hello" --output-format json` の `usage.cache_creation` で分かる（cache-insights I4）。
- **I 財布**: 今月の 90% のうち、workbase の改善や調べ物が含まれていれば、それを個人側に移すだけで大きく減る。規程の判断なので ee が決める。

## 3. 進め方の推奨（暫定）

1. 単位を確かめ、PC1 で A の計測を1回（今月の上位10会話と合計）。これで角度の優先順位が決まる。
2. 単位が U1 なら C → B → D、U2 なら C → E → F → D の順で詰める。I は単位に関係なく、規程を確認するだけで済むので並行。
3. J（予算の配分と見張り）は、来月の始めまでに置く。

A の計測を待つ間に進められるのは、C の目安の見直し案と、D の棚卸しの枠（作業の種類の一覧）。

## 4. 追記（2026-10-26 ee の訂正: 上限は「2億トークン」）

- 単位は U1（トークン数）で確定に近い。今月は約1.8億使用、1日あたり約700万。
- 2億はキャッシュ読みを含む数と見る（量の約96%が読み）。含まないなら実質の枠はずっと小さいので、PC1 の集計の合計が約1.8億に近いか（読みを含む）、約8百万か（含まない）で確かめる。
- **haiku 案**: トークン数で数える上限では、モデルを変えても数は減らない。効くのは「ゲートウェイがモデルで重みを付けている」場合か、モデルごとに別の枠がある場合だけ。勤務先に確認が要る。金額の上限ではなく量なので、haiku は主役ではなく、定型処理（`wrap` のコミット、点検の実行、整形）を別の短い会話で回す補助。同じ会話の途中で切り替えるとキャッシュが切れて逆効果。
- 優先は C（切る）→ B（土台）→ D（線引き）。E（間）・F（モデル）は、重み付けが分かるまで保留。
- PC1 で取るもの: `python -I workflow-kit/tools/usage_report.py --by month --last 2 --top 10`（月の合計、読取率、モデル別、プロジェクト別、上位10会話）と `heavy_sessions.py --since 2026-10-01 --top 10`。出力は集計の数字だけなので、題名に機密が出ていないかを見てから貼る。
