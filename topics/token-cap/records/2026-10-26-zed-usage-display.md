# Zed のチャット欄下の使用量表示と、1 セッションの目安

2026-10-26。調べたもの: ACP アダプタ `@agentclientprotocol/claude-agent-acp` 0.95.0 の配布物（`dist/acp-agent.js`）。Zed 側の描画のコードは見ていない（未確認）。前の調査は `notes/token-saving/2026-10-17-zed-session-cost.md`（0.93.0）。

## 結論: リアルタイムの累計ではなく、「いまの会話の大きさ」

- 表示の元は ACP の `usage_update`（`used` と `size`）。`used` は、直近の応答の入力・出力・キャッシュ読み・キャッシュ書き込みの合計（`totalTokens()`）。`size` はモデルの文脈の窓（1M のモデルなら約 100万）。
- `used` は応答の途中（ストリーミング）でも更新される。応答のたびに「会話の全体の大きさ」へ置き換わるので、足し算ではない。圧縮（compact）をすると、圧縮後の大きさに下がる。
- 費用（`cost.amount`、USD）は、ターンの終わりに累計で付く。ゲートウェイ経由で単価が合うかは未確認。
- したがって、表示が 100,000 のとき、その会話の次の応答は約 10万トークンを入力として読む。上限（2億）に数えられる量は、各応答の入力の合計（会話の大きさ × 応答数）で、表示の値を毎回足していく形になる（勤務先の数え方が読みを含む場合）。

## 1 セッション 10万の目安は妥当か

- 目安の根拠は、費用の統計（100k 以上の会話が応答の 44%、費用の 56%。`guides/explain/claude-code-cost-session-size.md`）と、切る損益の式（`notes/token-saving/2026-10-18-cache-insights.md`）。**費用（金額）に対する目安**。
- 量で数える上限では、基準が変わる。会話が土台 B（約 2.4 万）から切る大きさ C まで一定の割合で伸びるとき、1 応答あたりの平均の入力は (B + C) / 2。

| 切る大きさ C | 平均（1 応答の入力） | 10万に対する比 |
|---|---|---|
| 10万 | 約 6.2万 | 1.00 |
| 7万 | 約 4.7万 | 0.76 |
| 6万 | 約 4.2万 | 0.68 |
| 5万 | 約 3.7万 | 0.60 |

- 試算の前提: 土台 24k、伸びは一定、応答数は同じ、引継ぎ（`wrap` と新しい会話の最初の読み込み）の手間は無視。目安は暫定で、PC1 の実測で直す。
- 5〜6万に下げると、同じ作業量で上限の消費が約 3〜4 割減る見込み。引継ぎの回数が増えるので、`wrap` の依頼文を使って切る手間を小さくする前提。
- 「10万」は、上限の観点では緩い目安。表示を見て、5〜6万で区切りを考え、10万は超えない上限にするのが現実的（ee の判断。Open Questions）。
