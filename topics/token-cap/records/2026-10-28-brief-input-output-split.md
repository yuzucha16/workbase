# brief の引数を「入力」と「出力」に分ける案

2026-10-28。`hook-room-alignment` の会話で出た案（未決・未実装。ee の決定待ち）。`docs/log.md` の Next Actions 6 の詳細。

## 背景

- 100k で区切ると、1 回の枠で挟める会話は 3 つ程度。開始（`brief`）と終了（`wrap`）を除くと、間は 1 会話。
- 引数つき `brief` は、`brief-hook.md`（8KB）+ `brief-modes.md`（4.9KB）+ `brief-work-types.md`（3.3KB）を読み、型ごとの聞き取りで往復も増える。読んだ分は以後の全応答に乗る。
- 10-18〜27 のログ（引数つき 10 回。別名は未集計）: 改善 5、振り返り 4、計画 1、解決・変更・調査は 0。

## 分け方

| | 入力の型 | 出力の型 |
|---|---|---|
| 中身 | どのモードかを選ばせる聞き取り（ゴール、やり方、範囲、読者） | 応答の形（章立て、含める項目、順序） |
| 価値 | 低め。ピンポイントの依頼文で足りる | 高い。期待に近い形で返ってくるかは、調査と改善/振り返りで特に効く（ee） |
| 方針 | 引数なしの `brief` + 普通の依頼文を主にし、使われないモードを削る | 残す。ただし常時は読まない |

## 案: 依頼の言葉に反応して、出力の型だけを呼ぶ

`find_knowledge.py --triggers` と同じ仕組み（ノートの `triggers:` と依頼文の語を照合し、一致したノートだけ読む）を、出力の型にも使う。使わない会話では 0 トークン。

概要:

1. 出力の型を、モードの手順書から切り出して、1 型 1 ノートにする（各ノートの `triggers:` に、その依頼で出る語を書く）。
2. 作業の前の索引（UserPromptSubmit の「作業の言葉の索引」）が、依頼文の語で型のノートを出す。AI はそれを読んで、その形で返す。
3. `brief` は引数を持たない。モードの選択は、依頼文の語が代わりに行う。

具体例（設計の見本。型の名前と語は仮）:

- 「今日の daily を振り返って」→ 語 `振り返り` が一致 → 振り返りの出力の型だけを読む（例: 良かった点 / 詰まった点 / 次に変える 1 点、の順で返す）。`brief 改善 daily` と打たなくてよい。
- 「〇〇について調べてまとめて」→ 語 `調べて` が一致 → 調査の出力の型を読む（結論 / 確認できなかった点 / 出典、の順。`brief-modes.md` の調査の項に既にある章立て）。
- 「〜したい」の計画の依頼 → 語 `計画` が一致 → 計画の出力の型（ゴール・期日・読みの分かれ目・置き場の 4 点。`brief-plan.md`）。
- 一致する語が無い依頼（ふつうの作業）→ 何も読まない。
