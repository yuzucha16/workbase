# kit-growth: 決定

## 2026-10-16 フックの重さの基準を `hook-matrix.md` に置き、`review` で比べる（ユーザーの依頼。N=20% は根拠なしの仮）

- 【汎用】基準日 2026-10-16 の各フックの字数・手順の項目数・報告の項目数を `hook-matrix.md` の「重さの基準」に固定した。`review` が今の値と比べ、字数は +20%、項目数は +2 以上増えたフックを見直しの対象にし、そのフックの星取り表と修正・削除・追加の対応表（`improvement-coverage-matrix`）を作る。決めたこと（AI の設計。ユーザーは未確認）: 項目数は割合でなく +2（小さい数で割合が跳ねるため）、比べる相手は前回でなく基準（少しずつの増加を見逃さないため）、基準は実施後に更新、減ったときは基準を下げる。
- 見直しの条件: 3回の `review` の後に、対象になった件数で N を決め直す（毎回対象になる、または一度もならないなら N が合っていない）。

## 2026-10-16 `wrap` を軽くした（`start 改善` の星取り表から、ユーザーが1・2・3 と、6 の変形を選択）

- 【汎用】`wrap` は `docs-rules.md` の「コミットと push」の節だけを読む（全文 約9.4k字のうち約4k字減）。報告の型は6項目から5項目（「更新した docs/」と「昇格の案」を統合、【汎用】の件数は `review` に任せて外す）。`wrap` の改善案は、その場で提案せず、`docs/log.md` の Open Questions に `場所 / 問題 / 案` の1行で足し、`review 消化` で承認を取って直す（`review-hook.md` の消化モードに1文足した）。根拠: ユーザーの選択。改善の提案が遅れるだけで内容は失われない。却下・見送り: push 条件の `gh repo view` を毎回やめる案（4）、手順1の対象特定を縮める案（5）。
- 見直しの条件: Open Questions の改善案が `review 消化` で消化されずに溜まるなら、`wrap` での提案に戻す。

## 2026-10-16 `docs-rules.md` に「期日の節」と「定例」を足した（ユーザーの承認）

- 【汎用】`log.md` の書式に「期日」の節（日付つきの項目があるときだけ）を足した。表は `期日 | 種別 | 内容 | 担当`。種別は単発と定例。定例は実行したら次回の期日に書き換える。Next Actions と Open Questions には終わりのある項目だけを置く（周期のある項目を置くと「0 になる」判定が成り立たない）。works が先に進んでいた期日の節を kit に戻した（`alignment-baseline.md` の行 5）。

- 【汎用】`review-hook.md` の入力 8 に、リポジトリ間の整合の点検を足した（ユーザーの指示、2026-10-16）。{リポジトリ} × {`AGENTS.md`、`README.md`、`docs/log.md`} の「現状」の表と、影響・リスクで優先度を付けた「ギャップ」の表を作る。足した分の対（畳むもの）は未定で、次の `review` で挙げる。

- 【汎用】一律に kit を正とはしない。kit が遅れているときは、明らかにずれている箇所を事前に確認して、kit 側を直す（ユーザー、2026-10-16）。
