## 依頼

あなたは、個人の AI 活用基盤のレビュアーです。次の仕組みの**目的の置き方・指標・費用対効果**を、批判的に診断してください。褒めは不要です。実装と書き直しはしないでください。

### 背景

個人（ユーザー1人）が、AI エージェント（Claude Code など）と業務で作業しています。複数の PC とモバイルから使います。構成は次のとおりです（詳細は今回のレビュー対象ではありません）。

- 作業ログのリポジトリ（ローカル専用）: 作業の経緯・判断を `docs/` に残す。
- 共有リポジトリ: 再利用する知識（`exmem/knowledge/`、約40件、約600KB）と、手順書（フック。約30ファイル、約250KB）。
- 手順書は、エージェントが、ユーザーの合言葉（`init` `open` `start` `wrap` `close` `stock` `integrate` `review`）で読んで実行する。毎回読み込む指示ファイル（AGENTS.md）が、各リポジトリにある。
- 約3週間で、手順書・指標・台帳・自動採用の規則が増え、規模が大きくなった。ユーザーは「肥大化している」と感じている。

### ユーザーが述べた目的（原文に近い表現）

仕事を楽にしたい。AI に何度も同じことを言わない。AI に同じことを聞かれない。目的地に、できるだけ最短で近づきたい。

#### 目的の注釈（定性表現を、定量の指標に対応づける）

「言わない」「聞かれない」は、AI に質問や指摘をさせない、という意味ではありません。**AI からの初回の質問・指摘は歓迎**で、不明点は聞いてほしい。自己改善（AI が質問・提案の質を測って直す）とも矛盾しません。避けたいのは、**既に伝えた・既に調べれば分かることの繰り返し**です。次のように、観測できる件数・率に対応づけます。

| 表現         | 意味                       | 対応する指標（現状。母数が小さく不安定）                                                                                                                      |
| ---------- | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 同じことを言わない  | 一度伝えた前提・方針を、再度伝え直さない     | 漏れ（`gap`: 聞かれなかった前提が後から出た件数。11件、うち AI 起因 7・不明 4）。**同種の `gap` の再発率**が本命だが、未集計。補足（`supplement`: 質問の範囲を超えてユーザーが情報を足した件数。質問25件中10件、提案59件中23件） |
| 同じことを聞かれない | 調べれば分かること、既に書いてあることを聞かない | 冗長率（`answerable` / 質問数。質問25件中 12%、提案59件中 2%）。知識側では、空振り（探したが無い・古い）と参照率（業務側スレッド17件中 24%）                                                    |
| 最短で目的地に近づく | 手戻り・やり直し・無駄な往復が少ない       | 直接の指標は**無い**。代理: 覆り率（採用後に撤回された割合。提案75件中3件）、修正（`fix`: 質問・提案の前提を直された件数。質問25件中2、提案59件中8）、セッションの達成度、ツールエラー率、ターン数・自走時間                         |

つまり、定量化できているのは「聞かれない」の一部だけで、「言わない」の再発率と「最短」は、まだ測れていません。この対応づけが妥当か、足りない指標は何かも、レビューしてください。

### 目的の階層（**仮説**。これ自体をレビューしてください）

```
主目的   業務の生産性向上
  手段    ナレッジの再利用率を上げる
  経路 1  集約・引継ぎ: 複数デバイスで生まれた知識を1か所にまとめ、どこからでも使える
  経路 2  自己改善:     質問・提案の質（適合率・冗長率）を測って直し、無駄を減らす
```

ユーザー自身が、「目的と手段が混じっている」と認めています。たとえば「再利用率を上げる」は目的でなく手段です。

### 現状の指標と実測

- 質問・提案の質の指標（約190件のイベントログ）: 適合率（ユーザーに直されずに通った割合）、冗長率（聞かなくても分かった質問の割合）、採用率（約98%。判別力が低いと自分で注記している）、覆り率。
- スレッド・セッションの指標（自動抽出）: 自走時間、ツールエラー、トークン量。ユーザー本人の自己改善用。
- **再利用率の直接測定（本日追加。試験運用）**: 会話履歴から、`knowledge/` の読み込み（参照率）と、手順書の読み込みを数える。実測（約2週間、業務側スレッド17件。下限値: 読み込みと検索の呼び出しだけを数えた）:
  - 参照率: 4/17（24%）
  - `knowledge/` 約42件のうち、期間内に1度でも読まれたもの: 5件
  - 検索したが何も読まなかったスレッド: 7件
  - 手順書（約14本）のうち読まれていないもの: 1本。最も読まれたのは `docs/` の運用規則（19スレッド）。
- 見直し（`review`）の記録: 0件。

### 制約・前提

- ユーザーは1人。組込みのシニアエンジニアで、サイズ予算・規則数の管理には慣れている。
- 母数は小さい（スレッド数十件）。率は不安定。
- 安全規則（push・機密・破壊的操作）は削除候補にしない。

### 観点（これに限らず、追加してよい）

1. **目的の階層**: 仮説は、目的と手段が正しく分かれているか。ユーザーの述べた目的（言わない・聞かれない・最短）から見て、どう組み直すべきか。2つの経路は、本当に同じ仕組みで追うべきか。
2. **指標と目的の対応**: 上の「目的の注釈」の対応づけは妥当か。「言わない」の再発率と「最短」を、最小のコストで測るには何を足すか（足さない選択も含めて）。目的を直接表す指標があるか。再利用率の直接測定（参照率など）は、目的の代理として妥当か。「参照されたこと」と「役に立ったこと」の隔たりを、どう埋めるか。
3. **費用対効果**: 維持コスト（規則・手順書・指標の量、読み込みトークン、運用の手間）と効果を、どう比べるか。この規模のコストは、現時点の実測（上）に見合うか。
4. **指標の副作用**: 指標を取ることが、行動を歪める（参照率を上げるために無駄に読む、など）場面。自己改善の指標自体が肥大化の原因になっていないか。
5. **成功の定義とやめる基準**: 1か月後・3か月後に、何が観測できれば成功か。何が観測できなければ、何を畳むか。数値で置けるか。
6. **最小の核**: 目的を果たす最小の仕組みは何か。いまの仕組みのうち、核でないものはどれか（根拠つきで）。
7. 見落としているリスクや、もっと単純な代替案（1〜2案。短く）。

### 出力の形

- 指摘は、重大度（高・中・低）の順に、番号つきで。各指摘に、「根拠（どの記述・数字か）」「放置した場合の結果」「最小の対策案」を、1〜3文ずつ。
- 目的の階層は、書き直した案を示す（1つ）。
- 最後に、「この目的・指標のまま、1か月運用してよいか」を、はい・条件つきではい・いいえ、のどれかで答え、条件があれば列挙してください。
- 分からないこと・仮定したことは、「仮定」と明記してください。回答の妨げになる不明点は、仮定を置いて先に進んだうえで、末尾に「確認したいこと」として列挙してください（ユーザーは後から答えられます）。
