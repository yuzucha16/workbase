## 目的

作業を始める前に、ゴールと前提をそろえる。ユーザーが毎回プロンプトに書いているものを、AI が先に集めて、要約で返す。終了処理（`closing-hook.md`）で、ゴールと結果を突き合わせる。

## 手順

1. **事前確認**（質問の前に、AI が行う）: 対象の `docs/log.md` の Next Actions と Open Questions、README の完了条件と範囲外を読む。環境で確認できる前提（コンパイラの有無など）は、実際に確認する。利用者の前提（専門領域・経験）が、記憶にあるか確かめる。
2. **項目を埋める**: 下の共通の項目と、作業の種類の差分の項目について、答えが1つに定まるものは質問せず、要約に宣言する。残りを、選択式（既定値に Recommended）で聞く。**質問のまとまりの最後に、「ほかに前提はありますか」の自由記述を1つ置く**（承認: 2026-10-06。選択肢の外の前提を、最初から拾う）。
3. **要約を返す**: 「今日のゴール」を、項目ごとに返す。反対があるときだけ、ユーザーが直す。
4. **記録する**: 質問ごとに、`docs/metrics/events.csv` に1行（`kind=interview`）。回答を受けた同じターンで。聞かなかった前提が後から出たら、`kind=gap` の行を足す。
5. **作業する**。
6. **終了処理で**: ゴールの達成度を Log に書き、`adopted` と `reversed` を確定する。

## 共通の項目

| 項目 | 内容 | 省略してよい条件（宣言だけにする） |
|---|---|---|
| ゴール | このセッションで到達したい状態（1文） | 省略しない（候補は Next Actions から出す） |
| 前提・制約 | 環境、期限、使える道具 | 環境の確認で1つに定まるとき |
| 対象と資料 | 対象の Project・Area と、読む資料 | 進行中の Project が1つだけのとき |
| 触ってよい範囲 | リポジトリ・ディレクトリ単位の許可（この Project、dotfiles、kit、`resources/` など）。変更の可否と、変更前に確認が要るもの | 既定（この Project の中だけ）で足りるとき |
| やらないこと | 範囲外にする作業（機能、方式） | 「特になし」を既定にして、範囲外は README を守る |
| 完了の判断 | 何が出たらこのセッションを終えるか | ゴールの文に含まれるとき |

「触ってよい範囲」と「やらないこと」を分ける理由: 2026-10-06 の試行で、「やらないこと」の選択肢に、リポジトリの変更の許可（dotfiles は可、kit は不要）を混ぜて、ユーザーに直された。

## 作業の種類の差分

### 開発（設計・実装・評価）（承認: 2026-10-06）

実装の**前に**聞く。いずれも、2026-10-06 に、後から出た前提（`gap`）。

| 項目 | 内容 | 理由（`events.csv`） |
|---|---|---|
| 設計の優先順位 | 安全性・速度・フットプリント・可読性などの順 | `s3-g02`: 優先順位が聞かれず、AI の推奨が、ユーザーの優先（安全性 > 起動速度）と逆だった。`s3-i02` |
| コーディングルールとチェックの有無 | 書式、制約（変数、再帰、動的確保、ポインタ操作など）、機械チェックと linter の有無、導入してよい道具、準拠する規格（MISRA など）の要否 | `s2-g01` `s5-g01`: 規則と制約が後から出た。`s2-i03` |
| 対象環境 | ターゲット（コア、ワード幅）、ツールチェーン | `s3-g01` と、判断 D・F（M0 の除算）。ここは、環境の確認で分かる部分は聞かない |
| 最適化の軸と、測る対象の操作 | 「チューニング」「最適化」「短縮」などの語が出たら、軸（速度・サイズ・消費電力など）と、測る操作（例: 確保、解放、初期化）を、測る前に確認する。ハードウェアの条件（例: 乗算のサイクル数）も、結果が変わるものは聞く | `2026-10-07-s2-g01`: 「チューニング」をサイズの削減と取り違えて、見積もりを出した。`2026-10-07-s2-i01`。乗算のサイクル数は、見積もりの結果を変えた（1 サイクルと 32 サイクル） |

### 文書作成（仕様・設計・調査）

1回目の実測（2026-10-07、手順書の作成）から、次の項目を足した。2〜3回の実測がたまってから、全体を設計する（例: 調査なら「結論の用途」）。

| 項目 | 内容 | 理由（`events.csv`） |
|---|---|---|
| ゲート承認の判断基準 | レビュー版を承認する前に、合否の項目（チェックリスト）を決め、レビュー版に付ける。完了条件のチェックリストを、ゲートの合否の項目に直す | `2026-10-07-s3-g01`: 判断基準が無く、ユーザーが「判断が難しい」と指摘した。`2026-10-07-s3-i01`（承認: 2026-10-07） |
| 骨子のすり合わせ | 初稿の前に、骨子（構成・ストーリーライン。例: 前半は概要の箇条書きとフローチャート、後半は詳細手順）をすり合わせる | `2026-10-07-s3-g02`。`2026-10-07-s3-i02`（承認: 2026-10-07） |
| 図の要否と水準 | 図（mermaid 程度など）の要否と水準を、「範囲外」の語から推測せず確認する | `2026-10-07-s3-g03`。`s3-i02` |
