用途: 別のモデルに、下の「依頼」以降を貼って、プロセスと統制の設計の穴と、改善案を出してもらう。自己完結（ほかのファイルを見せなくてよい）。固有名・機密は含めていない。回答は `docs/decisions.md` に検討結果として残す（採否はユーザーが決める）。レイヤごとの依頼の第3弾（L0 目的、L1 構造に続く）。L4（エージェント向けの面）は、L1 の結論に沿って実施済みなので、独立の依頼はしない。L2（データ）の実測は、背景に含めた。

## 依頼

あなたは、個人の AI 活用基盤の運用設計のレビュアーです。次の仕組みの**プロセス（合言葉と手順書、その連鎖、権限と承認）と、運用・統制（検査、変更管理、肥大化の防止）**を、批判的に診断し、**比較して推奨案を出して**ください。褒めは不要です。実装はしないでください。序盤なので、大きく作り直す案も歓迎します（制約は小さくしてよい）。

### 1. 前段の結論（承認済み・実施済み）

- **主目的（L0）**: ユーザーの負担（再伝達・不要な往復・手戻り）を減らす。目標は3つ: 一度伝えたことを二度言わない／調べれば分かることを聞かれない／手戻り・遠回りが少ない。指標は、再伝達 `again` の件数と、各セッションの終わりの1問「今日の遠回りは、なし・少し・大きく」。再利用率・参照率は診断用の補助で、目標値を置かない。
- **最小の核（L0 のレビュアーの案）**: (1) サイズ予算つきの指示ファイル、(2) 繰り返し言ったことを指示ファイルか知識に昇格する1手順、(3) 複数デバイス間の引継ぎ（開始・終了）の最小手順、(4) 週1回の見直し。
- **構造（L1）**: リポジトリは2つのまま（作業側＝非公開、共有側＝公開されうる）。作業ログは「現在状態」（開始時に読む）と「経緯」（読まない）に分割。呼び出し表（合言葉→手順書）の正本は共有側の1ファイル。共有側の手順書は、作業ディレクトリへの「契約」（必須ファイル、任意の記録名）だけを前提にする。
- **実施の結果**: 開始時に読む指示は 約7.98万字 → 約0.62万字。規模は凍結中（手順書・指標・規則は、1つ足すなら1つ畳む。判定日 2026-11-08）。

### 2. 現状のプロセス

#### 2.1 合言葉（フック）と手順書

エージェントは、ユーザーが合言葉を言ったときだけ、対応する手順書（Markdown）を読んで実行する。

|---|---|---|---|---|

| `start` | セッションの開始 | 2,900 | 開始インタビュー（ゴール・完了条件・制約の聞き取り） | 試験運用。手順書を読んだスレッドは2 |

- 連鎖: `init`、`open → [start → 作業 → wrap]×N → close`。`stock` と `integrate` は随時。
- 別名（日本語）があり、「終了処理して」→ `wrap`、「ナレッジ化して」→ `stock` など。
- `wrap` を1回実行すると、`docs-rules.md` + `wrap` + `stock` で 約2.4万字を読む。

#### 2.2 `wrap` の手順（9段階）

1. プランモードなら抜ける。2. 対象の特定（複数リポジトリ、Project の `docs/` を含む）。3. `docs/` を更新（作業ログの Next Actions、判断記録。追加の手順があれば続ける）。4. 棚卸し（`check-docs` スクリプトで判断記録の「行き先」を点検）。5. ナレッジ化（`stock` の手順 2 以降）。6. コミット（パス指定、ステージ行数の確認、agent の身元とトレーラー）、許可リストのリポジトリなら push。7. 統合待ちの報告（未統合メモ数、`転記待ち` の件数）。8. 報告。9. 改善案（あったときだけ）。

#### 2.3 権限・承認の仕組み

| 区分 | 扱い |
|---|---|
| 承認制 | 手順書・規則の変更案は、提案し、ユーザーの承認を得てから直す。ただし実績として、改善案の承認は 89 件中 88 件が採用で、修正・補足は 0（ゲートとして情報量が無かった） |
| 自動採用（2026-10-08〜。試験運用） | `wrap` の改善案のうち、運用の補助だけ、承認なしに ID つきの「自動採用の規則」の節へ追加・削除してコミット。`review` が要・不要を判断。ユーザーはいつでも「戻して」と言える。現在1件 |
| 安全規則 | push・機密・破壊的操作・コミットの身元・決定の記録の原則・書き込み先・承認の規則は、常に承認制。縮小の対象外。作業側 AGENTS の先頭に要約を置く |
| push | 許可リスト（作業側の `main` だけ。非公開であることを毎回確認、fast-forward、機密の検索）。共有側は対象外でユーザーが行う |
| 決定の記録 | ユーザーが明示または承認したものだけを `decisions.md` に決定として書く。AI の提案は「提案」と書く |

#### 2.4 検査・統制の仕組み

- **検査スクリプト（PowerShell 7）**: 判断記録の「行き先」の状態・書式の点検（約57項目、点検111〜114件）、inbox メモの形式の点検、知識の検索、項目の本文ハッシュ。**クラウドのセッションには PowerShell が無く**、その場合は手で確認し「未実行」と書く。
- **転記の仕組み**: 判断記録の各項目に「行き先」の6状態（`未仕分け` `転記待ち` `転記済` `local` `滞留` `破棄`）。`転記待ち` はメモ名と本文ハッシュを持ち、共有側の台帳（追記のみ）と突き合わせて、`review` が `転記済` に進める。照合（メモと統合先の比較）は `integrate` の時点でユーザーが承認する。
- **指標**: イベント記録（質問・承認・改善案・再伝達・漏れ。197行）、セッション記録（9行）、見直し記録（0行）、規則の働いた記録（0行）、会話履歴からの自動抽出（66スレッド）。自動で、`knowledge/` の読み込み、手順書の読み込み、再伝達の検出も数える。
- **変更管理**: 手順書の変更は承認制。版番号と変更履歴は廃止し、git のコミットメッセージと、改善記録（直近と、提案・却下・自動採用の行だけ）で管理。履歴の全文は git のタグ。
- **凍結**: 手順書・指標・規則は、1つ足すなら1つ畳む（〜2026-11-08）。
- **試験運用の表示**: 8フックのうち 4つ（`open` `start` `close` `review`）と、自動採用、台帳、ログ分割、`docs-rules` の開始時読み込み廃止が試験運用中。判定日は 2026-10-15（読み落とし点検）、2026-10-22（権限移譲と台帳）、2026-11-08（目的の置き直し全体）。

### 3. 観察（事実）と気になる点（解釈。検証してください）

事実:
- `review` は実施 0回。`start` `open` `close` は、手順書を読んだスレッドが各2。`wrap` `stock` `docs-rules` が実質の主役（読んだスレッドは、それぞれ9・14・19）。
- `wrap` の9段階のうち、棚卸し・ナレッジ化・統合待ちの報告・改善は、ユーザーの目的（言わない・聞かれない・最短）の達成より、**仕組み自身の維持**のための工程の比重が大きい。
- 承認の仕組みは、改善案の承認が素通りで、一般の承認確認では修正・補足が機能している（55件中、修正7・補足21）。
- 検査スクリプトは1つの言語・環境に依存し、クラウドで動かない。
- 手順書に書かれた規則は、エージェントが読み落とすことがある（L0・L1 のレビューの指摘。実績の測定は 2026-10-15 に予定）。

解釈（検証してください）:
- 合言葉8つ＋別名は、1人のユーザーの記憶負担になっている。
- 「規則が規則を生む」構造（自動採用、見直し、台帳、指標）が、本来の目的に比べて重い。
- 検査を、エージェント向けの手順書でなく、機械（git フックなど）で強制すれば、手順書は小さくできる。

### 4. 制約・前提（緩めてよい点）

固定する:
- 作業側の機密・個人情報・会社固有の情報を、共有側に出さない。共有側は公開されうる前提。
- ユーザーは1人。複数 PC（Windows + WSL）とクラウドのセッション、主に Claude Code。Codex も使う。
- 安全規則（push・機密・破壊的操作）は削除候補にしない。

緩めてよい:
- 合言葉の数・名前・連鎖。手順書の分け方。別名。
- 試験運用中の仕組み（自動採用、台帳、`review`、`start` `open` `close`）を畳むこと。
- 検査スクリプトの言語・実行の場所。
- 承認の仕組み（どこに人の承認を置くか）。

### 5. 比較してほしい案

A〜D を同じ軸で比較してください。より良い案 E があれば追加して構いません。

- **A. 現状維持＋試験期間の判定**: 8合言葉のまま、判定日に採否を決める。
- **B. 合言葉の統合**: 4つ程度に統合する（例: 開始、終了、知識化、見直し）。`open` `close` `init` は手順の一部か、まれな操作に格下げする。別名は廃止する。
- **C. 最小の核だけ**: L0 の4つ（指示ファイル、昇格、引継ぎ、週1見直し）に絞り、`start` `open` `close` と自動採用・台帳・`review` の仕組みは畳む（安全規則を除く）。必要になったら足す。
- **D. 検査の機械化**: 判断記録の書式・コミットの確認・機密の検索などの検査を、git のフックや単純なスクリプトで強制し、手順書から検査の記述を減らす。クラウドでも動く方法（POSIX sh など）を前提にする。

### 6. 観点（これに限らず追加してよい）

**プロセス（L3）**
1. 合言葉と連鎖: 主目的（言わない・聞かれない・最短）に対して、各合言葉が何に効いているか。畳める・統合できるのはどれか。1人用で、`open` `close` の連鎖は必要か。別名は必要か。
2. `wrap` の9段階: 目的に直接効く段階と、仕組みの維持のための段階を分けると、どう分かれるか。省略・自動化・移動できる段階は。
3. 権限と承認: 承認が素通りしているゲートと、機能しているゲートがある。人の承認を置くべき場所と、置かなくてよい場所の線引きは妥当か。自動採用の範囲は妥当か。安全規則の置き場所（作業側 AGENTS の先頭の要約と、手順書の正本の二重）は。
4. 引継ぎ: 複数デバイスとクラウドをまたぐ引継ぎの最小手順は何か。今の仕組みは、それを満たしているか。
5. 読み落とし対策: 規則が多いほど守られにくい前提で、規則の置き方（強制・チェックリスト・機械化）はどうあるべきか。

**運用・統制（L5）**
6. 検査: 今の検査を、人（エージェント）の手順・スクリプト・git フックのどこに置くのが適切か。環境差（PowerShell の有無）をどう扱うか。検査自体が肥大化の原因になっていないか。
7. 転記の仕組み（行き先の6状態、台帳、本文ハッシュ、`review`）: 効果とコストは見合うか。もっと単純で安全な代替は。
8. 指標と変更管理: 指標の種類と更新の手間は、目的（再伝達と遠回りの件数）に対して過剰か。承認、改善記録、凍結、判定日の運用で、肥大化と劣化を止められるか。止められないなら何が足りないか。
9. 試験運用の終わり方: 「試験運用」の表示が多い。終了の判定基準と、畳む条件（実績がなければ畳む）は、明確で実行可能か。
10. 見落としているリスク。

### 7. 出力の形

- 指摘は、重大度（高・中・低）順に番号つきで。各指摘に「根拠（どの記述・数字か）」「放置した場合の結果」「最小の対策」を、1〜3文ずつ。
- 案 A〜D（と E）の比較表。軸は、(a) 主目的の3つの目標への効き、(b) 読み込み量と維持コストの削減、(c) 移行コスト、(d) 可逆性、(e) 新たなリスク、(f) クラウド・複数 PC・Codex での扱いやすさ。
- 推奨案を1つ。理由と、移行のステップ（番号つき。各ステップに「可逆か」「何を壊しうるか」）。畳むもの、残すもの、足すもの（足すなら畳むものと対）を一覧にする。
- 「このプロセスと統制のまま1か月運用してよいか」を、はい・条件つきではい・いいえ、のどれかで答え、条件があれば列挙する。
- 事実と解釈を分け、分からないことは「仮定」と明記する。回答の妨げになる不明点は、仮定を置いて先に進んだうえで、末尾に「確認したいこと」として列挙する（ユーザーは後から答えられる）。
