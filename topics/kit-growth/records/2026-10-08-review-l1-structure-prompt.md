# 第三者レビュー依頼文: L1 リポジトリ構成・責務・データ・インタフェース（別モデル向け。2026-10-08）

用途: 別のモデルに、下の「依頼」以降を貼って、構造（アーキテクチャ）の穴と改善案を出してもらう。自己完結（ほかのファイルを見せなくてよい）。固有名・機密は含めていない（リポジトリ名は役割名に置き換えた）。回答は `docs/decisions.md` に検討結果として残す（採否はユーザーが決める）。レイヤごとの依頼の第2弾。第1弾（L0 目的）の結論を前提に入れてある。

---

## 依頼

あなたは、個人の AI 活用基盤のアーキテクトです。次の仕組みの**構造（リポジトリの切り方、責務、データ構造、リポジトリ間のインタフェース、エージェント向け指示ファイルの役割と縮小）**を、批判的に診断し、**比較して推奨案を出して**ください。褒めは不要です。実装はしないでください。移行の制約は小さくしてよい（序盤なので、大きく作り直す案も歓迎します）。

### 1. 背景と、前段（L0）の結論

個人（ユーザー1人）が、AI エージェント（主に Claude Code。Codex や Copilot も同じ指示ファイルを読めるようにしている）と業務で作業しています。複数の PC（Windows + WSL）とモバイル（クラウドのセッション）から使います。人間は Obsidian で閲覧・編集します。

前段のレビュー（L0）の結論（ユーザーが承認済み）:

- **主目的**: ユーザーの負担（再伝達・不要な往復・手戻り）を減らす。目標は3つ: 一度伝えたことを二度言わない／調べれば分かることを聞かれない／手戻り・遠回りが少ない。
- 知識の再利用率・参照率は、目的でなく診断用の補助。
- **最小の核**（L0 のレビュアーの案）: (1) サイズ予算つきの指示ファイル（安全規則と恒久的な前提）、(2) 繰り返し言った事柄を指示ファイルか知識に昇格する1手順、(3) 複数デバイス間の引継ぎ（開始・終了）の最小手順、(4) 週1回の見直し。これ以外は「核でない」候補。
- **コストを制約に置く**: 常時読み込み（開始時に読む指示）の量に上限を置く。現状は約8万字（作業ログ約5万字、判断記録約1.4万字、運用規則約0.9万字、指示ファイル約0.7万字）。規模は凍結中（1つ足すなら1つ畳む）。
- 実測（約2週間、業務側スレッド17件）: 知識を1件以上読んだ割合 24%。知識約42件のうち、読まれたのは5件。見直し（週1回の定期点検）の実施 0 回。

### 2. 現状の構造

#### 2.1 リポジトリとディレクトリ

```
ワークスペース（Obsidian Vault のトップ。「作業側」。PC ごとのローカルな git リポジトリ。remote は非公開）
├─ AGENTS.md / CLAUDE.md（CLAUDE.md は `@AGENTS.md` の1行）
├─ docs/            作業ログ（log 94KB）、判断記録（decisions 25KB）、指標（metrics/ 約150KB。CSV とスクリプト）、下書き（drafts/）
├─ areas/ projects/ archives/   PARA。ローカルな作業
├─ resources/       ← 別リポジトリ「共有側」の clone。作業側の .gitignore で除外
│  ├─ AGENTS.md（共有側全体の規約）
│  ├─ exmem/        知識（external memory）。knowledge/ 42件 519KB、contexts/ 7件 41KB、inbox/、台帳、検査スクリプト
│  ├─ workflow-kit/ 共通の手順書（フック）の正本。31ファイル 247KB
│  ├─ cheatsheets/  チートシート 12件 79KB
│  └─ handson/      ハンズオン 5件 12KB
├─ repos/           ghq で clone した個別のリポジトリ（dotfiles など。それぞれ別の git リポジトリで、各自の docs/ を持つものがある）
└─ .obsidian/       dotfiles からのジャンクション
```

- 共有側（workbase）は、**公開範囲が未定**で、公開されうる前提で書く。機密・会社固有・PC ごとのデータを入れない。
- 作業側から共有側へのリンクは可。逆（共有側から作業側へのリンク）は禁止（他の PC でリンク切れになる）。
- そのほかに、切り出し前の旧リポジトリ（旧構成の完全な写し。最終コミット 2026-10-05）の clone が残っている。作業側と共有側の旧い写しを含み、旧名のファイルもある。

#### 2.2 データの種類と、現状の寿命・正本

| データ | 置き場 | 性質 | 備考 |
|---|---|---|---|
| 作業ログ（現在状態・次にやること） | 各作業ディレクトリの `docs/log.md` | 追記。**開始時に毎回全文を読む指示** | 作業側の log が 94KB。退避の規則なし |
| 判断記録（根拠・却下案・詰まり） | `docs/decisions.md` | 追記。各項目に「行き先」の状態（`未仕分け` `転記待ち` `転記済` `local` ほか）を持つ | 状態遷移を人手の Markdown で管理 |
| 一般化した知識 | `exmem/knowledge/` | 1ファイル1トピック。frontmatter、固定の見出し（Principles / Decisions / Gotchas）、タグ語彙 | 作業側の判断から、`inbox/` に一般化メモを置き、後で統合する |
| 未整理メモ | `exmem/inbox/` | 一時置き場。統合したら削除 | 作業側からの書き込みは、ここに新規ファイルを置くことだけ許す |
| 台帳 | `exmem/integrated.md` | 追記のみ。統合のたびに1行（メモ名と統合先） | 作業側の「転記済」への確定の根拠 |
| 引継ぎコンテキスト | `exmem/contexts/<名前>/context.md` | 作業側から見えない場所（モバイルなど）の作業の現在状態 | 消化する手段は未定 |
| 手順書（フック8個＋規則） | `workflow-kit/*.md` | 版つき。改善提案 → 承認 → 修正 | 版が1日に5回上がった日がある。変更履歴・改善記録が大きい（README 50KB、改善記録 42KB） |
| 指標 | 作業側 `docs/metrics/` | CSV（イベント約190行、スレッド66行、セッション9行）とスクリプト | PC ごとに閉じる |

#### 2.3 インタフェース（リポジトリ間・ディレクトリ間）

- **参照の方向**: 作業ディレクトリ → 共有側（手順書と知識）は読み取り。共有側 → 作業側は禁止。
- **場所の取り決め**: 手順書の場所は、環境変数でなく、`$HOME\works\resources\workflow-kit`（WSL では `/mnt/c/Users/<名前>/works/...`）という**固定のパス**で、各ディレクトリの指示ファイルに書いてある。読めなければ、記憶で代用せずにユーザーに伝えて止まる。
- **書き込みの例外**: 作業側から共有側へ書いてよいのは、ユーザーの指示があるときの `inbox/` への新規ファイル1つだけ。
- **フックの呼び出し**: ユーザーの合言葉（`init` `open` `start` `wrap` `close` `stock` `integrate` `review`。日本語の別名つき）で、エージェントが対応する手順書を読む。ワークスペース → Project → セッションの寿命ごとに開始・終了が対になる。
- **バージョン**: 手順書に版があり、`inbox` のメモには、作成時の版を書く。
- **変更権限**: 手順書の変更は承認制。ただし1つの節（「自動採用の規則」）だけは承認なしで追加・削除できる。push は許可リスト（作業側の `main` だけ）。

#### 2.4 エージェント向けの指示ファイル（AGENTS / CLAUDE / README）

- 作業側 AGENTS.md（約8KB。長い箇条書きが約13項目。指標の記録手順、`start` `review` `wrap` の細則、push の許可リストを含む）、共有側 AGENTS.md（4KB）、知識置き場 AGENTS.md（104行 8KB。台帳や作業側の手順の記述を含む）、手順書置き場 AGENTS.md（11行）、各作業ディレクトリ向けのひな形（28行）、個別リポジトリの AGENTS.md（dotfiles は34行）。
- CLAUDE.md は、各所で `@AGENTS.md` の1行（正本は AGENTS.md）。
- 手順書置き場の README は50KB。フックの体系、用語、変更履歴を含む。
- **同じ「フックの呼び出し表」（どの合言葉でどの手順書を読むか）の写しが、少なくとも5か所にある**: 作業側 AGENTS、共有側 AGENTS、手順書置き場 README、ひな形 AGENTS、個別リポジトリの AGENTS。このうち共有側 AGENTS と個別リポジトリの AGENTS は、旧名のまま（新しい合言葉が載っていない）。旧名の手順書は、新名への案内だけのファイルとして残してあるので動くが、写しがずれていることの実例。

### 3. 観察（事実）と、気になる点（解釈）

事実:
- 手順書置き場の AGENTS は「特定のディレクトリの固有事情を書かない」と定めているが、手順書8本が、作業側固有のもの（指標の CSV の列、特定の記録ファイル名）を名指しで前提にしている。
- 共有側 AGENTS は「このリポジトリは単独で clone しても自己完結する」と書いているが、手順書は、作業側の `docs/` の構造と指標を前提にしている。
- 知識置き場の AGENTS に、作業側の `転記待ち` や、手順書の「終了処理」「見直し」の記述が入っている。
- 共有側には、知識・手順書のほか、本運用と関係の薄いチートシートとハンズオンが同居している（計約90KB）。
- クラウドのセッションには PowerShell が無く、検査スクリプト（PowerShell）が動かせない。
- 手順書の中で最も読まれたのは、「作業を始める前に必ず読む」と指示されている運用規則（19スレッド）。これは指示の遵守を示すだけで、有用性の証拠ではない。
- 知識42件のうち、業務側で読まれた5件は、環境構築・シェル・Obsidian に偏っている。

気になる点（解釈。検証してください）:
- 責務の切り方が「性質（共有か個人か）」と「種類（知識か手順書か）」の2つの軸で混ざっている。
- 変更頻度と利用者が違う知識と手順書が同じリポジトリにあり、コミットとレビューが混ざる。
- 規則を書く場所が、指示ファイル・手順書・README・判断記録に分散し、正本が不明確。
- 「コピーを持たず、1か所を参照する」という原則を掲げているのに、呼び出し表の写しが増えている。

### 4. 制約・前提（緩めてよい点を明記）

固定する:
- 作業側の機密・個人情報・会社固有の情報を、共有側に出さない。
- 複数 PC とクラウドのセッションから使える。クラウドでは、リポジトリを clone できるが、PowerShell は無い。
- 人間が Obsidian で閲覧・編集できる（wikilink と frontmatter）。
- 安全規則（push・機密・破壊的操作）は削除候補にしない。

**緩めてよい**（序盤なので、構成を大きく変えてよい）:
- リポジトリの分割・統合・改名・新設。共有側の「単独で自己完結」という方針。
- 手順書の配置・版の運用・合言葉の数。
- 旧名のファイル、旧リポジトリの clone、同居している周辺物（チートシートなど）。
- 指標・台帳・自動採用の規則のうち、核でないもの。

### 5. 比較してほしい案

次の A〜E を、同じ軸で比較してください。より良い案 F があれば、追加して構いません（ゼロベースで構成し直す案も可）。

- **A. 現状維持＋境界の線引き**: リポジトリの切り方は変えない。責務、正本、参照の方向を文書で固定し、重複を削る。
- **B. 手順書を独立リポジトリに**: 手順書置き場を、共有側から別リポジトリに切り出す。知識は共有側に残す。
- **C. 手順書を薄くする**: 手順書は最小の本文＋検査スクリプトだけにし、背景・経緯・変更履歴・改善記録は知識側か履歴（git）へ。フックの数も統合する。
- **D. 各作業ディレクトリが版つきの写しを持つ**: 手順書を各ディレクトリにコピーし、バージョンで同期する。
- **E. 1ファイル＋1語方式**（L0 のレビューの案1）: 恒久的な前提は、サイズ予算つきの指示ファイルだけに置く。ユーザーが `again`（前にも言った）と言ったら、その場で指示ファイルか知識に昇格する。手順書・台帳・自動採用の規則は、安全規則以外を凍結（または畳む）。計測は `again` の件数だけ。

### 6. 観点（これに限らず追加してよい）

1. **責務**: 各リポジトリ／主要ディレクトリが、1文で責務を言えるか。混在・重複はどこか。責務の切り方は、性質と種類のどちらの軸を主にすべきか。
2. **データ構造**: 各データ（作業ログ、判断記録、知識、未整理メモ、台帳、引継ぎコンテキスト、手順書、指標）について、正本は1つか。寿命・退避・サイズ上限の規則はあるか。人手の Markdown で管理している状態遷移（`転記待ち` など）は、構造化すべきか。毎回全文を読む作業ログの設計は妥当か。
3. **インタフェース**: 参照の方向、パスの取り決め、書き込みの例外、版、結合度は妥当か。共有側が作業側を前提にしている点（上の観察）を、どう解消するか。固定パスと環境変数のどちらがよいか。
4. **指示ファイルと README の役割**: 「毎回読む憲法」「呼ばれたときに読む手順書」「人間向けの案内」の線引きは。写しをなくす方法。縮小の具体案（サイズ予算の目安、何を AGENTS から出し、どこへ置くか）。エージェントが読み落とす確率と、サイズの関係。
5. **案 A〜E の比較**: 表で。軸は、(a) L0 の3つの目標（言わない・聞かれない・最短）への効き、(b) 常時読み込みの削減量、(c) 移行コスト、(d) 可逆性、(e) 新たなリスク、(f) クラウド・複数 PC での扱いやすさ。
6. **推奨案と移行の順序**: 推奨する案と、その理由。移行は、可逆なものから、小さい単位に分ける（各ステップが何を壊しうるか、戻し方も）。「やらないこと」も。
7. **見落としているリスク**: 例えば、エージェントが規則を読み落とす、規則同士の矛盾、旧い写しの誤読、整備自体が本業化する、など。

### 7. 出力の形

- 指摘は、重大度（高・中・低）順に番号つきで。各指摘に「根拠（どの記述・数字か）」「放置した場合の結果」「最小の対策」を、1〜3文ずつ。
- 案 A〜E（と F）の比較表。
- 推奨案を1つ。理由と、移行のステップ（番号つき。各ステップに「可逆か」「何を壊しうるか」）。
- 「この構造のまま1か月運用してよいか」を、はい・条件つきではい・いいえ、のどれかで答え、条件があれば列挙する。
- 事実と解釈を分け、分からないことは「仮定」と明記する。回答の妨げになる不明点は、仮定を置いて先に進んだうえで、末尾に「確認したいこと」として列挙する（ユーザーは後から答えられる）。
