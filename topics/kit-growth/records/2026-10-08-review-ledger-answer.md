# レビュー結果: 転記の台帳方式の時系列整合（2026-10-08）

対象: 「第三者レビュー依頼文: 転記の台帳方式の時系列整合」に対する指摘。採否はユーザーが決める。

## 前提（仮定）

- **仮定A**: 作業側の `docs/decisions.md` は1ファイルに複数項目を持つ。
- **仮定B**: 両リポジトリとも git 管理で、本文外しは履歴から復元できる。このため、主なリスクは「取り返せない損失」ではなく「気づかない損失・誤り」として評価している。
- **仮定C**: メモ名はエージェントか人が自由に付ける文字列で、一意性の仕組みは無い。

## 重大度: 高

### 1. 確認3（最終更新日）は、ファイル単位の日付では機能しない

- **筋書き**: (1) 項目Xのメモを作る。(2) 同じ `decisions.md` の別項目Yを編集する。(3) 見直しで `git log` を引く。
- **結果**: 仮定Aのもとでは、ファイルの最終更新日は無関係な編集でも進む。そのため確認3がほぼ常に不成立になり、何も進まない。逆に `git log -L` で行範囲を追うと、項目の移動や整形で壊れる。さらに、見直し自身が状態を `転記済` に書き換える編集も「更新」に数えられ、再実行時に自分で不成立にする。
- **対策**: 日付をやめ、メモ作成時に項目本文のハッシュ（状態行を除く）を `転記待ち` 行とメモに記録する。見直しでは「現在の本文ハッシュが記録値と一致するか」で判定する。

### 2. 確認3の比較対象のデータが台帳に無い

- **筋書き**: 台帳の「日付」は統合日である。メモは統合後に削除されるので、メモ作成日は共有側の削除済みファイルの `git log` からしか取れない。
- **結果**: エージェントが統合日で代用すると、「メモ作成後〜統合前の改訂」を見逃す。日単位・`≤` 比較なので、同日中の改訂も素通りする。複数端末とクラウド（UTC）が混ざると、日付が前後に1日ずれる。
- **対策**: 1と同じく、ハッシュ方式で日付比較そのものを廃止する。日付を残すなら、タイムスタンプとタイムゾーンを明記する。

### 3. メモ名の再利用・衝突で、別のメモの台帳行に一致する

- **筋書き**: (1) メモ `foo` を統合し、台帳に行が残る。(2) 項目を改訂し、「再度ナレッジ化」で同じ名前 `foo` のメモを作る（または別の作業リポジトリが同名を使う）。(3) 見直しが古い行に一致する。
- **結果**: 新しいメモが未統合なのに、確認1が成立する。統合先に旧版の見出しがあるので確認2も成立し、確認3は日付次第で成立する。結果、誤って `転記済` に進む。
- **対策**: メモ名とは別に一意IDを振り（作成日時と短いランダム値）、台帳はIDで引く。

### 4. 第2段（本文外し前の照合）は、従来の重い工程そのものを、承認なしのAI判断に移しただけ

- **筋書き**: 第2段は「根拠と却下案が欠けなく写っているか、混入は無いか」を本文で確認する。これは従来の手間の中心と同じ作業である。しかも、過去5件すべてで混入を起こした種類のAIが「怪しくなければ事後報告」で外す。
- **結果**: 手間は減らず先送りになるだけで、判定の責任がユーザーからAIへ移る。厳しく判定すれば全件がユーザー行きになり、緩く判定すれば実測の誤りがそのまま通る。1週間の間隔は、その間に起きる変化（改訂、統合先の書き換え）を検出する仕組みが無い限り、何も防がない。
- **対策**: 照合は統合の時点で、メモと統合先の差分として行う（メモが手元にあり、比較が最も安い）。統合エージェントに「メモに無い記述」「メモから落ちた記述」の一覧を出させ、ユーザーが共有側で1回承認する。試験運用中は、本文外しを自動化せずユーザー承認にする。

## 重大度: 中

### 5. 確認2（見出しの実在）は、内容の正しさを何も保証しない

- **筋書き**: 統合は書き直すので、見出しは通常一致せず、不成立になる。一方、統合エージェントが確認2を通すために見出しを残すよう学習すると、中身が古い・欠けていても成立する。旧版の統合や似た見出しの別項目でも成立する。
- **結果**: 偽陰性と偽陽性の両方が出る。「見出しは残っているが却下案が落ちた」は検出できない。
- **対策**: 台帳に統合コミットのハッシュを記録し、確認2を「そのコミットの差分にメモIDへの参照がある」に置き換える。統合先の本文にメモIDを注記する方法もある。

### 6. 撤回・改訂が共有側へ伝わらない

- **筋書き**: (1) 項目が `転記済（本文残し）` または `転記済` になる。(2) ユーザーが判断を撤回、または大きく改訂する。
- **結果**: `knowledge/` に撤回済みの判断が残り続ける。本文残しの段階なら、第2段の照合が「欠落」と誤認し、統合先に合わせる方向へ誤修正する恐れもある。
- **対策**: `転記待ち` 以降の項目を改訂したら、ハッシュの不一致で検出し、状態を `未仕分け（前回 → 統合先）` に戻して、訂正メモの候補として報告する。

### 7. 追記のみの台帳でも、git では競合する。統合・台帳・削除が別々にずれうる

- **筋書き**: (1) 2つのセッションが同じ `inbox/` を見て、同じメモを統合する。両者とも末尾に追記する。(2) push で末尾行が競合し、エージェントが片方を採って解消する。
- **結果**: 台帳行が消える、`knowledge/` に重複統合ができる、1つのメモに統合先の異なる2行ができる、のいずれかが起きる。台帳行だけが push され、統合や削除が未 push・中断のままになると、「台帳上は統合済み、実体は無い」状態になる。
- **対策**: 統合・台帳追記・メモ削除を1コミットにする（原子性）。台帳を1統合1ファイル（`integrated/<メモID>.md`）にするか、`.gitattributes` で `merge=union` を指定する。統合の前に `inbox/<メモ>` を削除予約するロックとして、先にコミットする方法も有効。

### 8. 台帳の訂正の意味が未定義

- **筋書き**: 誤記を「行を足して訂正」したが、見直しが最初に一致した行を読む。または、メモ名の打ち間違いで永遠に一致しない。
- **結果**: 誤った統合先で `転記済` になる、または `転記待ち` に永久に滞留する。
- **対策**: 行に種別（統合／取消／訂正）を持たせ、IDごとに最新行を有効とする規則を明文化する。見直しの際、台帳のIDが共有側の `inbox/` の履歴に実在するかを検証する。

## 重大度: 低

### 9. 捨てられたメモの `転記待ち` が無期限に滞留する

- **筋書き**: 統合せずに `inbox/` から削除されたメモは、台帳に載らない。
- **結果**: 見直しでは「何もしない」が続き、気づけない。
- **対策**: N週を超えた `転記待ち` を毎回報告に載せる。台帳に「破棄」行も書く方法もある。

### 10. 1メモの分割統合・統合先の後日移動

- **筋書き**: 1つのメモを2ファイルに分けて統合する。または、後日 `knowledge/` を再編して統合先が移動・合併される。
- **結果**: 台帳の統合先は1列なので、確認2が不成立、または一部だけを照合して本文を外す。外した後に統合先の内容が消えても、誰も気づかない。
- **対策**: 統合先を複数書けるようにする。`転記済` 行に統合時の共有側コミットハッシュを残し、後から辿れるようにする。

### 11. 見直しが古いクローンを読む

- **筋書き**: 作業側の端末で、共有側を pull せずに見直す。
- **結果**: 進捗が遅れるだけで、誤った前進にはならない。ただし、クラウドのセッションがブランチで統合して未マージの場合、どちらの台帳を正とするかが曖昧になる。
- **対策**: 見直しの前に fetch し、main の台帳だけを正とする。

## 代替案

- **案1（推奨: 照合を統合時に寄せる）**: 統合エージェントが統合時に「メモ⇔統合先」の差分レポート（欠落・混入）を出し、ユーザーが共有側で1回承認する。台帳にはメモID、メモの本文ハッシュ、統合コミットを記録する。作業側の見直しは「ハッシュが一致すれば `転記済`」だけの完全に機械的な処理になり、AIの解釈が入る工程が1か所になる。
- **案2（最も単純）**: 本文を外さない運用にする。`転記済（→ 統合先, コミット）` の印だけを付け、作業側の本文は「正本ではない控え」と明記する。二重管理のコストは増えるが、時系列の穴の多く（4・6・10）が「損失」から「表記の不一致」に格下げされる。

## 試験運用（2週間）に進めてよいか

**条件つきではい。** 本文外しは git で戻せる（仮定B）ので、試験自体のリスクは小さい。ただし、次の条件を満たさないと、2週間で得られる情報が少なくなる。

1. 確認3を、日付比較から項目本文のハッシュ比較に置き換える（指摘1・2）。
2. メモに一意IDを振り、台帳はIDで引く（指摘3）。
3. 統合・台帳追記・メモ削除を1コミットにし、台帳を1ファイル1行にするか `merge=union` にする（指摘7）。
4. 試験期間中、本文外し（第2段）は自動にせず、一覧を示してユーザー承認にする（指摘4）。
5. 台帳行の種別と最新行優先の規則を、試験前に1段落で定める（指摘8）。

補足: 週1回の見直しで2週間だと、第2段は実質1回しか走らない。評価を目的にするなら、試験中だけ見直しの頻度を上げるか、期間を4週間にすることを勧める。
