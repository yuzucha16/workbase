# 6R: 会議録のナレッジ化

計画のやり方（`workflow-kit/start-plan.md` の A）。ユーザーの承認済み（2026-10-21）。憲章・WBS・マイルストーンは [[private-knowledge-plan]]、作り方のメモは [[private-knowledge-plan-notes]]。トピックの窓口は [[private-knowledge-start-here]]。置き場はこのトピックの `records/`（`records/` は2か所。`topics/private-knowledge/docs/decisions.md`）。

要求: 顧客を含む打合せ内容を知識化したい。
条件: AI 向け（`lessons`）と私向け（`explain`）と同じ扱い・方針・ルールにしたい。

## 1. 状況と問題意識（まとめた欄）

**顧客を含む打合せの内容が、知識として残らず、Project をまたいで使えない。**
- 会議録の置き場も型もない。`exmem/` と `guides/` は公開リポジトリにあり、業務の文脈を書けない〔資料: `exmem/AGENTS.md`〕。
- 既存の置き場は Project の `ai/work` と `ai/in` で、特定の Project からしか参照できない。Project が閉じれば `archives/` に移る〔資料: ユーザーの発言、`para-operations`〕。
- 入力は、自動の文字起こし（長く、言い直しや話者の誤りがある）と、自分の議事録・メモ〔資料: ユーザーの回答。誤りの点は〔推測〕〕。

## 2. 要求

**打合せごとに、決定・ToDo・背景を取り出し、Area 内で Project をまたいで引ける形で残す。**
- 見る単位は打合せ1件。統計量は、打合せ1件あたりの「冒頭に収まる行数」と「人が直した箇所の数」。
- 使い方は、ToDo・アクションアイテムの抽出、決定事項の要約、各 Project への入力と方向修正、Area・Project 全体に効くナレッジ〔資料: ユーザーの発言〕。
- 周りと同じ仕組み（型・タグ・索引・昇格の流れ）を使い、シンプルに保つ。ファイル分割は最小にする〔資料: ユーザーの回答〕。

## 3. 意図・裏づけ・仮説

**1つの情報を、1ファイルの2層で、人と AI の両方に読ませる。**
- 意図: 冒頭の数行に決定・ToDo・次の一手を置き、人はそこだけ読む。その下に背景・経緯・事実を密に書き、AI は必要な節だけ読む〔資料: 採用した案 A〕。横断の ToDo・決定の一覧は Bases で出す（B の要素）。
- 使ってみて確かめること: 冒頭と本文の2層で、人と AI の両方の読み方が足りるか（仮説）。
- 裏づけ（未確認。最初に確かめる。結果は [[private-knowledge-checks]] に書き戻す）:
  - 〔未確認〕works 側（Area）にも `inbox` → 統合の流れを置けるか。置けるなら、`stock` と `integrate` を場所の引数で使い回せるか。
  - 〔未確認〕3ラベル（【この件】【案件】【汎用】、`para-operations`）で、会議録の出力が仕分けられるか。
  - 〔未確認〕frontmatter の `org:`（自社 / 顧客A）を使った Bases の絞り込みで、横断の ToDo 一覧が作れるか。
  - 〔未確認〕マスク後の `ai/in` に、2層のファイルをそのまま渡せるか（冒頭の数行に顧客名が混ざらないか）。
  - 〔未確認〕進行中の `stock` のモード追加（`kind: lesson | explain`、[[stock-modes-plan]]）と、どこで重なるか。あちらは公開してよい知識（`exmem/inbox/` 経由）、こちらは works 側の知識。

## 4. 今回のスコープ（期日: 2026-10-28、既定の1週間）

**会議録を Area に残す型と流れを決め、実例1件で通す。**
- やる: 型（冒頭の数行と本文、frontmatter の項目）、置き場（Area 配下、`org:` の項目）、流れ（文字起こしまたはメモ → 下書き → 承認 → Area）、3ラベルとの対応、マスクの扱い。
- 対象外とその理由:
  - 録画・音声から文字起こしにする工程。入力は文字起こし済みとする。見直しは、手作業が負担になったとき。
  - 自社と顧客Aの本格的な抽出。`org:` の項目を持たせるまでを範囲とする。Bases の画面づくりは、実例が3件溜まったとき。
  - 手順書のように問いが変わる文書。別の型のままとする。見直しは、会議録から手順書が出るようになったとき。
- 前提・注意:
  - 実データの置き場は works 側の Area。機微は有り（顧客名と案件の内容）。公開リポジトリには入れない。このリポジトリに置くのは規則・型・マスク済みの見本だけ。
  - 承認が要る変更先は `workflow-kit/` の `stock` と `integrate`、`methods.md`。ユーザーの承認なしに書き換えない。

## 5. 期待する成果

**会議録1件から、冒頭の数行と本文を持つ知識が、Area に1ファイルで残る。**
- 指標: 実例1件で、冒頭の数行に収まった決定・ToDo の数と、人が直した箇所の数。
- 未決（何を見れば決まるか）:
  - 作る流れを `stock` / `integrate` の拡張にするか、並行する手順にするか。裏づけの1つ目を確かめれば決まる。
  - 冒頭の数行の行数の上限。実例1件を作って測れば決まる。
