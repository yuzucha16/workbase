# 判断の記録（decisions）

## Decisions

### 【この件】環境を特定する語は、性質で書く表現に置き換える。履歴は段階的に回収する（2026-10-27）

- 動機（ユーザー）: 「公開されても差し支えない表現にしたい」「スクリプトのコマンド例に（環境を特定する語が）書かれていて、私の精神衛生上よくない。できれば隠ぺいしたい」。
- 方式（ユーザー）: 「性質で書く：こちらを採用します。代名詞 ラボはある意味思いつきなのでこだわりはない。私の精神衛生が保たれればOK」。却下案: 新しい固有名（「ラボ」）で統一する。AI が規則の緩みと読む、制約の連想が消える、依頼文の語と合わなくなる、の 3 点が理由（`records/2026-10-27-impact-analysis.md`）。
- 履歴（ユーザー）: 「許容できないので段階的に回収していきたい。ただ急いではいない。過去に push force で書き換えた実績もあるので問題はない」。現在の文言の整理（段階 1〜3）を先に行い、履歴の書き換え（段階 4）は最後に 1 回にまとめる。force push は、実行時にユーザーが deny を切ったときだけ行う（`commit-push-rules.md` の「しないこと」。前例: root の `docs/decisions.md` の 2026-10-25）。
- 機密規則は緩めない。「固有の情報を入れない」の禁止範囲は、語を変えても同じにする。
- PC1（ユーザー）: 名前はそのまま。意味としてラボ環境（制約のある環境）の PC とする。置換の対象にしない。定義の 1 行を足すかどうかは、段階 2 で決める。
- 段階 2（ユーザー、2026-10-28）: PC1 の定義の 1 行を README に足す。公開前の検索（`commit-push-rules.md` の push の条件 4）に対象語を足す。法人格の語と Office のプロパティ名は、当たっても止まらず、ユーザーに見せて確かめる。
- 置換後の語（ユーザー、2026-10-28）: 「勤務先」。「組織」は抽象的で、雇用先の機密を負う含意が落ちるため。規則は「勤務先に固有の情報」「勤務先名」、環境は「PC1」「検査用のルート証明書」「管理側」。段階 4 の履歴の置換語も「勤務先」（「会社名」→「勤務先名」、「会社固有」→「勤務先固有」、「会社 PC」→「PC1」）を既定とする。法人格の語と Office の「会社」プロパティは対象外のまま。
