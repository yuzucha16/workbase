# 6R: stock のモード追加

計画のやり方の試行（[[planning-method-draft]]）。`start 計画` の A（事前の仕込み）。ユーザーの承認後に憲章・WBS・マイルストーンへ進む。

要求: 私用のナレッジ整理（`guides/explain`）と AI 用のナレッジ整理（`exmem/lessons`）を、同じフックで動かしたい。
条件: `stock` にモードを追加する。

## 状況と問題意識

`stock` は AI 用（`exmem/inbox/` → `lessons/`）だけを扱い、人向けの理解ガイドは手で書いている。〔資料〕

- 人向けの文書と AI 向けの知識は、読む人も形も違う（`reference-doc-types`）。同じ手順（判定 → 重複確認 → 点検 → 報告）を使えれば、ふぞろいが減る。〔推測〕
- 窓口を増やすと、「窓口は2か所だけ」（`hooks.md` の跨ぎの型3）、権限表、`integrate` の入力が連動して変わる。〔資料〕
- `lessons/` の7見出し（Principles など）は、説明の流れの理解ガイドに合わない。〔推測〕

## 要求

- `stock 理解` と `stock ナレッジ` で、同じ手順を共有し、書き込み先と形式だけをモードで切り替えたい。〔資料〕
- 見る単位はフックの1回の実行。統合の流れ（`integrate`）も同じモードで通ること。〔推測〕

## 意図・裏づけ・仮説

- 意図: 知識の整理を1つの入口にする。モードを足すのは手段で、理解ガイドを同じ品質管理（重複確認・点検）に乗せるのが目的。
- 裏づけ（未確認。最初に確かめる）:
  - `hooks.md` の窓口の記述と、`stock` `integrate` の権限（works・dotfiles・room からの書き込み）が、`guides/inbox/` を足して矛盾しないか。〔推測〕
  - `check-inbox` の点検（7見出し）が、`type: inbox` の理解ガイド向けメモに通るか、別の形が要るか。〔推測〕
  - `guides/` 側のルール（`guides/AGENTS.md`: 一意なファイル名、`guides-index.md` の更新、タグは `exmem/tags.md`）を統合の手順に写せるか。〔資料〕

## フィードバック（憲章・WBS・マイルストーンを書いた後。2026-10-20）

6R から憲章・WBS・マイルストーンを作った時点の所見。題材は kit の手順書の変更（kit 内部、1人、1週間、見本なし）。実行（設計・実装）の所見は、実行後に別に足す。

### 埋めるのに情報が足りなかった項目

- **予算**: 6R に基準が無い（既定は「1週間」だけ）。憲章には「ユーザーの判断 4〜5 回、2〜3 セッション」と書いたが、根拠は前回の試行の所見（日数より判断の回数が実態に合う）だけで、この題材の見積もりではない。変更量（触るファイル数、行数）が 6R にあれば、見積もりの根拠になる。
- **開始日と順序（依存関係）**: マイルストーンの日付は「開始日 10-20 から出した推測」。6R に開始日も、作業の順序（設計 → 手順書 → 点検 → 試験）も無く、M1〜M3 の切り方は AI の判断になった。誰がどのゲートを承認するか（M1 は誰が確認するか）も 6R に無い。
- **品質（合否の基準）**: 6R の「期待する成果」は動作の説明と指標1つだけ。憲章の品質の欄は、そこから「引数なし・ナレッジの動作が変わらない」（回帰）を導き、`check-hook-outline` が通ること（`hook-common.md` から）を足した。後者は 6R に無い情報を、別の文書から持ち込んでいる。「変えないこと」を書く場所が 6R に無い。
- **WBS の葉（変更先のファイル）**: 6R のスコープの対象は6行で、葉は9になった。増えた分（`room-context.md`、`hook-matrix.md`、各 README など）は、`grep` で参照を探して足した。6R の裏づけに「変更先を洗い出す」があれば、再現しやすい。
- **試験の題材**: 通し試験に使う既存の理解ガイドが決まっていない（6R の指標は「既存の理解ガイド1本分」）。どれを使うかで、試験の難しさが変わる。

### 使わなかった・解釈が難しい項目

- **要求の「見る単位」**: 6R に「フックの1回の実行」と書いたが、憲章にも WBS にも使わなかった。測る道具の計画向けの項目で、手順書の変更のような題材には当てはまらない（`start-plan.md` の「要求の欄に、見る単位…があれば書く」は、条件つきなので、書かなくてもよいはずが、書いてしまった）。
- **状況**: 3項目のうち1つ（現状の事実）だけが状況で、残りは設計上の観察だった。問題意識と重なる（前回の所見と同じ）。
- **仮説**: 書かなかった。意図・裏づけ・仮説の欄の「仮説」は、この題材では「裏づけ」に吸収された。
- **前提の表**: 列を2列（読み・内容）から3列（論点・読み・内容）に変え、確定を太字、却下を括弧内で書き分けた。決まった書式が無く、書くたびに揺れる。読みの名前（A/B/C/D/A'）は、会話の中で付けた名前（質問1の A/B/C、次の A/D/C）と表の行がずれ、ユーザーの「A」が表のどの行を指すか、書き手が読み替えた（A'）。選択肢の名前は、表に書いた名前で呼ぶ必要がある。
- **〔資料〕〔推測〕のタグ**: 出典（どのファイルを読んだか）が付いていないので、後から検証できない。憲章・WBS・マイルストーンには、タグ自体が引き継がれず、推測の値（予算、日付）が断定のように見える（日付に「推測」の注記を足して補った）。
- **対象外**: 憲章に欄が無く、6R に残るだけ。見直す条件を6Rに書いたのに、マイルストーンでその条件を確かめる点が無い。

### 再現性を落とす可能性のある点

- **裏づけ（未確認。最初に確かめる）が、WBS の葉やマイルストーンに結びつかない**。今回は6R に3項目あったが、確かめる作業が計画のどこにも置かれず、未確認のまま残った（`room.py` を読んでいない）。裏づけの確認を「M1 の前に行う」「葉にする」と決めておかないと、書き手によって扱いが分かれる。
- **既存ツールの役割の行が、葉に写されなかった**。6R の前提の表に「`find-knowledge`（`guides/` への拡張は未決）」と書いたのに、最初の WBS に葉が無かった。変更の記録で後から足した。表の行から葉への対応を点検する手順が無い。
- **憲章と他の表の間の矛盾**: 憲章の「完了時期（バッファ込み）」が、マイルストーンの「バッファは 10-28 以降」と食い違った。憲章の欄に「バッファ込みか」を書く規則は無い。
- **葉と1ファイルの対応**: 1.2.3 は7ファイルの整合を1つの葉にまとめ、1.4.2 は親にまとめた。「葉は1ファイルに対応させ、ファイルにならないものは親にまとめる」の線引きが、書き手によって変わる。
- **憲章の指標と品質の重複**: 指標（FAIL が 0）は品質の言い換えになった。欄を分ける意味が、この題材では薄い。
