# IR（中間表現）を今の仕組みに当てはめる案（雑談の叩き台）

2026-10-30。添付 `2026-10-30-office-ooxml-ai-artifact-workflow.md` を、room・cleankit・基準文書・`script-guide.md`・`topics/token-cap/records/2026-10-26-macro-split.md`・`exmem/lessons/excel-vba-ai-development.md` に当てはめた。kit は未変更。

## 1. IR と基準文書の関係（指摘）

- 添付の IR は「生成の入力」だけで、基準文書の必須 3 つのうち「正の向き」しか持たない。目的・満たすべきこと（ID）・検証項目が無い。
- なので **IR = 基準文書** ではなく、**IR は基準文書の一部（形の契約）** と置くのが合う。基準文書 = 要件（ID）＋ 形の契約（IR）＋ 検証ケース（ID に紐づく）。
- 正の向きは、新規・繰り返す成果物なら「基準文書が正、ファイルは生成物」で、添付の方針（AI の出力とファイル形式を結合しない）と一致する。

## 2. マクロ（.bas）の場合、IR は何か（指摘）

- 添付のパイプラインは「中身を Office ファイルにする」話で、マクロ作りにはそのまま当たらない。.bas はすでにテキストで、AI が直接書いてよい。
- マクロで IR が効くのは、.bas の外側の 2 か所:
  1. **シートの契約**: シート名、見出し行、列、名前付き範囲、ボタンとマクロの対応、表示形式（`@` など）。今 ee が手でやっている「レイアウト」がこれ。
  2. **検証ケース**: ダミーの入力 → 期待する出力（CSV）。ID で要件に紐づく。
- 粒度の推奨: シートの契約は**シート・列・名前付き範囲の単位**（セル単位や OOXML の差分は細かすぎ、AI が読む量が増える）。.bas の修正は**プロシージャ単位の差分**（macro-split 案のまま）。

## 3. 当てはめ案（1 つ）

| 工程 | 人（ee） | AI | コード（部屋で決定論） | Windows（人が実行） |
|---|---|---|---|---|
| 基準文書 | 承認 | 要件（ID）・シートの契約・検証ケースを下書き | 契約の形式チェック | |
| ひな形 | | | `gen_template.py`: 契約 → ひな形 xlsx（レイアウト＋ダミーデータ） | |
| 実装 | | モジュールごとに別の短い会話で .bas | `check_bas.py`: 静的検査（Option Explicit、宣言の位置、予約名、cp932 に無い文字、ブロック対応）→ cp932・CRLF に変換 | |
| 実行 | ひな形に .bas を組み込み、コンパイル、ダミーで実行 | | | 出力を CSV で保存 |
| 判定 | 差分の報告を部屋に戻す | 差分だけ読んで、該当プロシージャを直す | `compare.py`: 出力 CSV と期待 CSV の差分を、ケース ID つきの数行に | |
| 本番 | 実データで実行（`_noai` 側。部屋に入れない） | | | |

トークンが減る所:
- AI は xlsx を読まない。読むのは基準文書と、数行の差分の報告だけ。
- 合否の判定をコードがするので、「動いた？どう違う？」のラリーが減る（今月の主因の 1 つ。`room-windows-balance` の診断ログ案と合流できる）。
- 静的検査で、コンパイルエラーの往復を部屋の中で潰す。
- レイアウトを人が手で作らないので、「レイアウトと .bas の食い違い」の往復が消える（両方が同じ契約から出るため）。

## 4. 今の仕組み・PC1 と合わない所（指摘）

1. **openpyxl / python-pptx が部屋で使えるか未確認。** 部屋に uv はあるが、PyPI に届くか（社内ネット・TLS 検査）は確かめていない。届かなければ、標準ライブラリの zip/XML（cleankit と同じ作り）か、部屋の LibreOffice（headless で生成・再計算・PDF 化）で代える。ひな形の生成だけなら、LibreOffice でも足りる見込み。
2. **マクロの実行は部屋ではできない。** LibreOffice の VBA 互換は当てにならず、xlsm の `vbaProject.bin` はバイナリで、openpyxl は保持はできても作れない。組み込み・コンパイル・実行は Windows の人のまま残る。
3. **組み込みの自動化（COM の `VBComponents.Import`）は今回は外す。** 「VBA プロジェクトへのアクセスを信頼」の設定が要り、COM を使わない方針（10-24 の回答）に当たる。手で組み込む手間は残るが、1 モジュール数クリック。
4. **実データ**: ひな形とダミーは部屋で作るので、境界は変わらない。既存のブックを AI に見せる必要が出たときだけ cleankit → mask を通す。
5. **pptx は添付の形がそのまま合う**（Markdown/JSON → テンプレ → python-pptx）。`notes/office-deliverable-workflow/2026-10-07-design-draft.md` の一方向フローと同じ。見た目の確認は LibreOffice で PNG にして**人が見る**（AI に画像を読ませると重い）。
6. **時期**: token-cap の 10-29 の決定で「マクロ作成作業の型は token-cap の方向が出てから」。今の 1000 行のマクロはほぼ完了なので、この案は次のマクロから試す想定。

## 5. 進める順の推奨

1. `compare.py` と `check_bas.py`（判定とコンパイル前の検査）を先に。ラリーに直接効き、openpyxl も要らない（CSV と .bas のテキストだけ）。`check_bas.py` は lessons の規約をそのまま規則にできる。
2. 次に、検証ケース（ダミー入力 → 期待 CSV）の書き方を基準文書の型に入れる。
3. ひな形の生成（`gen_template.py`）は、部屋で openpyxl が使えるか確かめてから。
