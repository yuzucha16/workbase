# Excel・PowerPoint（OOXML）の内部構造とAIによる成果物作成

## 1. 質問の経緯・目的

Excel（`.xlsx`）やPowerPoint（`.pptx`）は、ZIPアーカイブの中にXMLや画像などのパーツを格納して構成されていると聞いた。内部の仕組みと構造を詳しく理解したい。

最終的な目的は、**AIとコードで成果物作成を分担すること**。OfficeファイルをAIに丸ごと作らせるのではなく、AIの分析・構成能力と、コードによる再現可能な生成・検証処理を組み合わせる設計を検討している。

## 2. 基本概念

Officeの`.xlsx`／`.pptx`は、Office Open XML（OOXML）に基づくパッケージ形式。

- **ZIP**：ファイルやディレクトリ相当のパーツを格納するコンテナ。
- **XML**：文書の構造、データ、設定などを表現する。
- **OPC（Open Packaging Conventions）**：パーツをパッケージに格納し、パーツ間の関係を管理する仕組み。
- **Relationships（`.rels`）**：ワークブック、シート、スライド、画像、レイアウトなどの参照関係を定義する。
- **`[Content_Types].xml`**：パーツごとのコンテンツ型を宣言する。

したがって、Officeファイルは「XMLの集合」ではなく、XML・バイナリパーツ・参照関係を組み合わせたパッケージである。

## 3. 共通パッケージ構造

典型例：

```text
example.xlsx / example.pptx
├── [Content_Types].xml
├── _rels/
│   └── .rels
├── docProps/
│   ├── core.xml
│   └── app.xml
├── xl/                 # Excel
│   ├── workbook.xml
│   ├── _rels/
│   ├── worksheets/
│   ├── styles.xml
│   └── media/
└── ppt/                # PowerPoint
    ├── presentation.xml
    ├── _rels/
    ├── slides/
    ├── slideLayouts/
    ├── slideMasters/
    ├── theme/
    └── media/
```

実際に存在するパーツは文書の内容や機能によって異なる。上記は典型例であり、すべてのパーツが常に存在するわけではない。

### Relationshipsの重要性

例：Excelの`xl/workbook.xml`にシートが定義される。

```xml
<sheet name="売上" sheetId="1" r:id="rId1"/>
```

`r:id="rId1"`は、`xl/_rels/workbook.xml.rels`の関係定義を通じて実際のシートXMLに結び付く。

```xml
<Relationship
    Id="rId1"
    Type=".../worksheet"
    Target="worksheets/sheet1.xml"/>
```

注意点：

- `sheetId`と`r:id`は別の識別子であり、意味が異なる。
- `r:id`はRelationshipを参照するID。
- `Target`は参照先パーツを示す。
- パーツを追加・削除・移動する場合、XML本体だけでなくRelationshipやコンテンツ型宣言などの整合性も必要になる。

## 4. Excel（SpreadsheetML）の構造

主なパーツ：

| パーツ | 役割 | 編集上の注意 |
|---|---|---|
| `xl/workbook.xml` | シート一覧、ブック設定 | シート追加・削除時はRelationshipも確認 |
| `xl/worksheets/sheetN.xml` | セル、数式、行列、シート設定 | 数式、セル参照、結合セル、行列構造 |
| `xl/styles.xml` | フォント、塗り、罫線、表示形式など | セルの書式IDとの整合性 |
| `xl/sharedStrings.xml` | 共有文字列テーブル（存在する場合） | セル側のインデックスとの整合性 |
| `xl/tables/` | テーブル定義 | 範囲、列名、フィルターなど |
| `xl/charts/` | グラフ | データ系列・参照範囲との整合性 |
| `pivotCache`関連 | ピボット関連データ | キャッシュと元データの整合性 |

### セル値・数式・計算結果

数値セルの例：

```xml
<c r="A1">
  <v>100</v>
</c>
```

数式セルの例：

```xml
<c r="A3">
  <f>SUM(A1:A2)</f>
  <v>300</v>
</c>
```

- `c`：セル
- `r`：セル番地
- `f`：数式
- `v`：値、または保存済みの計算結果
- 文字列は共有文字列テーブル、またはインライン文字列として保存される場合がある。

**重要な区別：**
1. 入力データ（セル値）
2. 計算ロジック（数式）
3. 計算結果（キャッシュ値、再計算後の値）

`<v>`の計算結果はキャッシュである。XMLを書き換えただけでExcelの数式計算が確実に実行されるわけではない。数式を設定できたことと、計算結果が正しいことは別に検証する。

### 書式

セルの書式は通常`styles.xml`側の定義を参照する。セルの`s`属性は書式テーブルのインデックスを示す。

```xml
<c r="A1" s="2">
  <v>100</v>
</c>
```

書式IDを誤って扱うと、値は保持されていても見た目が変わる可能性がある。

## 5. PowerPoint（PresentationML）の構造

主なパーツ：

| パーツ | 役割 |
|---|---|
| `ppt/presentation.xml` | スライド一覧、プレゼン全体の設定 |
| `ppt/slides/slideN.xml` | スライド内のテキスト、図形、画像配置など |
| `ppt/slideLayouts/` | タイトル＋本文、2カラムなどのレイアウト |
| `ppt/slideMasters/` | 共通背景、ロゴ、フッター、プレースホルダーなど |
| `ppt/theme/` | テーマカラー、フォントなど |
| `ppt/media/` | 画像などの素材 |

### テーマ・マスター・レイアウト・スライド

| 階層 | 主な役割 |
|---|---|
| テーマ | 色やフォントなどの共通デザイン体系 |
| スライドマスター | プレゼン全体の共通要素 |
| スライドレイアウト | タイトル＋本文、2カラムなどのページ構成 |
| 個別スライド | そのページ固有のテキスト、図形、画像など |

表示はスライドXMLだけでは決まらず、マスター・レイアウト・テーマから継承される設定も関係する。そのため、個別スライドXMLだけではフォントや色などの最終的な表示を完全に判断できない場合がある。

### 画像の参照

典型的には、スライドXMLが`r:embed="rId2"`などのIDを持ち、スライドの`.rels`が`ppt/media/image4.png`などの画像ファイルを参照する。

画像を新規追加する場合、画像ファイルの追加だけでなく、RelationshipとスライドXMLの更新が必要になることがある。

### 編集時に注意する点

- 図形の位置・サイズ・重なり順
- テキストボックス内の段落や改行
- マスター／レイアウトから継承される書式
- 画像・グラフへのRelationship
- グラフとデータキャッシュ
- アニメーション、ノート、コメント

XML構文が正しくても、Office上の見た目や機能が正しいとは限らない。

## 6. AIと成果物作成を分担する設計

推奨する考え方は、**AIの出力とOfficeファイル形式を直接結合しないこと**。AIは意味・構造・編集指示を生成し、コードがそれをOfficeファイルに反映する。

推奨パイプライン：

1. **要件・素材**：目的、データ、制約、既存テンプレート
2. **AI（Research / Analysis / Planning）**：調査、分析、構成、計算根拠、スライド設計
3. **中間表現（IR）**：JSON、Markdown、表データ、図表定義、編集差分
4. **Execution／生成エンジン**：ライブラリやテンプレートでファイルを生成・編集
5. **検証**：構造、数値、内容、描画をそれぞれ検証
6. **成果物**：編集可能で検証済みの`.xlsx`／`.pptx`

### 中間表現（IR）の例

PowerPointのスライドを、直接OOXMLで書かせず、独自JSONとして表現する。

```json
{
  "slide_id": "slide_03",
  "layout": "two_column",
  "title": "現状と課題",
  "sections": [
    {
      "heading": "現状",
      "bullets": [
        "処理時間が増加している",
        "運用負荷が高い"
      ]
    },
    {
      "heading": "課題",
      "bullets": [
        "処理のボトルネックが未特定",
        "監視指標が不足している"
      ]
    }
  ]
}
```

これはOOXML標準ではなく、AIと生成エンジンの間で使う独自の中間表現である。`layout`などの意味を、生成エンジンが実際のスライドレイアウトや図形へ変換する。

この分離によって、AIモデルの交換、再生成、差分レビュー、自動テストが容易になる。

## 7. 実装手段の比較

| 手段 | 得意分野 | 主な制約 |
|---|---|---|
| `openpyxl` | Excelのセル、数式、書式、シートなど | 数式計算エンジンではない。一部の高度な機能には制約 |
| `python-pptx` | PowerPointのスライド、図形、テキスト、画像など | アニメーション等、すべてのPowerPoint機能を操作できるわけではない |
| XML・ZIPの直接操作 | パーツ単位の細かな制御 | Relationship、書式参照、コンテンツ型などの整合性管理が必要 |
| Open XML SDK | .NETでのOOXML操作・検証 | .NET環境が必要。視覚的な正しさまでは保証しない |

基本方針は、**高水準ライブラリを基本にし、対応できない箇所だけOOXMLを直接操作する**こと。既存の複雑なファイルでは、ライブラリが未対応機能を保持できるとは限らないため、事前に検証する。

## 8. 安全性・品質保証

AIエージェントにファイル編集を任せる場合の最低限のルール：

- 元ファイルを直接上書きせず、コピーやバージョン管理を使う。
- 編集対象のパーツを限定する。
- Relationshipの参照切れを検証する。
- 数式と計算結果を別々に検証する。
- 生成後、ZIPとして開けることを確認する。
- Officeアプリで開いて、見た目と機能を確認する。
- マクロや埋め込みファイルは別扱いにし、想定外の実行や情報流出リスクを抑える。

**構造検証・内容検証・数値検証・描画検証は別の工程**として設計する。XMLが整形式であることは、成果物の正しさを保証しない。

## 9. 学習・検証の進め方

1. 小さな`.xlsx`と`.pptx`を用意し、ZIPとして展開する。
2. Excelでは`workbook.xml`と`sheetN.xml`、PowerPointでは`presentation.xml`と`slideN.xml`を読む。
3. `.rels`を追い、シート、スライド、画像、レイアウトの関係を確認する。
4. ライブラリで1セル変更・1図形追加などを行い、生成前後のXML差分を比較する。
5. 限定的なXML直接編集を試し、Officeで開けることと表示が維持されることを確認する。

仕様書を最初から通読するより、実ファイルの小さな変更と差分確認を通じて構造を理解する方が効率的。

## 10. 今後の論点

次の設計判断は未確定であり、用途に応じて決める必要がある。

- **新規生成か既存ファイル編集か**：既存テンプレートや複雑な機能を保持する必要性で手段が変わる。
- **Excelの計算結果をどう保証するか**：Excel等で再計算するのか、外部で計算するのか。
- **PowerPointの描画検証をどう自動化するか**：Office環境、PDF変換、画像比較などの手段を検討する。
- **中間表現の粒度**：スライド単位、図形単位、セル範囲単位、編集差分単位のどれにするか。
- **テンプレート管理**：テーマ、マスター、書式をどこまで固定し、AIにどこまで決めさせるか。
- **既存ファイルの未対応機能をどう保護するか**：ライブラリによる読み書きで機能が失われないかを検証する。
- **検証・差分レビューの仕組み**：生成物、変更箇所、検証結果を再現可能な形で保存する。

## 11. 結論

OOXMLは、AIに直接すべてを書かせるためのフォーマットというより、**AIが作った情報をOffice成果物へ変換し、構造や差分を検査するための操作可能な内部形式**として扱うのが適切。

初期構成の推奨：

- AIの出力：JSON／Markdownなどの中間表現
- Excel生成：`openpyxl`
- PowerPoint生成：`python-pptx`
- 例外：ライブラリで扱えない部分のみOOXMLを直接操作
- 品質保証：構造・内容・数値・描画を分けて検証

AIは分析・構成・編集指示を担当し、コードは決定論的なファイル生成と検証を担当する。この分離により、再現性、保守性、差分レビューのしやすさを確保する。
