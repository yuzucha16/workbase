# Area を跨ぐ共有知: workbase の共有知との違いと、設計の軸（理解ガイド）

works の Area（非公開）に溜める知識を、別の Project の AI 作業部屋でも使えるようにするとき、何が難しいのか、公開の共有知（workbase の `exmem` と `guides`）と何が違うのか、どこで設計を選ぶのかを、自分で説明できるところまで理解するための文書。会議録は最初の題材だが、この文書は題材を限らない一般の話として書く。

> **状態: 草稿（未レビュー）。** 2026-10-21 時点の読み取りに基づく。設計の軸のうち、渡し方（a）、選び方（絞って人が確認。仮案）、マスクの時期（渡すとき）、戻り、統合（Area に置く）、3層は、ユーザーが決めた。「案」と書いた部分は AI の提案で、承認前。実機で確かめていない点は「要確認」とした。

- 前提: works は PARA 構成（`areas/` `projects/` `archives/`）で、リポジトリの外にある。AI 作業部屋（[[ai-room-why]]）は、作業中の Project の `ai/` だけを見せる WSL の部屋。共有知の正本は workbase の `exmem/`（AI 向け）と `guides/`（人向け）
- 確認状況: 規則と手順書を読んだ範囲での整理。取り出し・マスク・統合・戻しは、2026-10-21 に実機の通し試験で問題なし（ダミーの Area）。Obsidian の Bases での一覧は未確認
- 勤務先名、顧客名、実際の Project 名などの固有情報は、この文書に書かない

## 1. 状況と解決（ダイジェスト）

**状況**

- 打合せの決定・ToDo・背景のような知識は、特定の Project に閉じず、Area 全体に効く。しかし置き場が Project 内（`ai/work` と `ai/in`）だと、Project が閉じて `archives/` に移るときに、他の Project から引けなくなる
- workbase の共有知は、公開リポジトリにあり、固有名を持たない。顧客名や案件の内容を含む知識は、そこに置けない

**原因**

1. 部屋の AI は、Area を直接読めない。部屋に渡るのは、Project の `ai/` と、Area の README の写し（`ai/ctx/area-README.md`）だけ
2. Area の知識は実名を含む。部屋の AI には、マスクした写しだけを渡す決まり
3. workbase の共有知には、書き込みから育てる流れ（`stock` → `inbox` → `integrate`）がある。Area の側には、同じ流れがまだ無い

**解決の方向（案）**

- 知識は Area 内に実名で置き、**渡すときにマスクした使い捨ての写しを作って**部屋の `ai/in/` に置く
- 渡す分は、`org:` やタグで絞り、人が確認する
- 部屋の AI の出力は、既存の `room close` →（Area の）`ai/docs/inbox.md` で Area に戻す

```
Area（非公開・実名）                       AI 作業部屋
  知識ファイル（冒頭の数行＋本文）
  org: タグ ─ 絞り込み ─ マスク ─────────▶ ai/in/（使い捨ての写し）
                                              │ AI が作業
  ai/docs/inbox.md（【案件】） ◀── room close ──┘
```

## 2. 理解のための基礎知識

### 2.1 workbase の共有知との違い（マトリックス）

| 軸 | workbase の共有知（exmem / guides） | Area を跨ぐ共有知 |
|---|---|---|
| 共有の単位 | 全作業ディレクトリ | 1つの Area（その中で `org:` などで絞る） |
| 公開範囲 | 公開リポジトリ | 非公開（works 側） |
| 実名を消す時期 | 書くとき（一般化して固有名を剥がす） | 渡すとき（使い捨ての写しをマスクする） |
| AI の読み方 | 直接読む（読み取り専用の参照、`find-knowledge`） | 直接読めない。取り出して渡す経路が要る |
| 知識の性質 | 一般化した原則・落とし穴。1ファイル1トピック。長持ち | 固有の事実・決定・ToDo。打合せ1件が単位。寿命は Area に紐づく |
| 書き込みの流れ | `stock` → `inbox` → `integrate` でトピックに統合する | 統合先が未定。件ごとに溜まる |
| 読み手 | AI 向け（`exmem`）と人向け（`guides`）に分ける | 1ファイルに2層（冒頭の数行は人向け、本文は AI 向け）（案） |
| 置き場と同期 | 公開 Git。複数 PC に配る | works 側（リポジトリの外）。PC ごとの扱いは要確認 |
| 索引・タグ | `exmem-index.md` と `tags.md` が正本 | 同じ型・タグ・索引にそろえると決めたが、索引の置き場は未設計 |
| リンクの向き | 共有側から works へは張れない | works 側から workbase へは張れる（一方向） |
| 退役 | `status: superseded` で残す | Project や Area が閉じると `archives/` に移る |

最大の違いは、「AI が直接読めるか」と「実名を持つか」の2つ。ほかの違いの多くは、ここから出る。

### 2.2 設計の軸

| 軸 | 選択肢 | 案（推奨） |
|---|---|---|
| 渡し方 | (a) 必要な分を Area から取り出し、マスクして `ai/in/` に置く / (b) 知識を常にマスク済みの写しで持つ / (c) AI が Area を直接読む | **(a)**。(c) は `areas/` を AI が扱わない決まりに反する。(b) は二重管理で同期がずれる |
| 選び方 | 全部 / タグ・`org:` で絞る / 人が指定する | **絞る＋人が確認**。全部は漏れの面積が大きい。足りなければ人が足す |
| マスクの時期 | 書くとき / 渡すとき | **渡すとき**。Area 内は実名で書ける。写しは使い捨てで、持ち越さない |
| 戻り | AI の出力を Area に戻す / 戻さない | **既存の `room close` → `ai/docs/inbox.md`（【案件】）**。新しい経路は作らない |
| 統合 | 件ごとに溜める / 統合して育てる | **Area に置く**（ユーザーの決定、2026-10-21）。実行は**部屋の作業**: マスクした写しを `ai/in/` に置き、部屋の AI がマスクのまま統合し、人が `restore` で実名に戻して Area に置く。works の AI は実名を読まない。`integrate` の権限は変えない。戻り先の経路は `room` に足す（設計中） |
| 知識の層 | ① 事実（実名、Area）/ ② 部屋用の写し（渡すときに作る）/ ③ 一般化した教訓（workbase） | 3層。固有の事実は、仮名にしても workbase に切り出さない。③ は一般化したものだけを、既存の `room stock` で出す（ユーザーの決定） |

### 2.3 一般の型（案）

1. Area の知識は、種類を問わず同じ約束事を持つ: frontmatter に `org:` とタグ、冒頭の数行（人向け）、本文（AI 向け）
2. 渡すときは、条件に合う知識を取り出し、既存の `mask.toml` と `mask-spec.md` でマスクして `ai/in/` に置く。新しいマスクは作らない
3. マスクの警告（人名、敬称、メール、電話、URL）が出たら、人が語を足して通す。警告が残ったままの渡しは止める
4. 渡した一覧（どのファイルを、どの条件で）を、部屋の記録に残す

自分で説明するときの一言: 「Area の知識は実名のまま持ち、AI に渡す瞬間だけ、絞ってマスクした使い捨ての写しにする。結果は既存の経路で Area に戻す」

## 3. チェックリスト（症状・疑問 → 原因 → 対処）

| 症状・疑問 | 原因 | 対処 |
|---|---|---|
| 別の Project の部屋で、Area の過去の決定が引けない | 部屋に渡るのは Project の `ai/` と Area の README の写しだけ | 条件で絞ってマスクした写しを `ai/in/` に置く（案） |
| マスクしたはずなのに人名が残る | 辞書にない名前は置換されない | マスクの警告を見て、`mask.toml` に語を足す |
| frontmatter の `org:` の値が置換される | md の frontmatter を特別扱いする記述が無く、語に当たれば置換される（仮説） | 実機で確認する。必要なら `org:` の値を辞書の対象外にする設計を検討する |
| 冒頭の数行と frontmatter の ToDo がずれる | 同じ内容を二重に持った | frontmatter を正にして、冒頭の数行をそこから書く |
| 横断の ToDo を1件ずつ並べられない | Bases は1行が1ファイル（仮説） | frontmatter に件数と期日を持たせ、一覧は会議録単位で見る。ToDo 単位の一覧は別の形が要る |

## 4. 補足

### 4.1 【案件】の行き先は2つの記述がある

`para-operations`（2026-10-07）は Area の `docs/decisions.md` に直接書くとし、後の実装（2026-10-14）は `ai/docs/inbox.md` への転記になっている。現行がどちらかは未確認。この設計は、後者（`ai/docs/inbox.md`）を前提にしている。

### 4.2 経緯

- 最初の題材は、顧客を含む打合せの記録（会議録）。「AI 向けと私向けの2系統にしたい」は手段で、論点は「読者の違う1つの情報をどう管理するか」だった
- 分ける基準は「読む問いが違い、かつ中身も違うか」。同じ事実の表示違いは分けない（分けると同期がずれる）。手順書のように問い（順序・実行）が違うものは分ける

## 5. 要確認事項

- （済 2026-10-21）取り出し（`room pull`）と戻し（`restore` の Area 書き出し）は実装し、実機の通し試験で問題なし（`org:` の値の置換、部屋の AI の読み取り、人の変更を守る停止を含む。手順は `guides/howto/ai-room-setup-script.md` の 4.1・6.1）
- 【案件】の行き先（4.1）
- Area 側の保管場所と同期（Git か、PC ごとのローカルか）
- 統合の流れ（件ごとに溜める / 統合して育てる）をどうするか
- 型の用語（冒頭の数行＝人向け、本文＝AI 向け）が、理解ガイドの型（6 つの見出し）と食い違わないか
