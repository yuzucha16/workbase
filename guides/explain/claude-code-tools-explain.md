# Claude Code のツールが何をするかと、応答数・トークンとの関係

## 冒頭

会話に出てくる Read・Grep・Glob・Edit・Write・Bash・Agent が実際に何をするか、なぜ「どのツールを、何回、何応答で呼ぶか」がトークンの消費に効くかを、自分で説明できるようにする。前提: Claude Code を使い、月次の上限に向けて token-cap で削減を見直している。確認状況: 各ツールの役割は一般的な理解（Claude Code の標準ツール）。PC1 の呼び出し回数は 2026-11-06 の実測（確認: 2026-11-06、根拠: `topics/token-cap/records/2026-11-06-pc1-room-effect.md` の 8）。
近い既存ガイド: `claude-code-cost-session-size.md`（会話の大きさと費用）。

## ダイジェスト

- 状況: token-cap で、PC1 の room（作業用の隔離環境）の依頼のうち、応答 21 以上の長い 7 件がトークンの 42% を使っていた。調べると、その 7 件はすべて Edit・Write が 0 回で、Bash が 20〜32 回（応答の 87%）だった。
- 原因: ツールを 1 回呼ぶごとに応答が 1 つ増え、その応答は会話の履歴全体を入力として再送する。Bash を 1 つずつ直列に呼ぶと、応答数が増え、履歴も積み上がる。「Bash だけで読みも書きもする」作業で、読みの Bash（`head` `cat` `grep` `sed -n` `ls`）が書きの Bash を上回っていた。
- 解決（途中）: 新しい規則は足さず、`AGENTS.md` に「読みの Bash は 1 回のコマンドに連結する」を 1 行足した（2026-11-06）。効果は、次回の `requests_by_kind.py` の測定で見る。
- 今後の見通しは「補足」の末尾に書いた。

## 基礎知識

### 応答とツールの関係

- 応答 = モデルへの 1 回の呼び出し。モデルは「このツールをこの引数で実行して」と要求を返し、ツールはローカルで実行される（トークンを使わない）。結果を付けて、次の応答を呼ぶ。
- 呼び出しのたびに履歴の全部が入力になる。合計 = 各応答の入力の足し算。だから「ツール呼び出しの回数」は、そのまま「応答数」になり、費用の掛け算の片方になる（もう片方は会話の大きさ）。
- 並列呼び出し = 依存のない複数のツールを、1 つの応答にまとめて要求すること。10 個まとめても 1 応答として数える。直列 = 1 応答に 1 個ずつ、前の結果を見てから次を呼ぶこと。
- 並列にできるのは、結果が互いに要らないとき。例: 3 つのファイルを読む。できないのは、前の結果で次の中身が決まるとき。例: 検索して、見つかったファイルを開く。
- 出力の量（ツールの結果の文字数）は、以後のすべての応答の入力に乗り続ける。読んだ内容は消えない（会話を切るまで）。

### ツールの一覧

| ツール | 何をするか | 読み／書き | トークンの癖 |
|---|---|---|---|
| Read | ファイルを読む（行範囲 `offset` `limit` が指定できる。画像・PDF も読める） | 読み | 全文を読むと、その分が以後の全応答に乗る。必要な節だけ読むのが基本 |
| Grep | ファイルの中身を検索する（正規表現）。件数だけ・ファイル名だけ・内容つきの出力を選べる | 読み | 広い語で内容つきの出力を取ると大きい。先にファイル名か件数で見る |
| Glob | ファイル名のパターンで一覧を取る | 読み | 小さい |
| Edit | ファイルの一部分を、文字列の置換で書き換える。事前に Read 済みが必要 | 書き | 変更箇所だけを送るので小さい。成功したら読み直さない |
| Write | ファイル全体を書く（新規作成か、全体の置き換え） | 書き | 全体を送るので、大きいファイルの部分修正には向かない（Edit を使う） |
| Bash | シェルのコマンドを実行する（`ls` `cat` `grep` `sed` `python` `git` など何でも）。Windows の PC では PowerShell | 読みも書きも | 万能。専用ツールで足りる作業まで Bash で行いがち。結果が長いと大きい |
| Agent | 別のエージェント（サブエージェント）に作業を任せる。任せた先の読み・書きの内容は、元の会話に入らず、最後の報告だけが戻る | 両方 | 探索を任せると元の会話が膨らまない。ただし起動のたびに最初から読み直すので、小さい作業には割高 |

- Read・Grep・Glob と、Edit・Write は、専用の道具で、画面に何をしたかが分かりやすく出る。Bash は何でもできるが、1 つ見ても中身（読みか書きか）が分からない。
- 書きの Bash の例: `sed -i`、`>` `>>` のリダイレクト、`git commit`、`python` で書き出す。読みの Bash の例: `head` `cat` `grep` `ls` `sed -n`。

### 専用ツールと Bash の違い

専用ツール（Read・Write・Edit・Grep・Glob）はシェルコマンドではない。Claude Code 本体のプログラムが、ファイル操作の関数を直接呼ぶ。`cat` や `echo` を裏で呼んでいるのではない（一般的な理解。実装は未確認）。Bash は、シェルのプロセスを起動して、コマンド文字列を渡す。

| | 専用ツール | Bash（Windows は PowerShell） |
|---|---|---|
| 実行する主体 | 本体のプログラム | シェルのプロセス |
| 入力 | 構造化された引数（`file_path`、`old_string` など） | コマンド文字列 1 本 |
| OS による違い | なし。WSL でも Windows でも同じ引数なら同じ結果 | あり。WSL は bash、Windows は PowerShell で、コマンドも構文も違う |

専用ツールがある理由:

- Edit の安全装置: 事前に Read 済みであること、`old_string` が一意であることを本体が検査し、違えば書き換えずに失敗する。`sed -i` は置換の失敗が黙って通ることがある。
- Read の機能: 行範囲の指定、行番号の付与、画像・PDF の読み取り。`cat` には無い。
- 権限の制御: ツールの種類ごとに許可・拒否を設定できる。Bash は何でも実行できるので、制御が粗くなる。
- 引用符の問題を避ける: Write は内容をそのまま渡す。`echo` や here-string は、`$` や引用符のエスケープが事故のもとになる。
- 画面の表示: 読みか書きかが分かりやすい。Bash は 1 本のコマンドから読み書きを見分けにくい（PC1 の分析で手間がかかった理由）。

トークンの面では、「Bash か専用ツールか」より、直列に呼ぶ回数が効く。専用ツールに寄せる利点は、失敗しにくさと権限の制御で、トークンの節約は未確認。

### 自分で説明するときの一言

「ツールを 1 回呼ぶと応答が 1 つ増え、そのたびに会話の全部が再送される。だから費用は、呼ぶ回数と会話の大きさの掛け算。依存のない呼び出しは 1 応答にまとめ、読みは必要な分だけにする。」

## チェックリスト

| 症状 | 原因 | 対処 |
|---|---|---|
| 1 依頼の応答が 20 を超える | Bash の読みを 1 個ずつ直列に呼んでいる | 読みのコマンドを `;` で連結して 1 回で呼ぶ。独立なら並列にまとめる |

| 設定の問題ではないか（Edit・Write が使えない？） | PC1 は使える状態だった。許可の偏りも無かった（確認: 2026-11-06、根拠: PC1 の設定ファイルの permissions と会話記録の呼び出し数） | 設定は疑わなくてよい。使われないのはモデルの選択 |
| 探索で元の会話が膨らむ | 多くのファイルを自分で読んでいる | Agent に任せる案。効果は未測定（要確認事項） |

## 補足

### token-cap の経緯（時系列）

| 日付 | 出来事 |
|---|---|
| 10 月 | 職場の月次上限（月 2 億トークン）に向け、トークン削減の見直しを始めた。ある月の実測で、トークンの 91% がキャッシュ読みで、60k 超の応答が 90% を占めた |
| 10-27 | 切る目安を「作業の区切り、または 100k」にした |
| 10-29 | 全文読みの上位ファイル（規則書など）を縮小・分割した。応答数を減らす施策（出力の型、依存のない呼び出しの並列化）を決めた |
| 11-05 | PC2（Windows）の効果確認。ピーク 89k → 55〜65k。1 件のトークンは 574k → 323〜384k |
| 11-06 | PC1 の効果確認。ピーク 86k → 51〜58k だが、1 件のトークンは 436k → 371〜420k（−4〜15%）。応答数が 5.8 → 6.8〜7.8 に増え、会話を小さく保つ効果が一部打ち消された |
| 11-06 | 応答 21 以上の 7 件を調べ、Bash の直列が原因と分かった。`AGENTS.md` に 1 行足した |

### 背景と問題の整理

- 会話を小さく保つ施策（100k で切る）は、ピークを下げるが、再開のたびに土台を読み直すので、応答数が増えると効果が減る。「応答数 × 会話の大きさ」の積で見る。
- 応答数の分布は、中央値 5 で変わらず、21 以上の 6〜7 件（7.5%）がトークンの 42%。平均を下げるより、尾を切るほうが効く。
- 尾の正体は、Edit・Write でなく Bash が応答の 87%（PC1 の全期間でも Bash 89%、Edit 16・Write 13 回）。`cd … &&` で始まる呼び出しが約 170 回あった。Bash を 1 回に連結すれば、応答数が減る。
- 注意: 1 応答で大量に読むと逆効果。連結しても、結果が大きければ以後の全応答に乗る。

### 今後の見通し

1. 次回の `requests_by_kind.py` で、応答 21 以上の件数と、読みの Bash の連続の長さが減ったかを見る。減らなければ、連結の規則が守られていないか、読みが独立でない作業（検索 → 開く）が主だったと考える。
2. 効果が薄いときの次の手: (a) 専用ツール（Read・Grep）への誘導、(b) Agent に探索を任せる効果の実測。どちらも、結果を見てから決める。
3. 規則を増やしすぎない。AGENTS.md の行が増えるほど、読む量が全応答に乗る。PC1 に期日・確認項目も足さない（ee の決定 11-04）。
4. 切る目安を 60k に下げる再判断は、NA と OQ が全部閉じた後。
