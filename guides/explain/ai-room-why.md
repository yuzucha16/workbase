# AI 作業部屋: なぜこの仕組みを導入するのか（理解ガイド）

顧客データや社外秘のファイルを AI に見せないまま AI を使えるようにする「AI 作業部屋」について、なぜ必要になり、どの選択肢から、なぜこの形を選び、何を試して確かめたかを、自分で説明できるところまで理解するための文書。導入の手順は [[ai-room-setup]]。

> **状態: 草稿（未レビュー）。** 2026-10-18 に、実機の通しの結果と、旧トピック（`ai-workspace-boundary`）の設計ノートの内容を取り込んだ（ノートは削除。履歴は git）。ユーザーのレビューで外す。レビュー前の内容は、事実の確認と表現を見直す前提で読む。

- 前提: Windows 11 と WSL2 がある。AI は Claude Code が主（Obsidian と Zed から使う）。作業の置き場は PARA 構成の works（`areas/` `projects/` `archives/`）で、works のルートはリモートを持たないローカルの git 管理
- 確認状況: **実機で検証済み**（2026-10-12 に手作業で2巡、2026-10-14 にマスク・復元・共有知の送付・`stock` をダミーで、2026-10-18 に `init` から `reap` までの通し）。操作を自動化するスクリプト `room`（`workflow-kit/room/`）は、`init` `open` `mask` `start` `restore` `readme` `stock` `close` `reap` まで実装済み。実データでの確認と、いくつかの残りは 5 章にまとめる
- 勤務先名、顧客名、実際の Project 名などの固有情報は、この文書に書かない

## 1. 状況と解決（ダイジェスト）

**状況**

- AI は works のルートで起動するので、非公開側の `areas/` `projects/` `archives/` を全部読める。公開と非公開の境界は、GitHub に出す（workbase）かどうかの1本だけ
- 顧客データ・社外秘を AI に見せたくない。一方で、見せたくないファイルを works の外に置くと、ファイルが点在して作業効率が大きく落ちた
- 要望は次のとおり
  - 顧客データはマスクしたものを AI に渡す。マスク前の原本は、案件のフォルダに一緒に置きたい
  - AI の出力に顧客データは無い。ただし、その中間ファイルをもとに、顧客データを含む成果物を作る
  - Excel のままやり取りする（ピボットテーブルの作成を頼む。まれに VBA も頼む）
  - 手数を少なく、1パターンに揃える。作業記録が残り、再現でき、Project の成果を Area に戻せる

**原因**

1. 「全部見える状態で、見せたいものだけ隠す」（禁止リスト）方式は、隠し忘れると見える側に倒れる
2. Claude Code の許可設定（deny）は、AI のファイル操作と、名前を指定した読み取りは止める。しかし、AI が書いたスクリプトが中でファイルを開く場合や、`grep -r` のような名前を指定しない読み取りは止められない
3. Claude Code のサンドボックスは、Windows ネイティブでは効かない。Obsidian と Zed から起動すると Windows ネイティブになる

**解決**

- 「何も見えない状態で、渡したものだけ見える」（許可リスト）方式にする。Project の作業を、**WSL の専用ディストリビューション（部屋）の中**で行い、部屋には作業中の Project の `ai/` フォルダ**だけ**を渡す
- 部屋は C: ドライブをマウントせず、Windows のプログラムも起動できない。部屋の AI は、物理的に works の他の場所を見られない
- 原本と、マスクの対応表は、`ai/` の外（`_noai/`）に置く。部屋には渡らない

```
works（Windows）                                  AI 作業部屋（WSL のディストリビューション）
projects/<Project>/
  README.md                                       （部屋からは見えない。写しを ai/ctx/ に置く）
  _noai/raw/   原本 ─┐  マスク（人が実行）
  _noai/map/   対応表 ┘ ──────────────────────▶ ai/in/    マスク済みの入力
  ai/  ◀══ このフォルダだけをマウント ══════════▶ ai/work/  AI のスクリプト
                                                  ai/out/   AI の成果物（マスク済み）
  _noai/final/ 実データ入りの成果物 ◀── 復元（人が実行）── ai/out/
```

## 2. 理解のための基礎知識

### 禁止リストと許可リスト

| 方式 | 既定 | 忘れたとき | 例 |
|---|---|---|---|
| 禁止リスト | 全部見える。隠すものを列挙 | 見える側に倒れる（危険） | Claude Code の deny、`.gitignore`、`_noai/` を隠す案 |
| 許可リスト | 何も見えない。渡すものを列挙 | 見えない側に倒れる（安全） | 部屋にマウントした `ai/` だけを見せる |

- 許可リストは、AI の種類（Claude Code、Codex、Copilot）にも、AI が書くスクリプトにも依存しない。境界が AI のツールでなく、OS（ファイルシステム）にあるため

### なぜ許可設定（deny）だけでは足りないか

- Claude Code の `Read(<名前>/**)` の deny は、どの深さの同名フォルダにも効き、Edit / Write も止める。`cat` `head` のように名前を指定した読み取りも止める
- 止められないもの: `grep -r` のような名前を指定しない読み取り、AI が書いた Python が中で開くファイル（xlsx を `openpyxl` で開くなど。**ここが最大の抜け道**）。`.claudeignore` は効かない
- Claude Code のサンドボックスは macOS・Linux・WSL2 だけ。Windows ネイティブでは効かない。WSL の中なら使える
- Zed の Claude Agent は別プロセスで動き、Claude Code の設定を読むかは文書に記述が無い
- 以上は公式文書の記述（2026-10 時点）。部屋の方式では、これらに頼らない

### 部屋の作り方（WSL の機能の使い方）

| 設定・操作 | 何をするか | 部屋での役割 |
|---|---|---|
| ディストリビューションを専用に作る | 他の WSL 環境と、ホームも設定も別になる | 部屋ごとの隔離の単位 |
| `/etc/wsl.conf` の `[automount] enabled=false` | C: などを `/mnt` に自動でマウントしない | works が存在しない |
| `/etc/wsl.conf` の `[interop] enabled=false` | WSL から Windows のプログラムを起動しない | `cmd.exe` や `powershell.exe` 経由の抜け道が無い |
| drvfs で、フォルダ単位のマウント | Windows の特定のフォルダだけを、Linux の特定の場所に出す | `ai/` だけを渡す |
| 一般ユーザーで AI を動かす | mount や sudo ができない | root は C: 全体をマウントできてしまうため |

- WSL の設定は、ディストリビューションごと。Windows からは `\\wsl.localhost\<ディストリビューション名>\` で、部屋の中のファイルにも届く
- 注意: 部屋の中の root は、`mount -t drvfs C: ...` で C: 全体をマウントできる（実機で確認）。AI は必ず一般ユーザーで動かす

### 部屋の粒度（Area ごとのディストロ、Project ごとのマウント）

- ディストリビューションは **Area ごと**、マウントは **Project ごと**（作業中の Project の `ai/` だけを、`/mnt/room/<Project>` に出す）
- 同じ Area の中では、会話履歴などが部屋の中で共有される。そこで **「Area は、顧客・機密度の境界と一致させる」**（顧客の違う Project は、別の Area に置く）と決めた
- 顧客をまたぐ「横展開」は、汎用化した成果だけを、人が確認して共有側（workbase）へ回す経路で行う。顧客Xの成果物が、顧客Yの部屋から見えることはない

境界を守るための歯止め:

| 歯止め | 内容 |
|---|---|
| `area:` の一致 | Project の `README.md` の `area` と、ディストロ名（`room-<Area>`）が一致しないと、マウントしない |
| `boundary:` の印 | Area の `README.md` に、顧客・機密度の印を持たせる |
| 来歴チェック | `ai/in/` の各ファイルの由来（Area と Project）を記録し、由来の違うファイルがあれば止める |
| 記録 | 実行のたびに、日時・Area・Project・マウント先・チェック結果を `ai/records/` に追記する |
| 同じ Project を二重に開かない | 同じ Project の `start` は、自分のマウントが残っていれば止まる。同じ部屋（同じ Area）の別の Project は、並行して開いてよい（2026-10-21。下記） |

- 並行して開くとき、部屋の AI は `/mnt/room/` の下で、ほかの Project の `ai/` を読める。分離の単位は **Area（`boundary:`）**で、Project ではない。同じ Area は同じ境界という前提なので、境界の違うデータを同じ Area に置かない。運用の約束: `~/shared` は最新に揃え、`start` は同じタイミングで行い、後から Project を足すときは動いているセッションを止める

- 限界: 人が Windows 側で、Area をまたいでファイルをコピーすること自体は止められない（来歴チェックで検出して記録するところまで）

#### Project をどの Area に置くか（迷ったとき）

| 問い | 答え | 置き場 |
|---|---|---|
| 顧客（または機密度）が既存の Area と同じか | 同じ | その Area |
| 違う顧客のデータや資料を、この Project に入れるか | 入れる | 別の Area（顧客ごとに Area を切る） |
| 顧客を持たない社内の作業か | はい | 社内用の Area（`boundary: internal`） |
| 顧客をまたぐ知見を残したいか | はい | 汎用化して【汎用】の経路（`room stock`）で workbase へ。生データや顧客名は渡さない |

Area を増やすと、部屋（ディストロ）とログインも増える。迷ったら、顧客の境界で切る。同じ顧客の Project 同士は同じ Area に置く（会話履歴などが共有されても境界を越えない）。

### マスクと復元

- **データの扱いは Project ごとに3つの型から選ぶ**（2026-10-19。`data:`）。`none` はマスクも復元もしない（機密なし。`dev` はこれだけ）、`mask` はマスクだけで復元しない（顧客情報を含む資料の要約・抽出。読むのは本人だけ）、`restore` はマスクして、終了時に復元する。「マスクしない作業」「マスクして戻さない作業」があるため、`type` とは別の軸にした。`_noai/` に人だけの仮置き `user/` を足した（予約名。AI にも `room` にも触らせない）。手順は [[ai-room-mask-summary]]、仕様は `workflow-kit/room/README.md` の「データの扱い」
- マスクと復元は、**AI にやらせない**（原本と対応表を読むことになるため）。人が実行するスクリプトで行う
- プレースホルダーは、AI が書き換えにくく、検索しやすい形にする（例: `⟦CUST_001⟧`）。ただし、Excel の定義名には `⟦⟧` が使えない（実機で確認）ので、定義名は ASCII（`NAME_001`）にする。シート名は `⟦⟧` も使えるが、ASCII に揃える
- 数値は、既定ではマスクしない（集計の作業で要るため）。語は対応表で、列単位でマスクするものは列指定で、決める
- xlsx は、セルの値以外にも名前が残る: シート名、コメント、ヘッダー・フッター、隠しシート、定義名、ピボットのキャッシュ、ファイルのプロパティ（作成者・会社名）、印刷設定。**xlsx の中の XML 全体に文字列置換をかける**（zip レベル）と、これらを一括で置換でき、ピボットも壊れない（実機で確認）
- 置換の後に、対応表の語が残っていないかを全部品で点検し、残っていれば止める
- **一致は広く拾う**（部分一致、大小文字と全半角を区別しない）。漏れ（機密が AI に渡る）のほうが、余分なマスクより重い失敗で、余分なマスクは復元で正式名に戻るため
- **全ての語を、長い語を優先して1回の走査でまとめて置換する**。順番に置換すると、置換後のプレースホルダーの中の文字（`CUST` など）を、別の語が拾う事故が起きる
- 点検では、対応表に無い固有名詞の候補（法人格、敬称、メールアドレス、電話番号、URL、郵便番号の形）も一覧にする。止めずに警告にとどめ、人が見て、必要なら指定に足す
- 番号は一度振ったら変えない（同じ語は何回マスクしても同じ番号）。対応表は追記専用
- 復元は既知の形式（csv、md、txt、bas、json、html、xlsx）だけ。それ以外が `ai/out/` にあれば、復元せずに止める。戻らなかったプレースホルダーが1件でもあれば、成果物を確定せずに止める
- 人が `_noai/final/` を仕上げた後に、次の復元が無条件に上書きしないよう、前回の書き出しと違えば止める（`--force` で上書き）
- 限界: 往復で表記ゆれは正規化される（元の表記は戻らない）。対応表にも列指定にも無い語（人名など）は、マスクされずに残る

### AI と人（スクリプト）の分担

- **判断は AI、副作用はスクリプト**。マウント、マスク、復元、移動、コミットは、`room`（人が Windows の端末で実行）が行う。聞き取り、確認、振り分け、下書きは、部屋の AI が行い、結果を決まったファイルに書く。AI には `room` を実行させない（原本と対応表を読むため）
- 2つの層の接点は、**ファイルの受け渡しだけ**にする

| 向き | 受け渡し |
|---|---|
| スクリプト → AI | `ai/ctx/`（README と Area の README の写し）、`ai/in/`（マスク済みの入力）、`~/shared`（共有知の写し）、部屋の `AGENTS.md` |
| AI → スクリプト | `ai/out/close.md`（`close` の判断）、`ai/out/readme-draft.md`（README の下書き）、`ai/out/stock/`（【汎用】の下書き）、`ai/docs/decisions.md` の【案件】ラベル（Area への転記） |

- 名前の衝突を避ける。`open` `start` `close` は、`room` のコマンドと、AI が手順書を読んで実行する合言葉の両方にある。会話と文書では、`room` のコマンドは必ず `room` を前置し、AI の合言葉は日本語の別名（「作業を始めて」「終了処理して」）で呼ぶ
- 正本は、`room` が `workflow-kit/room/README.md`、合言葉が `workflow-kit/hooks.md`。部屋の中での読み替え（`docs/` → `ai/docs/`、分担）は `workflow-kit/room-context.md`

### 共有知（workbase）との行き来

部屋は `ai/` しか見えない閉じた世界なので、workbase とは意図して行き来の道を作る。

| 方向 | 方式 | 理由 |
|---|---|---|
| 入る（部屋の AI が読む） | 起動のたびに、`room` が workbase の写しを部屋の `~/shared` に**読み取り専用**で送る。途中では更新しない。送った版のコミットを manifest に記録する | 分離する前と同じ環境になり、再現できる。workbase は公開されうる前提で書くので、部屋に入れてよい。`resources/` を2つ目のマウントにする案は部品が増え、部屋の中で clone する案は認証情報が要るので避けた |
| 出る（部屋の知見を共有知へ） | 下書き（`ai/out/stock/`）だけ。人が確認して workbase の `exmem/inbox/` へ運ぶ | 公開されうる共有知へ入るので、勤務先固有の内容が混ざっていないかを人が見る門を必ず通す |

- 下書きには、**基準コミット**（写しの workbase のコミット）と**観測日**を持たせる。git の rebase にならい、変更に基準を持たせて、後から3点（基準・下書き・最新）で比べるため
- 「いつ・誰が」は、検出と解決を分ける。検出（機械的）は、回収のときに `room` が、統合先が基準以降に変わっていれば「基準が古い」の印を付ける。解決（意味の判断）は、`integrate` のときに、workbase 側の AI と人が3点で行う。部屋の AI は rebase しない（最新の版が見えないため）
- 並べる順序は、到着順でなく観測日

### Excel の作業の分け方

- Excel のまま渡す（csv に平らにしない）。ピボットテーブルの作成と、まれに VBA を頼むため
- 部屋から Excel は起動しない（`interop` を有効にすると、Excel 経由で C: 全体に届く）。AI は、データの xlsx と、ピボットを作る VBA を書き、**人が Windows の Excel で、中身を見てから実行する**。マクロの安全面でも都合がよい
- 検証を2層に分ける。部屋の中で完結する検証は AI、実環境が要る検証は人が行い、結果を AI に渡すときは、人が実データの語を伏せる
- ピボットのキャッシュには、マスクした値が残る。復元の後に、Excel で「すべて更新」をする（人）
- 成果物の置き場: `type: dev` の Project は、`ai/out/<成果物名>/` に一式（README、`src/`、`docs/`、`tests/`、`tools/`）を置く。1 Project = 1 成果物。自己完結で配布の単位になり、`restore`（`ai/out/` の置き換え）がそのまま掛かる。理由と固有の知識は `exmem/lessons/ai-tool-deliverable-structure.md`
- Project をまたぐ約束は、Area の README に書き、`room start` が `ai/ctx/area-README.md` に読み取り専用で写す。Area は境界の単位なので、写るのは同じ Area の Project 名だけ。写しは追跡せず、終了のたびに消える

### ライフサイクルと記録

プロセスのたとえ（次の表）の補足:

- **1セッション = `room start` 1回**。シェルが子を fork して exec し、終わるのを wait するのと同じ形で、回収の手順を忘れない
- 回収が失敗したら（戻らなかったプレースホルダーなど）、`archives/` に移さず、zombie のまま残して再実行できるようにする
- **Area への同期は郵便受け方式**。回収のとき、【案件】の項目を Area の `ai/docs/inbox.md` に追記し、Area の AI が次の `start` で取り込む。Area の `decisions.md` に直接書かないのは、Area の部屋が同時に開いていると書き込みがぶつかるため。毎セッション少しずつ進み、`close` に集中しない
- 【汎用】のナレッジ化は、ユーザーが言ったときだけ。部屋の AI は下書きまで

| 記録 | 中身 | 置き場 |
|---|---|---|
| 作業ログ | `log.md`、`decisions.md`（AI が `wrap` で書く） | `ai/docs/` |
| 変更の履歴 | `room start` の回収ごとのコミット | Vault の git |
| manifest | 入力のハッシュ、マスクの規則の版、スクリプトと kit の版（対応表の中身は入れない） | `ai/records/` |
| スクリプト | AI が書いた集計や VBA | `ai/work/` |
| セッションの記録 | 会話の履歴（マスク済みの内容だけ） | reap のときに `ai/records/sessions/` へ写す設計（今は写さずに消す。未実装） |

- 再現の範囲: マスク済みの段階までは常に再現できる（入力、スクリプト、記録が `ai/` にある）。実データ入りの成果物まで再現するには、`_noai/raw/` と `_noai/map/` が残っている必要がある。そこで **`_noai/` は archives に移した後も当面残す**（決定。Vault は private 領域なので、対応表の漏えいは AI 分離とは別の論点として扱う）

### プロセスのたとえ

部屋のライフサイクルは、Unix のプロセスに似ている。

| たとえ | 部屋での意味 | コマンド |
|---|---|---|
| fork | Project の `ai/` をマスクして部屋に出す | `room start` の前半 |
| exec | 部屋で AI を起動する | `room start` の中盤 |
| wait | AI が終わったら回収する（復元、Area への同期、コミット） | `room start` の後半 |
| exit → zombie | Project を閉じる。部屋の会話履歴だけが、やり直しの余地として残る | `room close` |
| reap | 期限（既定14日）の後に、履歴を記録に写して消す | `room close` / `room reap` |

### 自分で説明するときの一言

> AI に見せたくないものは、設定で隠すのではなく、**そもそも渡さない**。Project ごとに、Windows が見えない部屋（WSL）を作り、作業中の `ai/` フォルダだけを部屋に渡す。原本と対応表は部屋の外に置き、マスクと復元は人が行う。

| 部屋でも `mount -t drvfs C: ...` で C: が見える | root で実行している（root は C: をマウントできる） | AI は一般ユーザーで動かす。既定ユーザーを設定する |

| `mount ... -o ...` が「オプションを解釈できない」で失敗する | `-o` をデバイス名の後ろに書いた | `mount -t drvfs -o <オプション> <デバイス> <マウント点>` の順 |
| `rg <pattern>` が、何も検索しない | 標準入力が読める状態で、パスを省略すると標準入力を検索する | `rg <pattern> .` と、パスを書く |
| Zed で開いたら、works 全体が見える | ローカルのフォルダを開いた（Agent も Windows 側で動く） | 部屋は、Zed の **WSL リモート**で開く |
| Excel で開いている xlsx を、部屋から上書きできない | Excel の共有ロック | 読み取りと別名での保存はできる。Excel を閉じてから上書きする |
| `ai/out/` に `~$...xlsx` ができた | Excel のオーナーファイル（Windows のユーザー名が入る） | `.gitignore` に `~$*` を足し、回収では無視する |
| 数千ファイルを扱う処理が遅い | マウントは、小さいファイルが多いと50倍以上遅い | 大量の一時ファイルは、部屋のローカル領域（`~/tmp/`）に置く |
| 部屋へのスクリプトで、代入した変数（`$d`）が空になる | `wsl.exe` が `sh -c` の引数を、部屋の側の外側のシェルでもう一度解釈する | 変数を使わず `$HOME/...` を直接書く。複数行は標準入力（`sh -s`）で渡す |
| 日本語の Windows で、`python -I` から `⟦` を出すと `UnicodeEncodeError` | `-I` は `PYTHONIOENCODING` を無視し、標準出力が cp932 のまま | `-X utf8` を付ける |
| 部屋を作るたびに、Windows Terminal の設定に差分が出る | WSL の動的プロファイルが、部屋ごとに自動で書き足される | 動的プロファイルを無効にして、普段使いの1つだけ固定する。部屋へは専用の関数で入る |
| `--no-launch` の待ちで、Enter が戻らない | 待ちのプロセスがコンソールを共有していた | 修正済み（コンソールから切り離した） |
| `reap` の確認で、削除に成功したのに「消せなかった」と出る | 確認の `ls` の終了コードを失敗と判定していた | 修正済み |
| AI に境界を破るよう頼んだが、断られた | モデルの判断（保証ではない） | 境界の確認は、一般ユーザーでの直接の探索（`find /`、`mount`、`sudo`、`../`）で行う |

## 4. 補足

### 4.1 検討した選択肢と、選ばなかった理由

最初の案（A）から、前提が増えるたびに見直し、最終的に案 Y にした。

| 案 | 内容 | 良い点 | 選ばなかった理由 |
|---|---|---|---|
| A | Project の中に `_noai/` を作り、deny、git ignore、エディタの除外で隠す（禁止リスト） | 点在しない。設定が軽い | スクリプトと他の AI ツールには効かない。Windows ネイティブでは、サンドボックスも効かない。忘れると見える側に倒れる |
| B | works の外に、同じ構成の木を作る | どの AI ツールにも効く | 点在が戻る（作業効率の要望に反する） |
| C | 原本をパスワード付きで保存（Office のパスワード、7z など） | スクリプトからも、どの AI からも読めない | 開くたびにパスワードが要る。特に機密の高い原本だけの補助策 |
| D | AI の作業ディレクトリを `work/` に絞る | 設定が軽い | Obsidian と Zed は、works のルートで開くので、効かない場面が多い |
| **Y** | **Project ごとの「AI 作業部屋」。WSL に作り、渡したものだけを見せる（許可リスト）** | **物理的な分離。AI の種類に依存しない。マスクが手順に組み込まれる** | **採用** |

部屋の強さ（3段階）:

| 段階 | 内容 | 判断 |
|---|---|---|
| L1 | いつもの WSL で、Claude Code のサンドボックスと deny で `/mnt/c` を塞ぐ | 設定ミスで抜けうる |
| **L2** | **専用ディストリビューションで、C: をマウントしない、interop を切る** | **最初から採用**。works が存在しないので、設定ミスや exe 経由の抜け道が無い |
| L3 | L2 に加えて、ネットワークを必要なサイトだけに絞る | 任意の追加策（未検証） |

粒度の選択:

| 案 | 内容 | 判断 |
|---|---|---|
| Project ごとにディストロ | 隔離が強い。ログインと導入が、Project の数だけ要る | 選ばない |
| **Area ごとにディストロ、Project ごとにマウント** | **ライフサイクルが分かりやすい。ログインと導入は Area の数だけ** | **採用**。Area を顧客・機密度の境界と一致させる運用で補う |
