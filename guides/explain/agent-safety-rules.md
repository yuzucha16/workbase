# エージェントの安全規則: 導入の経緯、違反までの流れ、対策（理解ガイド）

AI エージェント（Claude Code など）に git のコミットと push を任せるときの「安全規則」について、なぜ作ったか、どう育ち、どこで破られ、どう直したかを、自分で説明できるところまで理解するための文書。

> **状態: 草稿（未レビュー）。** 事実は 2026-10-14 時点の会話履歴とコミットから起こした。違反の「なぜ」は推測を含む（4 章に明記）。

- 前提: Vault のトップ（`works`。PC ローカルの非公開リポジトリ）と、共有リポジトリ `workbase`（`resources/`）の 2 つがあり、エージェントがコミットする
- 範囲: 規則の導入から 2026-10-15 の点検まで。個々の手順書の中身は `workflow-kit/docs-rules.md` が正本
- 固有情報（社名、ユーザー名など）は書かない

## 2. 理解のための基礎知識

### 2.1 なぜ「規則」が要るのか

エージェントは速く、疲れず、一度に多くのコマンドを打つ。その分、1 回の判断ミスが大きく広がる。特に取り返しがつきにくいものを規則で縛る。

| 取り返しにくいこと | 例 | 規則 |
|---|---|---|
| 機密が公開される | 公開リポジトリへの push | 公開範囲を毎回確認する。許可リスト外へは push しない |
| 他人の変更を巻き込む | ユーザーや並行セッションの未コミットの変更を、自分のコミットに入れる | 自分が変えたファイルだけをパス指定で `git add` する |
| 履歴が壊れる | `--force`、`--amend`、`reset --hard`、`rebase` | 使わない |
| 検査が飛ばされる | `--no-verify` | 使わない |
| 決定の取り違え | AI の提案を、決まったことのように書く | 決定として書くのは、ユーザーが明示または承認したものだけ |

### 2.2 「規則」の置き場所と読まれ方

- 作業側 `AGENTS.md` の先頭の「安全規則」: エージェントが毎回読む。短く、縮小・整理の対象外。変えるときはユーザーの承認が要る
- `docs-rules.md`（手順書）: コミット・push・`docs/` 更新の前に読む。詳しい手順と根拠がある。開始時には読まない（2026-10-08〜）

読み込みを減らした（開始時の読み込みを約 8 万字から約 6 千字へ）代わりに、「必要な場面で読み直す」ことが前提になった。ここが弱点になりうるので、2026-10-15 に点検した。

### 2.3 `git add` の落とし穴

| コマンド | 何が起きるか |
|---|---|
| `git add .` / `git add -A`（パスなし） | 作業ツリー全体を入れる。他人の変更や機密も入る |
| `git add <パス>` | そのパスだけ。ただし、そのファイルに他人の未コミットの編集があれば、それも入る |
| `git add -A <パス>` | そのパスの中だけ。**削除と rename も入る** |
| `git commit -- <パス>` | index でなく作業ツリーの現在の内容をコミットする。ステージで分けた意味がなくなる |

自分で説明するときの一言: **危ないのは `-A` という文字でなく、範囲が決まらないこと。** パスで範囲を決めていれば、`-A` は削除を入れるための普通の道具。

## 4. 違反の中身と「なぜ起きたか」

### 4.1 何が起きたか

2026-10-12 の `close`（Project を閉じて `archives/` へ移す作業）で、エージェントは次のことをした。

1. 派生ファイルを削除した
2. `git add -A projects/<名前> areas/<名前> .gitignore` で、削除と rename をまとめてステージした
3. `git status --short` だけを見て、`git diff --cached` なしでコミットした
4. この間、`docs-rules.md` は読んでいなかった（`close-hook.md` と `wrap-hook.md` は読んでいた）

実害はなかった。`-A` はパス指定つきで、`git status` でも範囲を確認していたため。

### 4.2 なぜ起きたか（推測。本人の意図は履歴から確定できない）

- 安全規則の文言は「`git add -A` / `git add .` は使わない」で、理由とパス指定の例外が書かれていなかった。実際には、削除や rename を含む Project の移動では、パス指定つきの `-A` が自然な道具だった
- 規則が「毎回読む短い先頭」と「必要なときに読む手順書」に分かれ、このスレッドは手順書を読まずに進んだ。読む場面（コミット前）の引き金が弱かった
- 同じスレッドで、`resources`（`workbase`）にも `git diff --cached` なしのコミットが約 9 件あった。`close` の手順書の側に「コミット前に何を確認するか」が書かれていなかった可能性がある（未確認）

## 5. 対策

| 対策 | 内容 | 状態 |
|---|---|---|
| 禁止の範囲を、実態に合わせて狭める | 「パスなしの `git add -A` / `git add .`」を禁止にする。`git add -A <パス>` は、パスが自分の作業の範囲内ならよい（削除・rename のステージに必要） | ユーザー承認済み（2026-10-15）。作業側 `AGENTS.md` と `docs-rules.md` に反映 |
| 理由を書く | 禁止の理由は「範囲が決まらず、他人の変更を巻き込むから」 | 上の反映に含める |
| 読む場面を強める | 開始時の読み込み廃止は続ける。そのうえで、安全規則に「コミット・push の前に、そのセッションで未読なら `docs-rules.md` の「コミットと push」を読む。`close` `wrap` などのフック経由でも、`resources/` や dotfiles でも同じ。コミット前は `git diff --cached --stat`」と明記した | ユーザー決定（2026-10-15）。作業側 `AGENTS.md` に反映 |
| 機械的な検査 | それでも抜けるかは、次の点検で見る。安全の検査スクリプト（pre-push など）は 11-08 の判定で扱う | 未決 |

## 6. 要確認事項

- 4.1 の `close` で、`docs-rules.md` を読まなかった理由（手順書が呼ぶ指示になかったのか、読み飛ばしたのか）
- `resources`・dotfiles のコミットにも、`docs-rules.md` の「コミットと push」を適用する範囲（今は暗黙）
- この点検の方法（履歴の機械走査）は、スレッド単位の粗い判定。圧縮や再開をまたいだ読み込みは見落としうる

## 7. 自分で説明するときの一言

- 安全規則は、取り返しがつきにくいこと（公開、他人の変更の巻き込み、履歴の破壊）を先に縛るためにある
- 規則を短くした代わりに、「読む場面」が弱点になった。その点検が 10-15 で、見つかった違反は 1 件だった
- 直したのは、規則を増やすことでなく、実態に合わせて範囲と理由を書くこと
