# guides: 手順書・理解ガイド・クイックリファレンス

このディレクトリは、ユーザーが手順や仕組みを思い出すための文書を置く(旧 `cheatsheets/`、2026-10-10 に改名)。
文書の種類は、読む人の最初の問いで決める。種類ごとの型は `exmem/lessons/reference-doc-types.md`。
Claudeは、以下のルールに従って作業する。以下は主に `howto/` の手順書のルール。

入口は `guides-index.md`(やりたいこと・場面から引く索引)。文書を足したら・消したら、索引も同じコミットで直す(更新の規則は索引の末尾)。

## ディレクトリ構成

| ディレクトリ | 種類 | 読む人の問い | 例 |
|---|---|---|---|
| `howto/` | 手順書 | どの順で何をやるんだっけ | `win11.md`、`debian-family.md`、`fonts-setup.md`。1ファイル=1系統 |
| `explain/` | 理解ガイド | なぜそうなる? どう動いている? | `ssl-inspection.md` |
| `quickref/` | クイックリファレンス | あのコマンドは何だっけ | `apt.md`、`git.md`。`やりたいこと | コマンド | 注意` の表 |

- frontmatter に `type`(`howto` / `explain` / `quickref`)、`title`、`tags` を付ける
- `guides-index.md` だけは `type: index`(どの種類のディレクトリにも置かない)
- ファイル名は、リポジトリ内で一意にする(`exmem/lessons/` と重ならない名前にする。例: `fonts-setup.md`)

## 手順書(howto/)の作り方

### 範囲と正

- 手順書は、**ゴール(完了の目安)を先に決めてから**書く。範囲は「準備」から「ゴール」まで。範囲外は書かない
- 自動化できる作業は、dotfiles(`$HOME\works\repos\github.com\yuzucha16\dotfiles`)のスクリプトが**正**。手順書は、スクリプトの前後(手動でしかできない作業)と、順序・注意点を書く
- スクリプトの中身(パッケージ一覧など)を手順書に写さない。重複は、片方が古くなる原因になる。スクリプトやマニフェストを指すだけにする
- 手順書を書いて、dotfiles と食い違いが見つかったら、手順書側で直さず、**課題として報告する**(付録に書く)。dotfiles は、承認を得てから変更する

### ファイルの分け方

- 分け方は**パッケージ系統**で決める(Windows、apt 系など)。ディストロ単位では分けない
- 同じ系統のディストロ差分は、**節の末尾の差分表**に書く。本文に `[MX]` のようなタグを散らさない
- 差分が全体の3割を超えたら、ファイルを分ける
- 差分がないことも書く(「全ディストロ共通」)

### 構成

1. frontmatter(`title`、`type: howto`、`tags: [howto, env, <os>]`)
2. 冒頭の説明(範囲とゴール、スクリプトとの関係)
3. **対応バージョン表**(次節)
4. **全体の流れ**の表(章、区分=手動/スクリプト、完了の目安)
5. 各章
6. 任意設定(やらなくてもゴールに届くもの)
7. 付録: dotfiles 側の課題

### 各章の書式

- 見出しは `## N. 名前`。ゴールまでの順に並べる
- 手動の作業は、番号付きの手順にする。コマンドはコードブロックにする
- スクリプトの作業は、`スクリプト名 / 内容 / 注意` の表にする
- **よく忘れる点を、独立した行や箇条書きで書く**(EFI フラグ、再起動のタイミング、USB を抜く、新しいターミナルを開く、など)
- 章の終わりに完了の目安を書く。人間が実際に見て確かめられる形にする(コマンドの出力、画面)
- 長い説明より、**判断の分かれ目**(いつ・どちらを選ぶか)を表にする

### バージョン依存の情報

- バージョン番号、コードネーム、ISO の入手元、廃止された手順などは、**冒頭の対応バージョン表にだけ**書く。本文には書かない
- 表には「手順の確認日」を入れる。新しい版が出たら、表の更新と手順の再確認を行う
- 版によって使える・使えない方法は、**新しい順に並べ、状態を明記する**(推奨 / 使えない / 要確認)

### 事実の扱い

- 確認していない仕様は断定せず、**「要確認」**と明記する
- 変わりやすい情報(OS のビルド、廃止された回避策、ISO の URL)は、書く前に Web で調べて、参照元をリンクで残す
- 実機で試していないことは、手順書の冒頭や該当箇所で分かるようにする

### 書いてはいけないもの

- 個人情報: メールアドレス、社員番号、アカウント名、社内ホスト名・VPN などの組織情報
- 秘密情報: パスワード、鍵、トークン
- PC 固有の値(ユーザー名を含むパス)。`%USERPROFILE%`、`$HOME`、`<name>` のようなプレースホルダーにする
- git のユーザー名・メールは、手順書に書かず、`~/.gitconfig_local` に置く、と書く

### 文体

- 日本語。簡潔に書く。体言止めと箇条書きを使う
- コマンド・パス・キー名はバッククォートで囲む
- 画面上のボタン名・メニュー名は、画面の表記のまま書く
- 「やってはいけないこと」は、理由を一緒に書く

## 新しい手順書を作る流れ

1. 人間から「対象(OS・ディストロ)」「ゴール」「前提(ネット有無、デュアルブートなど)」を受け取る。不足は、答えないと書けない点だけ質問する
2. 既存の手順書と、dotfiles の `scripts/`・`manifests/`・README を読む。同じ系統の手順書があれば、**新しいファイルを作る前に、差分表に列を足せないか**を検討する
3. 構成案(章立てと、スクリプトとの対応)を示し、合意を得る
4. 事実を調べる(バージョン、廃止された手順)。参照元を残す
5. 書く。完了後、dotfiles との食い違いを付録にまとめて報告する
6. 古い手順書を置き換えるときは、旧ファイルの内容を**スコープの参考にだけ**使い、削除する(履歴から復元できる)

## コマンド集(クイックリファレンス)の追加

- 書式は `quickref/apt.md` に合わせる(場面ごとの節に、`やりたいこと | コマンド | 注意` の表)。文書の種類(手順書・理解ガイド・クイックリファレンス)の分け方と型は `exmem/lessons/reference-doc-types.md`
- 注意が無い表は `やりたいこと | コマンド` の2列でよい。複数行のコマンドは1つのセルに `<br>` でつなぐ
- `git.md` `docker.md` `shell.md` は表の形に書き直した(2026-10-10。説明は元の英語のまま)。`markdown.md`(記法の見本)と `ssh.md`(メモ)は、コマンドの表にならないので書き直していない
- 手順書(`howto/`)は、手順の順序があるもの。クイックリファレンスは、順序のないリファレンス。説明が目的なら理解ガイド(`explain/`)。迷ったらこの基準で分ける

## Git

- コミットメッセージは `[対象] 内容`(例: `[guides] add win11 setup`)
- 手順書の変更を、dotfiles の変更と同じ作業でするときは、コミットはリポジトリごとに分ける
