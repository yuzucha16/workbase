# wrap フック（別名「終了処理して」）

呼び出し名は wrap（セッションの終了）。別名は「終了処理して」。呼び出し表の正本は `hooks.md`。以下の「終了処理して」は、wrap と読み替える。

作業の終わりに行う処理を、順序を固定して1つにまとめたフック。ユーザーが「終了処理して」と言ったときだけ実行する（自発的には実行しない）。ソース側（作業ディレクトリ）の終了処理で、exmem 側の統合（`integrate-hook.md`）とは独立している。

目的は、次のセッション（別の端末やクラウドを含む）が、言い直しなしに再開できること。そのため、手順は 3 段階（現在状態の更新、昇格の案、コミットと push）と報告に絞ってある（2026-10-08 に、9 段階から縮めた）。各手順の中身は、既存の正本（`docs-rules.md`）を参照し、ここに複製しない。

## 場所と書き込みの制約

- 書き込み先は、`docs/`（`docs-rules.md`）と、作業ディレクトリのコミットだけ。`exmem/knowledge/` などは触らない（統合は `integrate-hook.md`）。`exmem/inbox/` のメモを作るのは `stock-hook.md`（このフックは作らない）。
- push は、呼び出し元の `AGENTS.md` の許可リストにあるリポジトリだけ、エージェントが行う（`docs-rules.md` の「push」）。許可リストに無いリポジトリは、push しない（ユーザーが行う）。クラウドのセッションからも、許可リストのリポジトリには push してよい（`docs-rules.md` の「使い捨ての環境での緩和」）。
- 手順の途中で承認が要るもの（既存ファイルの差分、リスクや制約が生まれる変更）は、`docs-rules.md` に従って、先にユーザーへ確認する。

## 手順

1. **対象を特定する。** 既定は、この作業で変更したリポジトリの `docs/`。複数のリポジトリにまたがるときは、すべてを対象にする。Project・Area が自分の `docs/` を持つとき（`projects/` `areas/` `archives/` 配下）は、それも別の対象に数える。リポジトリの外だけを変えたとき、または変更したリポジトリに `docs/` が無いときは、親のワークスペースの `docs/`、それも無ければ、Claude Code を開いた作業ディレクトリの `docs/` を対象にする（別のリポジトリなので、そのリポジトリでコミットする）。exmem だけで進めた作業は、`exmem/contexts/<名>/context.md` の `Current State` と `Next Actions` を更新する。どれも無ければ、この手順を省略して、報告に書く。
2. **現在状態を更新する。** `docs/log.md` を、次のセッションが読むだけで再開できる現在状態に**上書き**する（Next Actions、Open Questions）。経緯を残す場所が、呼び出し元の `AGENTS.md` にあれば、そこへ追記する。`decisions.md` は、ユーザーが明示または承認した決定があったときだけ書く（`docs-rules.md`）。呼び出し元の `AGENTS.md` が定める追加の手順（指標の記録など）は、続けて行う。
3. **昇格の案を出す。** このセッションで、ユーザーが同じことを言い直した（`again`）、または新しい恒久的な前提が出たなら、`AGENTS.md` か知識への昇格の案を、1行で出す（承認制）。まとまった知識化は、ユーザーが「ナレッジ化して」と言ったときに `stock-hook.md` で行う。
4. **コミットする。** `docs-rules.md` の「コミットと push」に従う（パス指定、ステージの行数の確認、agent の身元とトレーラー）。**コミットの後、そのリポジトリが許可リストにあれば push する**（`docs-rules.md` の「push」の条件を、毎回確認する。1つでも満たさなければ push せず、理由を報告する）。
5. **報告する**（下の「報告の型」）。

## 報告の型

1. **更新した `docs/`**: パスと、変更の要点（2〜3行）。
2. **昇格の案**: あれば1行。`decisions.md` で `→` の無い【汎用】項目の件数。
3. **コミット**: ハッシュと内容、含めなかったファイル。push の結果。許可リストに無いリポジトリは、push のコマンド（実行しない）。
4. **終了時の1問**: 「今日の遠回りは、なし・少し・大きく のどれか」を聞く（答えは、呼び出し元の `AGENTS.md` が定める記録に残す）。前回の `review` から7日以上たっていれば、`review` を勧める。
5. **改善案**（あったときだけ）: `hook-common.md` の「改善」に従う。

## 自動採用の範囲（2026-10-08 ユーザーの決定。試験運用）

**停止中（2026-10-08 ユーザーの決定。判定日 2026-11-08 まで）**: 新しい自動採用の規則は足さない（規則を生む流量を絞るため）。下の既存の 1 件は、`review` が 1 回だけ要・不要を判断する。再開するかは、11-08 の判定で決める。

改善案は、次の線で扱いを分ける。**線は一律にしない**（承認の素通りが続いている部分だけ、承認を外す。ユーザーの方針）。

| 区分 | 扱い | 対象 |
|---|---|---|
| 自動採用 | 承認を取らずに、追加・削除してコミットする | 下の「自動採用の規則」の節の項目（ID 付き）。運用の補助（報告の追加項目、確認の観点、閾値の注意など）に限る |
| 承認制 | 提案して、ユーザーの承認を得てから直す（従来どおり） | 下の安全規則と、手順の本体（番号つきの手順、報告の型、書き込み先の制約）を変える案。`wrap` 以外のフックの改善案 |

**安全規則（自動採用の対象外。常に承認制）**: ① push・remote・リポジトリの公開範囲、② 機密・個人情報の扱い、③ 破壊的な操作（`reset --hard`、`--force`、`rebase`、削除）、④ コミットの身元とトレーラー、⑤ 決定の記録の原則（ユーザーが明示または承認したものだけを Decisions に書く）、⑥ 書き込み先の制約（どこに書いてよいか）、⑦ この「自動採用の範囲」の節と、`review` の削除・復活の権限、⑧ ユーザーへの質問・承認の確認の規則。迷ったときは、安全規則として、承認制にする。

自動採用の手順: ① 規則を、下の節に、ID（`R-YYYYMMDD-n`）と一緒に足す。足した行に、見直し日（足した日から7日後）、戻す条件、`保険` か否かを書く。② `improvements.md` に1行足す（状態「自動採用・試用中」、ID、見直し日、戻す条件）。③ 1改善 = 1コミットにする（`git revert` で戻せるように、ほかの変更と混ぜない）。④ `events` に `kind=improvement`、`answered=0`、`adopted=1`、`basis` に `live;auto` を書いた行を足す（承認の指標でなく、自動採用の指標として扱う）。⑤ コミットメッセージに「自動採用」と ID を書く。⑥ 報告で、承認制の案と分けて、何を足したかを知らせる。**ユーザーが後で「戻して」と言ったときは、その場で戻す**（ユーザーは、いつでも拒否できる）。
