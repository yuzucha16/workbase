# wrap フック（別名「終了処理して」）

呼び出し名は wrap（セッションの終了）。別名は「終了処理して」。呼び出し表の正本は `hooks.md`。以下の「終了処理して」は、wrap と読み替える。

作業の終わりに行う処理を、順序を固定して1つにまとめたフック。ユーザーが「終了処理して」と言ったときだけ実行する（自発的には実行しない）。ソース側（作業ディレクトリ）の終了処理で、exmem 側の統合（`integrate-hook.md`）とは独立している。

出力のブレを減らすため、順序・報告の型を固定してある。各手順の中身は、既存の正本（`docs-rules.md`、`stock-hook.md`）を参照し、ここに複製しない。

## 場所と書き込みの制約

- 書き込み先は、手順ごとの正本に従う。`docs/`（`docs-rules.md`）、`exmem/inbox/` の新規ファイル（`stock-hook.md`）、作業ディレクトリのコミット（`docs-rules.md` の「コミットと push」）。`exmem/knowledge/` などは触らない（統合は `integrate-hook.md`）。
- push は、呼び出し元の `AGENTS.md` の許可リストにあるリポジトリだけ、エージェントが行う（`docs-rules.md` の「push」。2026-10-08 から試験運用）。許可リストに無いリポジトリは、push しない（ユーザーが行う）。`exmem/inbox/` のメモはコミットしない（`docs-rules.md`）。例外: 使い捨ての環境（クラウドのセッション）では、メモもコミットし、push まで行う（`docs-rules.md` の「使い捨ての環境での緩和」）。
- 手順の途中で承認が要るもの（既存ファイルの差分、リスクや制約が生まれる変更）は、`docs-rules.md` に従って、先にユーザーへ確認する。

## 手順

1. **プランモードなら先に抜ける**（`stock-hook.md` の手順 1 と同じ）。
2. **対象を特定する。** この作業で変更したリポジトリを列挙し（`git status`）、`docs/` を持つものを更新対象にする。作業が複数のリポジトリにまたがるときは、すべてを対象にする。**リポジトリの中の Project・Area が、リポジトリの `docs/` とは別に、自分の `docs/`（`decisions.md` を含む）を持つとき（`projects/` `areas/` `archives/` 配下）は、それも別の対象に数える**（`log.md` と `decisions.md` の更新と、棚卸しの対象。閉じた Project の `archives/` 配下も、今回の作業で変更したか、`未仕分け` `転記待ち` が残っていれば対象）。リポジトリのファイルを何も変えず、変更先が `~\.claude` やアプリのデータなど、リポジトリの外だけのとき（`git status` が、どのリポジトリでも空）は、Claude Code を開いた作業ディレクトリの `docs/` を対象にする。変更したリポジトリに `docs/` が無く、その親のワークスペース（Vault のトップなど）に `docs/` があるとき（例: `workbase` だけを変えた作業の `works/docs/`）は、親の `docs/` を対象にする（別のリポジトリなので、そのリポジトリでコミットする）。どれにも `docs/` が無ければ、変更した共通機能の変更履歴を対象にする。exmem だけで進めた作業（Vault から見えない場所の作業。クラウドのセッションなど）では、`exmem/contexts/<名>/context.md` の `Current State` と `Next Actions` を更新の対象にする（`exmem/AGENTS.md` の「作業を終えるとき」）。それも無ければ、この手順を省略して、報告に書く。
3. **`docs/` を更新する。** `docs-rules.md` に従い、`log.md` の Next Actions と Log、`decisions.md` を更新する。Decisions に書くのは、ユーザーが明示または承認したものだけ。作業ディレクトリや、その親ディレクトリの `AGENTS.md` が、終了処理の追加の手順（指標の記録など）を定めていれば、`docs/` の更新に続けて行う。更新したファイルは、手順 6 のコミットの対象に含める（別のリポジトリのファイルは、そのリポジトリでコミットする）。
4. **棚卸しをする。** `pwsh -NoProfile -File <kit>/tools/check-docs.ps1`を、対象ごとに実行する。`pwsh` が無い環境（クラウドのセッションなど）では手で確認し、報告に「点検スクリプトは未実行（手で確認）」と書く。手で見る項目は、各項目に【汎用】か【この件】と `行き先:` が1つずつあること、状態が6種のどれかであること、`転記待ち` が20件以下であること（`docs-rules.md`）。`docs/` が無く、`context.md` だけを更新した作業は、`転記待ち` が無いので「対象の `docs/` なし」と書く。FAIL は直す。`未仕分け` `転記待ち` `滞留` の件数を報告に書く。`転記待ち（→ exmem/inbox/<メモ>）` の項目の `転記済` への確定は、`review`（`review-hook.md` の B）が、台帳とハッシュで行う（2026-10-08 から）。ここでは、メモが `exmem/inbox/` に無くなっているのに `転記待ち` のままの項目があれば、件数を報告して、`review` を勧めるだけにする（台帳に記録が無い、2026-10-08 より前の項目は、`docs-rules.md` の「棚卸し」の従来の方式）。
5. **ナレッジ化する。** 知識があれば、`stock-hook.md`（手順 2 以降）に従う。会話に、再利用できる知識が無ければ、「ナレッジ無し」と報告して、この手順を省略する。`docs/` の `未仕分け` の【汎用】項目も、`stock-hook.md` の定めどおり対象にする。**メモを作ると、元の項目の行き先が `転記待ち` に変わるので、手順 4 の `check-docs.ps1` を、メモを作った対象について再実行し、以後の報告（手順 7・8）の件数は再実行後の値にする。**
6. **コミットする。** `docs-rules.md` の「コミットと push」に従う（パス指定、ステージの行数の確認、agent の身元とトレーラー）。`exmem/inbox/` のメモはコミットしない。作業の途中で、すでにエージェントがコミットしているなら、その身元とトレーラーも点検し、外れていれば報告する（履歴の書き換えは、ユーザーの確認なしにしない）。**コミットの後、そのリポジトリが許可リストにあれば push する**（`docs-rules.md` の「push」の条件を、毎回確認する。1つでも満たさなければ push せず、理由を報告する）。
7. **統合待ちを報告する。** 次の2つを数える。
   - `exmem/inbox/` の未統合メモの数（`README.md` を除く）。
   - 対象の `docs/decisions.md` にある `転記待ち` の件数（`check-docs.ps1` の内訳）。**対象が複数あるときは、`docs/` ごとの件数と、合計の両方を報告する。**
   - メモが **5 件以上**、または、いずれかの `docs/` で `転記待ち` が **15 件以上**（上限は 20 件で、`check-docs.ps1` は `docs/` ごとに FAIL にする。合計では判定しない）なら、「inboxを整理して」（`integrate-hook.md`）を勧める。合計が 15 件以上で、どの `docs/` も 15 件未満のときは、勧めずに、合計と内訳を報告する。
8. **報告する**（下の「報告の型」）。

## 報告の型

1. **更新した `docs/`**: パスと、変更の要点（Project・Area の `docs/` も、別の行で）。
2. **棚卸し**: `check-docs.ps1` の結果（FAIL / WARN の件数、`未仕分け` `転記待ち` `滞留` の件数）。対象ごとに書く。件数は、ナレッジ化の後の再実行の値（メモを作ったときは、`転記待ち` が増えている）。`転記済` に進める案があれば、一覧にする（承認が要る）。
3. **ナレッジ化**: 作成したメモのパス（コミットしていない旨を、メモに限定して添える）。無ければ「ナレッジ無し」。
4. **コミット**: ハッシュと内容、含めなかったファイル。push の結果（許可リストにあるリポジトリ）。許可リストに無いリポジトリは、push のコマンド（実行しない）。
5. **統合待ち**: 未統合メモの数、`転記待ち` の件数（`docs/` ごとと合計）、統合を勧めるか。前回の `review` から7日以上たっていれば、`review`（`review-hook.md`）を勧める。
6. **改善**: 下の「このフックの改善」に従う。自動採用したもの（ID と内容）と、承認を求める案を、分けて書く。

## このフックの改善

改善の流れは、`stock-hook.md` の「このフックの改善」と同じ（1〜3点を `場所 / 問題 / 案` で提案、承認後に kit を直し、`improvements.md` に残し、見本やモバイル用プロンプトを合わせる）。実行後に、次を確認して報告する。

- 順序で迷った点、手順の間で重複した作業、コンテキストが膨らんだ箇所。
- 閾値（メモ 5 件、`転記待ち` 15 件）が、実際の運用に合っていたか。
- 今回の作業で働いた、または漏れを防いだ「自動採用の規則」があれば、ID を `docs/metrics/rule-hits.csv` に足す（`date,session,rule_id,effect,note`。`effect` は `fired`（働いた）、`prevented`（漏れを防いだ）、`noise`（邪魔だった））。`review` が、要・不要の根拠に使う。

## 自動採用の範囲（2026-10-08 ユーザーの決定。試験運用）

改善案は、次の線で扱いを分ける。**線は一律にしない**（承認の素通りが続いている部分だけ、承認を外す。ユーザーの方針）。

| 区分 | 扱い | 対象 |
|---|---|---|
| 自動採用 | 承認を取らずに、追加・削除してコミットする | 下の「自動採用の規則」の節の項目（ID 付き）。運用の補助（報告の追加項目、確認の観点、閾値の注意など）に限る |
| 承認制 | 提案して、ユーザーの承認を得てから直す（従来どおり） | 下の安全規則と、手順の本体（番号つきの手順、報告の型、書き込み先の制約）を変える案。ほかのフック（`stock` `integrate` `start` `open` `close` `init` `review`）の改善案 |

**安全規則（自動採用の対象外。常に承認制）**: ① push・remote・リポジトリの公開範囲、② 機密・個人情報の扱い、③ 破壊的な操作（`reset --hard`、`--force`、`rebase`、削除）、④ コミットの身元とトレーラー、⑤ 決定の記録の原則（ユーザーが明示または承認したものだけを Decisions に書く）、⑥ 書き込み先の制約（どこに書いてよいか）、⑦ この「自動採用の範囲」の節と、`review` の削除・復活の権限、⑧ ユーザーへの質問・承認の確認の規則。迷ったときは、安全規則として、承認制にする。

自動採用の手順: ① 規則を、下の節に、ID（`R-YYYYMMDD-n`）と一緒に足す。足した行に、見直し日（足した日から7日後）、戻す条件、`保険` か否かを書く。② `improvements.md` に1行足す（状態「自動採用・試用中」、ID、見直し日、戻す条件）。③ 1改善 = 1コミットにする（`git revert` で戻せるように、ほかの変更と混ぜない）。④ `events.csv` に `kind=improvement`、`answered=0`、`adopted=1`、`basis` に `live;auto` を書いた行を足す（承認の指標でなく、自動採用の指標として扱う）。⑤ kit の版を上げ、`README.md` の変更履歴に「自動採用」と書く。⑥ 報告で、承認制の案と分けて、何を足したかを知らせる。**ユーザーが後で「戻して」と言ったときは、その場で戻す**（ユーザーは、いつでも拒否できる）。

## 自動採用の規則（試験運用）

`review` が、週1回を目途に、要・不要を判断する。形: `- 〔R-ID〕規則。見直し日: YYYY-MM-DD。戻す条件: …。保険: 有/無`。

- 〔R-20261008-1〕コミットの前に `git status --short` を見て、自分が触っていない `docs/` のファイルに `M` があるとき（並行セッションやユーザーの未コミットの編集）は、そのファイルをパス指定の `git add` で入れず、`HEAD` の内容に自分の変更だけを適用して index に入れる（`docs-rules.md` の「コミットを分けるとき」。`git update-index --cacheinfo` の引数は、PowerShell ではカンマごと引用符で囲む）。根拠: 2026-10-08 に、並行セッションの未コミットの項目が、自分のコミットに混ざった（`git diff --cached --stat` の行数が多いのを、見落とした）。見直し日: 2026-10-15。戻す条件: 削除の後に、並行する編集の混入が起きたら復活させる。保険: 有（めったに起きないが、他人の変更を巻き込む）。

## このフックの改善の承認

自動採用の対象外の案は、`stock-hook.md` の「このフックの改善」の流れで提案し、**承認なしに、kit を書き換えない。** 自動採用の節の項目は、上の手順で、承認なしに直してよい。
