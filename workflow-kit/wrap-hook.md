# wrap フック（別名「終了処理して」）

呼び出し名は wrap（別名「終了処理して」。表の正本は `hooks.md`）。

## 目的と契機

作業の終わりの処理を順序を固定してまとめ、次のセッション（別の端末やクラウドを含む）が言い直しなしに再開できるようにする。ユーザーが言ったときだけ実行する。exmem 側の統合（`integrate-hook.md`）とは独立している。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」（部屋での扱いは `room-context.md`）。
- 書き込み先: `docs/`（`docs-rules.md`）と、作業ディレクトリのコミットだけ。`exmem/lessons/` などは触らない（統合は `integrate-hook.md`）。`exmem/inbox/` のメモを作るのは `stock-hook.md`（このフックは作らない）。
- 既存のファイル: `docs/log.md` は現在状態に上書きする。経緯の記録先と `decisions.md` は追記する。
- コミットと push は `hook-common.md` の「コミットと push」に従う（部屋では、部屋の git へのコミットまで AI が行う。push はしない。works へのコミットは人の `room start` の回収）。
- 手順の途中で承認が要るもの（既存ファイルの差分、リスクや制約が生まれる変更）は、`docs-rules.md` に従って、先にユーザーへ確認する。

## 手順

手順は 3 段階（現在状態の更新、昇格の案、コミットと push）と報告に絞ってある。各手順の中身は、既存の正本（`docs-rules.md`）を参照し、ここに複製しない。

1. **対象を特定する。** 既定は、このセッションで作業した単位（起動した単位、または「<名前> の続き」で読みに行った単位。`hooks.md` の「起動する場所」）の `docs/` と、この作業で変更したリポジトリの `docs/`。複数のリポジトリにまたがるときは、すべてを対象にする（`hooks.md` の「領域とフックの権限」の型2）。Project・Area が自分の `docs/` を持つとき（`projects/` `areas/` `archives/` 配下）は、それも別の対象に数える。既定が当てはまらないとき（`docs/` が無い、リポジトリの外だけ、exmem だけ）は `wrap-targets.md` を読む。
2. **現在状態を更新する。** `docs/log.md` を、次のセッションが読むだけで再開できる現在状態に**上書き**する（Next Actions、Open Questions）。上書きの前に、残っている項目を**すべて**（このセッションで触れていない項目も）次の 3 つに分ける（2026-10-28 ユーザーの決定）。
   - **済**: 項目の完了条件（無ければ、項目に書かれた「次」）が、このセッションの作業、`git log`、実ファイルのどれかで確かめられる。全文を `log-history.md` の当日の見出しへ根拠（コミットやファイル）つきで移し、`log.md` から消す。
   - **一部済**: 済んだ部分だけを `log-history.md` へ移し、項目は残りの作業だけの文に書き直す（起票日は変えない）。進みを、子の箇条書き（`【MM-DD】〜した`）や「（済 日付）」の印で項目に足さない。
   - **未**: そのまま残す。実機・他PC・ユーザーの判断でしか確かめられないものもここに入れ、報告で「閉じてよいか」を聞く。
   上の階層の `docs/log.md`（リポジトリ直下など）には、この単位固有の Next Actions を置かない（二重管理になる。2026-10-29 ユーザーの決定）。あれば、単位側に無い内容だけを単位側へ移して消す。期日の表（`docs/due.md`）は直下に残す。経緯を残す場所が、呼び出し元の `AGENTS.md` にあれば、そこへ追記する。`decisions.md` は、ユーザーが明示または承認した決定があったときだけ書く（`docs-rules.md`）。呼び出し元の `AGENTS.md` が定める追加の手順（指標の記録など）は、続けて行う。
3. **昇格の案を出す。** このセッションで、ユーザーが同じことを言い直した、または新しい恒久的な前提が出たなら、`AGENTS.md` か知識への昇格の案を、1行で出す（承認制）。まとまった知識化は、ユーザーが「ナレッジ化して」と言ったときに `stock-hook.md` で行う。部屋の中の扱いは `room-context.md`。
4. **コミットする。** `hook-common.md` の「コミットと push」に従う（コミットの後、許可リストにあれば push する）。
5. **報告する**（下の「報告の型」）。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」。コミット、次にやること、固有の項目、ユーザーに求めることの順）を報告する。このフックでの追記:

- **ユーザーに求めること**: 昇格の案があれば1行（承認制。手順「昇格の案を出す」）。`review` を勧める条件を満たすときは、勧める（`hook-common.md` の「他のフックを勧める条件」）。
- **次にやること**: `wrap` は作業の区切りなので、切るを既定の推奨にする（続ける条件を満たすときを除く）。

固有の項目（「次にやること」の後、「ユーザーに求めること」の前）を次の順で報告する。

1. **更新した `docs/`**: パスと、変更の要点（2〜3行）。手順 2 で閉じた項目と縮めた項目の数、閉じてよいかを聞く項目（1項目1行）。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」。このフックでは、順序で迷った点、手順の間で重複した作業、コンテキストが膨らんだ箇所も対象にする。
