# wrap フック（別名「終了処理して」）

呼び出し名は wrap（セッションの終了）。別名は「終了処理して」。呼び出し表の正本は `hooks.md`。以下の「終了処理して」は、wrap と読み替える。

## 目的と契機

- **目的**: 作業の終わりに行う処理を、順序を固定して1つにまとめたフック。次のセッション（別の端末やクラウドを含む）が、言い直しなしに再開できるようにする。
- **契機**: ユーザーが「終了処理して」と言ったときだけ実行する（自発的には実行しない）。ソース側（作業ディレクトリ）の終了処理で、exmem 側の統合（`integrate-hook.md`）とは独立している。

## 場所と書き込みの制約

- 書き込み先は、`docs/`（`docs-rules.md`）と、作業ディレクトリのコミットだけ。`exmem/lessons/` などは触らない（統合は `integrate-hook.md`）。`exmem/inbox/` のメモを作るのは `stock-hook.md`（このフックは作らない）。
- push は、呼び出し元の `AGENTS.md` の許可リストにあるリポジトリだけ、エージェントが行う（`docs-rules.md` の「push」）。許可リストに無いリポジトリは、push しない（ユーザーが行う）。クラウドのセッションからも、許可リストのリポジトリには push してよい（`docs-rules.md` の「使い捨ての環境での緩和」）。
- 手順の途中で承認が要るもの（既存ファイルの差分、リスクや制約が生まれる変更）は、`docs-rules.md` に従って、先にユーザーへ確認する。

## 手順

そのため、手順は 3 段階（現在状態の更新、昇格の案、コミットと push）と報告に絞ってある（2026-10-08 に、9 段階から縮めた）。各手順の中身は、既存の正本（`docs-rules.md`）を参照し、ここに複製しない。

1. **対象を特定する。** 既定は、このセッションで作業した単位（起動した単位、または「<名前> の続き」で読みに行った単位。`hooks.md` の「起動する場所」）の `docs/` と、この作業で変更したリポジトリの `docs/`。複数のリポジトリにまたがるときは、すべてを対象にする。Project・Area が自分の `docs/` を持つとき（`projects/` `areas/` `archives/` 配下）は、それも別の対象に数える。変更したリポジトリに `docs/` が無く、そのリポジトリの `AGENTS.md` が `wrap` の既定の対象を定めていれば、それを対象にする。リポジトリの外だけを変えたとき、または変更したリポジトリに `docs/` も既定の対象も無いときは、親のワークスペースの `docs/`、それも無ければ、Claude Code を開いた作業ディレクトリの `docs/` を対象にする（別のリポジトリなので、そのリポジトリでコミットする）。exmem だけで進めた作業は、該当する `exmem/lessons/` のノートの `Open Questions` / `Next Actions` を更新する（`contexts/` は 2026-10-10 に廃止）。どれも無ければ、この手順を省略して、報告に書く。
2. **現在状態を更新する。** `docs/log.md` を、次のセッションが読むだけで再開できる現在状態に**上書き**する（Next Actions、Open Questions）。経緯を残す場所が、呼び出し元の `AGENTS.md` にあれば、そこへ追記する。`decisions.md` は、ユーザーが明示または承認した決定があったときだけ書く（`docs-rules.md`）。呼び出し元の `AGENTS.md` が定める追加の手順（指標の記録など）は、続けて行う。
3. **昇格の案を出す。** このセッションで、ユーザーが同じことを言い直した、または新しい恒久的な前提が出たなら、`AGENTS.md` か知識への昇格の案を、1行で出す（承認制）。まとまった知識化は、ユーザーが「ナレッジ化して」と言ったときに `stock-hook.md` で行う。
4. **コミットする。** `docs-rules.md` は「コミットと push」の節だけを読み（見出しの一覧で位置を見る。全文は読まない）、それに従う（パス指定、ステージの行数の確認、agent の身元とトレーラー）。**コミットの後、そのリポジトリが許可リストにあれば push する**（`docs-rules.md` の「push」の条件を、毎回確認する。1つでも満たさなければ push せず、理由を報告する）。
5. **報告する**（下の「報告の型」）。

## 報告の型

1. **更新した `docs/` と昇格の案**: パスと、変更の要点（2〜3行）。昇格の案があれば1行。
2. **コミット**: ハッシュと内容、含めなかったファイル。push の結果。許可リストに無いリポジトリは、push のコマンド（実行しない）。
3. **終了時の1問**: 「今日の遠回りは、なし・少し・大きく のどれか」を聞く（答えは、**起動した単位**の `AGENTS.md` が定める記録に残す。作業したリポジトリが別でも、起動した単位に書く。2026-10-16 ユーザーの決定）。前回の `review` から7日以上たっていれば、`review` を勧める。
4. **次の会話への依頼文**: この会話はここで切り、次は新しい会話で始める（`--resume` で続けない。履歴は毎ターン再送されるため）。新しい会話に貼る依頼は「<作業した単位> の続き」の1行（状態は単位の窓口と `docs/log.md` が持つ）。
5. **改善案**（あったときだけ）: このフックでは、その場で提案せず、手順「現在状態を更新する」で更新する `docs/log.md` の Open Questions に、`場所 / 問題 / 案` の1行で足す（`review 消化` で承認を取って直す。承認は `hook-common.md` の「承認」）。順序で迷った点、手順の間で重複した作業、コンテキストが膨らんだ箇所も対象にする。報告には「Open Questions に足した」と1行だけ書く。
