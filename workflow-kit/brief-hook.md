# brief フック（別名「作業を始めて」）

呼び出し名は brief。別名は「作業を始めて」。呼び出し表の正本は `hooks.md`（体系の経緯は `README.md` の「フックの体系」）。以下の「作業を始めて」は、brief と読み替える。

## 目的と契機

- **目的**: 作業を始める前に、ゴールと前提をそろえる。ユーザーが毎回書いているものを、AI が先に集めて、要約で返す。
- **契機**: ユーザーが「作業を始めて」と言ったときだけ実行する（自発的には実行しない）。
  - 単独で呼べる。進行中の Project があるとき（小さな再開を含む）は、そのまま始める。
  - 進行中の Project が無い、または新しい Project を始めるときは、先に人が `room open` でひな形を作る（立てる前の判断基準は `project-structure.md`）。Project の README の本文が雛形のままなら、この `brief` の最初に下書きする（部屋の中だけ。書き方は `room-context.md` の「README 本文の下書きの書き方」）。
  - **モード**: `brief 解決` / `brief 改善` / `brief 変更` / `brief 調査` / `brief 計画` と言われたときは、下の「引数つきモード」に従う。引数なしの `brief` は、下の手順どおり。
  - 小さな再開では、全項目を聞かず、「`docs/log.md` の Next Actions の先頭でよいか」の1問に縮めてよい（未決: 縮め方は実測で決める）。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」に従う（部屋での扱いは `room-context.md`）。
- 書き込み先: 呼び出し元の `events` の行だけ（あるときだけ。手順「記録する」）。
- 既存のファイル: `events` は追記する（既存の行は変えない）。
- 作業での変更は、要約で合意した「触ってよい範囲」に従う（下の「インタビューの項目」）。

## 手順

1. **事前確認**（質問の前に、AI が行う）: 対象の `docs/log.md` の Next Actions と Open Questions、README の完了条件と範囲外を読む。環境で確認できる前提（コンパイラの有無など）は、実際に確認する。利用者の前提（専門領域・経験）が記憶にあるか確かめる。`review` と `review 消化` を勧める条件（`hook-common.md` の「他のフックを勧める条件」の節だけ読む。全文は読まない）を満たすときは、一度だけ「見直しをしますか」「`review 消化` をしますか」と提案する（実行は言われたときだけ）。呼び出し元の `docs/log.md` に期日つきの項目があり、期日を過ぎていれば、最初に知らせて判断を求める。
2. **モードを決める**: 1問で、ゴールを先に決めるか（確定型）、仮ゴールで走るか（探索型）を聞く。Recommended は、成果物の合否を事前に書けるか（仕様、規格、数値）で決める。書けるなら確定型、出してみないと評価が決まらないもの（設計案、文書の骨子、運用の形）なら探索型。ユーザーがモードや型を先に言っていれば、聞かずに宣言する（根拠: exmem の `lessons/session-goal-modes.md`）。確定型は、次の手順をインタビューの項目すべてで行う。探索型は、仮のゴールと「ゴールを変える条件」だけを聞き、残りは、答えが定まるものを宣言して省く。
3. **項目を埋める**: 下のインタビューの項目と、作業の種類の差分の項目について、答えが1つに定まるものは質問せず、要約に宣言する。残りを、選択式（既定値に Recommended）で聞く。**質問のまとまりの最後に、「ほかに前提はありますか」の自由記述を1つ置く**。
4. **要約を返す**: 「今日のゴール」を、項目ごとに返す。反対があるときだけ、ユーザーが直す。
5. **記録する**: 呼び出し元に `events` があるときだけ、質問ごとに1行（`kind=interview`）を、回答を受けた同じターンで足す（書式は、呼び出し元の記録の定義に従う）。探索型でゴールが変わったら、`kind=goal_change` の行を足す。
6. **作業する**。探索型でゴールが変わったら、理由と新しいゴールを `docs/log.md` に1行足し、1回と数える。全体（最初のゴールを含む）が4回を超えたら、「未決」として、残った論点を `docs/log.md` に書き、ユーザーに決めを求める。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」の節だけ読む。全文は読まない。ユーザーに求めること、コミットを先に、次にやることを最後に）を報告する。このフックでの追記:

- **ユーザーに求めること**: 要約への反対（無ければ「なし」）と、聞いて答えが未確定の項目。
- **コミット**: このフックはコミットしないので、「なし」と書く。

続けて、固有の項目を、手順「要約を返す」の要約で報告する（作業の終わりには行わない）。

1. **今日のゴール**: 要約を、項目ごとに返す。宣言した項目（答えが1つに定まったもの）と、聞いた項目を分ける。探索型では、仮ゴールと「ゴールを変える条件」を返し、モード（確定型か探索型か）を明記する。

## 引数つきモード

`brief 解決` `brief 改善` `brief 変更` `brief 調査` `brief 計画` と言われたときは、`brief-modes.md` を読んで従う（言われたときだけ読む。引数なしの `brief` では読まない）。手順「事前確認」と「記録する」は、このファイルの手順どおり。

## インタビューの項目

| 項目 | 内容 | 省略してよい条件（宣言だけにする） |
|---|---|---|
| ゴール | このセッションで到達したい状態（1文） | 省略しない（候補は Next Actions から出す） |
| 前提・制約 | 環境、期限、使える道具 | 環境の確認で1つに定まるとき |
| 対象と資料 | 対象の Project・Area と、読む資料 | 進行中の Project が1つだけのとき |
| 触ってよい範囲 | リポジトリ・ディレクトリ単位の許可（この Project、dotfiles、kit、`resources/` など）。変更の可否と、変更前に確認が要るもの | 既定（この Project の中だけ）で足りるとき |
| やらないこと | 範囲外にする作業（機能、方式） | 「特になし」を既定にして、範囲外は README を守る |
| 完了の判断 | 何が出たらこのセッションを終えるか | ゴールの文に含まれるとき |

「触ってよい範囲」と「やらないこと」は分ける。やらないことの選択肢に、リポジトリの変更の許可を混ぜると、ユーザーに直される。

## 利用者の前提

専門領域・経験・立場は、記憶に残し、毎回は聞かない。記憶に無い、または不足しているときだけ、最初に1度聞く（聞かずに、設計の前提が後から出た実例がある）。

## 作業の種類の差分

種類は、Project の README の `type`（`dev` `inv`）に対応する。`dev` の開発・文書作成の項目は `brief-work-types.md`。`inv` の調査は `brief 調査`（引数つきモード）で扱う。

## 未決

- 作業の種類ごとの定型の設計（項目と差分に分ける）。小さな再開での縮約の形。
- モードの目安（成果物の合否を事前に書けるか）が実例に合うか。探索型の上限（全体4回）は実測した数字ではない。`typed` の比較は実測してから。
- 「ほかに前提はありますか」の効果の測定。
