# init フック（別名「workflowを導入して」）

呼び出し名は init。別名は「workflowを導入して」。呼び出し表の正本は `hooks.md`。以下の「workflowを導入して」は、init と読み替える。

## 目的と契機

- **目的**: 作業ディレクトリに、workflow-kit の共通機能を導入するためのフック。
- **契機**: ユーザーが「workflowを導入して」と言ったときだけ実行する（自発的には導入しない）。
- **モード**: `init 更新`（別名「雛形を反映して」）と言われたときは、`init-update.md` を読み、そこに従う（項目 5 で作った works に、その後の雛形の変更を反映する）。下の入力と手順は使わない。

## 導入項目の一覧

導入項目は増やせる。workflow に新しい機能を足すときは、「導入項目の一覧」に行を足す（手順は下の「導入項目を足すとき」）。

| # | 項目 | 生成物 | 必須 | 規則の正本 |
|---|---|---|---|---|
| 1 | 共通ルールの参照 | `AGENTS.md`、`CLAUDE.md` | 必須 | `templates/AGENTS.md` |
| 2 | 作業ログと判断ログ | `docs/log.md`、`docs/decisions.md` | 必須 | `docs-rules.md` |
| 3 | 「ナレッジ化して」 | なし（`hooks.md` の表で呼べる。`AGENTS.md` の共通ルールのポインタが入口） | 必須 | `stock-hook.md` |
| 6 | 「終了処理して」「inboxを整理して」 | なし（`hooks.md` の表で呼べる。`AGENTS.md` の共通ルールのポインタが入口） | 「終了処理して」は必須 | `wrap-hook.md`、`integrate-hook.md` |
| 4 | 履歴からの復元 | `docs/` の Log と判断記録の補完 | 任意 | `init-restore.md` |
| 5 | works の生成 | `.gitignore`、`.ignore`、`.gitattributes`、`README.md`、`AGENTS.md`（works 用）、PARA の3フォルダ、`resources_p/`（PC ローカルの resources。追跡しない）、`git init` | 任意（トップを作るときだけ。1〜3 も合わせて導入する） | `templates/workspace/`、`init-workspace.md` |
| 7 | 雛形の反映（`init 更新`） | 雛形の変更を当てた `AGENTS.md`、ignore、`.claude/settings.json` など。コミットの `Template-Rev` | 任意（雛形が更新されたとき） | `init-update.md` |

### 導入項目を足すとき

1. 上の表に行を足す（生成物、必須か任意か、規則の正本）。
2. 「手順」に、その項目の作り方を足す（長い任意の項目は、`init-` で始まる別ファイルに分け、その項目のときだけ読むと書く）。
3. 「自己点検」に、その項目の確認を足す。
4. 見本（`examples/setup-example.md`）を合わせる。
5. 改善の受け皿（`topics/kit-growth/docs/decisions.md`）に1行残す（`improvements.md` は凍結）。

## 場所と書き込みの制約

- 書き込み先: 対象ディレクトリの中の `AGENTS.md`、`CLAUDE.md`、`docs/` だけ。`exmem` やその他は触らない。
- **既存のファイルは、上書きしない。** 既存があれば、差分の案を示して承認を得る。承認の前に変更しない。
- コミットと push は `hook-common.md` の「コミットと push」に従う（項目 5 の初回コミットは、`init-workspace.md` の「初回コミットをする」）。
- 対象の `docs/` が、`.gitignore` の既定でローカル専用になる場合は、その旨を報告に書く（確認: `git check-ignore -v <パス>`）。ローカル専用の `docs/` は、他のPCに届かない。
- 項目 5（works の生成）だけは、上の書き込み先に加えて、対象の `.gitignore`、`.ignore`、`.gitattributes`、`areas/` `projects/` `archives/`、`resources_p/`、`.git/`（`git init` と `.git/hooks/pre-push`）に書く。`resources/` と `.obsidian/` は作らない・書き換えない（`resources/` は別リポジトリの clone、`.obsidian/` は dotfiles が張るジャンクション）。
- このフックを呼べる領域は、`hooks.md` の「領域とフックの権限」に従う。ユーザーがこのファイルのパスを指示したときも呼べる。新しい PC で works を作るときは、`workbase` の clone の中で呼ぶ（初回の例外）。それ以外の場所からの入口は、Claude 用スキル（未作成。TODO）。

## 入力

次の4項目。会話に材料があれば、質問せずに埋めて、報告で確認する。足りない項目だけ、1回に1問ずつ質問する。

1. 対象ディレクトリ（絶対パス）
2. 目的（1〜2行）
3. 読む順番の、固有の項目（`README.md` など。無ければ「なし」）
4. 固有ルール（編集の注意、コミットの規則など。無ければ「なし」）

### 既定値（項目 5）

「workflowを導入して」が、**`workbase` の clone の中**（`resources/.git` があり、`origin` が `workbase`）で、**対象のパスを指定されずに**言われたときは、項目 5（works の生成）とみなす。質問せずに、次の既定値で行う。ユーザーが言葉で指定した項目は、それを優先する。

既定値の表は `init-workspace.md` の「既定値」。

`workbase` の外（作業ディレクトリの中）で言われたときは、従来どおり、その作業ディレクトリに項目 1〜3 を導入する。対象が既に works（`.git` があり、コミットがある）なら、生成せず、その旨を報告する。

項目 5（works の生成）のときは、上の4項目（対象ディレクトリは、works のルート。通常は works のトップ）に加えて、次の3項目を受け取る。

5. PC の役割（例: 業務用 / 個人用）
6. remote の方針（なし / 非公開リポジトリの URL）。業務用の既定は「なし」
7. 初回コミット（する / しない。既定: する）

## 手順

出力のブレを減らすため、入力・手順・自己点検・報告の型を固定してある。迷ったら、このファイルと `examples/setup-example.md`（見本）に合わせる。

1. **対象を確認する。** `AGENTS.md`、`CLAUDE.md`、`docs/` の有無、`.git` の有無、`.gitignore` による追跡状況を調べる。`docs/` がローカル専用（`.gitignore` で除外される）と分かったときは、共有するかをユーザーに質問する。既定は、ローカル専用のままにする。`.gitignore` を変更するのは、リスクや制約が生まれる変更なので、ユーザーの承認を得てから行う。**導入する単位も確認する。** `AGENTS.md` と `docs/` を置くのは、リポジトリや作業ディレクトリのルートか、独立して判断を積む単位だけ。小さなサブディレクトリごとには置かない（AI が読む前提資料が作業単位ごとに増え、管理コストだけが膨らむ）。対象がサブディレクトリで、独立して判断を積む単位でないときは、導入せずに、親（ルート）への導入を提案する。
2. **入力を受け取る。**
3. **生成する。**
   - `AGENTS.md`: `templates/AGENTS.md` を埋める。「共通ルール」の節（パスと `hooks.md` へのポインタ、読めない場合の一文）は、雛形のまま変えない。既存があれば、追加する節（共通ルール、読む順番）の差分案を示して承認を待つ。既存の `AGENTS.md` がそれ自体で規則を持つときは、「読む順番」の2番目を「この `AGENTS.md` の各節」とする。
   - `CLAUDE.md`: `@AGENTS.md` の1行。既存があれば、`@AGENTS.md` が入っているかを確認し、無ければ差分案を示す。
   - `docs/log.md`、`docs/decisions.md`: `templates/` から作り、冒頭の説明に目的を入れる。既存があれば触らない。
4. **任意: 履歴から復元する**（ユーザーが望むときだけ。`init-restore.md` を読む）。
5. **任意: works を生成する**（トップを作るときだけ。`init-workspace.md` を読む）。
6. **「自己点検」を通す**（下の節）。
7. **コミットする。** 生成・変更したファイルを、`hook-common.md` の「コミットと push」に従ってコミットし、許可リストにあれば push する。項目 5 の初回コミットは `init-workspace.md` の「初回コミットをする」で行う（入力 7 が「しない」なら行わない）。承認待ちの差分案は含めない。
8. **報告する**（下の「報告の型」）。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」。ユーザーに求めること、コミットを先に、次にやることを最後に）を報告する。このフックでの追記:

- **ユーザーに求めること**: 既存ファイルの差分案（承認待ち）、`docs/` を共有するか（ローカル専用だったとき）、導入する単位（サブディレクトリで、親への導入を提案するとき）。works の生成のとき（項目 5）は、手作業が要ること（`resources/` の clone、実ディレクトリの `.obsidian` の退避、push、未追跡の既存ファイルの扱い）も挙げる。
  - **git の身元の設定をユーザーに促す**（項目 5 のとき、必ず書く）。`git config --global --get user.name` と `user.email` を確認し、未設定または仮値（`example.com` を含むもの）なら、現在値を示して設定を促す。設定済みなら、その旨を1行書く。エージェントのコミットは agent の身元を使うので、この設定が無くても導入は止まらない。ユーザー自身が、この PC で手動のコミットをするときに要る。設定は、ユーザーが行う（エージェントは `git config` を書き換えない）。コマンド例: `git config --global user.name "<名前>"`、`git config --global user.email "<メール>"`（会社の PC では、会社で使うアドレスの扱いを確認する）。
- **コミット**: 項目 5 の初回コミットのときは、含めなかったファイル（未追跡の既存ファイル）も書く。push は `hook-common.md` の「コミットと push」に従う（works は許可リストに無いのが通常なので、remote があれば push のコマンドを書く）。

続けて、固有の項目を次の順で報告する。

1. **対象**: ディレクトリのパス。
2. **条件**（項目 5 のとき。必ず書く）: 対象、目的、PC の役割、remote の方針、初回コミットを示し、各項目に「既定値」か「指定」を添える。変えたいときの方法も書く（役割と目的は `AGENTS.md` の冒頭を直す。remote を足すときは `git remote add origin <URL>`、remote なしの方針だったときは `.git/hooks/pre-push` の削除も）。
3. **変更したファイル**: 新規に作ったファイルと、差分案を示した既存ファイル（承認待ち）。
4. **追跡状況**: 共有（Git 管理）かローカル専用か。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」。このフックでは、次も確認する。

- 入力の型・雛形・自己点検で、曖昧だった点、迷った点、足りなかった項目。
- 導入項目の一覧に、足すべき機能。

## 自己点検

報告の前に、次をすべて確認する。1つでも外れたら直す。

- [ ] 導入する単位が、リポジトリや作業ディレクトリのルートか、独立して判断を積む単位である（小さなサブディレクトリではない）
- [ ] 書き込み先が、対象ディレクトリの中だけ
- [ ] 既存のファイルを上書きしていない（差分案を示して、承認を待っている）
- [ ] `AGENTS.md` の「共通ルール」の節が、雛形どおり（パスと `hooks.md` へのポインタ、読めない場合の一文）
- [ ] 「読む順番」が、窓口（あれば）→ `docs/log.md` の順で、`docs/decisions.md` を開始時に読まない（決める前に検索する）
- [ ] `CLAUDE.md` が `@AGENTS.md` を含む
- [ ] `docs/log.md` の見出しが Next Actions / Open Questions / Log、`docs/decisions.md` の見出しが Principles / Decisions / Gotchas
- [ ] 雛形のプレースホルダ（`<` `>`）が残っていない
- [ ] 目的が1〜2行
- [ ] 共有したくない値が無い
- [ ] 追跡状況（共有かローカル専用か）を報告に書いた
- [ ] 復元した場合は、出典・範囲・「不明」の明記がある
- [ ] works を生成した場合（項目 5）: `init-workspace.md` の「自己点検（項目 5）」をすべて確認した
