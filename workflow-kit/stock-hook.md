# stock フック（別名「ナレッジ化して」）

呼び出し名は stock（随時）。別名は「ナレッジ化して」。呼び出し表の正本は `hooks.md`。以下の「ナレッジ化して」は、stock と読み替える。

## 目的と契機

- **目的**: 作業で得た、次回以降も使える知識を exmem に残すためのフック。
- **契機**: ユーザーが「ナレッジ化して」と言ったときだけ実行する（自発的には書かない）。

## 場所と書き込みの制約

- exmem: `$HOME\works\resources\exmem`（WSL: `/mnt/c/Users/<Windows のユーザー名>/works/resources/exmem`）
- 書き込みは `exmem/inbox/` の**新規ファイルだけ**（話題ごとに1ファイル）。`knowledge/` `contexts/` など inbox 以外は編集しない。例外: ユーザーが明示したときだけ、このフックが作った同日のメモ（未追跡のもの）に、追記・修正してよい（手順「知識かどうかを判定する」の「既存のメモへの追記」）。
- inbox のメモを `knowledge/` へ統合するのは exmem 側の運用（`integrate-hook.md` の「統合そのものの手順」）。ここでは行わない。
- **このフックが `exmem/inbox/` に作ったメモは、コミットしない**（ユーザーの指示、2026-10-05。全体に適用）。理由: inbox のメモは、exmem 側で解釈して `knowledge/` に統合した後に削除する運用で、統合後は不要になるため。メモは未追跡のまま残す。コミットしないのは、このフックが作ったメモのファイルだけ（ほかの変更は対象外）。ほかの変更のコミットは `docs-rules.md` の「コミットと push」に従う。push はしない（ユーザーが行う）。例外: 使い捨ての環境（クラウドのセッション）では、メモもコミットして push する（`docs-rules.md` の「使い捨ての環境での緩和」）。

## 手順

出力のブレを減らすため、手順・表記・項目の型・自己点検・報告の型を固定してある。迷ったら、このファイルと `examples/inbox-example.md`（形式の見本）に合わせる。

実行の順序: 作業の終わりの処理（`docs/` の現在状態の更新、昇格の案、コミット）は、「終了処理して」フック（`wrap-hook.md`）が行う。`wrap` は、昇格の案を1行出すだけで、このフックは呼ばない。「ナレッジ化して」だけが言われたときは、知識の抽出だけを行い、`docs/` の更新・コミットには手を出さない。ただし、`docs/log.md` が今回の作業を反映した現在状態になっているか（`git status` の差分の有無だけでは判定できない）を確認し、報告の末尾に「`docs/` は未更新（または更新済み）。続けるなら『終了処理して』と言ってください」と1行添える。ナレッジ化の内容は、更新済みの `docs/` を根拠にできる。

1. **知識かどうかを判定する。** 会話から、知識・ルール・経験を抜き出す。判定の問いは「この会話を知らない人やAIが、別の作業で使えるか」。使えるものだけを残す。
   - 規則や置き場の選択（「AGENTS.md に規則として足す」など）も、ユーザーが明示または承認したなら Decisions に書く（根拠と却下案をそろえる）。AI が選んだだけで承認を確認できないものは、Decisions に書かず、Open Questions に「提案」として書く。
   - **依頼された実装と、AI が選んだ方式**: ユーザーが依頼した実装は、その依頼を根拠に Decisions に書いてよい（根拠に、依頼の内容を書く）。依頼に無い選択（AI が選んだ方式など）は、実機で問題なしと報告されただけでは承認とみなさず、Open Questions に「提案」として書く。迷うときは、報告で、ユーザーに承認を確認する。
   - 残す: 判断の原則と根拠、却下した案とその理由、実機で確認した事実、ハマりどころと解決方法。
   - 残さない: 何をいつやったかの作業ログ、そのディレクトリ固有で他に使い回せない経緯（これらは `docs/` に残す）。
   - **kit 自身の作業**（手順書・規則・ツールの設計や変更）は、一般化できるものだけを残す（2026-10-08 ユーザーの決定）。残すのは、他の作業でも使える進め方と判断の型（論点の抽出、選択肢の列挙、判断条件と材料の集め方、揃え方や点検の原則など）。その場の決定と経緯は、`docs/decisions.md` と各手順書、`git log` が正本なので、メモにしない。一般化できるものが無ければ、手順「該当する知識が無ければ」で「ナレッジ無し」と答える。
   - 同じ会話で、すでに「ナレッジ化して」を実行しているときは、前回の実行以降の内容だけを対象にする（前回が範囲を限定していたときは、「範囲を限定されたとき」の項目）。前回のメモは、同日の既存メモとして扱う（次の項目）。
   - 同じ日の `exmem/inbox/` に既存のメモがある場合は、先にそのファイル名と見出しを確認する。既存のメモに書いた話題は、重複して作らない。既存のメモの決定と、このメモの決定が食い違うときは、Open Questions に「他のメモとの食い違い」として、該当するメモ名と決定の見出しを書く（既存のメモは、次の項目のユーザーの明示が無い限り編集しない）。
   - **既存のメモへの追記・修正**: ユーザーが「このメモに追記して」のように明示したときだけ。対象は、このフックが作った同日のメモに限る（`knowledge/` に統合済みのものや、他のセッションのメモは編集しない）。追記は、そのメモに無い情報だけ（既存の内容は、事実が変わったときだけ直し、消さない）。追記したメモも、`sources` の追加と点検の対象にする。元のメモと別メモの両方に関わる原則は、片方に書き、もう片方からメモ名で参照する。
   - **範囲を限定されたとき**（例: 「この部分だけ」）は、その範囲だけを対象にする。範囲が曖昧なときは、書く前に1問だけ確認する。範囲を限定した実行のあと、次の実行は、前回の範囲を除く会話の内容を対象にする（「前回の実行以降」だけでは、前回の範囲より前の内容が漏れる）。範囲を限定したメモも、同日の既存メモとして扱い、話題を重複させない。
   - **`docs/decisions.md` の項目**: 会話に加えて、`→` の無い【汎用】項目も対象にする（`docs-rules.md` の「decisions.md の項目を知識にしたとき」。`docs/` と `workbase` が同じ PC にある直結ソースだけ。隔離ソースは運び方が違う）。項目は、固有情報を剥がして一般化してから書く。メモを作ったら、元の項目の末尾に `→ inbox/<メモ名>` を足す（`docs/` の更新で、この節の「書き込みの制約」の対象外。メモが統合されて消えた後も、`→` は消さない）。会話の内容と重なる項目は、会話の内容と合わせて1つのメモにする。
2. **該当する知識が無ければ、ファイルは作らず「ナレッジ無し」と答える。**
3. **話題を分ける。** 主な統合先（最も近い `knowledge/` のファイル）が異なる話題は別ファイル（1ファイル1テーマ）、同じなら1ファイルにまとめる。迷うときは分ける（統合のときに exmem 側でまとめられる）。ただし、分けた各ファイルの Principles と Decisions が合わせて3項目に満たなければ、近い話題のファイルに統合する。共通する事実・落とし穴は1つのファイルにだけ書き、他からは Goal か Open Questions でファイル名で触れる。分けたら、ファイルごとに `topic` と `title` を変える。汎用的な部分と固有の部分を分けるよう求められたときは、別ファイルにせず、項目の頭に【汎用】と【この件】を付けて1ファイルの中で分ける（【この件】も作業ログにせず、観点・判断・観測した事実だけを書く）。統合先の候補は、広い候補（【汎用】）と狭い候補（【この件】）を並べる。
4. **既存の知識と重なるか確認する。**
   1. テーマと tags から、検索キーワードを2〜4語選ぶ（日本語と英語の両方を含める）。
   2. `exmem/knowledge/` のファイル名、見出し（`^#`）、frontmatter の `tags` と `aliases` の行を、キーワードで検索する。`pwsh -NoProfile -File <kit>/tools/find-knowledge.ps1 <キーワードを空白で並べる>` で、ヒットしたキーワードの種類が多い順に、最大3件のファイルと根拠の行が出る（読み取り専用。部分一致なので、`git` が `GitHub` にもヒットする。根拠の行を見て判断する）。見出しや `tags` に無い語（コマンド名、エラー文言、変数名）で探すときは、`-Body` を付けると、本文の行も検索する。`pwsh` が無い環境では、手で検索する。
   3. 扱う範囲が最も近いノートを、最大2件選ぶ。
   4. Goal の末尾に、1行で書く。見つかったとき: `統合先の候補: knowledge/<ファイル>.md（キーワード: a, b, c）`。見つからなかったとき: `統合先の候補: 新規トピック（キーワード: a, b, c）`。内容がそのノートの範囲より広い（例: 特定の用途のノートに、汎用ツールの話が混ざる）ときは、狭い候補と広い候補（または新規トピック）を並べてよい。
   5. 選んだノートの記述と、このメモの内容が食い違うときは、該当する行（見出しや要旨）を Open Questions に「統合時の修正」として書く。`knowledge/` は編集しない。
   6. 同じスレッドで、エージェントが `knowledge/` のノートを直接編集済みのとき（呼び出し元の作業で、exmem の知識ノートを書き換えた場合）は、編集済みのノートと節を、Open Questions に「統合時の重複」として書く（内容が、このメモと重なるため）。
5. **書く前に、「自己点検」の手で確認する項目を通す**（下の節）。
6. `exmem/inbox/YYYY-MM-DD-<topic>.md` に新規作成する。同名のファイルがあれば上書きせず、別の名前にする。**作ったら、点検スクリプトを実行する**: `pwsh -NoProfile -File <kit>/tools/check-inbox.ps1 <作ったメモのパス...>`（パスは空白で並べる。引数なしなら、今日の日付のメモをすべて点検する）。FAIL が出たら直して、再実行する。WARN は、内容を見て判断する（`<…>` の WARN は、インラインコード内を除いて数える。複数のメモを点検したときの「メモの間」の WARN は、同じインラインコードが複数のメモの Facts / Gotchas にあるという重複の候補なので、同じ事実・落とし穴を重複して書いていないか確認する）。点検の結果は、スクリプト自体の改善にも使う（「このフックの改善」の「点検スクリプトの改善」）。`pwsh`（PowerShell 7）が無い環境（クラウドのセッションなど）では、「自己点検」の項目と「書き方」の規則を手で確認し、報告に「点検スクリプトは未実行（手で確認）」と書く。
7. **報告する**（下の「報告の型」）。

## 報告の型

書き終えたら、次の順で報告する。

1. **ファイル**: 作成したパス（複数なら全部）。「このメモのファイルはコミットしていない」と、範囲をメモに限定して添える（ほかの変更のコミットの有無は別に書く。「変更全体がコミット対象外」と読める書き方をしない）。点検スクリプトの結果（PASS / FAIL / WARN の件数と、WARN の判断）も1行で添える。
2. **要点**: 各見出しの要点を1行ずつ（「なし」の見出しも「なし」と書く）。
3. **統合先**: 統合先の候補と、使ったキーワード。
4. **終了処理の案内**（単独で言われたときだけ）: 上の「実行の順序」の1行。
5. **改善案**（あったときだけ）: `hook-common.md` の「改善」に従う。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」。このフックでは、次も確認する。

- exmem の統合に必要なのに欠けていた情報、`docs-rules.md` や見本の使いにくかった点。
- 点検スクリプトの誤検知・見逃し・分かりにくさ。点検スクリプトの改善案は、フックの改善案とは分けて書く。
- 手順や形式を変えたときは、`exmem/inbox/README.md` のモバイル用プロンプトと見本（`examples/`）を合わせる。
- スクリプトを直すときは、直す前に問題を一時ディレクトリで再現し、直した後に期待どおりになること（ほかの項目の結果が変わっていないことも）を確認する。

## 書き方

### ファイル名・title・tags

- `<topic>`: テーマを表す英単語2〜5語の kebab-case（例: `terminal-cursor-blink-decscusr`）。語数は、ハイフンで区切った語の数で数える（`dry-run` は2語。複合語は1語にまとめてよい: `dryrun`）。書いたら語数を数える。
- `title`: 日本語の名詞句（例: `ターミナルのカーソル点滅を止める`）。
- 日付: 今日の日付（`YYYY-MM-DD`）。
- `sources`: `<実行中のAI名> conversation "<テーマ>"`（例: `Claude Code conversation "fzf のキーバインド整理"`）。`"<テーマ>"` の後ろに、日付などを足さない（点検スクリプトが FAIL にする）。
- `tags`: 英小文字の kebab-case で3〜6個。`exmem/tags.md` の語彙から選び、語彙に無いものは書いてよい（統合のときに exmem 側で正規化する）。ソフトウェアは `tool/<名前>`、AIサービスは `ai/<名前>`。`type` や `status` の値（`inbox`、`knowledge` など）はタグにしない。

### 文章の規則

- **単体で読めるように書く。** 「上記」「この会話」「さっきの」など会話に依存する表現を避ける。
- **分量**: 1項目は1〜3文。ファイル全体の目安は150行以内。超えるなら、話題が複数でないかを疑う。
- 共有したくない値（会社名・ユーザー名・ユーザー名を含むパス・トークン・URL の秘匿値・実在のメールアドレス）は書かない。例示用のメールドメイン（`example.com` `*.local` `*.invalid` `*.test`）は書いてよい（点検スクリプトも FAIL にしない）。パスは `%USERPROFILE%` `$HOME` などにする。
- 確認した事実と仮説の表記を固定する:
  - 確認した事実: `（確認: YYYY-MM-DD、根拠: <実行したコマンドや見たファイル、またはユーザーの発言>）`
  - 未確認: `（仮説）`。この形のとおりに書く（点検スクリプトが完全一致で見る）。`（仮説: …）` や `（仮説。…）` は FAIL になる。補足は、括弧の外の別の文に書く（例: `…（仮説）。補足: …`）。

### 見出しごとの項目の型

| 見出し | 書くこと | 項目の型 |
|---|---|---|
| Goal | 何を考えたかったか。末尾に統合先の候補の1行 | 1〜3文 + 統合先の候補 |
| Principles | 判断の拠り所になる一般則（「〜しない」「〜を優先する」） | `- <原則>。理由: <1文>` |
| Decisions | この件で選んだこと（ユーザーが明示または承認したものだけ） | 下の3点セット |
| Facts | 観測した事実。根拠や却下案が無い決定もここ | `- <事実>（確認: …、根拠: …）` または `（仮説）` |
| Gotchas | 実際に遭遇した詰まりだけ | 下の3行セット |
| Open Questions | まだ決まっていないこと | `- <問い>` |
| Next Actions | 次にやること | `- <動詞で始める1文>`。作業が途中で、前提の状態が変わり得るとき（食い違った状態、未実行の手順など）は、末尾に `（YYYY-MM-DD 時点）` を付ける |

Decisions の項目（根拠と却下案が必須。無ければ Facts に書く）:

```markdown
- **<決めたこと>**（YYYY-MM-DD）
  - 根拠: <理由>
  - 却下案: <案>（<却下した理由>）
```

Gotchas の項目（原因が分からなければ「不明」）:

```markdown
- 状況: <何をしたときに>
  - 原因: <原因>
  - 解決: <解決方法>
```

AI が提案した内容で、ユーザーの承認を確認できないものは、Decisions に書かず、Open Questions に「提案」として書く（例: `- 提案: <内容>（AI の提案。未承認）`）。

仕分けの判断: 「他の件でも成り立つ一般則」→ Principles。「この件でAではなくBを選んだ」→ Decisions。「観測した」→ Facts。「実際にハマった」→ Gotchas。方針や一般的な注意点は、Gotchas に書かない。

## 自己点検

メモを書く前に、手で確認する項目を通す。機械で確認できる項目（ファイル名、frontmatter、見出し7つとその順番、Goal の末尾、Decisions の日付・根拠・却下案、Facts の表記、Gotchas の3行セット、「なし」の行、会話に依存する表現、共有したくない値、行数）は、上の「書き方」と下の「形式」のとおりで、作った後に点検スクリプト（`tools/check-inbox.ps1`）が見る。`pwsh` が無い環境では、これらも手で確認する。1つでも外れたら直す。

- [ ] 1ファイル1テーマ（統合先が異なる話題を混ぜていない）。分けた場合は、各ファイルの Principles と Decisions が合わせて3項目以上あり、同じ事実・落とし穴を重複して書いていない
- [ ] 同じ日の既存の inbox メモと、話題が重複していない。既存のメモに追記したときは、ユーザーが明示した場合だけで、元のメモに無い情報だけを足し、`sources` を足し、元の内容を消していない
- [ ] 「何をいつやったか」の作業ログが混ざっていない（【この件】の項目も、観点・判断・観測した事実だけ）
- [ ] Decisions の全項目が、ユーザーが明示または承認した決定である（AI の提案は Open Questions に「提案」としてある。依頼された実装は、依頼を根拠にできる）
- [ ] 確認した事実の根拠が本当である（実行したコマンド、見たファイル、またはユーザーの発言）
- [ ] 範囲を限定された場合、その範囲だけで、前回までの範囲と重複していない

## 形式

見出しは次の7つを、この順番で、省略せずに書く: Goal / Principles / Decisions / Facts / Gotchas / Open Questions / Next Actions。該当が無い見出しは「なし」と書く。**「なし」は、見出しの直後に、1語だけの行として書く**（点検スクリプトが `なし` との完全一致で見る。補足を同じ行に書くと、項目ありとみなされ、Gotchas などが3行セットでないとして FAIL になる）。補足は、別の見出しか、別のファイルに書く。frontmatter（`type: inbox`、`title`、`tags`、`created`、`sources`）から全見出しまでの通しの形は、`examples/inbox-example.md` が正本。
