# stock フック（別名「ナレッジ化して」）

呼び出し名は stock。別名は「ナレッジ化して」。呼び出し表の正本は `hooks.md`。以下の「ナレッジ化して」は、stock と読み替える。

## 目的と契機

- **目的**: 作業で得た、次回以降も使える知識を exmem に残すためのフック。
- **契機**: ユーザーが「ナレッジ化して」と言ったときだけ実行する（自発的には書かない）。
- **モード**: `stock ナレッジ`＝「ナレッジ化して」（AI 用。`kind: lesson`。`exmem/lessons/` 向け。省略時の既定）。`stock 理解`＝「理解ガイドにして」（人用。`kind: explain`。`guides/explain/` 向け。違う点は `stock-explain.md`、以下「理解」）。合言葉だけ（`stock`）で、モードが分からないときは、1問で選ばせる（選択肢は「理解」と「ナレッジ」。「両方」は無い。会話の中心が「なぜ・どう動く」なら理解、「判断・原則・落とし穴」ならナレッジを勧める）。「理解」のときは、先に `stock-explain.md` を読む。書き込み先は同じ `exmem/inbox/`。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」に従う（部屋での扱いは `room-context.md`）。
- exmem の場所は `hooks.md` の「exmem の場所」。
- 書き込み先: `exmem/inbox/` の**新規ファイルだけ**（話題ごとに1ファイル）。`lessons/` など inbox 以外は編集しない。例外は、ユーザーが明示したときだけ、このフックが作った同日のメモ（未追跡のもの）に、追記・修正してよい（手順「知識かどうかを判定する」の「既存のメモへの追記」）。
- 既存のファイル: 作るのは新規ファイルだけ。同名のファイルがあれば上書きせず、別の名前にする。
- inbox のメモを `lessons/` へ統合するのは exmem 側の運用（`integrate-hook.md` の「統合の細則」）。ここでは行わない。
- **このフックが `exmem/inbox/` に作ったメモは、コミットしない**（統合後に削除する運用のため、未追跡のまま残す。対象はメモのファイルだけ。ほかの変更と push は `hook-common.md` の「コミットと push」に従う。使い捨ての環境では、メモもコミットして push する）。

## 手順

出力のブレを減らすため、手順・表記・項目の型・自己点検・報告の型を固定してある。迷ったら、このファイルと `examples/inbox-example.md`（形式の見本）に合わせる。

実行の順序: 作業の終わりの処理（`docs/` の更新、昇格の案、コミット）は `wrap`（`wrap-hook.md`）が行い、`wrap` はこのフックを呼ばない。「ナレッジ化して」だけが言われたときは、知識の抽出だけを行い、`docs/` の更新・コミットには手を出さない。報告の共通の項目「次にやること」に、`docs/` の更新が要るなら「終了処理して」を挙げる（`docs/log.md` は読まない）。

1. **知識かどうかを判定する。** 会話から、知識・ルール・経験を抜き出す。判定の問いは「この会話を知らない人やAIが、別の作業で使えるか」。使えるものだけを残す。
   - **決定の承認**: 規則や置き場の選択、実装の方式は、ユーザーが明示または承認したときだけ Decisions に書く（根拠と却下案をそろえる。ユーザーが依頼した実装は、依頼の内容を根拠にしてよい）。AI が選んだだけで承認を確認できないもの（実機で問題なしと報告されただけの方式を含む）は、Decisions に書かず、Open Questions に「提案」として書く。迷うときは、報告で承認を確認する。
   - 残す: 判断の原則と根拠、却下した案とその理由、実機で確認した事実、ハマりどころと解決方法。
   - 残さない: 何をいつやったかの作業ログ、そのディレクトリ固有で他に使い回せない経緯（これらは `docs/` に残す）。
   - **固有の事実**（顧客・案件。Area の `knowledge/` や会議録に由来するもの）: 仮名にしても書かない。一般化した教訓だけを残す（どのモードでも同じ）。ただし部屋の中では、固有でも Area の業務に使い回せる知は捨てず、`scope: area` で `ai/out/knowledge/` に書く（`room-context.md` の `stock` の節。`exmem/inbox/` には運ばない）。
   - **「理解」の判定の問い**は「仕組みを、自分で説明できるようになるか」（`stock-explain.md`）。この手順の「話題を分ける」にある Principles と Decisions の件数の規則は、「ナレッジ」だけに適用する。
   - **kit 自身の作業**（手順書・規則・ツールの設計や変更）は、一般化できるものだけを残す。残すのは、他の作業でも使える進め方と判断の型（論点の抽出、選択肢の列挙、判断条件と材料の集め方、揃え方や点検の原則など）。その場の決定と経緯は、`docs/decisions.md` と各手順書、`git log` が正本なので、メモにしない。一般化できるものが無ければ、手順「該当する知識が無ければ」で「ナレッジ無し」と答える。
   - **例外**（2回目以降の実行、同日の既存メモがある、追記・修正、範囲の限定、`docs/decisions.md` の項目が対象、汎用と固有を分ける求め）のときだけ、`stock-exceptions.md` を読む。同日の既存メモは、どの場合も先にファイル名と見出しを確認し、話題を重複させない。
2. **該当する知識が無ければ、ファイルは作らず「ナレッジ無し」と答える。**
3. **話題を分ける。** 主な統合先（最も近い `lessons/` のファイル）が異なる話題は別ファイル、同じなら1ファイルにまとめる。迷うときは分ける。ただし、分けた各ファイルの Principles と Decisions が合わせて3項目に満たなければ、近い話題のファイルに統合する。共通する事実・落とし穴は1つのファイルにだけ書き、他からは Goal か Open Questions でファイル名で触れる。分けたら `topic` と `title` を変える。汎用と固有を分けるよう求められたときは `stock-exceptions.md`。
4. **既存の知識と重なるか確認する。**（「理解」は `guides/guides-index.md` で確認する。`stock-explain.md`）
   1. テーマから検索キーワードを2〜4語選び（日本語と英語の両方）、`pwsh -NoProfile -File <kit>/tools/find-knowledge.ps1 <キーワード...>` で `exmem/lessons/` を検索する（見出し・tags・aliases。最大3件と根拠の行が出る。部分一致なので根拠の行を見て判断する。コマンド名やエラー文言は `-Body` で本文も検索する。`pwsh` が無い環境では、`python <kit>/tools/find_knowledge.py [--body] <キーワード...>` で同じ検索ができる。どちらも無いときは、手で検索する）。
   2. 最も近いノートを最大2件選び、Goal の末尾に1行で書く: `統合先の候補: lessons/<ファイル>.md（キーワード: a, b, c）`。見つからなければ `統合先の候補: 新規トピック（キーワード: …）`。範囲が広いときは、狭い候補と広い候補を並べてよい。
   3. 選んだノートの記述と食い違うときは、Open Questions に「統合時の修正」として書く。同じスレッドで `lessons/` のノートを直接編集済みのときは、「統合時の重複」として書く。`lessons/` は編集しない。
5. **書く前に、「自己点検」の手で確認する項目を通す**（下の節）。
6. **作る。** `exmem/inbox/YYYY-MM-DD-<topic>.md` に新規作成する。同名のファイルがあれば上書きせず、別の名前にする。**作ったら、点検スクリプトを実行する**: `pwsh -NoProfile -File <kit>/tools/check-inbox.ps1 <作ったメモのパス...>`（パスは空白で並べる。引数なしなら、今日の日付のメモをすべて点検する）。FAIL が出たら直して再実行する。WARN は、行の確認点を見て判断する。`pwsh` が無い環境では `python <kit>/tools/check_inbox.py <パス...>`。どちらも無いときは「自己点検」と「書き方」を手で確認し、報告に「点検スクリプトは未実行（手で確認）」と書く。
7. **報告する**（下の「報告の型」）。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」。コミット、次にやること、固有の項目、ユーザーに求めることの順）を報告する。このフックでの追記:

- **ユーザーに求めること**: 承認を確認したい決定（AI が選んだ方式など。手順「知識かどうかを判定する」）、WARN の判断で聞きたいこと。
- **コミット**: 「このメモのファイルはコミットしていない」と、範囲をメモに限定して書く（ほかの変更のコミットの有無は別に書く。「変更全体がコミット対象外」と読める書き方をしない）。

固有の項目（「次にやること」の後、「ユーザーに求めること」の前）を次の順で報告する。

1. **ファイル**: 作成したパス（複数なら全部）。点検スクリプトの結果（PASS / FAIL / WARN の件数と、WARN の判断）も1行で添える。
2. **要点**: 各見出しの要点を1行ずつ（「なし」の見出しも「なし」と書く）。
3. **統合先**: 統合先の候補と、使ったキーワード。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」。このフックでは、次も確認する。

- exmem の統合に必要なのに欠けていた情報、`docs-rules.md` や見本の使いにくかった点。
- 点検スクリプトの誤検知・見逃し・分かりにくさ。点検スクリプトの改善案は、フックの改善案とは分けて書く。
- 手順や形式を変えたときは、`exmem/inbox/README.md` のモバイル用プロンプトと見本（`examples/`）を合わせる。
- スクリプトを直すときは、直す前に問題を一時ディレクトリで再現し、直した後に期待どおりになること（ほかの項目の結果が変わっていないことも）を確認する。

## 書き方

### ファイル名・title・tags

- `<topic>`: テーマを表す英単語2〜5語の kebab-case（例: `terminal-cursor-blink-decscusr`）。語数は、ハイフンで区切った語の数で数える（`dry-run` は2語。複合語は1語にまとめてよい: `dryrun`）。書いたら語数を数える。
- `title`: 日本語の名詞句（例: `ターミナルのカーソル点滅を止める`）。
- 日付: 今日の日付（`YYYY-MM-DD`）。
- `sources`: `<実行中のAI名> conversation "<テーマ>"`（例: `Claude Code conversation "fzf のキーバインド整理"`）。`"<テーマ>"` の後ろに、日付などを足さない（点検スクリプトが FAIL にする）。
- `tags`: 英小文字の kebab-case で3〜6個。`exmem/tags.md` は読まない。自由に書く（語彙への正規化は、統合のときに exmem 側で行う）。ソフトウェアは `tool/<名前>`、AIサービスは `ai/<名前>`。`type` や `status` の値（`inbox`、`knowledge` など）はタグにしない。

- `triggers`（必須。2026-10-25）: 後で同じ作業をするとき、依頼文に出そうな言葉（コマンド名、拡張子、症状、作業名）を、同義語・言い換えを含めて30語まで、`triggers: [語, 語]` の1行で書く（`tags` の次の行）。`find_knowledge.py --triggers "<依頼文>"` が、この語を依頼文と部分一致で照合して、作業の前にノートを引き当てる。書いた直後から、未統合のメモとして引かれる。`integrate` が、統合先に引き継ぐ。「理解」も同じ。

### 文章の規則

- **単体で読めるように書く。** 「上記」「この会話」「さっきの」など会話に依存する表現を避ける。
- **分量**: 1項目は1〜3文。ファイル全体の目安は150行以内。超えるなら、話題が複数でないかを疑う。
- 共有したくない値（勤務先名・ユーザー名・ユーザー名を含むパス・トークン・URL の秘匿値・実在のメールアドレス）は書かない。例示用のメールドメイン（`example.com` `*.local` `*.invalid` `*.test`）は書いてよい（点検スクリプトも FAIL にしない）。パスは `%USERPROFILE%` `$HOME` などにする。
- 確認した事実と仮説の表記を固定する:
  - 確認した事実: `（確認: YYYY-MM-DD、根拠: <実行したコマンドや見たファイル、またはユーザーの発言>）`
  - 未確認: `（仮説）`。この形のとおりに書く（点検スクリプトが完全一致で見る）。`（仮説: …）` や `（仮説。…）` は FAIL になる。補足は、括弧の外の別の文に書く（例: `…（仮説）。補足: …`）。

### 見出しごとの項目の型

| 見出し | 書くこと | 項目の型 |
|---|---|---|
| Goal | 何を考えたかったか。末尾に統合先の候補の1行 | 1〜3文 + 統合先の候補 |
| Principles | 判断の拠り所になる一般則（「〜しない」「〜を優先する」） | `- <原則>。理由: <1文>` |
| Decisions | この件で選んだこと（ユーザーが明示または承認したものだけ） | 下の3点セット |
| Facts | 観測した事実。根拠や却下案が無い決定もここ | `- <事実>（確認: …、根拠: …）` または `（仮説）` |
| Gotchas | 実際に遭遇した詰まりだけ | 下の3行セット |
| Open Questions | まだ決まっていないこと | `- <問い>` |
| Next Actions | 次にやること | `- <動詞で始める1文>`。作業が途中で、前提の状態が変わり得るとき（食い違った状態、未実行の手順など）は、末尾に `（YYYY-MM-DD 時点）` を付ける |

Decisions の項目（根拠と却下案が必須。無ければ Facts に書く）:

```markdown
- **<決めたこと>**（YYYY-MM-DD）
  - 根拠: <理由>
  - 却下案: <案>（<却下した理由>）
```

Gotchas の項目（原因が分からなければ「不明」）:

```markdown
- 状況: <何をしたときに>
  - 原因: <原因>
  - 解決: <解決方法>
```

AI が提案した内容で、ユーザーの承認を確認できないものは、Decisions に書かず、Open Questions に「提案」として書く（例: `- 提案: <内容>（AI の提案。未承認）`）。

仕分けの判断: 「他の件でも成り立つ一般則」→ Principles。「この件でAではなくBを選んだ」→ Decisions。「観測した」→ Facts。「実際にハマった」→ Gotchas。方針や一般的な注意点は、Gotchas に書かない。

## 自己点検

メモを書く前に、手で確認する項目を通す。機械で確認できる項目は、作った後に点検スクリプト（`tools/check-inbox.ps1`）が見る。`pwsh` が無い環境では、Python 版（`tools/check_inbox.py`）を使う。どちらも無いときは、「書き方」を手で確認する。1つでも外れたら直す。以下は「ナレッジ」の項目（「理解」は `stock-explain.md` の自己点検）。

- [ ] 1ファイル1テーマ（統合先が異なる話題を混ぜていない）。分けた場合は、各ファイルの Principles と Decisions が合わせて3項目以上あり、同じ事実・落とし穴を重複して書いていない
- [ ] 同じ日の既存の inbox メモと、話題が重複していない。既存のメモに追記したときは、ユーザーが明示した場合だけで、元のメモに無い情報だけを足し、`sources` を足し、元の内容を消していない
- [ ] 「何をいつやったか」の作業ログが混ざっていない（【この件】の項目も、観点・判断・観測した事実だけ）
- [ ] Decisions の全項目が、ユーザーが明示または承認した決定である（AI の提案は Open Questions に「提案」としてある。依頼された実装は、依頼を根拠にできる）
- [ ] 確認した事実の根拠が本当である（実行したコマンド、見たファイル、またはユーザーの発言）
- [ ] 範囲を限定された場合、その範囲だけで、前回までの範囲と重複していない

## 形式

「ナレッジ」の見出しは次の7つを、この順番で、省略せずに書く（「理解」の6見出しは `stock-explain.md`）: Goal / Principles / Decisions / Facts / Gotchas / Open Questions / Next Actions。該当が無い見出しは「なし」と書く。**「なし」は、見出しの直後に、1語だけの行として書く**（点検スクリプトが `なし` との完全一致で見る。補足を同じ行に書くと、項目ありとみなされ、Gotchas などが3行セットでないとして FAIL になる）。補足は、別の見出しか、別のファイルに書く。frontmatter（`type: inbox`、`title`、`tags`、`triggers`、`created`、`sources`）から全見出しまでの通しの形は、`examples/inbox-example.md` が正本。
