# 「ナレッジ化して」フック

作業で得た、次回以降も使える知識を exmem に残すためのフック。ユーザーが「ナレッジ化して」と言ったときだけ実行する（自発的には書かない）。

出力のブレを減らすため、手順・表記・項目の型・自己点検・報告の型を固定してある。迷ったら、このファイルと `examples/inbox-example.md`（形式の見本）に合わせる。

## 場所と書き込みの制約

- exmem: `C:\vault\works\resources\exmem`（WSL: `/mnt/c/vault/works/resources/exmem`）
- 書き込みは `exmem/inbox/` の**新規ファイルだけ**（話題ごとに1ファイル）。`knowledge/` `contexts/` など inbox 以外は編集しない。例外: ユーザーが明示したときだけ、このフックが作った同日のメモ（未追跡のもの）に、追記・修正してよい（手順 2 の「既存のメモへの追記」）。
- inbox のメモを `knowledge/` へ統合するのは exmem 側の運用（`exmem/AGENTS.md` の「inbox を整理するとき」）。ここでは行わない。
- **このフックが `exmem/inbox/` に作ったメモは、コミットしない**（ユーザーの指示、2026-10-05。全体に適用）。理由: inbox のメモは、exmem 側で解釈して `knowledge/` に統合した後に削除する運用で、統合後は不要になるため。メモは未追跡のまま残す。コミットしないのは、このフックが作ったメモのファイルだけ（ほかの変更は対象外）。ほかの変更のコミットは `docs-rules.md` の「コミットと push」に従う。push はしない（ユーザーが行う）。

## 手順

実行の順序: 作業の記録（`docs/`）が未更新なら、先に `docs-rules.md` に従って更新してからナレッジ化する。ナレッジ化の内容は、更新した `docs/` を根拠にできる。更新済みかは、`docs/log.md` の今日の日付の項目に今回の作業が書かれているかで確認する（`git status` の差分の有無だけでは判定できない）。作業が複数のリポジトリにまたがるときは、変更したリポジトリのうち `docs/` を持つものすべてを更新対象にする（呼び出し元が kit で `docs/` を持たなくても、記録先は別のリポジトリにある。呼び出し元の変更履歴だけで済ませない）。変更したどのリポジトリにも `docs/` が無い場合は、変更した共通機能の変更履歴を更新対象にする。それも無ければ省略し、報告にその旨を書く。

1. **プランモードなら先に抜ける。** inbox への書き込みは編集なので、プランモードのままでは書けない。`ExitPlanMode` で通常モードに戻す（承認が必要なら、このフックの実行であることを添える）。承認を拒否されたら、書き込まずに、解除方法（Shift+Tab で切り替える）を案内して待つ。Zed の `agent_servers.claude-acp.default_config_options.mode` が `"plan"` だと、新しいセッションは毎回プランモードで始まる。その場合は最初に承認が要ることを想定しておく。
2. **知識かどうかを判定する。** 会話から、知識・ルール・経験を抜き出す。判定の問いは「この会話を知らない人やAIが、別の作業で使えるか」。使えるものだけを残す。
   - 規則や置き場の選択（「AGENTS.md に規則として足す」など）も、ユーザーが明示または承認したなら Decisions に書く（根拠と却下案をそろえる）。AI が選んだだけで承認を確認できないものは、Decisions に書かず、Open Questions に「提案」として書く。
   - **依頼された実装と、AI が選んだ方式**: ユーザーが依頼した実装は、その依頼を根拠に Decisions に書いてよい（根拠に、依頼の内容を書く）。依頼に無い選択（AI が選んだ方式など）は、実機で問題なしと報告されただけでは承認とみなさず、Open Questions に「提案」として書く。迷うときは、報告で、ユーザーに承認を確認する。
   - 残す: 判断の原則と根拠、却下した案とその理由、実機で確認した事実、ハマりどころと解決方法。
   - 残さない: 何をいつやったかの作業ログ、そのディレクトリ固有で他に使い回せない経緯（これらは `docs/` に残す）。
   - 同じ会話で、すでに「ナレッジ化して」を実行しているときは、前回の実行以降の内容だけを対象にする（前回が範囲を限定していたときは、「範囲を限定されたとき」の項目）。前回のメモは、同日の既存メモとして扱う（次の項目）。
   - 同じ日の `exmem/inbox/` に既存のメモがある場合は、先にそのファイル名と見出しを確認する。既存のメモに書いた話題は、重複して作らない。既存のメモの決定と、このメモの決定が食い違うときは、Open Questions に「他のメモとの食い違い」として、該当するメモ名と決定の見出しを書く（既存のメモは、次の項目のユーザーの明示が無い限り編集しない）。
   - **既存のメモへの追記・修正**: ユーザーが「このメモに追記して」のように明示したときだけ行う。対象は、このフックが作った同日のメモに限る（`knowledge/` に統合済みのものや、他のセッションのメモは編集しない）。追記の範囲は、そのメモに無い情報だけ（既存の内容は、事実が変わったときだけ直し、消さない）。追記したメモも、`sources` の追加、自己点検、点検スクリプトの対象にする。元のメモと別メモの両方に関わる原則は、片方に書き、もう片方からメモ名で参照する（重複して書かない）。追記と別メモの作成が同時に求められたときは、別メモの話題が元のメモの範囲に入らないことを確認してから分ける。
   - **範囲を限定されたとき**（例: 「この部分だけ」）は、その範囲だけを対象にする。範囲が曖昧なときは、書く前に1問だけ確認する。範囲を限定した実行のあと、次の実行は、前回の範囲を除く会話の内容を対象にする（「前回の実行以降」だけでは、前回の範囲より前の内容が漏れる）。範囲を限定したメモも、同日の既存メモとして扱い、話題を重複させない。
3. **該当する知識が無ければ、ファイルは作らず「ナレッジ無し」と答える。**
4. **話題を分ける。** 主な統合先（最も近い `knowledge/` のファイル）が異なる話題は、別ファイルにする（1ファイル1テーマ）。主な統合先が同じなら1ファイルにまとめる。判断に迷うときは、話題ごとに別ファイルにする（統合のときに exmem 側でまとめられる）。ただし、分けた各ファイルの Principles と Decisions が合わせて3項目に満たない場合は、近い話題のファイルに統合する。分けた複数のファイルに共通する事実・落とし穴は、1つのファイルにだけ書く（重複させない）。他のファイルには書かず、関連を示したいときは、Goal か Open Questions にファイル名で触れる。分けたときは、ファイルごとに `topic` と `title` を変える。汎用的な部分と固有の部分を分けるよう求められたときは、別ファイルにせず、項目の頭に【汎用】（他の作業でも使える）と【この件】（この件に固有）を付けて、1ファイルの中で分ける。【この件】は、何をいつやったかの作業ログにせず、観点・判断・観測した事実だけを書く。統合先の候補は、広い候補（【汎用】）と狭い候補（【この件】）を並べる。
5. **既存の知識と重なるか確認する。**
   1. テーマと tags から、検索キーワードを2〜4語選ぶ（日本語と英語の両方を含める）。
   2. `exmem/knowledge/` のファイル名、見出し（`^#`）、frontmatter の `tags` と `aliases` の行を、キーワードで検索する。`pwsh -NoProfile -File <kit>/tools/find-knowledge.ps1 <キーワードを空白で並べる>` で、ヒットしたキーワードの種類が多い順に、最大3件のファイルと根拠の行が出る（読み取り専用。部分一致なので、`git` が `GitHub` にもヒットする。根拠の行を見て判断する）。`pwsh` が無い環境では、手で検索する。
   3. 扱う範囲が最も近いノートを、最大2件選ぶ。
   4. Goal の末尾に、1行で書く。見つかったとき: `統合先の候補: knowledge/<ファイル>.md（キーワード: a, b, c）`。見つからなかったとき: `統合先の候補: 新規トピック（キーワード: a, b, c）`。内容がそのノートの範囲より広い（例: 特定の用途のノートに、汎用ツールの話が混ざる）ときは、狭い候補と広い候補（または新規トピック）を並べてよい。
   5. 選んだノートの記述と、このメモの内容が食い違うときは、該当する行（見出しや要旨）を Open Questions に「統合時の修正」として書く。`knowledge/` は編集しない。
   6. 同じスレッドで、エージェントが `knowledge/` のノートを直接編集済みのとき（呼び出し元の作業で、exmem の知識ノートを書き換えた場合）は、編集済みのノートと節を、Open Questions に「統合時の重複」として書く（内容が、このメモと重なるため）。
6. **書く前に、「自己点検」のうち手で確認する項目を通す**（下の節）。
7. `exmem/inbox/YYYY-MM-DD-<topic>.md` に新規作成する。同名のファイルがあれば上書きせず、別の名前にする。**作ったら、点検スクリプトを実行する**: `pwsh -NoProfile -File <kit>/tools/check-inbox.ps1 <作ったメモのパス...>`（パスは空白で並べる。引数なしなら、今日の日付のメモをすべて点検する）。FAIL が出たら直して、再実行する。WARN は、内容を見て判断する（`<…>` の WARN は、インラインコード内を除いて数える）。点検の結果は、スクリプト自体の改善にも使う（「このフックの改善」の「点検スクリプトの改善」）。`pwsh`（PowerShell 7）が無い環境では、「自己点検」の全項目を手で確認する。
8. **報告する**（下の「報告の型」）。

## 書き方

### ファイル名・title・tags

- `<topic>`: テーマを表す英単語2〜5語の kebab-case（例: `terminal-cursor-blink-decscusr`）。語数は、ハイフンで区切った語の数で数える（`dry-run` は2語。複合語は1語にまとめてよい: `dryrun`）。書いたら語数を数える。
- `title`: 日本語の名詞句（例: `ターミナルのカーソル点滅を止める`）。
- 日付: 今日の日付（`YYYY-MM-DD`）。
- `kit`: このメモを作った時点の workflow-kit の版。`README.md` の「版」の値を、そのまま書く。統合のとき、`knowledge/` の frontmatter には写さない（版ごとの出力を比べるための記録）。
- `sources`: `<実行中のAI名> conversation "<テーマ>"`（例: `Claude Code conversation "fzf のキーバインド整理"`）。`"<テーマ>"` の後ろに、日付などを足さない（点検スクリプトが FAIL にする）。
- `tags`: 英小文字の kebab-case で3〜6個。`exmem/tags.md` の語彙から選び、語彙に無いものは書いてよい（統合のときに exmem 側で正規化する）。ソフトウェアは `tool/<名前>`、AIサービスは `ai/<名前>`。`type` や `status` の値（`inbox`、`knowledge` など）はタグにしない。

### 文章の規則

- **単体で読めるように書く。** 「上記」「この会話」「さっきの」など会話に依存する表現を避ける。
- **分量**: 1項目は1〜3文。ファイル全体の目安は150行以内。超えるなら、話題が複数でないかを疑う。
- 共有したくない値（会社名・ユーザー名・ユーザー名を含むパス・トークン・URL の秘匿値・実在のメールアドレス）は書かない。例示用のメールドメイン（`example.com` `*.local` `*.invalid` `*.test`）は書いてよい（点検スクリプトも FAIL にしない）。パスは `%USERPROFILE%` `$HOME` などにする。
- 確認した事実と仮説の表記を固定する:
  - 確認した事実: `（確認: YYYY-MM-DD、根拠: <実行したコマンドや見たファイル、またはユーザーの発言>）`
  - 未確認: `（仮説）`。この形のとおりに書く（点検スクリプトが完全一致で見る）。`（仮説: …）` や `（仮説。…）` は FAIL になる。補足は、括弧の外の別の文に書く（例: `…（仮説）。補足: …`）。

### 見出しごとの項目の型

| 見出し | 書くこと | 項目の型 |
|---|---|---|
| Goal | 何を考えたかったか。末尾に統合先の候補の1行 | 1〜3文 + 統合先の候補 |
| Principles | 判断の拠り所になる一般則（「〜しない」「〜を優先する」） | `- <原則>。理由: <1文>` |
| Decisions | この件で選んだこと（ユーザーが明示または承認したものだけ） | 下の3点セット |
| Facts | 観測した事実。根拠や却下案が無い決定もここ | `- <事実>（確認: …、根拠: …）` または `（仮説）` |
| Gotchas | 実際に遭遇した詰まりだけ | 下の3行セット |
| Open Questions | まだ決まっていないこと | `- <問い>` |
| Next Actions | 次にやること | `- <動詞で始める1文>`。作業が途中で、前提の状態が変わり得るとき（食い違った状態、未実行の手順など）は、末尾に `（YYYY-MM-DD 時点）` を付ける |

Decisions の項目（根拠と却下案が必須。無ければ Facts に書く）:

```markdown
- **<決めたこと>**（YYYY-MM-DD）
  - 根拠: <理由>
  - 却下案: <案>（<却下した理由>）
```

Gotchas の項目（原因が分からなければ「不明」）:

```markdown
- 状況: <何をしたときに>
  - 原因: <原因>
  - 解決: <解決方法>
```

AI が提案した内容で、ユーザーの承認を確認できないものは、Decisions に書かず、Open Questions に「提案」として書く（例: `- 提案: <内容>（AI の提案。未承認）`）。

仕分けの判断: 「他の件でも成り立つ一般則」→ Principles。「この件でAではなくBを選んだ」→ Decisions。「観測した」→ Facts。「実際にハマった」→ Gotchas。方針や一般的な注意点は、Gotchas に書かない。

## 自己点検

次をすべて確認する。機械で確認できる項目は、メモを作った後に点検スクリプト（`tools/check-inbox.ps1`）が見る: ファイル名、frontmatter（`type` `title` `created` `kit` `tags` `sources`）、見出しの順番、Goal の末尾、Decisions の日付・根拠・却下案、Facts の確認・仮説の表記、Gotchas の3行セット、会話に依存する表現（一部）、共有したくない値（一部）、行数の目安。手で確認する項目: 1ファイル1テーマ、同じ日の既存メモとの重複、作業ログの混在、Decisions が承認済みか、確認した事実の根拠が本当か。書く前に手で確認する項目を通し、作った後にスクリプトを通す。1つでも外れたら直す。

- [ ] 1ファイル1テーマ（統合先が異なる話題を混ぜていない）。分けた場合は、各ファイルの Principles と Decisions が合わせて3項目以上ある
- [ ] 同じ日の既存の inbox メモと、話題が重複していない。既存のメモに追記したときは、ユーザーが明示した場合だけで、追記は元のメモに無い情報だけ、`sources` を足し、元の内容を消していない。分けたファイルの間で、同じ事実・落とし穴を重複して書いていない
- [ ] 見出しが7つ（Goal / Principles / Decisions / Facts / Gotchas / Open Questions / Next Actions）、この順番で、すべてある。該当が無いものは、見出しの直後に「なし」だけを書く（補足を同じ行に付けていない）
- [ ] Goal の末尾に「統合先の候補」の1行がある
- [ ] 会話に依存する表現が無い
- [ ] 共有したくない値が無い
- [ ] 確認した事実に `（確認: …、根拠: …）`、未確認に `（仮説）` が付いている
- [ ] Decisions の全項目に、日付と、根拠と却下案がある
- [ ] Decisions の全項目が、ユーザーが明示または承認した決定である（AI の提案は Open Questions に「提案」としてある。依頼された実装は、依頼を根拠にできる）
- [ ] Gotchas の全項目が「状況・原因・解決」の3行セットになっている
- [ ] 「何をいつやったか」の作業ログが混ざっていない
- [ ] 範囲を限定された場合、その範囲だけで、前回までの範囲と重複していない

- [ ] `tags` が3〜6個で、kebab-case、`type`/`status` の値を含まない
- [ ] 日付が今日で、`sources` が定形
- [ ] `kit` が、`README.md` の「版」と一致している

## 形式

見出しは省略しない。該当が無い見出しは「なし」と書く。**「なし」は、見出しの直後に、1語だけの行として書く**（点検スクリプトが `なし` との完全一致で見る。補足を同じ行に書くと、項目ありとみなされ、Gotchas などが3行セットでないとして FAIL になる）。補足は、別の見出しか、別のファイルに書く。見本は `examples/inbox-example.md`。

````markdown
---
type: inbox
title: <テーマ>
tags:
  - <タグ>
created: <今日の日付 YYYY-MM-DD>
kit: <README.md の「版」>
sources:
  - <このAIサービス名> conversation "<テーマ>"
---

# <テーマ>

## Goal
この会話で何を考えたかったか。
統合先の候補: <…>

## Principles
判断の拠り所になる方針・原則・教訓（「〜しない」「〜を優先する」など）。

## Decisions
決めたこと。それぞれに根拠と、検討して捨てた案を書く。

## Facts
確認できた事実。未確認のものは「仮説」と明記する。

## Gotchas
遭遇したエラーや詰まった点と、その解決方法。

## Open Questions
まだ決まっていないこと。

## Next Actions
次にやること。
````

## 報告の型

書き終えたら、次の順で報告する。

1. **ファイル**: 作成したパス（複数なら全部）。「このメモのファイルはコミットしていない」と、範囲をメモに限定して添える（ほかの変更のコミットの有無は別に書く。「変更全体がコミット対象外」と読める書き方をしない）。点検スクリプトの結果（PASS / FAIL / WARN の件数と、WARN の判断）も1行で添える。
2. **要点**: 各見出しの要点を1行ずつ（「なし」の見出しも「なし」と書く）。
3. **統合先**: 統合先の候補と、使ったキーワード。
4. **改善案**: 下の「このフックの改善」に従う。フックの手順の改善案と、点検スクリプトの改善案を、分けて書く。

## このフックの改善

このフックの指示は、使うたびに直して育てる。実行後に、次を確認して報告する。

- この手順で曖昧だった点、迷った点、書き方が揺れそうだった点。
- 出力された inbox メモで、exmem の統合に必要なのに欠けていた情報。
- `docs-rules.md`、雛形、見本で、使いにくかった点。

改善案があれば1〜3点を、`場所 / 問題 / 案` の形で提案する。無ければ「改善案なし」と報告する。

**ユーザーが承認したら**、次を行う。

1. このディレクトリ（workflow-kit）の該当ファイルを直す。呼び出し元ディレクトリの `AGENTS.md` にコピーを作らない。
2. `improvements.md` に1行足す（状態は「採用」）。却下されたものも、理由つきで「却下」と残す。

### 点検スクリプトの改善（フックの改善と同じ手順で回す）

点検スクリプト（`tools/check-inbox.ps1`、`tools/find-knowledge.ps1`）も、使うたびに直す（ユーザーの指示、2026-10-06）。手順の改善と同じく、実行の直後に、観点を固定して確認し、提案し、承認を得てから反映し、受け皿に記録する。実行後に、スクリプトの結果から、次を確認する。

- **誤検知**: 正しい書き方なのに FAIL / WARN になった項目。メモを書き換えて避けず、スクリプトの側の問題として扱う。
- **見逃し**: 手で確認して見つけた問題のうち、スクリプトが PASS にしたもの（例: メモをまたいだ重複、承認の見落とし）。
- **分かりにくさ**: 出力のメッセージだけでは、直し方が分からなかった項目。
- **検索の質**（`find-knowledge.ps1`）: ヒットが多過ぎる・少な過ぎる、関係の薄いファイルが上位に来た。

改善案があれば1〜3点を、`場所 / 問題 / 案` の形で提案する（フックの改善案とは別に数える）。無ければ「点検の改善案なし」と報告する。

**ユーザーが承認したら**、次を行う。

1. `tools/` の該当スクリプトを直す。直す前に、問題を一時ディレクトリで再現し（誤検知・見逃しを起こす小さなメモを作る）、直した後に期待どおりになることを確認する。ほかの項目の結果が変わっていないことも、実際のメモで確認する。
2. `improvements.md` に1行足す（`発生元` の末尾に `［点検スクリプト］` を付ける。状態は「採用」）。却下されたものも、理由つきで「却下」と残す。
3. `knowledge-hook.md` の自己点検、`README.md` の構成の説明が、スクリプトの項目と食い違うなら合わせる。版を上げる。
4. 呼び出し元ディレクトリの `docs/log.md` に1行残す。

**承認なしに、このディレクトリ（`tools/` を含む）を書き換えない。**
