# `start` フック（別名「作業を始めて」）

呼び出し名は `start`（セッションの開始）。別名は「作業を始めて」。ユーザーが言ったときだけ実行する（自発的には実行しない）。呼び出し表の正本は `hooks.md`（体系の経緯は `README.md` の「フックの体系」）。

実測で直して育てる（育成・改善方式: 最初は手動で聞き、実測で形式化する）。作業の種類ごとの差分の項目は、実測が少ないので、叩き台として扱う。

## 目的と契機

- **目的**: 作業を始める前に、ゴールと前提をそろえる。ユーザーが毎回プロンプトに書いているものを、AI が先に集めて、要約で返す。`wrap`（終了処理）で、開始時のゴールと結果を突き合わせる。
- **契機**:
  - 単独で呼べる。進行中の Project があるとき（小さな再開を含む）は、そのまま始める。
  - 進行中の Project が無い、または新しい Project を始めるときは、先に `open-hook.md` で Project を作る。`open` は、ひな形を作ったあとに、この `start` を呼ぶ。
  - `start 解決` / `start 改善` と言われたときは、下の「引数つきモード」に従う。引数なしの `start` は、下の手順どおり。
  - 小さな再開では、全項目を聞かず、「`docs/log.md` の Next Actions の先頭でよいか」の1問に縮めてよい（未決: 縮め方は実測で決める）。
  - 再開は、前の会話を `--resume` で続けず、新しい会話で `docs/log.md` から始める（`wrap` が出す依頼文を貼る）。履歴は毎ターン再送されるため。

## 場所と書き込みの制約

- このフック自身の書き込みは、呼び出し元の `events` の行だけ（あるときだけ。手順「記録する」）。
- 作業での変更は、要約で合意した「触ってよい範囲」に従う（下の「共通の項目」）。

## 手順

1. **事前確認**（質問の前に、AI が行う）: 対象の `docs/log.md` の Next Actions と Open Questions、README の完了条件と範囲外を読む。環境で確認できる前提（コンパイラの有無など）は、実際に確認する。利用者の前提（専門領域・経験）が、記憶にあるか確かめる。前回の `review` の日付（呼び出し元の見直し記録の最終行）から7日を超えていたら、一度だけ「見直しをしますか」と提案する。Next Actions と Open Questions の合計が10件を超えていたら、あわせて一度だけ「`review 消化` をしますか」と提案する（実行は言われたときだけ）。呼び出し元の `docs/log.md` に期日つきの項目があり、期日を過ぎていれば、最初に知らせて判断を求める。
2. **モードを決める**: 1問で、ゴールを先に決めるか（確定型）、仮ゴールで走るか（探索型）を聞く。Recommended は、成果物の合否を事前に書けるか（仕様、規格、数値）で決める。書けるなら確定型、出してみないと評価が決まらないもの（設計案、文書の骨子、運用の形）なら探索型。ユーザーがモードや型を先に言っていれば、聞かずに宣言する（根拠: exmem の `lessons/session-goal-modes.md`）。確定型は、次の手順「項目を埋める」を共通の項目すべてで行う。探索型は、仮のゴールと「ゴールを変える条件」だけを聞き、残りの共通の項目は、答えが定まるものを宣言して省く。
3. **項目を埋める**: 下の共通の項目と、作業の種類の差分の項目について、答えが1つに定まるものは質問せず、要約に宣言する。残りを、選択式（既定値に Recommended）で聞く。**質問のまとまりの最後に、「ほかに前提はありますか」の自由記述を1つ置く**（選択肢の外の前提を拾う）。
4. **要約を返す**: 「今日のゴール」を、項目ごとに返す。反対があるときだけ、ユーザーが直す。
5. **記録する**: 呼び出し元に `events` があるときだけ、質問ごとに1行（`kind=interview`）を、回答を受けた同じターンで足す（書式は、呼び出し元の記録の定義に従う）。探索型でゴールが変わったら、`kind=goal_change` の行を足す。
6. **作業する**。探索型でゴールが変わったら、変更の理由と新しいゴールを `docs/log.md` に1行足し、変更を1回と数える。全体（最初のゴールを含む）が4回を超えたら、「未決」として、残った論点を `docs/log.md` に書き、ユーザーに決めを求める。
7. **`wrap` で**: ゴールの達成度を `docs/log.md` に書く。

## 報告の型

1. **今日のゴール**: 要約（手順「要約を返す」）を、項目ごとに返す。宣言した項目（答えが1つに定まったもの）と、聞いた項目を分ける。探索型では、仮ゴールと「ゴールを変える条件」を返し、モード（確定型か探索型か）を明記する。
2. **改善案**（あったときだけ）: `hook-common.md` の「改善」に従う。

## 引数つきモード

`start 解決`（別名「解決で始めて」）と `start 改善`（「改善で始めて」）は、インタビューの代わりに、進め方（exmem の `lessons/`）を選んで始める。試験運用（実測してから、インタビューとの関係を決める）。

1. 手順「事前確認」を行う（`log.md` の読み込み、期日、`review` と `review 消化` の提案）。
2. ゴールを1文で聞く（Next Actions の候補つき）。「触ってよい範囲」は既定（この Project の中だけ）を宣言し、広げる必要があるときだけ聞く。
3. やり方を1問で選ばせる。Recommended は、ゴールの性質で決める。
   - 解決: `problem-solving-analogy`（一般化して類似問題の解き方を借りる）、`problem-solving-iterative-revision`（前提を書き戻して決定に差し戻す反復）。
   - 改善: `improvement-quantified-options`（現状を数値にして選択肢を比べる）、`improvement-expectation-gap`（想定と実際のズレを仮説にする）、`improvement-coverage-matrix`（観点を絞り、星取り表から案を出す）。
4. 選んだ lesson を読み、その手順で作業する。要約は、ゴール・やり方・触ってよい範囲の3点を返す。
5. 手順「記録する」と、`wrap` での突き合わせは、通常の `start` と同じ。

## 共通の項目

| 項目 | 内容 | 省略してよい条件（宣言だけにする） |
|---|---|---|
| ゴール | このセッションで到達したい状態（1文） | 省略しない（候補は Next Actions から出す） |
| 前提・制約 | 環境、期限、使える道具 | 環境の確認で1つに定まるとき |
| 対象と資料 | 対象の Project・Area と、読む資料 | 進行中の Project が1つだけのとき |
| 触ってよい範囲 | リポジトリ・ディレクトリ単位の許可（この Project、dotfiles、kit、`resources/` など）。変更の可否と、変更前に確認が要るもの | 既定（この Project の中だけ）で足りるとき |
| やらないこと | 範囲外にする作業（機能、方式） | 「特になし」を既定にして、範囲外は README を守る |
| 完了の判断 | 何が出たらこのセッションを終えるか | ゴールの文に含まれるとき |

「触ってよい範囲」と「やらないこと」は分ける。やらないことの選択肢に、リポジトリの変更の許可を混ぜると、ユーザーに直される。

## 利用者の前提

専門領域・経験・立場は、記憶に残し、毎回は聞かない。記憶に無い、または不足しているときだけ、最初に1度聞く。理由: 専門領域が聞かれず、設計の前提が後から出た実例がある。

## 作業の種類の差分

前提として後から出た（漏れ）項目を、作業の種類ごとに足している。いずれも、実測が少ない。種類は、Project の README の `type`（`doc` `dev` `research`。構造は `open-hook.md` の「Project の構造」）に対応する。

### 開発（設計・実装・評価）

実装の**前に**聞く。

| 項目 | 内容 |
|---|---|
| 設計の優先順位 | 安全性・速度・フットプリント・可読性などの順。AI の推奨が、ユーザーの優先と逆になった実例がある |
| コーディングルールとチェックの有無 | 書式、制約（変数、再帰、動的確保、ポインタ操作など）、機械チェックと linter の有無、導入してよい道具、準拠する規格（MISRA など）の要否 |
| 対象環境 | ターゲット（コア、ワード幅）、ツールチェーン。環境の確認で分かる部分は聞かない |
| 最適化の軸と、測る対象の操作 | 「チューニング」「最適化」「短縮」などの語が出たら、軸（速度・サイズ・消費電力など）と、測る操作（確保、解放、初期化など）を、測る前に確認する。ハードウェアの条件（例: 乗算のサイクル数）も、結果が変わるものは聞く。曖昧な語を、確認せずにサイズの削減と解釈して、見積もりを取り違えた実例がある |

### 文書作成（仕様・設計・手順書・調査）

| 項目 | 内容 |
|---|---|
| ゲート承認の判断基準 | レビュー版を承認する前に、合否の項目（チェックリスト）を決め、レビュー版に付ける。完了条件のチェックリストを、ゲートの合否の項目に直す |
| 骨子のすり合わせ | 初稿の前に、骨子（構成・ストーリーライン。例: 前半は概要の箇条書きとフローチャート、後半は詳細手順）をすり合わせる |
| 図の要否と水準 | 図（mermaid 程度など）の要否と水準を、「範囲外」の語から推測せず確認する |

調査など、ほかの種類は未設計（実測がたまってから。例: 調査なら「結論の用途」）。

## 未決

- 作業の種類ごとの定型の設計。共通の項目と、種類ごとの差分に分ける（抽象化・継承）。
- 小さな再開での縮約の形。
- モードの目安（成果物の合否を事前に書けるか）が、実例に合うか。探索型の回数の上限（全体4回）は、実測で決めた数字ではない。型を指定して始める方法の比較（`typed`）は、実測してから決める。
- 「ほかに前提はありますか」の効果（補足・漏れが減るか）の測定。
