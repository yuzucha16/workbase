# integrate フック（別名「inboxを整理して」）

呼び出し名は integrate。別名は「inboxを整理して」。呼び出し表の正本は `hooks.md`。以下の「inboxを整理して」は、integrate と読み替える。

## 目的と契機

- **目的**: `exmem/inbox/` のメモを `exmem/lessons/` に統合するためのフック。
- **契機**: ユーザーが「inboxを整理して」と言ったときだけ実行する（自発的には実行しない）。exmem 側の作業で、ソース側の `wrap` とは独立している。未統合のメモが 5 件以上たまったら、`review` の警告の目安として、このフックを勧める。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」に従う（部屋での扱いは `room-context.md`）。
- exmem の場所は `hooks.md` の「exmem の場所」。
- 書き込み先: `exmem/lessons/`、`exmem/exmem-index.md`（索引）、`exmem/tags.md`、統合したメモの削除。作業ディレクトリの `docs/` は書き換えない。
- 既存のファイル: 統合先の `lessons/` は、メモの内容を追記・更新する。統合したメモは削除する。
- コミットと push は `hook-common.md` の「コミットと push」に従う。コミット済みのメモ（使い捨ての環境で作られたもの）は、`git rm` で削除してコミットする。

## 手順

1. **統合する。** 下の「統合の細則」に従う（実物との照合、タグの正規化、統合先の選択、`README.md` の更新、メモの削除）。照合で、実物と食い違ったものは、実物を正として、`Open Questions` に残す。環境変数や WSL への受け渡しなど、起動の経路で結果が変わるものは、エージェント経由の確認だとその旨を書き、ユーザーの通常のターミナルでの確認を `Next Actions` に残す（確定とは言い切らない）。**統合先の Decisions に写す根拠と却下案は、メモ（と元の決定）に書かれたものだけにする。** 却下案が元に無い（「未検討」など）ときは、AI が案を補わず、「却下案: 未検討（<承認の経緯>）」と書く（Decisions は、ユーザーが明示または承認したものだけ。補った却下案は、ユーザーが選んでいない案を、決定の記録に混ぜる）。
2. **メモと統合先の照合を、報告に載せる。** 統合したメモごとに、メモと統合先（`lessons/` の該当箇所）を比べ、次の2つを挙げる。見出しの一致だけで済ませない。混入と欠落は、報告の前に、統合先を直す。
   - **メモに無い記述**（統合先に混ざった、AI が補った記述。却下案など）。
   - **メモから落ちた記述**（根拠、却下案、確認の日付と根拠）。
3. **コミットする（統合・メモの削除を1コミットにする）。** 統合先の `lessons/`、`README.md`（索引）などの変更と、コミット済みのメモの `git rm` を、1回のコミットにする（途中までの状態が push されないようにする）。コミットと push は `hook-common.md` の「コミットと push」に従う。`exmem/inbox/` の未追跡のメモは、ファイルを削除する（コミットの対象外）。
4. **報告する**（下の「報告の型」）。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」。ユーザーに求めること、コミットを先に、次にやることを最後に）を報告する。このフックでの追記:

- **ユーザーに求めること**: 食い違いの判断、ユーザーのターミナルでの確認（`Next Actions` に残したもの）。

続けて、固有の項目を次の順で報告する。

1. **統合**: 統合したメモと、統合先のファイル。新規に作ったファイル。
2. **食い違い**: 実物と食い違ったもの（`Open Questions` に残したもの）。
3. **照合**: メモごとの「メモに無い記述」「メモから落ちた記述」と、直したもの。

## 統合の細則

1. inbox のメモから Principles / Decisions / Gotchas / 事実 / Open Questions を抜き出す。
2. **実物と照合する。** メモの内容は会話から生まれたもので、実物と食い違うことがある。設定ファイル・コード・コマンド出力など確認できるものは実際に見て、一致すれば「確認済み」、食い違えば実物を正として記録し、食い違いを `Open Questions` に残す。確認できないものは仮説として書く。
3. **基準が古いメモ（`base_stale`）の扱い。** 部屋（AI 作業部屋）から運ばれたメモには、frontmatter に `base_commit`（書いた時点の workbase のコミット）と `observed`（観測した日）が付く。`base_stale` が付いたメモは、統合先の `lessons/` が基準以降に変わっている。`base_commit` の版（`git show <base_commit>:<パス>`）・メモ・最新の版の3点で比べ、メモの内容が最新の版と食い違うときは、最新の版を正として統合せず、食い違いを統合先の `Open Questions` に書く。食い違いが無ければ、そのまま統合してよい。複数のメモを並べるときは、到着順でなく `observed` の順にする。印が無いメモは、今までどおり統合する。（経緯は `room/README.md` の `stock`）
4. タグを `tags.md` の語彙に正規化する。
5. 該当する `lessons/*.md` に統合する。該当がなければ新しいファイルを作る。
6. 統合先の `lessons/` のノートの `Open Questions` / `Next Actions` を更新する（未完の項目の置き場）。
7. 新しいファイルを作ったら `exmem-index.md` に1行足す。
8. 統合したメモを inbox から削除する。削除の前に、上の「手順」の「メモと統合先の照合」を行う。

### `kind: explain` のメモ（理解ガイド）

frontmatter の `kind` が `explain` のメモは、上の統合の細則のうち次を読み替える。`kind` が無い、または `lesson` のメモは、上のとおり。

- **書き込み先**: `guides/explain/<name>.md` の**新規作成**と、`guides/guides-index.md` への1行（更新の規則は索引の末尾）。既存の `guides/explain/` への追記・上書きは行わない（同じテーマがあれば、統合せず、報告で食い違いとして挙げる）。権限は変わらない（`exmem/` 側の作業）。
- **変換**: frontmatter を `type: explain`、`title`、`tags` にする（`kind`、`created`、`sources` は外す。`checked` は調査の成果物だけ）。`tags` は `exmem/tags.md` の語彙に正規化する（無ければ先に追記）。本文は6見出しのまま使い、「冒頭」の末尾の「統合先の候補」の行は外す。
- **ファイル名**: リポジトリ内で一意にする（`exmem/lessons/` と重ならない。`guides/AGENTS.md`）。
- **照合**: 実物との照合と、手順「メモと統合先の照合を、報告に載せる」は同じ。基準が古いメモ（`base_stale`）の扱いは、新規作成なので該当しない。
