# 計画のやり方（`start 計画` の手順と欄の定義）

`start-hook.md` の「`start 計画`」から呼ぶ。やり方の位置付けは `methods.md` の「計画」、背景と注意点は exmem の `lessons/planning-method.md`。試験運用で、**Must だけ守る**。欄の名前は、書籍の図表の読み取りで、本文は未読（出どころは lesson の Facts）。

## A 事前の仕込み

- ユーザーが「〜したい」の1文と、任意の「条件:」1行を書く。AI が6Rの残りの欄を書く。
- 6R の欄（項目名）は6つ。順に、状況、問題意識、要求、意図・裏づけ・仮説、今回のスコープ、期待する成果。前半3つが状況の整理（状況 → 問題意識 → 要求）、後半3つが Reason（なぜ）・Range of Work（今回何をするか）・Result（どんな成果か）に答える。
- 各欄は、見出し1文と箇条書き3つまで。〔資料〕〔推測〕のタグを文に残す。読みが割れるときだけ、前提の表で読み（A〜C）を出し、ユーザーが選ぶ。
- 状況と問題意識が同じ内容になるときは、1欄にまとめてよい（試行で3項目とも重なった）。仮説は独立した欄にせず、「使ってみて確かめること」として裏づけに書く。
- 要求の欄に、見る単位（期間・セッション・プロジェクトなど）と統計量があれば書く。用語（「作業当たり」「傾向」など）は、単位を定義する。
- 今回のスコープの見出しか条件の行に、期日を書く（無ければ予算の1週間から出す）。対象外には、理由と見直す条件を添える。前提・注意に、実データ・出力の置き場と、機微の有無を書く。承認が要る変更先（例: `workflow-kit/` はユーザーの承認なしに書き換えない）があれば、ここに書く。
- 期待する成果は、題材の成果だけにする（試行の評価は別に書く）。数えられる指標を1つ書く（的外れなら「指標なし」も可）。未決には「何を見れば決まるか」を添える（最初の調べ物になる）。
- 裏づけ（未確認。最初に確かめる）は、確かめた結果と見つけた落とし穴を書き戻す。既存ツールがあるときは、前提の表に、その役割（本体・突合先・使わない）を分けて出す。
- 既定値（6R の欄にしない）: 予算（時間）は1週間。稼働日は平日のみ。バッファは土日2日を最後にまとめて置く。体制はオーナー ユーザー、メンバー ユーザーと AI、リーダーはユーザー兼任。
- AI が1セッションで作る小さな題材では、日数の見積もりが桁で外れた。予算は日数より、ユーザーの判断が要る回数とセッション数で書いてよい。
- 聞くのは、依頼から決まらないものだけ（選択式。最後に「ほかに前提はありますか」の自由記述）。

## B プロセス

1. **6R を作る**。ここで止まってよい（小さな再開では6Rだけ）。
2. **憲章を作る**。欄は、名前、更新日、使命（What）、ビジネスの目的（Why）、目標（完了時期・予算・品質・指標）、メンバー、リーダー、オーナー、必要なマイルストーン（主要3つまで）。全員がユーザーの1人の題材では、メンバー・リーダー・オーナーの欄と、マイルストーンの表と重なる必要なマイルストーンの欄は省いてよい。対象外・前提・リスク・未決は、出力に載せず6Rに残す。
3. **成果物 WBS を作る**。成果物（名詞）で分解する。親は子の足し算で、モレもダブりも無い（100%ルール）。「プロジェクトマネジメント」のまとまり（憲章・WBS・マイルストーン・課題ログ・使い心地の記録）も置く。止まらなければ空になる成果物は、名前に「（条件付き）」を付ける。葉は1ファイルに対応させ、各葉に置き場を書く（ファイルにならない確認メモなどは親の葉にまとめる）。「動作確認」（テスト、見た目の確認）の葉を、検証とは別に置く。要求が実行中に変わるので、WBS に「変更の記録」（日付・追加した葉・理由）を1行ずつ足す場所を置く。
4. **マイルストーンを作る**。置く基準は4つ（フェーズの開始・完了、成果物の作成完了、外部やオーナーとのレビュー、プロジェクト外のイベント）。期間は1・2・4週から選び、上限は3・5・9。開始の承認と終了の判断は数えない。ゴールから逆算して間隔を見る。
5. **出力と作り方のメモを、別ファイルにする**。出力は憲章・WBS・マイルストーンの Markdown だけ。作り方のメモは、迷った点・決めたこと・本との違いを書く。

## 置き場

題材が入る領域で決める（公開してよい中身か、進行中の下書きか承認済みの基準か）。

| 領域 | 置き場 |
|---|---|
| workbase（kit、exmem、guides） | **未決**。トピックを明示する経路が無く、`planning-method` は試行で作ったトピック。昇格するまでは**ユーザーに聞く**。`kit-growth/records/` は「測ったこと」だけの置き場（2026-10-20 の決定）なので、既定にしない |
| works（Project、Area） | AI が Project の `ai/work/` で下書きし、ユーザーが承認したものを人が同じ Project の `ai/in/` に置く（基準文書を次の Project に渡す型と同じ。部屋の AI は読むだけ）。Area の README には、最新の Project を1行書く |
| dotfiles | dotfiles 自身の `docs/` で完結させる（依存は dotfiles → workbase の一方向）。workbase に影響するときだけ、名前で指す1行を workbase 側に書く |
| room（道具の開発） | workbase の題材と同じ（道具のコードは `workflow-kit/room/`） |
| room の中（業務） | 部屋の `ai/work/` → `ai/in/`。マスク後の語だけで書く |

実務の中身は workbase に入れない。

- 聞けないとき（呼び出し元が置き場を指定していない）は、会話の中に出し、判断の記録に書く。

## Want（叩き台。1事例からの仮説）

WBS から憲章への逆向きの確認、計画と実績の日付、課題ログ、動的な確認、「検査を見せて」の運用。
