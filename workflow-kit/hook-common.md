# フック共通の規則

全フック（`*-hook.md`）に共通する規則の正本。各フックには書き写さず、ここを指す。章立ての共通部（`場所と書き込みの制約` → `手順` → `報告の型` → `このフックの改善`）と、以下の規則は、`tools/check-hook-outline.ps1` が点検する。

## 冒頭の定型

各フックの先頭（最初の H2 の前）に置く。

- 呼び出し名と別名。**呼び出し表の正本は `hooks.md`**（フックの側に表の写しを作らない）。
- ユーザーが言ったときだけ実行する（自発的には実行しない）。例外（`open` を `start` が案内する、`close` を AI が提案する、`review` を勧めるなど）は、そのフックに書く。
- 試験運用のフックだけ、`状態: **試験運用**` の行を置く。`hooks.md` の「読むファイル」列の（試験運用）と一致させる。

## 改善

各フックの `このフックの改善` の章と、報告の型の末尾の「改善案」は、次の流れに従う。章には、そのフック固有の確認項目だけを書く。

1. **提案**: 実行後に、手順で曖昧だった点・迷った点があれば、1〜3点を `場所 / 問題 / 案` の形で提案する。迷った点があったときだけ出す。無ければ、報告の「改善案」は書かない（`stock` と `init` は「改善案なし」と書く）。
2. **承認と修正**: ユーザーが承認したら、kit の該当ファイル（`tools/` を含む）を直し、`improvements.md` に1行足す（却下も理由つきで残す）。理由はコミットメッセージにも書く。呼び出し元の `AGENTS.md` にコピーを作らない。
3. **記録**: 呼び出し元に `events` があれば、改善案を1案1行で記録する（`kind=improvement`。提案の直後に行を足し、承認・却下・修正を受けた同じターンで埋める。列と定義は、呼び出し元の記録の定義）。`fix` と `reversed` を重視し、採用率は見ない。

## 承認

**ユーザーの承認なしに、kit（`tools/` を含む）を書き換えない。** 試験運用のフックも同じ。例外は `wrap-hook.md` の「自動採用の規則」の節の項目だけ（範囲と手順は同ファイルの「自動採用の範囲」。安全規則は対象外）。`review` は、週1回のその場の承認が、改善案の個別の承認に代わる（`review-hook.md`）。

## フックを足す・消すとき

1. `hooks.md` の呼び出し表に行を足す・消す（試験運用なら（試験運用）を付ける）。
2. `README.md` のファイル表の行と、連鎖・体系の記述を合わせる。
3. 冒頭の定型と、共通の4章を置く（足すとき）。参照している手順書（`wrap-hook.md` の自動採用の範囲、`init-hook.md` の導入項目の一覧、`templates/` の `AGENTS.md` など）を `grep` で探して合わせる（消すとき）。
4. `improvements.md` に1行足す。
5. `pwsh -NoProfile -File tools/check-hook-outline.ps1` を実行する。1〜3 のうち、表の過不足、章立て、冒頭の定型は、ここで漏れが分かる。
