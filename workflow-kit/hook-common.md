# フック共通の規則

全フック（`*-hook.md`）に共通する規則の正本。各フックには書き写さず、ここを指す。章立ての共通部（`目的と契機` → `場所と書き込みの制約` → `手順` → `報告の型`）と、以下の規則は、`tools/check-hook-outline.ps1` が点検する。

## 冒頭の定型

各フックの先頭（最初の H2 の前）に置く。

- 呼び出し名と別名。**呼び出し表の正本は `hooks.md`**（フックの側に表の写しを作らない）。
- ユーザーが言ったときだけ実行する（自発的には実行しない）。例外（`review` を勧めるなど）は、そのフックに書く。

## 目的と契機

最初の共通章。次の3項目を、この順で書く。既存の文を移すだけで、書かれていないことは書かない（該当が無い項目は、置かない）。項目の順（目的 → 契機 → 前提）は点検スクリプトが見る。

- **目的**: このフックが何のためにあるか（3文まで）。運用の方針（出力を固定してある、見本に合わせる）や経緯は、目的に書かず、`手順` の冒頭に書く。
- **契機**: いつ実行するか（誰が言う、いつ提案・案内する、頻度）。
- **前提**: 動くために必要な状態（例: works がある）。

## 章の並び

共通4章（`目的と契機` → `場所と書き込みの制約` → `手順` → `報告の型`）を、この順で、先に置く。**固有の章は、`報告の型` より後ろに置く。** 例外は `入力`（手順の入力。制約と手順の間）。固有の章のうち、「改善」の固有の確認項目を書く `このフックの改善` の章は、あるフックだけが持ち、固有の章の先頭に置く（次の「改善」）。

## 見出し

H2 の見出しは名前だけにする（括弧の注記を付けない）。日付、決定者、出典、状態は、本文の1行目に書く。見出しの名前で他から参照するため。H3 の括弧は、範囲を示す名前の一部なので許す。

## 報告の型

報告は、共通の項目（前半）と、そのフック固有の項目（後半）で構成する（2026-10-17 ユーザーの決定）。

**共通の項目**は3つ。1と2を報告の最初に、3を最後に置く（2026-10-17 ユーザーの決定）。どのフックの報告にも置き、書くことが無いときは「なし」と書き、項目ごと省かない（報告を読む人が、項目の有無で探さなくて済むため）。共通の項目の中身は、ここだけに書く。各フックは、この節を指し、そのフックでの追記だけを書く。

1. **ユーザーに求めること**: 承認、確認、手作業、質問の答え、反対の有無。1つずつ、何をすればよいかが分かる形で挙げる。無ければ「なし」。先頭に置くのは、読む人が最初に動けるようにするため。
2. **コミット**: `docs-rules.md` の「コミットと push」の「報告」と「push」に従う。ハッシュと内容、含めなかったファイル、push の結果（push したコミットの範囲、または止まった理由。公開範囲を確かめたときはそれも）。許可リストに無いリポジトリは、push のコマンドを書く（実行しない）。コミットしなかったときは「なし」と理由。

3. **次にやること**（最後の項目）: 次の一手を1行（そのフックに続くフック、または `docs/log.md` の Next Actions の先頭。無ければ「なし」）。続けるか切るかの推奨を、理由つきで1行。切るときだけ、新しい会話に貼る「<作業した単位> の続き」を1行（状態は単位の窓口と `docs/log.md` が持つので、長い依頼文は書かない）。報告を読んだ人が、次に何をするかで迷わないための項目。
   - **続ける**: 同じ単位で話題が同じ、直前の応答からの間がキャッシュの保持時間（TTL。サブスクは1時間、API キーは5分）以内、会話が約10万トークン未満。理由: キャッシュが効いている間は、毎ターン再送される履歴の単価が通常の約1/20。
   - **切る**: 話題が変わった、TTL を超えて間があいた、会話が約10万トークン以上、利用上限が近い。理由: キャッシュが切れると全履歴が割高で書き直され、長い会話ほど1ターンの入力が増える（書き直す量は、会話の大きさ H と新しい会話の土台 B の差 H − B）。例外: 会話が約2万トークン未満なら、間があいても続けてよい（切っても読み直しが同じ量になる）。
   - 間があいた古い会話を `--resume` で続けない（キャッシュが切れているため）。
   - 数値は暫定（2026-10-17。根拠は `exmem/lessons/session-handoff.md` の Decisions）。TTL は環境で違い（2026-10-18 に「間」を TTL 基準に直した）、AI は命中率もトークン数も正確には測れない。間の長さが分からないとき、トークン数が概算のときは、概算で推奨する。

**固有の項目**は、共通の項目1〜2の後、3の前に置く。番号つきのリストにし、各項目を太字のラベルで始める。番号は連番にする。リストの前に、共通の項目を指す1文と、そのフックでの追記（箇条書き。あるものだけ）を置く。**改善案は報告に載せない**（次の「改善」）。形式（番号、ラベル、改善案を載せないこと、共通の項目を指していること）は、点検スクリプトが見る。

## 手順の参照

手順を指すときは、番号でなく、手順の太字の見出しの名前で書く（例: 手順「記録する」）。手順を足す・消す・入れ替えても、参照が壊れないようにするため。名前は見出しの先頭と一致させる。番号参照が無いことと、名前が同じファイルの手順に実在することは、点検スクリプトが見る。他のファイル（README、`tools/` など）から指すときは、フックのファイル名を添えて `stock-hook.md` の手順「…」の形で書く（ファイル名が無い、または手順が無いと、点検スクリプトが検出する）。この表の「手順」列も、行のフックの手順を指す。

## 改善

**改善案は、報告に載せない**（2026-10-17 ユーザーの決定。報告を短く、セッションを短くするため）。迷った点は、次の流れで `docs/log.md` の Open Questions に残す。そのフック固有の確認項目（誤検知を見るなど）がある場合だけ、`このフックの改善` の章を置き、固有の確認項目だけを書く（章の先頭で、この節を指す）。

1. **残す**: 実行後に、手順で曖昧だった点・迷った点があれば、1〜3点を `場所 / 問題 / 案` の1行ずつにして、Open Questions に足す。迷った点があったときだけ足す。足す先は `wrap` と同じ（`wrap-hook.md` の手順「対象を特定する」）。この1行の追記は、各フックの「場所と書き込みの制約」にかかわらず許す（領域をまたぐ書き込みの型2。`hooks.md`）。ユーザーには、その場で聞かない。
2. **承認と修正**: Open Questions の行は、ユーザーが `review 消化` などで承認したら、kit の該当ファイル（`tools/` を含む）を直し、改善の受け皿（`docs/decisions.md`。無ければ記録しない）に1行足す（却下も理由つきで残す）。`improvements.md` は 2026-10-15 に凍結した（追記しない）。理由はコミットメッセージにも書く。呼び出し元の `AGENTS.md` にコピーを作らない。
3. **記録**: 改善案を記録するかは、呼び出し元の定義に従う（`hooks.md` の「任意の記録」。定められていなければ記録しない）。

## 承認

**ユーザーの承認なしに、kit（`tools/` を含む）を書き換えない。** 例外は無い（`wrap-hook.md` の自動採用の仕組みは、2026-10-15 に畳んだ）。`review` は、週1回のその場の承認が、改善案の個別の承認に代わる（`review-hook.md`）。

**仕組みの決定は、作業中に承認を求めない**（2026-10-18 ユーザーの決定）。kit・規則の決定は、`docs/log.md` の Open Questions に置き、`review 消化` で、待ち行列 → サブエージェントのスクリーニング → ユーザーの最終判断の3段で承認する。置いたセッションの消化では判断しない（頭を冷やす）。作業を止められない決定だけ、仮決めにする。手順、型、出力の形、仮決めの期限は `approval-screening.md`。

**承認を求めるときの添え書き**（2026-10-19。補正策の正本は `exmem/lessons/user-manual.md`）: 「効果の測り方・期日・戻し方」を1行ずつ付け、1回に求める件数を絞る。構造に効く決定では、推奨案の最大の弱点を1行添える。戻せない決定では、推奨を伏せてユーザーの選択を聞いてから照らす。

## コミットと push

コミットするフック（`wrap` `integrate` `review` など）の、コミットと push の書き方の正本（2026-10-18。各フックにあった同じ文を集めた）。各フックは、この節を指し、そのフック固有の追記だけを書く。

- `docs-rules.md` は「コミットと push」の節だけを読む（見出しの一覧で位置を見る。全文は読まない）。範囲、ステージの行数の確認、agent の身元とトレーラーは、その節に従う。
- コミットの後、そのリポジトリが呼び出し元の許可リストにあれば push する。同節の「push」の条件を、毎回確認する。1つでも満たさなければ push せず、理由を報告する。許可リストに無いリポジトリは、push のコマンドを報告に書く（実行しない）。
- 使い捨ての環境（クラウドのセッションなど）は、同節の「使い捨ての環境での緩和」に従う。部屋（AI 作業部屋）の中では、コミットと push は人が行う（`room-context.md`）。
- 報告の書き方は、「報告の型」の共通の項目2。

## 他のフックを勧める条件

あるフックが別のフックを勧めてよい条件の一覧（2026-10-18。数値の正本はここ。各フックは、この表を指す）。勧めるだけで、実行は言われたときだけ。

| 勧める側 | 勧める先 | 条件 | 回数 |
|---|---|---|---|
| `start`（`start-hook.md` の手順「事前確認」） | `review` | 前回の `review` から7日以上（前回の日付は、`[review]` で始まる最後のコミット。取り方は `review-hook.md` の手順「コミットする」） | 一度だけ |
| `start`（`start-hook.md` の手順「事前確認」） | `review 消化` | Next Actions と Open Questions の合計が10件を超える | 一度だけ |
| `wrap`（報告の「ユーザーに求めること」） | `review` | 同上（7日以上） | 報告のたびに、条件を満たすとき |
| `review`（入力 3 の警告の目安） | `integrate` | `exmem/inbox/` の未統合メモが5件以上 | 報告のたびに、条件を満たすとき |

## 記録

フックが書く「任意の記録」（`events` `sessions` `reviews`。名前と契約は `hooks.md`）の一覧。保存先と列は、呼び出し元が定める。定められていなければ記録しない（存在を確かめてから書く）。詳細（時機、種別）は、各フックの手順に書く。ここは、どのフックが何を書くかの索引で、フックを足す・消すときの更新先。

| フック | 書く記録 | 手順 |
|---|---|---|
| `start` | `events`: 質問ごとの行（`kind=interview`）、探索型でゴールが変わったとき（`kind=goal_change`） | 手順「記録する」 |
| `wrap` | なし | |
| `stock` | なし | |
| `integrate` | なし | |
| `review` | `reviews`: 1回につき1行。入力として `events` と `sessions` を読む | 手順「指標を足す」 |

## フックを足す・消すとき

1. `hooks.md` の呼び出し表に行を足す・消す。
2. `README.md` のファイル表の行と、連鎖・体系の記述を合わせる。
3. 冒頭の定型と、共通の4章を置く（足すとき）。参照している手順書（`templates/` の `AGENTS.md` など）を `grep` で探して合わせる（消すとき）。
4. 上の「記録」の表に行を足す・消す。
5. `hook-matrix.md` の列（フック名）と、各行の値、字数を更新する。章や方針を変えたときも同じ。
6. 改善の受け皿（`docs/decisions.md`）に1行足す（`improvements.md` は凍結）。
7. `pwsh -NoProfile -File tools/check-hook-outline.ps1`（`pwsh` が無い環境は `python tools/check_hook_outline.py`）を実行する。1〜4 のうち、表の過不足、章立て、冒頭の定型、記録の表の行、`hook-matrix.md` の列は、ここで漏れが分かる。
