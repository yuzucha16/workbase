# review フック（別名「見直して」）

呼び出し名は review（週1回・15分の目途）。別名は「見直して」。呼び出し表の正本は `hooks.md`。

## 目的と契機

- **目的**: 仕組みが、ユーザーの負担（言い直し・聞き直し・遠回り）を減らしているかを、事例で見て、**1つ直すか、1つ畳む**。率でなく、件数と事例で判断する（母数が小さいうちは）。
- **契機**: ユーザーが「review」「見直して」と言ったときに実行する。週1回の目途を過ぎていれば、`start` と `wrap` の報告で、一度だけ勧めてよい（自発的には実行しない）。「review 消化」「next action を消化して」と言われたときは、下の「消化モード」だけを行う（上の入力・手順は行わない）。`start` は、Next Actions と Open Questions の合計が10件を超えるとき、一度だけ勧めてよい。

## 場所と書き込みの制約

- 書き込み先: 呼び出し元の記録先（`reviews`）と、直す・畳むと決めたファイル。手順書・規則を直す・畳む案は、**ユーザーにその場で示し、承認を得てから**行う（週1回のこの承認が、改善案の個別の承認に代わる）。
- コミットは `docs-rules.md` の「コミットと push」に従う。push も同じ（許可リストにあるリポジトリだけ）。

## 入力

呼び出し元の記録から集める。無い、または少ないものは、「記録が少ない」と報告し、そのことから結論を出さない。

1. **終了時の1問の回答**（`sessions` の `detour`）。「大きく」「少し」の原因。
2. **開始時の読み込み字数**（呼び出し元が定める計測。増えていないか）。
3. **警告の目安**（目標ではない）: 新しく増えた知識のうち、仕組み自体を扱うものの割合。`exmem/inbox/` の未統合メモの数（5件以上なら `integrate` を勧める）。`decisions.md` で `→` の無い【汎用】項目の件数。
4. **トピックの点検**（呼び出し元に、トピックの置き場がある場合。例: `topics/`）: 30日更新の無いトピック、完了条件を満たしたのに残っているトピック、改善の受け皿（例: `topics/kit-growth/inbox.md`）の未選別の件数。1行ずつ挙げ、畳むか動かすかをユーザーに聞く（置き場が無ければ飛ばす）。
5. **重い会話**（呼び出し元に、会話履歴の集計がある場合。例: 1回の入力の最大トークン）: 大きい会話を上位1〜2件挙げ、切るべきだった区切り（話題の変わり目、`wrap` の後も同じ会話で続けた）があったかを見る。集計が無ければ飛ばす。
6. **機密の点検**（2026-10-16 に、`docs-rules.md` の「機密は書かない」の項を畳んで移した）: 呼び出し元のリポジトリの追跡ファイルを、`git grep -n -i -E 'token|secret|password|bearer|webhook'` と、URL 中の長い ID で検索する。ヒットは1行ずつ挙げ、機密かどうかをユーザーに聞く（説明文の語は除く）。機密なら、書き直しと履歴の扱いを案にする。
7. **トークン消費の自己採点**: `token-matrix.md` の星取り表（切る・絞る・予算・外部化）を、表の「採点のしかた」で採点し直す。前回の点（`reviews` の前回の行。無ければ表の「点の履歴」の最終行）より、どれかの列が下がったら、見直しの対象にする。
8. **リポジトリ間の整合**（同じ規則で運用する複数のリポジトリがあるとき。例: ワークスペース、共有リポジトリ、設定のリポジトリ。無ければ飛ばす。2026-10-16 に追加）: 呼び出し元の**基準**（保存先は呼び出し元の `AGENTS.md` が定める）にある2つの表を、今の状態と比べる。基準が無ければ、初回として表を作り、基準にする。
   - **現状**: 行を項目（共通ルールのポインタ、読む順番、窓口、`docs/log.md` の大きさ、コミット・push の規則、公開範囲、旧名・旧パスの参照、無いファイルなど）、列をリポジトリにした表。各行を今の状態と比べ、**基準と違う行だけ**を「見直し」として挙げる。
   - **ギャップ**: 食い違いを1行ずつ挙げた表。各行の状態（解消、残す、未着手）を今と比べ、違う行を見直しに挙げる。新しい食い違いは行を足す。影響（直したときに及ぶ範囲）とリスク（直して事故になる確率）を高・中・低で付けて、影響が高くリスクが低いものから並べる。`workflow-kit` が正とは限らない（kit が遅れている場合がある）ので、どちらに揃えるかを明記する。明らかにずれている箇所は、直す前にユーザーに確認する。直すのは、手順「1つ直すか、1つ畳む」の枠に数える。

## 手順

1. **入力を集める**（上の 1〜8）。
2. **事例を見る。** 同じことを言い直した事例があれば、`AGENTS.md` か知識に昇格すべきかを考える。遠回りの原因が、規則の読み落とし、情報の不足、手順の重さのどれかを分ける。
3. **網羅度を確認する。** `hook-matrix.md` を使う。①`pwsh -NoProfile -File <kit>/tools/check-hook-outline.ps1` を実行する（FAIL は Must の違反）。②表の字数の行を、測り直して更新する（測定は表の冒頭）。③区分が Must の行に、— のフックが無いか見る（点検スクリプトが見ない行も含む）。満たさないフックがあれば、直す案を出す。④区分が Want の行は、— のフックについて、足す案を最大1つ出す。案には、重さ（字数の増え方）と複雑性（影響する参照・点検の数）を添える。足さないと判断してよい。字数の目安（5,000 字。例外は表の「肥大化の抑制」）を超えるフックは、畳む案を出す。⑤表の「重さの基準」と比べ、増えたフック（字数 +20%、手順・報告の項目数 +2）を見直しの対象にして、そのフックの星取り表と修正・削除・追加の対応表を作り、ユーザーに示す（作り方は exmem の `lessons/improvement-coverage-matrix.md`。承認制。次の「最大1件」の枠とは別に数える）。Must の違反の修正は、次の「最大1件」の枠とは別に数える（承認制）。Want の案は、枠に数える。
4. **1つ直すか、1つ畳む。** トークン消費の点が下がっていたら、下がった行と理由を挙げ、戻す案を出す（承認制。下の「最大1件」の枠とは別に数える）。それとは別に、最大1件。足すなら、畳むものと対にする（規模の凍結）。ユーザーに示して、承認を得て行う。何も無ければ「今週は無し」と報告する。
5. **コミットする。** workbase で実行したときは、`token-matrix.md` の星取り表と「点の履歴」も更新する。
6. **指標を足す。** 呼び出し元に記録先があれば、`reviews` に1行を足す（足す値は下の「reviews に足す値」。列名と並びは呼び出し元が定める）。
7. **報告する**: 入力の要点、網羅度（Must の違反、Want の案）、直した・畳んだもの（または「今週は無し」）、コミット、警告の目安。

## 報告の型

手順「報告する」のとおり、次を順に報告する。

1. **入力の要点**。入力 8 を行ったときは、基準と違う行（見直し）と、ギャップの表（優先度つき）を添える。見直しの後は、基準を更新する。
2. **網羅度**: Must の違反（無ければ「なし」）、Want の案（あれば1つ。重さと複雑性つき）、重さの基準を超えたフック（無ければ「なし」）。
3. **直した・畳んだもの**（または「今週は無し」）。
4. **コミット**: ハッシュと内容。
5. **警告の目安**。
6. **改善案**（あったときだけ）: `hook-common.md` の「改善」に従う。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」（このフックの手順そのものと安全規則も承認制。上の「場所と書き込みの制約」）。このフックでは、次も確認する。

- 入力が足りたか。足りなければ、何を記録すべきか。
- 15分で終わったか。頻度が合っていたか。

## 消化モード

対象は呼び出し元の `docs/log.md` の Next Actions と Open Questions。並行作業で既に終わった項目が残るので、各項目を次の3つに分けて列挙する。

- 完了している可能性のあるもの
- すぐに完了にできそうなもの（残りの作業と所要を添える）
- それ以外

「それ以外」は、さらに次の2つに分ける。分けておくと、ユーザーの答えが「完了」「やる」の一言で済み、確認の往復が減る。

- 実機・他PC・ユーザーの判断でしか確かめられないもの: 完了かどうかをユーザーに聞く。
- 実機が要らず、いま書き換えられるもの: 承認を得たら、その場で書き換え、コミットまで一度に行う（push は、許可リストのリポジトリで条件を満たすときだけ）。

各項目に根拠を1行付ける（`git log`、実ファイル、`decisions.md` の該当箇所）。推測だけで「完了」としない。`wrap` が足した kit の改善案（`場所 / 問題 / 案` の1行）は、「それ以外」に入れず別に挙げ、承認された案は `hook-common.md` の「改善」の流れで kit を直す。完了の判断はユーザーが行い、承認された項目だけを `log.md` から消す（履歴は `docs-rules.md` に従って `log-history.md` へ）。`reviews` には記録しない。

## reviews に足す値

- 日付と、見直しの識別子。
- 終了時の1問の「大きく」「少し」の件数。
- 開始時の読み込み字数。
- トークン消費の点（4観点と合計）と、採点したコミット。
- 直した・畳んだものの1行（無ければ `none`）。
- メモ。
