# review フック（別名「見直して」。試験運用）

呼び出し名は review（随時。週1回を目途）。別名は「見直して」。名前の体系は README.md の「フックの体系」。ユーザーが「review」「見直して」と言ったときに実行する。週1回の目途を過ぎていれば、`wrap` の報告で、このフックを勧めてよい（自発的には実行しない）。

作業ディレクトリ側（ソース側）のフック。チェック機能は、今後ここに集約していく（2026-10-08 ユーザーの方針）。いま集約したのは、次の A と B の2つ。`wrap` の棚卸し（`check-docs.ps1`）など、ほかのチェックは、そのまま `wrap` に残す（集約は、実測してから1つずつ移す）。

## 場所と書き込みの制約

- 書き込み先: A は `wrap-hook.md` の「自動採用の規則」の節と `improvements.md` と、呼び出し元の記録先（`events` など）。B は呼び出し元の `docs/decisions.md` の `行き先` の行と、`転記済` にする項目の本文。それ以外（`wrap-hook.md` の節の外、ほかのフック、`docs-rules.md`）は、承認なしに書き換えない。
- コミットは `docs-rules.md` の「コミットと push」に従う。push も同じ（許可リストにあるリポジトリだけ）。
- **A で、人の承認なしに削除・復活できるのは、「自動採用の規則」の節の項目だけ。** 安全規則（`wrap-hook.md` の「自動採用の範囲」）と、承認済みの既存の規則は、触らない。見直しで疑わしいと思ったものは、改善案として、ユーザーに出す。

## 手順

1. **プランモードなら先に抜ける**（`stock-hook.md` の手順 1 と同じ）。
2. **A. 自動採用の規則を見直す。** `wrap-hook.md` の「自動採用の規則」の各項目（ID 付き）について、要・不要を判断する。
   - 根拠は、`rule-hits`（その ID が働いた記録）、`events` の `gap`（同種の漏れが出ていないか）、`improvements.md` の見直し日と戻す条件。**根拠が無い判断はしない。** 記録が少なくて判断できないものは、「保留」にして、見直し日を延ばす（延ばせるのは1回まで）。
   - **要**: 残す。見直し日を次回に更新する。
   - **不要**: その場で削除する（`improvements.md` の状態を「削除（見直し）」にし、理由と、戻す条件を残す）。削除の後に同種の `gap` が出たら、復活させる（状態「復活」。`reversed` を記録する）。
   - **保険**（発動が稀だが、外すと被害が大きいもの）: 規則に `保険` の印があれば、頻度では削除しない。「いまも被害が想定できるか」だけで判断し、判断を理由つきで残す。
   - 追加された規則が、既存の規則や、ほかの自動採用の規則と重複・矛盾していないかも確認する。重複していれば、統合または削除する。
3. **B. 転記を一括で確定する（lazy confirm）。** 呼び出し元の `docs/decisions.md` の `転記待ち（→ exmem/inbox/<メモ>、本文ハッシュ <8桁>）` を対象にする。照合（メモと統合先の比較）は、`integrate` の時点で、ユーザーが承認済み。ここでは、機械的な確認だけを行う。
   - 先に、`exmem/` を `git fetch` して、`main` の台帳だけを正とする（古いクローンを読まない）。台帳 `exmem/integrated.md` で、そのメモ名の**有効な行**を引く（同じメモ名の行が複数あるときは、日付が最も新しい行。同じ日付なら下の行）。
   - 台帳に行が無ければ、何もしない（未統合、または捨てられた）。種別が `取消` なら、`転記待ち` のまま、例外として報告する。
   - 種別が `統合` で、照合が `承認済` のとき、次を確認する。**どちらも満たしたものだけ**を `転記済（YYYY-MM-DD → <統合先>）` に進め、本文を外す（見出し・日付・行き先だけにする。`docs-rules.md` の「decisions.md の項目の行き先」）。
     1. 台帳の統合先のファイルが、すべて実在する。
     2. 項目の現在の本文ハッシュ（`tools/item-hash.ps1`）が、`転記待ち` の行に記録された本文ハッシュと一致する（項目が、メモを作った後に改訂・撤回されていない）。
   - 確認 2 が一致しないとき（項目が、メモの後に変わった）は、本文を外さない。台帳に統合の行があるなら、`未仕分け（前回の転記: <統合先>）` に戻し、訂正のメモを作る候補として報告する（共有側に、撤回・改訂前の内容が残っているため）。台帳に行が無ければ、`転記待ち` のままにして、メモを作り直す候補として報告する。
   - **14日を超えた `転記待ち`**（メモ名の先頭の日付から数える）を、毎回、報告に載せる（統合されないまま捨てられたメモの滞留に気づくため）。
   - **例外（ユーザーに聞くもの）**: 種別が `取消` の項目、本文ハッシュが無い項目（2026-10-08 より前の転記や、`pwsh` が無い環境で作ったメモ）、確認 1 を満たさない項目。ほかは、事後の報告だけで足りる。本文ハッシュが無い項目は、従来の方式（`integrate-hook.md` の手順 6〜7）で、ユーザーの承認を得て進める。
   - 隔離ソース（PC1 など、台帳を共有できない環境）は、この手順の対象外。従来どおり、`docs-rules.md` の目視の運搬で行う。
4. **コミットする。** 変更した対象ごとに、`docs-rules.md` に従う（パス指定、ステージの確認、身元とトレーラー）。
5. **指標を足す。** 呼び出し元に記録先があれば、`reviews` に1行を足す（列は下）。
6. **報告する**（下の「報告の型」）。

## reviews の列

`date,review_id,rules_total,rules_kept,rules_deleted,rules_restored,rules_held,delete_rate,recur_rate,rules_chars,ledger_confirmed,ledger_returned,ledger_exception,pending_over14d,note`

- `delete_rate` = `rules_deleted` / `rules_total`。**単独で見ない**（削除率が高いことは、良いことではない。過剰追加と過剰削除の往復でも上がる）。
- `recur_rate` = 前回までに削除した規則のうち、削除後に同種の `gap` が出て復活したものの割合。
- `rules_chars` = 「自動採用の規則」の節の文字数（規則の総量。増え続けていないか）。
- `ledger_confirmed` = B で `転記済` に進め、本文を外した件数、`ledger_returned` = ハッシュの不一致で戻した件数（`未仕分け` に戻した、または `転記待ち` のまま報告した件数）、`ledger_exception` = ユーザーに聞いた件数、`pending_over14d` = 14日を超えた `転記待ち` の件数。
- 3つの組（削除率、再発率、規則の総量）で見る。削除率だけ上がり、再発率も上がるときは、削除が早すぎる。

## 報告の型

1. **A**: 規則の件数（要・不要・保険・保留・復活）。削除した規則と理由。重複・矛盾の指摘。
2. **B**: `転記済` に進めて本文を外した件、ハッシュの不一致で戻した件（訂正メモの候補）、14日を超えた `転記待ち`、例外（ユーザーに聞くもの）。
3. **コミット**: ハッシュと内容、push の結果。
4. **指標**: `reviews` に足した行の要点（削除率、再発率、規則の総量の3つを一緒に）。
5. **改善案**: 下の「このフックの改善」に従う。

## このフックの改善

改善の流れは、`wrap-hook.md` の「このフックの改善」と同じ。ただし、このフックの手順そのものと、安全規則は、自動採用の対象外（承認制）。実行後に、次を確認して報告する。

- A の判断の根拠（`rule-hits` など）が足りたか。足りなければ、何を記録すべきか。
- B の2つの確認（統合先の実在、本文ハッシュ）で、誤って進めた・誤って戻した項目が無かったか。ハッシュが、軽微な編集（整形、追記）でも不一致になりすぎないか。
- 頻度が、規則と転記の量に合っていたか（試験期間 2026-10-08〜10-22 は、3〜4日おきに実行して測る。通常は週1回の目途）。
