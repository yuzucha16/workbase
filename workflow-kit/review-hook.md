# review フック（別名「見直して」）

呼び出し名は review。別名は「見直して」。呼び出し表の正本は `hooks.md`。

## 目的と契機

- **目的**: 仕組みが、ユーザーの負担（言い直し・聞き直し・遠回り）を減らしているかを、事例で見て、**1つ直すか、1つ畳む**。率でなく、件数と事例で判断する（母数が小さいうちは）。
- **契機**: ユーザーが「review」「見直して」と言ったときに実行する。週1回の目途を過ぎていれば、`brief` と `wrap` が勧めてよい（自発的には実行しない。条件は `hook-common.md` の「他のフックを勧める条件」）。`review 消化` を勧める条件も同じ表にある。
- **モード**: `review 消化`（別名「next action を消化して」）と言われたときは、下の「消化モード」だけを行う（上の入力・手順は行わない）。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」に従う（部屋での扱いは `room-context.md`）。
- 書き込み先: 呼び出し元の記録先（`reviews`）と、直す・畳むと決めたファイル。手順書・規則を直す・畳む案は、**ユーザーにその場で示し、承認を得てから**行う（週1回のこの承認が、改善案の個別の承認に代わる）。
- 既存のファイル: `reviews` は追記する。手順書・規則は、承認された箇所だけ直す。
- コミットと push は `hook-common.md` の「コミットと push」に従う。

## 入力

呼び出し元の記録から集める。無い、または少ないものは、「記録が少ない」と報告し、結論を出さない。

1. **遠回りの事例**: ユーザーが `topics/kit-growth/inbox.md` の「未選別」に足した遠回りの行と、各フックが Open Questions に足した改善案の行（`hook-common.md` の「改善」）。原因を見る。
2. **開始時の読み込み字数**（呼び出し元が定める計測。増えていないか）。
3. **警告の目安**（目標ではない）: 新しく増えた知識のうち、仕組み自体を扱うものの割合。`exmem/inbox/` の未統合メモの数（`integrate` を勧める条件は `hook-common.md` の「他のフックを勧める条件」）。`decisions.md` で `→` の無い【汎用】項目の件数。呼び出し元の基準（入力 8）に「点検の対象」の一覧があれば、一覧のリポジトリすべてで数える（起動した単位に `exmem/` が無くても見る）。
5. **重い会話**（呼び出し元に、会話履歴の集計がある場合）: `python -I workflow-kit/tools/heavy_sessions.py --since <前回の見直しの日付> --top 5` で、1回の入力の最大が大きい会話を挙げる。上位1〜2件について、切るべきだった区切り（話題の変わり目、`wrap` の後も同じ会話で続けた）があったかを見る。
5. **重い会話**（呼び出し元に、会話履歴の集計がある場合。例: 1回の入力の最大トークン）: 大きい会話を上位1〜2件挙げ、切るべきだった区切り（話題の変わり目、`wrap` の後も同じ会話で続けた）があったかを見る。集計が無ければ飛ばす。
6. **機密の点検**: 呼び出し元のリポジトリの追跡ファイルを、`git grep -n -i -E 'token|secret|password|bearer|webhook'` と、URL 中の長い ID で検索する。呼び出し元の基準（入力 8）に「点検の対象」の一覧があれば、一覧のリポジトリすべてを同じ検索で点検する（公開のリポジトリは、起動した単位でなくても点検する）。ヒットを1行ずつ挙げ、機密かどうかをユーザーに聞く（説明文の語は除く）。機密なら、書き直しと履歴の扱いを案にする。
7. **トークン消費の自己採点**: 前回の採点のコミット（`reviews` の前回の行。無ければ表の「点の履歴」の最終行）から、`git diff --stat <そのコミット>..HEAD -- workflow-kit exmem` に差分が無ければ、星取り表を読まず「変化なし」と報告する。差分があるときだけ、`token-matrix.md` の星取り表（切る・絞る・予算・外部化）を、表の「採点のしかた」で採点し直す。前回の点より、どれかの列が下がったら、見直しの対象にする。
8. **リポジトリ間の整合**（同じ規則で運用する複数のリポジトリがあるとき。例: works、共有リポジトリ、設定のリポジトリ。無ければ飛ばす）: 呼び出し元の**基準**（保存先は呼び出し元の `AGENTS.md` が定める）にある2つの表を、今の状態と比べる。基準が無ければ、初回として表を作り、基準にする。
   - **現状**: 行を項目（共通ルールのポインタ、読む順番、窓口、`docs/log.md` の大きさ、コミット・push の規則、公開範囲、旧名・旧パスの参照、無いファイルなど）、列をリポジトリにした表。各行を今の状態と比べ、**基準と違う行だけ**を「見直し」として挙げる。
   - **ギャップ**: 食い違いを1行ずつ挙げた表。各行の状態（解消、残す、未着手）を今と比べ、違う行を見直しに挙げる。新しい食い違いは行を足す。影響（直したときに及ぶ範囲）とリスク（直して事故になる確率）を高・中・低で付けて、影響が高くリスクが低いものから並べる。`workflow-kit` が正とは限らない（kit が遅れている場合がある）ので、どちらに揃えるかを明記する。明らかにずれている箇所は、直す前にユーザーに確認する。直すのは、手順「1つ直すか、1つ畳む」の枠に数える。
9. **知識の引き当てと参照構造**（workbase で実行したとき）: 引当率と参照構造（コールグラフ）を測り、数字を前回と比べる（読むだけ）。コマンドと見方は `review-triggers-check.md`。

## 手順

1. **入力を集める**（上の 1〜9）。
2. **事例を見る。** 同じことを言い直した事例があれば、`AGENTS.md` か知識に昇格すべきかを考える。遠回りの原因が、規則の読み落とし、情報の不足、手順の重さのどれかを分ける。
3. **網羅度を確認する。** `hook-matrix.md` の「review の点検」を行う（点検スクリプト、字数の測り直し、Must の行、各フックの領域の権限の期待、Want の案、重さの基準）。枠の数え方も、そこに従う。
4. **1つ直すか、1つ畳む。** トークン消費の点が下がっていたら、下がった行と理由を挙げ、戻す案を出す（承認制。下の「最大1件」の枠とは別に数える）。それとは別に、最大1件。足すなら、畳むものと対にする（規模の凍結）。ユーザーに示して、承認を得て行う。何も無ければ「今週は無し」と報告する。
5. **コミットする。** workbase で実行したときは、`token-matrix.md` の星取り表と「点の履歴」も更新する。メッセージは `[review] 内容` にする（`brief` と `wrap` が前回の日付を、このコミットから取るため）。直す・畳むものが無い週も、`git commit --allow-empty` で `[review] 今週は無し` を残す。前回の日付は `git log --grep='^\[review\]' -1 --format=%cs`（`resources/` で実行）。
6. **指標を足す。** 呼び出し元に記録先があれば、`reviews` に1行を足す（足す値は下の「reviews に足す値」。列名と並びは呼び出し元が定める）。
7. **報告する**（下の「報告の型」）。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」。ユーザーに求めること、コミットを先に、次にやることを最後に）を報告する。このフックでの追記:

- **ユーザーに求めること**: 直す・畳む案の承認（その場で示して得る）。トピックの点検と機密の点検でヒットした行の判断。基準と違う行の確認。

続けて、固有の項目を次の順で報告する。

1. **入力の要点**。入力 8 を行ったときは、基準と違う行（見直し）と、ギャップの表（優先度つき）を添える。見直しの後は、基準を更新する。
1b. **スキップした入力**（必須。1つも飛ばさなければ「なし」）: 飛ばした入力の番号と理由（仕組みで測れない、基準が無い、重くて見送った、など）。`reviews` の `skipped` 列にも書く。**同じ入力を3回続けて飛ばしたら、報告で警告し、その入力を測れるようにする案か、手順から外す案を、承認を求める案として出す**（静かな恒常的スキップを防ぐ）。
2. **網羅度**: Must の違反（無ければ「なし」）、Want の案（あれば1つ。重さと複雑性つき）、重さの基準を超えたフック（無ければ「なし」）。
3. **直した・畳んだもの**（または「今週は無し」）。
4. **警告の目安**。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」（手順そのものと安全規則も承認制。上の「場所と書き込みの制約」）。次も確認する。

- 入力が足りたか。足りなければ、何を記録すべきか。
- 15分で終わったか。頻度が合っていたか。

## 消化モード

対象は、このセッションで作業した単位（「<名前> の続き」で読みに行った単位を含む。無ければ呼び出し元）の `docs/log.md` の Next Actions と Open Questions。

最初に、仕組みの決定の待ち行列（Open Questions の `場所 / 問題 / 案` のうち、前のセッションで置かれたもの）を、`approval-screening.md` の手順でスクリーニングし、結果を1件ずつ見せて、ユーザーの最終判断を得る。期限切れの `【仮 〜日付】` も挙げ、正式化・却下・延長を聞く。

続いて、次の順でリスト化する（ユーザーが上から順に対応する）。並行作業で既に終わった項目が残っていることがある。

1. すでに close していそうなアイテム
2. すぐに close できそうなアイテム（残りの作業と所要、実機が要るかを添える）
3. 起票が古いアイテム（起票日を添える。1・2 に入れたものは除く）

実機・他PC・ユーザーの判断でしか確かめられないものは、完了かどうかをユーザーに聞く。それ以外で、いま書き換えられるものは、承認を得たら、その場で書き換え、コミットまで一度に行う（push は、許可リストのリポジトリで条件を満たすときだけ）。

各項目に根拠を1行付ける（`git log`、実ファイル、`decisions.md`）。推測だけで「完了」としない。`wrap` が足した kit の改善案（`場所 / 問題 / 案` の1行）は、「それ以外」に入れず別に挙げ、承認された案は `hook-common.md` の「改善」の流れで kit を直す。完了の判断はユーザーが行い、承認された項目だけを `log.md` から消す（履歴は `log-history.md` へ。`docs-rules.md`）。`reviews` には記録しない。

### 消化モードの報告

共通の項目（`hook-common.md` の「報告の型」）を報告する。固有の項目は、次の順に報告する。

1. **待ち行列と期限**: スクリーニングした決定（無ければ「なし」）と、期限切れの `【仮 〜日付】`・`【保留】` の扱い。
2. **3 つのリスト**: 上の順。各項目に根拠を1行添える。
3. **閉じた項目**: 承認されて消した項目、期限をつけた項目、残りの件数。

## reviews に足す値

記録先は `docs/metrics/reviews.csv`（`resources/` 直下の `docs/`。列は先頭行にある）。

- 日付と、見直しの識別子。
- 遠回りの事例の件数（入力 1）。
- 開始時の読み込み字数。
- トークン消費の点（4観点と合計）と、採点したコミット。
- 直した・畳んだものの1行（無ければ `none`）。
- 引当率（読まれた/出した）、上位 1 件の割合、取りこぼし候補の件数、届かない場面の件数、最大の循環の割合、未到達、入次数 0（入力 9。記録が無ければ `n/a`）。
- 飛ばした入力の番号（無ければ `none`）。3回続けた判定に使う。
- メモ。
