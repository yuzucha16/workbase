# review フック（別名「見直して」。試験運用）

呼び出し名は review（週1回・15分の目途）。別名は「見直して」。呼び出し表の正本は `hooks.md`。

状態: **試験運用**。

## 目的と契機

- **目的**: 仕組みが、ユーザーの負担（言い直し・聞き直し・遠回り）を減らしているかを、事例で見て、**1つ直すか、1つ畳む**。率でなく、件数と事例で判断する（母数が小さいうちは）。
- **契機**: ユーザーが「review」「見直して」と言ったときに実行する。週1回の目途を過ぎていれば、`start` と `wrap` の報告で、一度だけ勧めてよい（自発的には実行しない）。

## 場所と書き込みの制約

- 書き込み先: 呼び出し元の記録先（`reviews`）と、直す・畳むと決めたファイル。手順書・規則を直す・畳む案は、**ユーザーにその場で示し、承認を得てから**行う（週1回のこの承認が、改善案の個別の承認に代わる）。安全規則（`wrap-hook.md` の「自動採用の範囲」）は、ここでも承認制。
- コミットは `docs-rules.md` の「コミットと push」に従う。push も同じ（許可リストにあるリポジトリだけ）。

## 入力

呼び出し元の記録から集める。無い、または少ないものは、「記録が少ない」と報告し、そのことから結論を出さない。

1. **`again` の件数と内容**（`events`）。同種の `gap` が繰り返されていないかも見る。
2. **終了時の1問の回答**（`sessions` の `detour`）。「大きく」「少し」の原因。
3. **開始時の読み込み字数**（呼び出し元が定める計測。増えていないか）。
4. **警告の目安**（目標ではない）: 新しく増えた知識のうち、仕組み自体を扱うものの割合。`exmem/inbox/` の未統合メモの数（5件以上なら `integrate` を勧める）。`decisions.md` で `→` の無い【汎用】項目の件数。

## 手順

1. **入力を集める**（上の 1〜4）。
2. **事例を見る。** 同じことを言い直した事例があれば、`AGENTS.md` か知識に昇格すべきかを考える。遠回りの原因が、規則の読み落とし、情報の不足、手順の重さのどれかを分ける。
3. **1つ直すか、1つ畳む。** 最大1件。足すなら、畳むものと対にする（規模の凍結）。ユーザーに示して、承認を得て行う。何も無ければ「今週は無し」と報告する。
4. **自動採用の規則**（`wrap-hook.md` の節。停止中）があれば、要・不要を1回だけ判断する（根拠が無ければ保留）。
5. **コミットする。**
6. **指標を足す。** 呼び出し元に記録先があれば、`reviews` に1行を足す（列は下）。
7. **報告する**: 入力の要点、直した・畳んだもの（または「今週は無し」）、コミット、警告の目安。

## 報告の型

手順 7 のとおり、次を順に報告する。

1. **入力の要点**。
2. **直した・畳んだもの**（または「今週は無し」）。
3. **コミット**: ハッシュと内容。
4. **警告の目安**。
5. **改善案**（あったときだけ）: `hook-common.md` の「改善」に従う。

## このフックの改善

流れと承認は `hook-common.md` の「改善」「承認」（このフックの手順そのものと安全規則も承認制。上の「場所と書き込みの制約」）。このフックでは、次も確認する。

- 入力が足りたか。足りなければ、何を記録すべきか。
- 15分で終わったか。頻度が合っていたか。

## reviews の列

`date,review_id,again,detour_big,detour_little,load_chars,action,note`

- `again` = 期間内の件数、`detour_big` `detour_little` = 終了時の1問の「大きく」「少し」の件数、`load_chars` = 開始時の読み込み字数、`action` = 直した・畳んだものの1行（無ければ `none`）。
