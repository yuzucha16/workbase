# 解決・改善・変更・調査のやり方（要点の表）

やり方を選ぶための表。全文は読まず、該当の表の行だけ読む（`brief` の引数は 2026-10-28 に廃止。応答の形は `exmem/lessons/*-output.md` が依頼の言葉で出る）。**手順の骨子と選ぶ基準だけ**をここに置く。背景・理由・実例・落とし穴は、右端の `lessons/` のノートにある（選んだら、そのノートを読んでから進める）。ノート名が変わったら、この表の1か所を直す。新しいやり方を足すときは、`exmem/lessons/method-creation.md`（「やり方の作り方」）に従う。

## 解決（問題が見つかったとき）

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 解決1 アナロジー | 問題が構造で言い直せ、似た問題が他の領域に思い当たる。解がまだ無い | 固有名を抜いて一般化 → 観点別に類似問題を集める → 「世界 / 同じ問題 / 解き方 / こちらへの対応」の表にする → 借りるのは最小の構造だけ → 「いつ・誰が」に落として決める。適用した解は実測まで仮説 | `problem-solving-analogy` |
| 解決2 差し戻し | 解の案が既にあり、前提が後から出てきそう。判断軸を研ぎたい | 初期前提を仮と明示 → 決定を置く → 外の前提を書き出す → 決定に1つずつ当て、維持・変更・取り下げに分ける。全体4回まで、収まらなければ「未決」で打ち切る。決定に見直しの条件を1行添える | `problem-solving-iterative-revision` |

## 変更（既存の成果物を、決めたやり方で変えるとき）

解決・改善が「何をどう変えるか」を決めるやり方なのに対し、変更は、決まった変更を安全に入れるやり方。試験運用で、**Must だけ守る**（Must / Want の意味は `hook-matrix.md` の「区分」と同じ。欠けたら直す / あれば良い）。

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 変更1 基点つきの最小変更 | 既存の成果物があり、前提チェックを通る | 前提チェック → 影響範囲の列挙 → 基点の確定 → 最小実装 → 検証 → 記録 | `change-method` |

- **前提チェック**（Must。1行でよい）: 変更する成果物に、基準文書（成果物と分けた、AI が読めるテキストの明文化）があるか。無ければ、変更の前に補う（新規は自作、既存は抽出。抽出は人が照合する）。
- **基準文書の Must**: 正の向き・基点（冒頭の2行）、目的と満たすべきこと（ID つき、1 ID = 検証できる1文）、検証項目（誰が・どこで確認するか）。Want: 構造と依存、規則（定数・書式・中止条件）、不変条件。
- **変更の Must**: 前提チェック、影響範囲の列挙、基点の確定、最小実装、検証、記録（基点・影響範囲・検証の結果・見直しの条件）。Want: 案の比較と選択（案が2つ以上のときだけ）、点検（指す先まで）、利用側への反映、小さな変更の縮め方。
- **業務の成果物**（`areas/` `projects/`）では、AI が成果物の中身を見られないことがある。検証は、基準文書の検証項目に沿って、人かマスク済みの写しで行う。固有の中身は workbase に置かない。
  - 置き場: 成果物と同じフォルダ（`ai/out/<成果物名>/`）。`dev` の Project は `docs/` の3文書が兼ねる（`dev-deliverable-guide.md`）。
  - 書き方: マスク後の語か一般化した形だけで書く。抽出の基点は `ai/in/` の manifest の原本ハッシュ。照合の結果もマスク後の語で書き、実名を見て直す内容は `_noai/` に置く。
  - 次の Project へ: 人が `ai/in/` に置き、`room start --adopt` で渡す。Area の README の一覧に、成果物ごとの最新の Project を1行書く。

## 計画（これから始める取り組みの目的とゴールを、ユーザーと AI で共有するとき）

変更が「決まった変更を入れる」、調査が「知る」のに対し、計画は「始める前に目的とゴールをそろえる」やり方。試験運用で、**Must だけ守る**。A 事前の仕込み + B プロセスの2ブロック。手順と欄の定義は `brief-plan.md`。

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 計画1 6R と憲章 | 期限のある取り組み（Project 1つ。上限4週）を始める。目的とゴールが共有されていない、または手段が目的化しそう | A ユーザーの「〜したい」1文 → AI が6R（状況・問題意識・要求・意図/裏づけ/仮説・今回のスコープ・期待する成果）を〔資料〕〔推測〕つきで書く。既定値（予算・稼働日・バッファ・体制）は欄にしない。B 6R（ここで止まってよい）→ 憲章 → 成果物 WBS（100%ルール）→ マイルストーン（基準4つ、上限3つ）→ 出力と作り方のメモを別ファイルに | `planning-method` |

- **Must**: `brief-plan.md` の A・B のとおり。〔資料〕〔推測〕のタグ。知らないことは推測で埋めず、聞く。
- **置き場**: kit の題材は指定された場所。実務の題材は、AI が `ai/work/` で下書きし、ユーザーが承認したものを人が Project の `ai/in/` に置く（実務の中身は workbase に入れない）。

## 調査（調べて、読者が使える Markdown にまとめるとき）

解決・改善・変更が「何かを良くする・変える」やり方なのに対し、調査は「知る」やり方。調査1は主題を調べて**説明**し（要点は**構造化と想定読者**）、調査2は手順を調べて**実行できる手順書**にする（要点は**前提の確定と、従うルール・仕組みの一次情報での確認**）。試験運用で、**Must だけ守る**。どちらも **A 事前の仕込み + B 調査プロセス**（変更と同じ2ブロック）。

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 調査1 構造化と想定読者 | 主題があり、読者（既定は依頼した本人）が使える形にまとめたい | （型のノートに移した。2026-10-28） | `research-explain-output` |
| 調査2 手順を調べる | 技術的なインストール・導入や、ルール・仕組み（OS、サービス、規程）に沿ってやることがあり、そのまま実行できる手順書にしたい | （同上） | `research-procedure-output` |

- **置き場**: 下書きはプロジェクトの `notes/`、確定（公開してよく読者が本人）は `guides/explain/<主題>.md`（`checked` つき）、業務・機密は部屋の `ai/out/<成果物名>/report.md`（Area に実名で戻したい最終版は `ai/out/deliverable/` の下。それ以外は Project の `_noai/final/` に戻る）。調査2の確定版の置き場は未決（`research-method-2` の Open Questions）。下書きと業務・機密は同じ。
