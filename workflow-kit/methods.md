# 解決・改善・変更・調査のやり方（要点の表）

`start 解決` `start 改善` `start 調査`（`start-hook.md` の「引数つきモード」）が、やり方を選ぶための表。**手順の骨子と選ぶ基準だけ**をここに置く。背景・理由・実例・落とし穴は、右端の `lessons/` のノートにある（選んだら、そのノートを読んでから進める）。ノート名が変わったら、この表の1か所を直す。

## 解決（問題が見つかったとき）

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 解決1 アナロジー | 問題が構造で言い直せ、似た問題が他の領域に思い当たる。解がまだ無い | 固有名を抜いて一般化 → 観点別に類似問題を集める → 「世界 / 同じ問題 / 解き方 / こちらへの対応」の表にする → 借りるのは最小の構造だけ → 「いつ・誰が」に落として決める。適用した解は実測まで仮説 | `problem-solving-analogy` |
| 解決2 差し戻し | 解の案が既にあり、前提が後から出てきそう。判断軸を研ぎたい | 初期前提を仮と明示 → 決定を置く → 外の前提を書き出す → 決定に1つずつ当て、維持・変更・取り下げに分ける。全体4回まで、収まらなければ「未決」で打ち切る。決定に見直しの条件を1行添える | `problem-solving-iterative-revision` |

## 改善（既にあるものを良くするとき）

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 改善1 数値の選択肢 | 数値で測れる（性能、参加率など） | 現状を数値にする → 10%・20%・30% の選択肢を並べる → リスク・影響・難易度を比べる → 方向を決めてから実行 → 同じ測り方で測り直す | `improvement-quantified-options` |
| 改善2 ズレの仮説 | 数値にできない（構成、名前、運用） | 期待（設計時の想定）と実際（履歴、更新日、利用の有無）を同じ項目で並べる → **仮説は AI に伝えず**、原因を独立に挙げさせる → 人が照合 → 実態に合わせて直し、「想定どおりでなかった」ことも記録する | `improvement-expectation-gap` |
| 改善3 星取り表 | 仕組み（規約、手順書、スクリプト）が既にあり、観点が複数ある | 観点を影響度と支配度でランキング → 2〜4個に絞る → 星取り表（効き方つき） → 修正・削除・追加の案（影響範囲とリスクつき） → 優先度 → ユーザーが実施項目を決める | `improvement-coverage-matrix` |

選び方が割れるとき(例: 原因を調べて直す)は、解決で始め、直す段になったら改善に移る。迷ったら Recommended をユーザーに示して1問で決める。

## 変更（既存の成果物を、決めたやり方で変えるとき）

解決・改善が「何をどう変えるか」を決めるやり方なのに対し、変更は、決まった変更を安全に入れるやり方。試験運用で、**Must だけ守る**（Must / Want の意味は `hook-matrix.md` の「区分」と同じ。欠けたら直す / あれば良い）。

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 変更1 基点つきの最小変更 | 既存の成果物があり、前提チェックを通る | 前提チェック → 影響範囲の列挙 → 基点の確定 → 最小実装 → 検証 → 記録 | `change-method` |

- **前提チェック**（Must。1行でよい）: 変更する成果物に、基準文書（成果物と分けた、AI が読めるテキストの明文化）があるか。無ければ、変更の前に補う（新規は自作、既存は抽出。抽出は人が照合する）。
- **基準文書の Must**: 正の向き・基点（冒頭の2行）、目的と満たすべきこと（ID つき、1 ID = 検証できる1文）、検証項目（誰が・どこで確認するか）。Want: 構造と依存、規則（定数・書式・中止条件）、不変条件。
- **変更の Must**: 前提チェック、影響範囲の列挙、基点の確定、最小実装、検証、記録（基点・影響範囲・検証の結果・見直しの条件）。Want: 案の比較と選択（案が2つ以上のときだけ）、点検（指す先まで）、利用側への反映、小さな変更の縮め方。
- **業務の成果物**（`areas/` `projects/`）では、AI が成果物の中身を見られないことがある。検証は、基準文書の検証項目に沿って、人かマスク済みの写しで行う。固有の中身は workbase に置かない。
  - 置き場: 成果物と同じフォルダ（`ai/out/<成果物名>/`）。`dev` の Project は `docs/` の3文書が兼ねる（`dev-deliverable-guide.md`）。
  - 書き方: マスク後の語か一般化した形だけで書く。抽出の基点は `ai/in/` の manifest の原本ハッシュ。照合の結果もマスク後の語で書き、実名を見て直す内容は `_noai/` に置く。
  - 次の Project へ: 人が `ai/in/` に置き、`room start --adopt` で渡す。Area の README の一覧に、成果物ごとの最新の Project を1行書く。

## 調査（主題を調べて、読者が使える Markdown にまとめるとき）

解決・改善・変更が「何かを良くする・変える」やり方なのに対し、調査は「知る」やり方。要点は**構造化と想定読者**。試験運用で、**Must だけ守る**。調査 = **A 事前の仕込み + B 調査プロセス**（変更と同じ2ブロック）。

| やり方 | 選ぶ基準 | 骨子 | ノート |
|---|---|---|---|
| 調査1 構造化と想定読者 | 主題があり、読者（既定は依頼した本人）が使える形にまとめたい | A 問いを章立てに対応させる → 想定読者を決める → 品質条件を宣言する。B 一次情報の有無を確認 → 問いごとに調べ、出典を付ける → 事実と所感を分ける → 確認できなかった点を書く → 置いて記録する | `research-method` |

- **A の Must**: 構造化した問い（章立てと1対1。ひな形と、各章に含めるものは `research-method` の Facts）、想定読者（既定は依頼した本人。読者が変わるなら、業務の `research` type として扱う）、品質条件（一次情報を優先、出典に日付と URL（日付が無い資料は取得日）、推測と未確認を明記）。Want: 具体例の要否と条件（指標・対象の種類・件数）を最初に決める、類似ワードの候補（依頼者が挙げるもの）、結論の用途、出力先と形式。
- **B の Must**: 題材に一次情報があるかの確認（無ければ二次中心と明記）、問いごとに調べて出典を付ける（事実を述べる各問いに一次の出典を1件以上。無ければ「一次情報なし」と書く）、事実・推測・第三者の意見の分離、一次と二次の分離、確認できなかった点を末尾に書く、成果物の配置と記録。Want: 変わる値の取得日と手段、範囲を絞った基準の明記、章を足すときの番号と参照の点検。
