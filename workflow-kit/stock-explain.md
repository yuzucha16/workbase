# stock 理解（理解ガイドの下書きの書き方）

`stock-hook.md` のモード「理解」（別名「理解ガイドにして」）で読む。手順（判定、話題を分ける、重複確認、点検、報告）は `stock-hook.md` のとおりで、ここには**違う点だけ**を書く。形の見本は `examples/inbox-example-explain.md`。型の元は `exmem/lessons/reference-doc-types.md` の「理解ガイドの型」。

## 判定の問い

「この会話を知らない人が、仕組みを自分で説明できるようになるか」。使えるのは、用語・仕組み・症状と原因の対応・比べ方。判断の記録（なぜ A でなく B か）と、実機で踏んだ落とし穴は、`kind: lesson`（AI 用）に書く。1つの会話から両方が出るなら、2回に分けて実行する（読む問いが違い、中身も違うので、1ファイルにしない）。

## 書き込み先と統合

- `exmem/inbox/YYYY-MM-DD-<topic>.md` に新規作成する。frontmatter は `type: inbox`、`kind: explain`、`title`、`tags`、`created`、`sources`（書き方は `stock-hook.md` の「ファイル名・title・tags」と同じ）。
- `integrate`（`integrate-hook.md` の統合の細則）が `guides/explain/<name>.md` に新規作成する。既存の理解ガイドへの追記・上書きは対象外（同じテーマが `guides/guides-index.md` にあれば、メモを作らず報告する）。
- 重複確認は `find-knowledge`（`lessons/` の検索）を使わず、`guides/guides-index.md` を見て決める。`lessons/` に近いノートがあるときは、冒頭の末尾にその名前を添える。

## 見出し（6つ。この順番、省略しない）

冒頭 / ダイジェスト / 基礎知識 / チェックリスト / 補足 / 要確認事項。該当が無い見出しは `なし`（見出しの直後に1語だけの行）。

| 見出し | 書くこと |
|---|---|
| 冒頭 | 目的（自分で説明できるところまで）、前提、確認状況。末尾に `統合先の候補: guides/explain/新規（キーワード: …）` の1行 |
| ダイジェスト | 状況 → 原因 → 解決 |
| 基礎知識 | 用語、仕組み、表。末尾に「自分で説明するときの一言」 |
| チェックリスト | 症状 → 原因 → 対処の表 |
| 補足 | 比較表、経緯、一覧 |
| 要確認事項 | 確かめていないこと |

Area の会議録（`type: area-note`）の `冒頭` は別物（人向けの要約の数行）。この `冒頭` と混ぜない。

## 文章の規則

`stock-hook.md` の「文章の規則」と同じ（単体で読める、機微を書かない、確認は `（確認: YYYY-MM-DD、根拠: …）`、未確認は `（仮説）`）。違う点: 分量の目安はファイル全体で150行以内のまま。AI 用の根拠の細部（確認の日付と根拠）は、結論に必要な箇所だけにする（人用の文書に写すため）。固有情報（顧客名・案件）は、仮名にしても書かない。

## 自己点検（書く前に手で確認する）

- [ ] 1ファイル1テーマ。読む問いが「どう動く・なぜ」のもの（判断・原則・落とし穴は lesson へ）
- [ ] 同じテーマの理解ガイドが `guides-index.md` に無い
- [ ] 6見出しが、順番どおりにある。基礎知識の末尾に、自分で説明するときの一言がある
- [ ] 確認した事実の根拠が本当である。未確認は `（仮説）` と書いてある

機械で確認できる項目は、作った後に点検スクリプトが見る（コマンドは `stock-hook.md` の手順「作る」と同じ。`kind` で項目が切り替わる）。
