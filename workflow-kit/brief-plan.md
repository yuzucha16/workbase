# 計画のやり方（`brief 計画` の手順と欄の定義）

`brief-hook.md` の「`brief 計画`」から呼ぶ。やり方の位置付けは `methods.md` の「計画」、背景と注意点は exmem の `lessons/planning-method.md`。試験運用で、**Must だけ守る**。欄の名前は、書籍の図表の読み取りで、本文は未読（出どころは lesson の Facts）。

## A 事前の仕込み

- ユーザーが「〜したい」の1文と、任意の「条件:」1行を書く。AI が6Rの残りの欄を書く。
- 6R の欄（項目名）は6つ。順に、状況、問題意識、要求、意図・裏づけ・仮説、今回のスコープ、期待する成果。前半3つが状況の整理（状況 → 問題意識 → 要求）、後半3つが Reason（なぜ）・Range of Work（今回何をするか）・Result（どんな成果か）に答える。
- 各欄は、見出し1文と箇条書き3つまで。〔資料〕〔推測〕のタグを文に残す。〔資料〕には出典（読んだファイル、またはユーザーの発言）を添える。憲章以降に引き継ぐ推測の値（予算、日付）には「推測」と書く。読みが割れるときだけ、前提の表で読み（A〜C）を出し、ユーザーが選ぶ。
- 前提の表は、3列（論点・読み・内容）にする。確定した読みは太字、却下した読みは括弧内に書く。ユーザーとの会話では、表に書いた読みの名前で呼ぶ（会話の中で別の名前を付けない）。
- 状況と問題意識が同じ内容になるときは、1欄にまとめてよい（試行で3項目とも重なった）。仮説は独立した欄にせず、「使ってみて確かめること」として裏づけに書く。
- 問題意識は、依頼の手段ではなく論点で書く（例: 「2系統にしたい」は手段で、論点は「読者の違う1つの情報をどう管理するか」だった。1題材の所見）。
- 要求の欄の「見る単位（期間・セッション・プロジェクトなど）と統計量」は、測る道具の題材だけに書く。手順書の変更のような題材では書かない。書くときは、用語（「作業当たり」「傾向」など）の単位を定義する。
- 今回のスコープの下に、「変更先の洗い出し」（触るファイルとその根拠）を書く。WBS の葉、予算、規模の根拠になる。洗い出しは2軸で書く: 参照（`grep` で探す）と、振る舞いの依存（その値を読むコード・点検・テスト。参照語を持たないファイルもここで拾う）。「変えないこと」（回帰を見る範囲）もここに書き、何で・いつ（変更の前に）測るかを添える。
- 今回のスコープの見出しか条件の行に、期日を書く（無ければ予算の1週間から出す）。対象外には、理由と見直す条件を添える。前提・注意に、実データ・出力の置き場と、機微の有無（出力の機微はここだけに書き、憲章には書かない）を書く。既存の制約（字数の目安、点検の基準など。葉が分かれる原因になる）と、進行中の別の題材と共有する用語・ファイルも書く。承認が要る変更先（例: `workflow-kit/` はユーザーの承認なしに書き換えない）があれば、ここに書く。
- 期待する成果は、題材の成果だけにする（試行の評価は別に書く）。数えられる指標を1つ書く（的外れなら「指標なし」も可）。未決には「何を見れば決まるか」を添える（最初の調べ物になる）。
- 裏づけ（未確認。最初に確かめる）の各項目に、「確かめる方法」と「確かめる時期」（例: M1 の前）を添える。確かめた結果と見つけた落とし穴は、6R に書き戻す（量が多ければ確認メモのファイルにして、WBS の葉にする）。既存ツールがあるときは、前提の表に、その役割（本体・突合先・使わない）を分けて出す。
- 既定値（6R の欄にしない）: 予算（時間）は1週間。稼働日は平日のみ。バッファは土日2日を最後にまとめて置く。体制はオーナー ユーザー、メンバー ユーザーと AI、リーダーはユーザー兼任。
- AI が1セッションで作る小さな題材では、日数の見積もりが桁で外れた。予算は日数より、ユーザーの判断が要る回数とセッション数で書いてよい。
- 規模は、「変更先の洗い出し」のファイル数で測る。小さな題材では、WBS の葉の数をそのファイル数に合わせる（試行では、葉13に対して実際のファイルは4つだった）。6R・憲章・WBS は、実行中に更新する前提で書く。
- 聞くのは、依頼から決まらないものだけ（選択式。最後に「ほかに前提はありますか」の自由記述）。

## B プロセス

1. **6R を作る**。ここで止まってよい（小さな再開では6Rだけ）。
2. **憲章を作る**。欄は、名前、更新日、使命（What）、ビジネスの目的（Why）、目標（完了時期・予算・品質。完了時期は最終マイルストーンの日付を指すだけにし、日付を書かない。予算は、見積もりの根拠〔変更先のファイル数など〕があるときだけ書く。品質は合否の基準として書き、指標の欄は別に置かない）、メンバー、リーダー、オーナー、必要なマイルストーン（主要3つまで）。全員がユーザーの1人の題材では、メンバー・リーダー・オーナーの欄と、マイルストーンの表と重なる必要なマイルストーンの欄は省いてよい。対象外・前提・リスク・未決は、出力に載せず6Rに残す。
3. **成果物 WBS を作る**。成果物（名詞）で分解する。第2層は、工程（要件・設計・検証など）でなく、成果物の種類（利用者が受け取るもののまとまり）で分ける。工程はマイルストーンが持つ。親は子の足し算で、モレもダブりも無い（100%ルール）。「プロジェクトマネジメント」のまとまりは、実際に作る葉だけ置く（憲章・WBS・マイルストーン自身は読み手に新しい情報がない自己参照なので葉にしない。課題ログは置かず、判断は `decisions.md`、未決は `log.md` が持つ）。条件付きの葉と、未決の葉は置かず、条件が来たとき・決まったときに足す（変更の記録に理由を書く）。葉は1ファイルに対応させ、各葉に置き場を書く。対になるファイル（両方を同時に直さないと食い違うもの）は「対」と書いて1葉にしてよい。整合の葉は、ファイル単位に分けるか、洗い出しの表（ファイル・触る理由・触らない場合の根拠）を成果物にする。字数の目安などの制約で分かれうる葉には「分ける可能性」と書く。中間の記録（定義書、確認メモ、突合結果、決定）は、**後工程または利用者が入力として読むなら葉にする**（抜けを防ぐ）。作業のためだけに作り、読み手のいない本当の中間物（テスト、作業用スクリプト、途中のメモ）は葉にせず、親の葉の説明に「含む」と書く。判定は「このファイルを、後で誰かが読むか」。ファイルにならない確認は親の葉にまとめる（ユーザーの決定、2026-10-21）。「動作確認」（テスト、見た目の確認）の葉を、検証とは別に置く。要求が実行中に変わるので、WBS に「変更の記録」（日付・追加した葉・理由）を1行ずつ足す場所を置く。
4. **マイルストーンを作る**。置く基準は4つ（フェーズの開始・完了、成果物の作成完了、外部やオーナーとのレビュー、プロジェクト外のイベント）。期間は1・2・4週から選び、上限は3・5・9。開始の承認と終了の判断は数えない。ゴールから逆算して間隔を見る。上限は「日付を持つ節目」にだけ数える。判断の待ちが無く AI だけで進む区間は、日付でなく順序と承認点（ゲート）で置き、数えない（ユーザーの決定、2026-10-21）。終わる日の違う節目を束ねたときは、理由を計画に1行残す。日付を置くのは、ユーザーの待ちがあるゲートだけで、この判断は計画を書く時点で行う。各マイルストーンの確認には「確認する物（置き場と、番号つきの項目）」を添える（ユーザーが番号で一括承認できるように）。
5. **出力と作り方のメモを、別ファイルにする**。出力は憲章・WBS・マイルストーンの Markdown だけ。作り方のメモは、迷った点・決めたこと・本との違いを書く。実装が設計から外れたときは、「設計からの差分」（AI の判断。確認を求める）を `decisions.md` に書く。通し試験の結果の置き場は1か所にし、複製が要るときは親から指す。

## 置き場

題材が入る領域で決める（公開してよい中身か、進行中の下書きか承認済みの基準か）。

| 領域 | 置き場 |
|---|---|
| workbase（kit、exmem、guides） | 題材ごとのトピック `topics/<名前>/`（kebab-case、1階層）の `records/`。無ければトピックを作る。`kit-growth/records/` は「測ったこと」だけ（品質チェックと振り返り）。使わない: `kit-growth/plans/`、`planning-method/records/` への集約（ユーザーの決定 2026-10-21、正式化 2026-10-25） |
| works（Project、Area） | 承認版の計画は、実名なしで Project の `ai/in/plan/` に置く（`plan-room-link` の決定、2026-10-21）。知識は Area の `_noai/knowledge/`。作業用の下書きは、AI が `ai/work/plan/` に書き、ユーザーが承認したものを人が `ai/in/plan/` に置く（部屋の AI は読むだけ）。Area の README の最新の Project の1行は、`room open` が足す |
| dotfiles | dotfiles 自身の `docs/` で完結させる（依存は dotfiles → workbase の一方向）。workbase に影響するときだけ、名前で指す1行を workbase 側に書く |
| room（道具の開発） | workbase の題材と同じ（道具のコードは `workflow-kit/room/`） |
| room の中（業務） | 部屋の `ai/work/` → `ai/in/`。マスク後の語だけで書く |

実務の中身は workbase に入れない。

- 聞けないとき（呼び出し元が置き場を指定していない）は、会話の中に出し、判断の記録に書く。

## Want（叩き台。1事例からの仮説）

WBS から憲章への逆向きの確認、計画と実績の日付、課題ログ、動的な確認、「検査を見せて」の運用。

## 実行後の所見の置き場

一言なら `topics/kit-growth/inbox.md` の「未選別」に1行（題材名・欄名つき）。詳しくは題材のトピックの `records/` に番号つきで書く。測ったことは `kit-growth/records/planning-method-record.md`。規則の変更案は `docs/log.md` の Open Questions に `場所 / 問題 / 案` で置く。承認は `review 消化` で行う。
