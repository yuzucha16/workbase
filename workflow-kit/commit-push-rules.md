# コミットと push

`docs-rules.md` から切り出した（2026-10-26。`docs-rules.md` の全文読みが会話を 7〜12k 伸ばしていたため。`topics/token-cap/records/2026-10-26-growth-by-reads.md`）。コミット・push の前に、このファイルだけを読む。

コミットは、エージェントが行ってよい（ユーザーの許可: 2026-10-05。すべての作業ディレクトリに適用）。push は、許可リストにあるリポジトリだけエージェントが行い（下の「push」）、ほかはユーザーが行う。

- **範囲**: その作業で自分が変更・生成したファイルだけを、パスを指定して `git add` する（パスなしの `git add -A` と `git add .` は使わない。範囲が決まらず、他人の変更を巻き込むため。パスを指定した `git add -A <パス>` は、削除と rename のステージに使ってよい。2026-10-15 ユーザーの決定）。ユーザーの未コミットの変更、並行セッションの変更、内容を確認していない既存ファイル、機密の可能性があるものは、含めない。含めなかったものは、報告に書く。
- **コミットの前に確認する**: ① `git add` の直後に `git diff --cached --stat` で、意図したファイルだけか、**行数が自分の変更量と合うか**。共有された `docs/` や設定ファイルは、並行セッションやユーザーが同じファイルを編集していることがあり、パスを指定しても他人の変更が一緒にステージされる。行数が多いときは、`git diff --cached <パス>` で中身を見て、自分の変更だけに絞る（`git add -p`）か、混ざったことを報告する。② 身元が下の「コミットの身元とトレーラー」どおり。③ トークン、秘匿値、業務固有の情報が入っていない（`git diff --cached` を、`token` `secret` `password` `bearer` `webhook` で検索する。語だけでは漏れるので、URL 中の長い ID も見る）。④ 表や一覧を編集したときは、同じ行が重複していない（`git diff --cached` の追加行に同一の行が2つ無い）。外れたら、`git reset -q -- <パス>` でステージを戻して、コミットせずに報告する。
- **帰属を分けて示す**（2026-10-19。補正策の正本は `exmem/lessons/user-manual.md`）: コミットの前に、報告で「AI が触ったファイル」と「出所不明の差分（ユーザーの手動変更、他の PC、並行セッション）」を分ける。アプリが書き戻すファイルを新しく追跡する前は、毎回 diff が出ないかを確かめる。
- **コミットを分けるとき**（例: 改行だけの変更と内容の変更）は、`git commit` にパスを指定しない。パスを指定した `git commit -- <パス>` は、index ではなく作業ツリーの現在の内容をコミットするので、ステージで分けても1コミットにまとまる。分けたい内容は index に入れ（`git add -p`、または `git hash-object -w --no-filters` と `git update-index --cacheinfo`）、`git diff --cached --stat` で確認してから、パスなしでコミットする（2026-10-07 dotfiles で発生。未 push のコミットは `git reset --soft HEAD~1` でやり直せる）。
- **メッセージ**は `[領域] 変更内容`（そのリポジトリの `AGENTS.md` に固有の規則があれば、それを優先する）。
- **コミットの身元とトレーラー**（2026-10-06 ユーザーの決定。終了処理のコミットだけでなく、作業の途中でエージェントが作るコミットのすべてに適用する）: エージェントのコミットは、人間のコミットと区別できるようにする。remote なしのローカルリポジトリでも、`git log` で「誰の行動か」と「どの時点の規則か」が分かるようにするため。
  - 身元は、コミット1回ごとの `-c` で渡す。`git config`（グローバルも `.git/config`）は書き換えない（後で人間が手動でコミットしたときまで agent 名義になるため）。作者とコミッターは、どちらも agent にする。
  - 名前は `agent`、メールは `agent@agent.local`。道具やモデルは、名前でなくトレーラーに書く。
  - トレーラーは2行を毎回付ける（`git commit --trailer "<キー: 値>"`）。`Agent: <道具> <モデルID>`（例: `Agent: claude-code claude-sonnet-5-5`）、`Kit-Rev: <ハッシュ>`（`resources/` の `git rev-parse --short HEAD`。`resources/` に未コミットの変更（未追跡ファイルとステージ済みを含む。`.gitignore` で除外されたものは含まない）があれば末尾に `-dirty`。判定: `git status --porcelain` が空でない）。
  - `room mkworks`（`--update` を含む）のコミットは、人が打つコマンドが作るので、この身元とトレーラーの対象外（git の身元は人のもの。トレーラーは `Room-Op` `Room-Rev`。`room/README.md`）。旧 `init 更新` のコミットの `Template-Rev` は、`mkworks --update` が基点として読む。
  - 例: `git -c user.name=agent -c user.email=agent@agent.local commit -m "[works] ..." --trailer "Agent: claude-code claude-sonnet-5-5" --trailer "Kit-Rev: 3daeff6"`
  - 人間の名義でコミットしたい（ユーザーが言葉で指示した）ときだけ、`git config` の身元を使う。未設定、または `example.com` を含む仮値なら、コミットせずに設定を促して止まる。
  - 過去のコミットは書き換えない（`workbase` の既存コミットは `user` 名義のまま。移行日以降が agent 名義）。
- **コミットしないもの**: 「ナレッジ化して」で `exmem/inbox/` に作ったメモ（ユーザーの指示、2026-10-05）。inbox のメモは、解釈して `lessons/` に統合した後に削除する運用なので、未追跡のまま残す。**対象は、フックが作ったメモのファイルだけ。** 同じリポジトリのほかの変更（kit、`lessons/`、`tags.md`、`inbox/README.md`、手順書など）は対象外で、コミットしてよい。報告では「メモはコミットしていない」と範囲を限定して書き、「変更全体がコミット対象外」と読める書き方をしない。コミットを人に頼まない（人が行うのは push だけ）。
- **しないこと**: 許可リスト外の push、`git add -f`、`--amend`、`reset --hard`、`--force`、`--no-verify`、他のコミットの書き換え、コミットを消す・書き換える `rebase`（`-i`、`drop`、`squash`、`reword`、`edit`。ユーザーの承認が要る）（ステージを戻すだけの `git reset -q -- <パス>` は、してよい）。ユーザーが「コミットしないで」と言ったときも、しない。
- **未追跡のファイルの削除**（2026-10-18 ユーザーの決定。全フックに適用）: コミットや push のために、未追跡のファイルを削除することになる場合（`git clean`、`rm`、ブランチの切り替えや `rebase`・`stash` で消える場合を含む）は、先にユーザーに確認する。ファイルの一覧と、消えると困るかを示して、承認を待つ。承認が無ければ消さず、未追跡のまま残して報告する。フック自身が works の外の一時ディレクトリに作った作業用ファイルを消すことは、対象外。
- **`rebase` の許可**（2026-10-18 ユーザーの決定）: 複数端末の分岐による時系列のずれの修正と、その衝突の解消に限り、承認なしで行ってよい。対象は未 push のローカルのコミットを `origin/<ブランチ>` の上に載せることだけ。条件: ① 実行前に、双方のコミット日時と他端末由来かを示す（`exmem/lessons/git-rebase-chronology.md`）。② 衝突は、双方の内容を残して解く。③ マーカー（`<<<<<<<` など）が残っていないことを確かめてから `--continue` する。④ 終わったら、結果（`git log --oneline`）を報告する。コミットを消す・内容や情報を書き換える操作は、これまでどおりユーザーの承認が要る。
- **push** は、呼び出し元の `AGENTS.md` の**許可リスト**にあるリポジトリだけ、エージェントが行う（2026-10-08 ユーザーの決定。試験運用。2026-10-16 に、公開リポジトリ（`workbase`、dotfiles）も許可リストに載せてよいと、ユーザーが決めた。公開のまま、エージェントが push する）。許可リストに無いリポジトリは、報告にコマンドを書いて案内する（ユーザーに頼まれたときは、実行の直前に、remote、ブランチ、公開範囲を示して確認する）。許可リストのリポジトリでも、**毎回、次をすべて確認してから** push する。1つでも満たさなければ、push せず、理由を報告して止まる。
  1. 公開範囲を確認し、報告に書く（`gh repo view <owner>/<repo> --json visibility`。`gh` が使えない環境では、GitHub の API（MCP など）で確かめてよい。どちらでも確かめられなければ push しない）。**公開（PUBLIC）なら、条件 4 の検索を広げる**。push は世界に公開されるので、あとで消しても、キャッシュや履歴に残りうる。
  2. 現在のブランチが、許可リストのブランチ（通常は `main`）。クラウドの環境で作業ブランチ（例: `claude/...`）が指定されているときは、作業ブランチのまま `git push origin HEAD:<許可リストのブランチ>` で push してよい（2026-10-17 ユーザーの決定。指定ブランチへの push は要らない）。条件 3 と 4 は `origin/<許可リストのブランチ>` に対して確かめる。環境のローカルの `main` は古いことがあるので、checkout しない。
  3. `git fetch` の後に、fast-forward で push できる（`git merge-base --is-ancestor origin/<ブランチ> HEAD`）。そうでなければ（別の端末やセッションが先に push している）、止まって報告する。マージは、ユーザーの確認なしにしない。rebase は、上の「`rebase` の許可」の範囲でしてよい。
  4. push する範囲（`origin/<ブランチ>..HEAD`）の差分に、`token` `secret` `password` `bearer` `webhook` と、URL 中の長い ID が無い（`git diff origin/<ブランチ>..HEAD` を検索する）。公開リポジトリでは、さらに、メールアドレス、Windows のユーザー名を含む絶対パス、所属組織・顧客・個人を特定する名前が無いことを確かめる（見つけたら止まり、ユーザーに確認する）。追加行に `会社` が無いことも検索する（環境を特定する語を性質で書く方針。2026-10-28 ユーザーの決定。`topics/wording-neutralize/`）。法人格の語（株式会社・有限会社・合同会社）と、Office の「会社」プロパティを指す書き方は当たってよい。止まらず、ユーザーに見せて確かめる。
  5. `--force`、`--force-with-lease`、`--no-verify` を使わない。
  結果（push したコミットの範囲、または止まった理由）は、報告に書く。ハーネス（Claude Code）の権限設定が `git push` を許可していないときは、許可を求めず、報告にコマンドを書く。
- **使い捨ての環境での緩和**（2026-10-07 ユーザーの決定。試行）: クラウドのセッション（モバイルから使う Claude Code on the web など）は、環境が片付けられると、未 push のコミットと未追跡のファイルが消え、ユーザーは手元から push できない。この環境では、次の2点を緩和する。
  - push もエージェントが行う。セッションで最初の push の前に1回、remote、ブランチ、公開範囲を示して確認し、以後の push は報告に書くだけでよい。ブランチは、ユーザーが指定しなければ、そのリポジトリの通常の運用（`workbase` は `main`）に従う。push が失敗したら、コミットが環境の中にしか無いことを報告に書く。
  - 「ナレッジ化して」で `exmem/inbox/` に作ったメモも、コミットして push する（未追跡のままだと消えるため）。統合した後のメモの削除も、コミットする。作業の引継ぎ（現在の状態と次にやること）は、該当する `exmem/lessons/` のノートの `Open Questions` / `Next Actions` に書く（`exmem/AGENTS.md`。`contexts/` は 2026-10-10 に廃止）。
  - 身元とトレーラー、範囲、コミット前の確認は、上と同じ。
- **恒常許可の書き方**（2026-10-19 ユーザーの承認。クラウドのセッションの既定の制限が、リポジトリの規約と食い違うとき、Project の指示に書く雛形）: ① 対象のリポジトリとブランチ（例: `workbase` の `main` に直接）。② 承認の範囲（承認済みの変更だけ）。③ 毎回満たす条件（上の「push」の 1〜5）。④ 禁止するコマンド（上の「しないこと」）。
- **報告**に、コミットのハッシュと内容、含めなかったファイルを書く。
