# 仕組みの決定のスクリーニング

仕組み（kit・規則）の決定を、`review 消化` で承認するときの手順の正本（2026-10-18 ユーザーの決定。経緯と根拠は `docs/decisions.md` の同日の項）。流れは `hook-common.md` の「承認」、実行は `review-hook.md` の「消化モード」。

## 3段

1. **待ち行列**: 作業中に出た仕組みの決定は、承認を求めず、`docs/log.md` の Open Questions に `場所 / 問題 / 案` で置く。判断は、置いたセッションの次の `review 消化` 以降（その日のうちに決めない）。理由: 作業の話をしているときに、抽象度の高い仕組みの承認へ頭を切り替えると、判断がずれる。
2. **スクリーニング**: 消化の中で、サブエージェントを1回起動する。この会話の流れは渡さない。渡すのは、決定の文（決める内容をそのまま写す）、`decisions.md` の検索結果（同じ名前・置き場・論点）、`user-manual.md` の関連する Principles、下の型 A〜E。
3. **最終判断**: ユーザーが1件ずつ判断する。正式化、保留、却下。

## 型

過去の覆し・取り消し5件（2026-10-05 の cwd 前提の取り消しと `.obsidian` の置き場、10-16 の `_noai` 廃止と open/close 統合、10-17 の跨ぎ、10-16→10-18 の kit-growth の docs）から分けた。割り当ては AI の読みで、事実は各記録にある。

| 型 | 内容 |
|---|---|
| A | 先行する決定を示さずに提案・承認した |
| B | 削る・統合する案で、今の役目を挙げなかった |
| C | 場所・手段が曖昧なまま承認した（実現方法を任せた） |
| D | 別々の論点を1つの承認にまとめた |
| E | AI の推奨をそのまま通した |

型 C は、作業中の具体的な確認（実装前に場所・手段・呼び出し元を3行で見せる。`user-manual.md`）で防ぐ。ここでは A・B・D・E を見る。

## 出力の形

1件ごとに、次を固定の順で出す（モバイルで読める長さにする。1件で数行）。

- 決めたこと
- 食い違う過去の決定（日付つき。無ければ「なし」）
- 型の該当（A〜E。無ければ「なし」）
- 覆す可能性（高・中・低と理由1行）
- 代替案
- 推奨（正式化 / 保留 / 却下）

## 仮決め

作業を止められない決定だけ、待たずに `decisions.md` の見出しに `【仮 〜YYYY-MM-DD】` を付けて書く。期限は7日。`review 消化` が期限切れを挙げ、正式化・却下・延長をユーザーに聞く。延長は1回（7日）まで。2回目の期限が切れたら見出しを `【保留】` にする。`main` に入った変更は戻さない。
