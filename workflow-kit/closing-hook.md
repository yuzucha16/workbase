# 「終了処理して」フック

作業の終わりに行う処理を、順序を固定して1つにまとめたフック。ユーザーが「終了処理して」と言ったときだけ実行する（自発的には実行しない）。ソース側（作業ディレクトリ）の終了処理で、exmem 側の統合（`integrate-hook.md`）とは独立している。

出力のブレを減らすため、順序・報告の型を固定してある。各手順の中身は、既存の正本（`docs-rules.md`、`knowledge-hook.md`）を参照し、ここに複製しない。

## 場所と書き込みの制約

- 書き込み先は、手順ごとの正本に従う。`docs/`（`docs-rules.md`）、`exmem/inbox/` の新規ファイル（`knowledge-hook.md`）、作業ディレクトリのコミット（`docs-rules.md` の「コミットと push」）。`exmem/knowledge/` などは触らない（統合は `integrate-hook.md`）。
- push はしない（ユーザーが行う）。`exmem/inbox/` のメモはコミットしない（`docs-rules.md`）。例外: 使い捨ての環境（クラウドのセッション）では、メモもコミットし、push まで行う（`docs-rules.md` の「使い捨ての環境での緩和」）。
- 手順の途中で承認が要るもの（既存ファイルの差分、リスクや制約が生まれる変更）は、`docs-rules.md` に従って、先にユーザーへ確認する。

## 手順

1. **プランモードなら先に抜ける**（`knowledge-hook.md` の手順 1 と同じ）。
2. **対象を特定する。** この作業で変更したリポジトリを列挙し（`git status`）、`docs/` を持つものを更新対象にする。作業が複数のリポジトリにまたがるときは、すべてを対象にする。**リポジトリの中の Project・Area が、リポジトリの `docs/` とは別に、自分の `docs/`（`decisions.md` を含む）を持つとき（`projects/` `areas/` `archives/` 配下）は、それも別の対象に数える**（`log.md` と `decisions.md` の更新と、棚卸しの対象。閉じた Project の `archives/` 配下も、今回の作業で変更したか、`未仕分け` `転記待ち` が残っていれば対象）。どれにも `docs/` が無ければ、変更した共通機能の変更履歴を対象にする。exmem だけで進めた作業（Vault から見えない場所の作業。クラウドのセッションなど）では、`exmem/contexts/<名>/context.md` の `Current State` と `Next Actions` を更新の対象にする（`exmem/AGENTS.md` の「作業を終えるとき」）。それも無ければ、この手順を省略して、報告に書く。
3. **`docs/` を更新する。** `docs-rules.md` に従い、`log.md` の Next Actions と Log、`decisions.md` を更新する。Decisions に書くのは、ユーザーが明示または承認したものだけ。
4. **棚卸しをする。** `pwsh -NoProfile -File <kit>/tools/check-docs.ps1`を、対象ごとに実行する。`pwsh` が無い環境（クラウドのセッションなど）では手で確認し、報告に「点検スクリプトは未実行（手で確認）」と書く。手で見る項目は、各項目に【汎用】か【この件】と `行き先:` が1つずつあること、状態が6種のどれかであること、`転記待ち` が20件以下であること（`docs-rules.md`）。`docs/` が無く、`context.md` だけを更新した作業は、`転記待ち` が無いので「対象の `docs/` なし」と書く。FAIL は直す。`未仕分け` `転記待ち` `滞留` の件数を報告に書く。`転記待ち（→ exmem/inbox/<メモ>）` の項目は、メモが `exmem/inbox/` に無くなっていれば、`docs-rules.md` の「棚卸し」に従って、`転記済` に進める案を出す（統合先に、根拠と却下案が写っているかまで確認する）。
5. **ナレッジ化する。** 知識があれば、`knowledge-hook.md`（手順 2 以降）に従う。会話に、再利用できる知識が無ければ、「ナレッジ無し」と報告して、この手順を省略する。`docs/` の `未仕分け` の【汎用】項目も、`knowledge-hook.md` の定めどおり対象にする。**メモを作ると、元の項目の行き先が `転記待ち` に変わるので、手順 4 の `check-docs.ps1` を、メモを作った対象について再実行し、以後の報告（手順 7・8）の件数は再実行後の値にする。**
6. **コミットする。** `docs-rules.md` の「コミットと push」に従う（パス指定、ステージの行数の確認、agent の身元とトレーラー）。`exmem/inbox/` のメモはコミットしない。
7. **統合待ちを報告する。** 次の2つを数える。
   - `exmem/inbox/` の未統合メモの数（`README.md` を除く）。
   - 対象の `docs/decisions.md` にある `転記待ち` の件数（`check-docs.ps1` の内訳）。**対象が複数あるときは、`docs/` ごとの件数と、合計の両方を報告する。**
   - メモが **5 件以上**、または、いずれかの `docs/` で `転記待ち` が **15 件以上**（上限は 20 件で、`check-docs.ps1` は `docs/` ごとに FAIL にする。合計では判定しない）なら、「inboxを整理して」（`integrate-hook.md`）を勧める。合計が 15 件以上で、どの `docs/` も 15 件未満のときは、勧めずに、合計と内訳を報告する。
8. **報告する**（下の「報告の型」）。

## 報告の型

1. **更新した `docs/`**: パスと、変更の要点（Project・Area の `docs/` も、別の行で）。
2. **棚卸し**: `check-docs.ps1` の結果（FAIL / WARN の件数、`未仕分け` `転記待ち` `滞留` の件数）。対象ごとに書く。件数は、ナレッジ化の後の再実行の値（メモを作ったときは、`転記待ち` が増えている）。`転記済` に進める案があれば、一覧にする（承認が要る）。
3. **ナレッジ化**: 作成したメモのパス（コミットしていない旨を、メモに限定して添える）。無ければ「ナレッジ無し」。
4. **コミット**: ハッシュと内容、含めなかったファイル。push のコマンド（実行しない。使い捨ての環境では、push の結果）。
5. **統合待ち**: 未統合メモの数、`転記待ち` の件数（`docs/` ごとと合計）、統合を勧めるか。
6. **改善案**: 下の「このフックの改善」に従う。

## このフックの改善

改善の流れは、`knowledge-hook.md` の「このフックの改善」と同じ（1〜3点を `場所 / 問題 / 案` で提案、承認後に kit を直し、`improvements.md` に残し、見本やモバイル用プロンプトを合わせる）。実行後に、次を確認して報告する。

- 順序で迷った点、手順の間で重複した作業、コンテキストが膨らんだ箇所。
- 閾値（メモ 5 件、`転記待ち` 15 件）が、実際の運用に合っていたか。

**承認なしに、kit を書き換えない。**
