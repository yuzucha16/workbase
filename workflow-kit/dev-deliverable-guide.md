# `dev` の成果物の作り方

`type: dev` の Project で、作って保守する成果物（ツール、環境、テスト、文書）の、構成・文書・テスト・チェックの型。`room open` の前と最初の `brief` が、`type: dev` のときに読む。スクリプトを書く・動かすときは、全 type 共通の `script-guide.md`（言語の選び方、部屋で完結させる方針、Windows で実行するスクリプト）も読む。`inv`（調査）の成果物は `report.md` だけで、この文書は読まない。理由と根拠は `exmem/lessons/ai-tool-deliverable-structure.md`（他環境1か所の実績に基づく。この環境では未検証）。Excel VBA 固有の落とし穴は `exmem/lessons/excel-vba-ai-development.md`。

記号: `<Area>` は責任領域、`<Project>` は作業の単位、`<成果物名>` は配布する成果物1つ。1 Project = 1 成果物（`project-structure.md` の「Project を立てる前の判断基準」）。複数なら Project を分ける。

## 置き場

`ai/` と `_noai/` の直下の用途と、成果物（`ai/out/<成果物名>/`）の構成要素の用途は、`project-structure.md` が正本（ここに図を重ねない）。成果物は `ai/out/<成果物名>/` に置く。`close.md` `stock/` などの予約名は成果物の名前にしない。

Area の共通ルール（Project を跨ぐ約束）は、Area の README に書く。部屋の AI は `ai/ctx/area-README.md` で読む。Project 固有の約束は、成果物の README か、Project の `ai/docs/decisions.md` に置く。

## 構成要素の選び方（`ai/out/<成果物名>/`）

成果物の主な形で、置く構成要素を選ぶ（用途と主な活動は `project-structure.md`）。使わない構成要素は作らない。

| 成果物の主な形 | 置くもの |
|---|---|
| ツール・アプリ | `README.md` `docs/`（3文書）`src/` `tests/` `tools/` |
| 環境構築 | `README.md` `docs/`（環境の要求仕様と運用マニュアル）`env/` `tests/`（確認スクリプト）`report.md` |
| テストだけ | `README.md` `docs/`（テスト仕様）`tests/` `tools/` `report.md` |
| 文書だけ | `docs/`（基準文書の形は未決。`project-structure.md` の「未決」） |

`tests/` と `tools/` の境目: 基準文書の要求・検証項目に対応する検査は `tests/`（`env/` の確認スクリプトを含む）、成果物を作る・動かす補助（変換・生成・実行・検査の束ね）は `tools/`。

| パス | 内容 |
|---|---|
| `README.md` | 利用者向けの入口。章立ては下の「文書の型」の README の型 |
| `docs/` | 正本の文書（基準文書） |
| `src/` | ソース。正本と、そこから生成する派生物（実行環境が要求する形式） |
| `env/` | 実行環境の定義（セットアップのスクリプト、コンテナ定義、版の固定） |
| `tests/` | 自動テスト。末尾に「範囲外（実環境で確認する）」 |
| `tools/` | 変換・生成・実行の補助スクリプト |
| `report.md` | 実行の結果（`env/` の確認結果と版の一覧、`tests/` の実行結果） |

HTML など、`docs/` から生成するものは派生物。直接編集しない。

## 守ること

- 編集するのは正本だけ。派生物はスクリプトで生成する。検査に失敗したら何も書き出さない。
- 仕様書の識別子（関数名・定数名・シート名・セル番地）は、ソースと同じにする。食い違ったらソースが正で、文書を直す。
- 異常を見つけたら、何も書かずに中止する、または「要チェック」にして人に渡す。
- 設定値は先頭の定数に集め、一覧を機能仕様書に載せる。色・文言・書式は、決めたら1か所に書く。
- 未確認を確認済みと書かない。README の状況表に、実環境での確認の有無を書く。
- 同日の仕様変更は、要求 → 機能 → 運用 → README → テスト → 派生物の順に、全層をそろえる。

## 文書の型

- 3点セットは、「変更」（`methods.md`）の基準文書を兼ねる（`work/` の中間成果物は作業中の下書きで、別物）。
- 3点セット: 要求仕様書（何を満たすか。ID 付き、1 ID = 1要求 = 検証できる文）→ 機能仕様書（どう実現するか）→ 運用マニュアル（使い方と困ったとき）。ID は、既存の最後の番号の次から振る（欠番や振り直しをしない）。
- 要求は「〜する」で言い切り、数値・文言まで具体的に書く。中止の条件を列挙する。未確認は明記する。
- 図は1章に全体図を入れ、入力・本体・出力の3区分で説明する。用語表で、同じ概念に別の語を使わない。
- README の型: 状況（実環境での確認の有無を含む表）→ 実行環境 → ファイル構成（何が正本で、どれが生成物か、再生成のコマンド）→ 変更後の標準手順 → 導入 → 使い方 → 設定 → 注意。README と `docs/` で、同じ表を重複させない。
- 保守を AI に頼むため、運用マニュアルに変更依頼のひな形を持たせる。順序は、背景 → 入力 → 守ること → 出力の形式 → 注意 → 変更依頼。記入欄は、種類・したいこと・期待する動作・現在の動作・変えてはいけないこと・確認方法の希望。不具合のときは、再現手順、エラー全文（工程名つき）、結果の全文、期待値と実際の値を足す。

## テスト

- 2層に分ける。部屋の中で完結する層（合成データの自動テスト）は AI が実行する。実環境が要る層（Excel などのアプリ、実データでの見た目）は人が Windows で実行する。
- 合成データはスクリプトの中で作る。実データ・個人名・金額は使わない。
- 出力は `PASS <名前>` / `FAIL <名前> <詳細>` と最後の件数。終了コードは全件合格で 0、不合格ありで 1。所要は1分未満を目安にする。
- 区分の型: 準備、正常系（対象外と入力ファイルが不変であることを含む）、ログ、別モード、中止（何も書かれていないことを確認）。
- 実環境で実行した結果を AI に渡すときは、人が実データの語を伏せてから渡す（`ai/` と `_noai/` の往復を減らすため、できるだけ部屋の中のテストで済ませる）。

## チェック

立ち上げ（`room open` / 最初の `brief`）:

1. 曖昧な点を先に聞く（入力の取り方、置き場所、既定の挙動、境界ケース）。答えは `ai/docs/decisions.md` に「ユーザー回答」として残す。依頼文の誤記は、解釈の根拠を備考に残す。
2. 正本を書く（`src/` なら、定数を先頭に集めたソース。`env/` なら環境定義）。検査して派生物を生成する。
3. 合成データのテストを、正本と並行して育てる。
4. 文書を、要求 → 機能 → 運用 → README の順に、正本を見て識別子を合わせて書く。
5. `ai/docs/log.md` と `decisions.md` を更新する。報告に、「実環境で未確認の点」と「利用者にお願いする確認」を書く。

完了の定義（共通）: 検査が通り派生物が最新 / 自動テストが全件合格（件数を記録）/ 文書が最新で識別子が正本と一致 / 派生物を再生成済み / README の状況表に実環境での確認の有無を正直に書いた / 記録を更新した。成果物の形ごとの完了条件の例は、次の節。

## 環境構築とテストが主の成果物の差分

`dev` の工程のうち、環境構築とテストだけを成果物にする Project（2026-10-16 に `dev-env` `dev-test` の type として足した叩き台。2026-10-24 に type を `dev` と `inv` の2つに集約し、`env/` を構成要素にした。実測が無い）。`env/` が主の成果物が想定するのは、主にテスト環境を作ること。上の型（守ること、README の型、テストの2層、完了の定義）は、そのまま使う。違いだけをここに書く。

別の成果物との関係: 子の Project ではなく、独立の Project（1 Project = 1 成果物。Project は入れ子にしない）。成果物の受け渡しは、ほかの Project と同じく、人が次の Project の `ai/in/` に置き、`room start --adopt` で入力として記録する。例: `env/` が主の成果物 → 次の `dev` の `ai/in/`、`src/` の要求仕様書とソース → `tests/` だけの `dev` の `ai/in/`。

| | ツール・アプリ（`src/`） | `env/` が主（環境構築） | `tests/` だけ（テスト） |
|---|---|---|---|
| 成果物 | 上の「ツール・アプリ」 | 環境定義（`env/` にセットアップのスクリプト、コンテナ定義、版の固定ファイル）、`tests/` に確認スクリプト、README（導入手順）、`report.md`（確認の結果と版の一覧） | `tests/`、`tools/`（実行スクリプト）、`report.md`（実行結果。件数と、実環境での確認の有無） |
| 基準文書（`docs/`） | 3文書（要求仕様・機能仕様・運用マニュアル）。正はソース | 環境の要求仕様（対象、道具と版、ID 付きの検証項目）と運用マニュアル（導入、困ったとき）。機能仕様書は省いてよい | テスト仕様（要求 ID とテストの対応表、観点、合否の基準）。正の向きは、テスト対象の要求仕様（`ai/in/`）。食い違いは対象の Project に返す |
| 立ち上げで聞くこと | `brief-work-types.md` の開発の表 | 対象環境（OS、ネットワークの有無、管理者権限）、環境の置き場（下の表）、再現の方式（スクリプト、コンテナ、手順書）、版の固定の要否 | テスト対象と、その要求仕様の版、層（部屋の中の自動テスト / 実環境で人が実行）、合否の基準 |
| 完了条件の例 | 検査が通り、自動テストが全件合格し、文書が最新で識別子がソースと一致する | 新しい環境でセットアップを実行し、確認スクリプトが全件 PASS する（版の一覧を `report.md` に記録） | 要求仕様のすべての ID にテストが対応し（対応表に欠けが無い）、部屋の中の自動テストが全件実行され、結果を `report.md` に記録した |

環境の置き場（`env/` が主のときに聞く。答えで、公開時の扱い、検証する人、基準文書の正の向きが決まる）:

| 置き場 | AI ができること | 注意 |
|---|---|---|
| ローカル（部屋の中） | 作って、検査まで実行する | 通常の環境構築 |
| リモート・コンテナ（WSL から SSH で、user 権限で操作する場合を含む） | 部屋からは届かない。定義とスクリプトを作り、実行と確認は人が行う | ホスト名・認証情報はマスクして `ai/in/` に渡す。`remote` の type は足さない（2026-10-24 の決定。この質問で扱う） |
| リポジトリ（公開 / 非公開） | ファイルを作る | 公開なら秘匿値・社内のホスト名・絶対パスの検索を完了条件に入れる。正の向きはリポジトリ側（`project-structure.md` の「未決」） |
| GitHub / GitLab のようなサービス（CI、権限、設定） | できない（権限が無い）。ワークフローのファイルの案までで、設定と実行は人が行う | この仕組みでは AI に任せられない。人の作業として扱う |

- `env/` が主の成果物は、部屋の中では実環境を作れない。部屋の中で確かめるのは、スクリプトの静的な検査と、作れるならコンテナでの実行まで。実環境での実行と結果の記録は人が行う（検証項目に「人が実行」と書く）。
- `tests/` だけの成果物は、テスト対象を直さない（`ai/in/` は読み取り専用）。不具合は `report.md` に書き、対象の Project に返す。テストの不合格は、成果物の失敗ではない（完了条件は「対応と実行と記録」）。
- テスト対象がリポジトリの clone のときの置き場は、`project-structure.md` の「未決」（リポジトリが正の `src`）に従う。
