# plan フック（別名「計画を立てて」）

呼び出し名は plan。別名は「計画を立てて」。呼び出し表の正本は `hooks.md`。ユーザーが言ったときだけ実行する（自発的には実行しない。`brief` が勧めることはある）。手順と欄の定義は `plan-fields.md`。

## 目的と契機

- **目的**: Project の方向性が未決の状態（`room open` の直後）を、6R → 論点出し → 憲章以降（任意）で決め、`ai/work/plan/` に置く。作業を進める側（`room start` の直後）は `brief` が受け持つ。
- **契機**: ユーザーが「計画を立てて」と言ったときだけ。`brief` は、`ai/work/plan/` が無い、または先頭が `status: 仮` のときに、一度だけ勧める（止めない）。小さな Project で、計画をユーザーの頭の中で進めるなら、使わなくてよい。論点出しだけなら `frame`（「論点出し」「課題設定」。`frame-hook.md`）を使う。
- **前提**: Project が `room open` で作ってある（部屋の中）。workbase の題材は、置き場が `plan-fields.md` の「置き場」。

## 場所と書き込みの制約

- 起動できる領域は `hooks.md` の「領域とフックの権限」に従う（部屋での扱いは `room-context.md`）。
- 書き込み先: 部屋の `ai/work/plan/`（置き場の全体は `plan-fields.md`）と、ひな形のままの README 本文の下書き（人に断ってから。書き方は `room-context.md` の「README 本文の下書きの書き方」）。
- 承認（先頭の `status: 正式` と `approved:`）はユーザーが書く。AI は正式にしない。
- 既存の計画は、更新する（`正式` の計画を書き換えたら、次の `room start` が警告して `仮` に戻す）。

## 手順

1. **事前確認**: `ai/work/plan/` の状態（無い、`仮`、`正式`）を見る。閉じた Project の引き継ぎ（`ai/in/from-<前>/` がある）なら、`plan-fields.md` の A に従って前の計画と `close.md` を先に読む。
2. **作る**: `plan-fields.md` の B に従う。6R（必須。ここで止まってよい）→ 論点出し（6R に未決があるとき）→ 憲章・成果物 WBS・マイルストーン（任意。大きめの Project だけ）。README がひな形のままなら、6R の前に下書きする。
3. **返す**: 作ったものの要約と、ユーザーが直す点・決める点を返す。論点出しの判断（決・任・後・確・聞）はユーザーが付ける。
4. **記録する**: 迷った点・決めたことは、`plan-fields.md` の「実行後の所見の置き場」に従う。

## 報告の型

共通の項目（`hook-common.md` の「報告の型」の節だけ読む。全文は読まない。コミット、次にやること、固有の項目、ユーザーに求めることの順）を報告する。このフックでの追記:

- **ユーザーに求めること**: 承認（`status: 正式`）、論点の判断（決・任・後・確・聞）、直す点。
- **コミット**: このフックはコミットしないので、「なし」と書く。
- **次にやること**: 承認のあとは `brief`。

固有の項目（「次にやること」の後、「ユーザーに求めること」の前）:

1. **計画の状態**: 作った計画（6R、論点出し、憲章以降）のどこまでか、`status`（`仮` か `正式`）、置いたパス。
