## 区分（Must と Want）

- **Must**: 全フックに ○ か △ が付いている行（— が無い行）。満たさないフックがあれば、欠陥として直す案を出す。点検スクリプトが見る行は、`review` が実行して確認する。
- **Want**: — のフックがある行。足すかどうかは、重さ（字数の増え方）と複雑性（影響する参照・点検の数）で決める。足さなくてよい（フック固有の行を含む）。
- Must の行は、新しいフックにも求める。行が全フックで ○ か △ になったら、Must に上げる（表の「区分」を直す）。

## 肥大化の抑制（2026-10-08 ユーザーの決定）

- **字数の目安**: 各フックの本体（`*-hook.md`）は 5,000 字までを目安にする。超えるフックは、Want として畳む候補にする（`review` が測る）。
- **字数の例外**: stock（7.5k。書き方が、頻繁に使うために同居している。2026-10-17 に 8.8k から縮めた）、init（6.4k。任意の2章とモード `init 更新` は別ファイルに分離済み）。例外を増やすときは、理由をここに書く。
- **Want の行は増やさない**: 表に Want の行を足すときは、既存の Want の行を1つ畳む（規模の凍結と同じ考え方）。Must の行は、足してよい。

## review の点検

`review-hook.md` の手順「網羅度を確認する」が、この節を実行する（2026-10-16 に、手順の本文から移した。点検の項目が増えたため、この表と点検を1か所にまとめた）。

1. `pwsh -NoProfile -File <kit>/tools/check-hook-outline.ps1` を実行する（FAIL は Must の違反）。
2. 表の字数の行を、測り直して更新する（測定は表の冒頭）。
3. 区分が Must の行に、— のフックが無いか見る（点検スクリプトが見ない行も含む）。満たさないフックがあれば、直す案を出す。
4. **領域の権限の期待**: 「領域の権限の期待」の行を、`hooks.md` の「領域とフックの権限」の表と、各フックの「場所と書き込みの制約」で比べる。次を見直しとして挙げる: 手順書の記述が表と違うフック、書き込み先が増えたのに表が古いフック、表の型（読み・作業対象の `docs/`・窓口）に当たらない跨ぎ書き込みが書かれているフック。直したら、行の確認日を更新する。
5. 区分が Want の行は、— のフックについて、足す案を最大1つ出す。案には、重さ（字数の増え方）と複雑性（影響する参照・点検の数）を添える。足さないと判断してよい。字数の目安（5,000 字。例外は「肥大化の抑制」）を超えるフックは、畳む案を出す。
6. 「重さの基準」と比べ、増えたフック（字数 +20%、手順・報告の項目数 +2）を見直しの対象にして、そのフックの星取り表と修正・削除・追加の対応表を作り、ユーザーに示す（作り方は exmem の `lessons/improvement-coverage-matrix.md`。承認制）。

7. **変更・調査のやり方の Must**（試験運用。`methods.md` の「変更」「調査」）: 前回以降の変更を1〜2件選び、記録（コミットか `decisions.md`）に、基点・影響範囲・検証の結果があるかを見る。調査の成果物があれば1件選び、出典の日付と URL、一次と二次の区別、確認できなかった点があるかを見る。調査2の手順書があれば1件選び、各コマンドの出典（一次情報）、各手順の「確認」、確認できていない点、チェックリストがあるかを見る。振り返り（改善4）の成果物があれば1件選び、評価軸の宣言、見えない範囲、良い点と悪い点の各最大3個の対、AI による計数、施策の承認待ちの明記があるかを見る。無ければ Must の違反として直す案を出す。3回の `review` の後に、Must が重すぎないか・足りないかを見て、増減を決める（`topics/kit-growth/docs/log.md` の Next Actions）。

枠の数え方: Must の違反の修正と、重さの基準の見直し(6)は、`review-hook.md` の手順「1つ直すか、1つ畳む」の「最大1件」の枠とは別に数える（承認制）。Want の案(5)は、枠に数える。
