## 区分（Must と Want）

- **Must**: 全フックに ○ か △ が付いている行（— が無い行）。満たさないフックがあれば、欠陥として直す案を出す。点検スクリプトが見る行は、`review` が実行して確認する。
- **Want**: — のフックがある行。足すかどうかは、重さ（字数の増え方）と複雑性（影響する参照・点検の数）で決める。足さなくてよい（フック固有の行を含む）。
- Must の行は、新しいフックにも求める。行が全フックで ○ か △ になったら、Must に上げる（表の「区分」を直す）。

## 肥大化の抑制（2026-10-08 ユーザーの決定）

- **字数の目安**: 各フックの本体（`*-hook.md`）は 5,000 字までを目安にする。超えるフックは、Want として畳む候補にする（`review` が測る）。
- **字数の例外**: stock（8.8k。手順の例外の細則と書き方が、頻繁に使うために同居している）、init（6.4k。任意の2章は別ファイルに分離済み）。例外を増やすときは、理由をここに書く。
- **Want の行は増やさない**: 表に Want の行を足すときは、既存の Want の行を1つ畳む（規模の凍結と同じ考え方）。Must の行は、足してよい。
## 重さの基準

基準日 2026-10-16（`wrap` を軽くした `9fbf4e4` の後）。`review` が今の値と比べ、**基準より N 増えたフック**を見直しの対象にする。N は仮（2026-10-16 ユーザーが20%で開始。根拠なし。3回の `review` の後に、見直しの対象になった件数から決め直す）。

- **測り方**: 字数は上の「測定」のコマンド（`*-hook.md` の文字数。表の字数の行は0.1k単位の丸め）。項目数は、H2「手順」「報告の型」の番号つきの項目の数。
- **N**: 字数は基準の +20% 以上。項目数は小さい数で割合が跳ねるので、**+2 以上**（割合は使わない）。
- **比べる相手は前回でなく基準**（少しずつ増えて見逃すのを防ぐ）。見直しの対象になったら、`improvement-coverage-matrix.md` の流れで、そのフックの星取り表と修正・削除・追加の対応表を作り、承認された案を実施する（`review-hook.md` の手順「網羅度を確認する」）。実施後（または「このままでよい」とユーザーが決めたとき）に、基準をその時点の値に更新する。
- 基準より減ったときは、基準を下げる（軽くした分を、後から使い切れる余裕にしない）。
- 共有の参照ファイル（フックが読む。字数の参考）: `docs-rules.md` 9,396、`hook-common.md` 3,033、`hooks.md` 2,761。これも基準より +20% 増えたら、対象に挙げる。

## 残っているズレ（2026-10-08 時点）

1. **字数**: stock が 8.8k（手順 4.0k のうち例外の細則が約 1.3k、書き方 2.0k）。頻度が高く、分離は読み忘れのリスクがあるため、見送り。
2. **「前提」項目**: open と close だけが書く。書かれていないことは書かない約束なので、未記載のまま。
3. **承認が要る操作の明記**: 制約に書くフックと、書かないか部分的なフックが混在。
4. **自己点検**: init と stock だけ。

6. **自発実行の例外の書き方**: open、close、review、start の例外が、契機の文に散在。点検対象外。
