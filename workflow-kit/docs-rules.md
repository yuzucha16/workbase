# docs/ の運用規則

作業ディレクトリの経緯・決定・次にやることを、そのディレクトリの `docs/` に残す。`docs/` は各作業ディレクトリの側に置き、exmem には置かない（exmem は知識・経験・ルールの置き場で、作業ログは置かない。`docs/` は将来、日報・仕様書・手順書などの文書の入力にもなる）。ナレッジは exmem の担当で、ここには書かない（再利用できる知識は「ナレッジ化して」で渡す。`stock-hook.md`）。

## ファイル

| ファイル | 役割 |
|---|---|
| `docs/log.md` | 現在の状態と次にやること。作業を再開するときの入口（短く保つ。4KB 目安。上書きで更新する） |
| `docs/log-history.md` | 経緯（日付つきの Log）と、過去の Next Actions の全文。開始時に読まない。必要なとき検索する |
| `docs/decisions.md` | 判断の根拠（Why）、却下案、Gotchas、実機で確認した事実 |
| `README.md`（あれば） | 構成と使い方（How）の正本 |

`README.md` と `docs/` で同じ表を重複させない。

小さく一過性のディレクトリには、専用の `docs/` を置かない。親の作業ディレクトリの `docs/` に含める（小さな作業のために `docs/` 一式を持つのは適正でない）。

## 読む順番

1. 窓口（`README.md`、トピックは `*-start-here.md`。あれば）
2. `docs/log.md`（開始時に読むのはここまで。「期日」の節があれば、今日以前または3日以内の項目を、最初の返答で知らせて判断を求める）
3. `docs/decisions.md` と `docs/log-history.md` は開始時に読まない。何かを決める・変える前に `decisions.md` を検索して、既存の決定と矛盾しないか確かめる。経緯が要るときは `log-history.md` を検索する

### 上の階層で起動して「<名前> の続き」と言われたら

起動する単位（cwd）は、リポジトリのトップだけにする。下位の単位（リポジトリ直下のディレクトリ、トピック、Project、Area）は、cwd を増やさず、この規則で扱う。その単位の窓口 → `docs/log.md` の順で読む（`AGENTS.md` があればそれも読む）。その単位が、このセッションで作業した単位になる（`wrap` の書き込み先）。実行できるフックと、領域をまたぐ書き込みの型は、`hooks.md` の「領域とフックの権限」。単位に `docs/` が無いときは、親のリポジトリの `docs/` に書く。

## 更新のタイミング

- 作業の終わりの処理（更新、昇格の案、コミット）は、「終了処理して」フック（`wrap-hook.md`）が順序を固定して行う。
- 作業の終わりに、`log.md` の現在状態（Next Actions、Open Questions）を更新し、`log-history.md` の `## Log` の先頭に日付つきで追記する。
- 判断（決めたこと・根拠・却下案）、遭遇した詰まり、実機で確認した事実は、その場で `decisions.md` に書く。
- 「ナレッジ化して」の前に `docs/` が未更新なら、先に更新する。

## log.md の書式

```markdown
# 作業ログ（log）

<このディレクトリの現在状態と次にやること。経緯は docs/log-history.md、判断の根拠は docs/decisions.md。>

## 期日（日付つきの項目があるときだけ）
## Next Actions
## Open Questions
```

`log-history.md` の書式: `# 作業ログの経緯（log-history）`、`## Log`、日付の見出し `### YYYY-MM-DD`、1項目で完結する記述。過去の Next Actions の全文も、ここに残す。

- Log は日付の降順。新しい日付の見出しを上に足す。
- **1項目は単体で読めるようにする**: 何を・なぜ・結果（確認したか）を書く。判断を伴うなら `decisions.md` の項目名を添える。コミットや関連ファイルがあれば添える。日報・週報・仕様書などの入力に使うため、「あれ」「さっきの」のような会話依存の表現を避ける。
- Next Actions は、終わったら `log.md` から消す。経緯は `log-history.md` の Log に残る。一部が終わったら、その部分を `log-history.md` へ移し、項目は残りだけに書き直す。`log.md` に進み（`【MM-DD】〜した` の子項目、「（済）」の印）を積まない。移すのは `wrap`（`wrap-hook.md` の手順 2）。
- Open Questions は、決まったら `log-history.md` の Log に移して `log.md` から消す。
- **期日の節**（2026-10-16 ユーザーの決定）: 日付で浮上する項目の置き場。表は `期日 | 種別 | 内容 | 担当`。種別は、**単発**（判断すれば消える）と、**定例**（周期で戻ってくる。例: 週1の `review`）。定例は、実行したら次回の期日に書き換え、消さない。Next Actions と Open Questions には、終わりのある項目だけを置く。周期のある項目は置かない（置くと「0 になる」判定が成り立たない）。
- **Next Actions の期限**（2026-10-21 ユーザーの決定）: 無条件に、起票から1週間。項目の先頭に `【起票 MM-DD】` を付ける。期限（起票＋7日）が来たら、閉じるか、延ばすか（延ばすなら理由つきで起票し直す）を、最初の返答で聞く。起票日の無い既存の項目は、次に触るときに付ける。
- `log.md` が 4KB を超えたら、古い状態を `log-history.md` へ移して縮める。

## decisions.md の書式

```markdown
# 判断の記録（decisions）

## Principles
## Decisions
### 【汎用】<決めたこと>（YYYY-MM-DD）
- 決めたこと / 根拠 / 却下案 / 確認済み（日付と根拠）
- → <名前>（知識にしたとき。次の節）
## Gotchas
```

- Decisions は、決めたこと・根拠・却下案をそろえる。根拠や却下案が無いものは Facts として書く（見出し `## Facts` を足してよい）。
- **決定として書くのは、ユーザーが明示または承認したものだけ。** AI の提案は「提案」と書き、承認を確認できるまで決定にしない。理由: 提案が決定として残ると、以後の判断が、承認されていない前提に乗る。
- 撤回した決定は消さず、「撤回済み」と理由・日付を残す。
- 撤回・取り消しの理由は、「確認できた事実」と「推測」を分けて書く。同じ撤回を複数の場所に記録するときは、理由の正本を1か所に決め、ほかはそこを指す（理由を各所に書き直さない）。理由: cwd 前提の変更の取り消し（2026-10-05）は、理由が2か所で食い違い、誰も当時の理由を言えなくなった（2026-10-17 の振り返り）。
- 決定を覆したときは、「覆した決定」の行に、型（A〜E。不明なら「不明」）と欠けていた入力を1行で付ける（型は `approval-screening.md`）。仮決めは、見出しに `【仮 〜YYYY-MM-DD】` を付ける（同じ）。
- Gotchas は、実際に遭遇した詰まりと解決方法だけ。方針は Principles へ。
- 各項目に、ラベル（【汎用】【案件】【この件】のどれか）を付ける。知識にしたら `→ <名前>` を足す（次の節）。【案件】は AI 作業部屋の Project だけで使う（Area の他の Project にも効く項目。`room` が回収のときに Area の `ai/docs/inbox.md` へ転記する。2026-10-14 ユーザーの決定。部屋を使わない作業ディレクトリでは、【汎用】か【この件】だけ）。

## decisions.md の項目を知識にしたとき

`docs/` で生まれた知識とルールが、どこにも行き場がなく溜まるのを防ぐ。`docs/` は共有しないので、知識は exmem へ、全作業ディレクトリに効く規約は kit へ、一般化して渡す（コピーはしない。固有情報が共有側に出て、正本が複数になるため）。

- 項目の頭に、【汎用】（他の作業でも成り立つ）、【案件】（同じ Area の他の Project にも効く。部屋の Project だけ）、【この件】（この作業に固有）のどれかを付ける（【汎用】と【この件】は `stock-hook.md` と同じ定義）。【案件】は知識にしない（`→` は付けない。Area の `inbox.md` への転記が行き先）。
- 知識（exmem）や規約（kit）にしたら、その項目の末尾に `→ <名前>`（例: `→ inbox/2026-10-08-hook-naming`、`→ kit/hooks.md`）を1行足す。作業側から共有側への参照だけにする（共有側から作業側へは張らない）。**`→` のある【汎用】の項目は運んだもの、無い【汎用】は未**とみなす。状態の欄・日付・本文ハッシュは持たない。メモが統合されて消えた後も、`→` は消さない（統合先は exmem の git の履歴で追える）。
- 一般化とは、固有情報（勤務先・パス・その PC の事情）を剥がして、別のソースでも成り立つ形に書き直すこと。剥がすと意味が失われるものは、【この件】のままにする。
- 運んだ項目の本文は、外さなくてよい（根拠はこの `docs/` に残る）。長いときだけ、見出しと `→` の行に畳む。
- 2026-10-08 より前に書かれた `行き先:` の行は、履歴としてそのまま残す。新しい項目には書かない。
- `→` の無い【汎用】の項目の件数は、`wrap` の報告と `review` で見る（棚卸しのスクリプトは持たない）。

**運び方**はソースの種類で分ける。

- **直結ソース**（`docs/` と共有リポジトリ `workbase` が同じ PC にある）: 「ナレッジ化して」で、`→` の無い【汎用】の項目も対象にして、`exmem/inbox/` へ運ぶ（`stock-hook.md`）。ルールの変更は、kit の改善の流れ（`hook-common.md`）で、承認を得て行う。
- **隔離ソース**（`docs/` を git や通信で共有側へ出せない。例: PC1）: エージェントは、`→` の無い【汎用】の項目を grep し、一般化した短文を画面に出す（1回10件前後）。各件に「個人情報・機密・固有名が無い」確認欄を付ける。ユーザーが別の PC で入力して、「転記した」と申告したら、`→` を足す。

## コミットと push

コミットと push の規則は `commit-push-rules.md` に切り出した（2026-10-26）。コミット・push の前に、そちらを読む（このファイルの全文は読まなくてよい）。

## 書き方の共通ルール

- 日付、バージョン、OS を明記する。確認していないことは「仮説」「未確認」と書く。確認した事実には、根拠（実行したコマンド、見たファイル）を1語添える。
- 長い Markdown（`docs/log.md` など）の書き換えは、Edit ツールで行う。スクリプトで全文を読み書きすると、1か所のミスで文書全体を失う（2026-10-06 に、二重と空の事故があった）。やむを得ずスクリプトで書くときは、書き込みの直前に、内容が空でないことと行数を確認し、書く前に `git` でコミット済み（または退避済み）であることを確かめる。
- 階層化するときは、情報も階層化する。上段（リポジトリ直下の README など、最初に読むもの）は表引きにして、順序、要点、入口だけを書く。詳細（引数、入力、出力、失敗時の挙動、観点）は下段（近くの README など）に置き、上段から指す。詳細は捨てずに、原文のまま下段へ移す。上段と下段に同じ表を重複させない。
- リスクや制約が生まれる変更は、事前にユーザーへ確認する。

## 読み方の共通ルール

- 大きいファイル（目安 10KB 超）は、見出しの一覧を先に見て、必要な節だけを読む。理由: 会話の履歴は毎ターン再送されるので、一度読んだ量が、その後のターンにも載り続ける。
- ログ、一覧、コマンドの出力は、件数、`head`、検索で絞ってから読む。
- スクリプトに読ませるときは、表の全行でなく、要約と件数を返させる（例: 点検スクリプトは FAIL の行と件数だけ）。
