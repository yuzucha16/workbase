# docs/ の運用規則

作業ディレクトリの経緯・決定・次にやることを、そのディレクトリの `docs/` に残す。`docs/` は各作業ディレクトリの側に置き、exmem には置かない（exmem は知識・経験・ルールの置き場で、作業ログは置かない。`docs/` は将来、日報・仕様書・手順書などの文書の入力にもなる）。ナレッジは exmem の担当で、ここには書かない（再利用できる知識は「ナレッジ化して」で渡す。`stock-hook.md`）。

## ファイル

| ファイル | 役割 |
|---|---|
| `docs/log.md` | 現在の状態と次にやること。作業を再開するときの入口 |
| `docs/decisions.md` | 判断の根拠（Why）、却下案、Gotchas、実機で確認した事実 |
| `README.md`（あれば） | 構成と使い方（How）の正本 |

`README.md` と `docs/` で同じ表を重複させない。

小さく一過性のディレクトリには、専用の `docs/` を置かない。親の作業ディレクトリの `docs/` に含める（小さな作業のために `docs/` 一式を持つのは適正でない）。

## 読む順番

1. `docs/log.md`
2. `README.md`（あれば）
3. `docs/decisions.md`

## 更新のタイミング

- 作業の終わりの処理（更新、昇格の案、コミット）は、「終了処理して」フック（`wrap-hook.md`）が順序を固定して行う。
- 作業の終わりに、`log.md` の Next Actions を更新し、Log に日付つきで追記する。
- 判断（決めたこと・根拠・却下案）、遭遇した詰まり、実機で確認した事実は、その場で `decisions.md` に書く。
- 「ナレッジ化して」の前に `docs/` が未更新なら、先に更新する。

## log.md の書式

```markdown
# 作業ログ（log）

<このディレクトリの現在状態と次にやること。判断の根拠は docs/decisions.md。>

## Next Actions
## Open Questions
## Log

### YYYY-MM-DD

- <1項目で完結する記述>
```

- Log は日付の降順。新しい日付の見出しを上に足す。
- **1項目は単体で読めるようにする**: 何を・なぜ・結果（確認したか）を書く。判断を伴うなら `decisions.md` の項目名を添える。コミットや関連ファイルがあれば添える。日報・週報・仕様書などの入力に使うため、「あれ」「さっきの」のような会話依存の表現を避ける。
- Next Actions は、終わったら消す。経緯は Log に残る。
- Open Questions は、決まったら Log に移して消す。

## decisions.md の書式

```markdown
# 判断の記録（decisions）

## Principles
## Decisions
### 【汎用】<決めたこと>（YYYY-MM-DD）
- 決めたこと / 根拠 / 却下案 / 確認済み（日付と根拠）
- → <名前>（知識にしたとき。次の節）
## Gotchas
```

- Decisions は、決めたこと・根拠・却下案をそろえる。根拠や却下案が無いものは Facts として書く（見出し `## Facts` を足してよい）。
- **決定として書くのは、ユーザーが明示または承認したものだけ。** AI の提案は「提案」と書き、承認を確認できるまで決定にしない。理由: 提案が決定として残ると、以後の判断が、承認されていない前提に乗る。
- 撤回した決定は消さず、「撤回済み」と理由・日付を残す。
- Gotchas は、実際に遭遇した詰まりと解決方法だけ。方針は Principles へ。
- 各項目に、ラベル（【汎用】か【この件】）を付ける。知識にしたら `→ <名前>` を足す（次の節）。

## decisions.md の項目を知識にしたとき

`docs/` で生まれた知識とルールが、どこにも行き場がなく溜まるのを防ぐ。`docs/` は共有しないので、知識は exmem へ、全作業ディレクトリに効く規約は kit へ、一般化して渡す（コピーはしない。固有情報が共有側に出て、正本が複数になるため）。

- 項目の頭に、【汎用】（他の作業でも成り立つ）か【この件】（この作業に固有）を付ける（`stock-hook.md` と同じ定義）。
- 知識（exmem）や規約（kit）にしたら、その項目の末尾に `→ <名前>`（例: `→ inbox/2026-10-08-hook-naming`、`→ kit/hooks.md`）を1行足す。作業側から共有側への参照だけにする（共有側から作業側へは張らない）。**`→` のある【汎用】の項目は運んだもの、無い【汎用】は未**とみなす。状態の欄・日付・本文ハッシュは持たない。メモが統合されて消えた後も、`→` は消さない（統合先は exmem の git の履歴で追える）。
- 一般化とは、固有情報（会社・パス・その PC の事情）を剥がして、別のソースでも成り立つ形に書き直すこと。剥がすと意味が失われるものは、【この件】のままにする。
- 運んだ項目の本文は、外さなくてよい（根拠はこの `docs/` に残る）。長いときだけ、見出しと `→` の行に畳む。
- 2026-10-08 より前に書かれた `行き先:` の行は、履歴としてそのまま残す。新しい項目には書かない。
- `→` の無い【汎用】の項目の件数は、`wrap` の報告と `review` で見る（棚卸しのスクリプトは持たない）。

**運び方**はソースの種類で分ける。

- **直結ソース**（`docs/` と共有リポジトリ `workbase` が同じ PC にある）: 「ナレッジ化して」で、`→` の無い【汎用】の項目も対象にして、`exmem/inbox/` へ運ぶ（`stock-hook.md`）。ルールの変更は、kit の改善の流れ（`stock-hook.md`）で、承認を得て行う。
- **隔離ソース**（`docs/` を git や通信で共有側へ出せない。例: 会社 PC）: エージェントは、`→` の無い【汎用】の項目を grep し、一般化した短文を画面に出す（1回10件前後）。各件に「個人情報・機密・固有名が無い」確認欄を付ける。ユーザーが別の PC で入力して、「転記した」と申告したら、`→` を足す。
## コミットと push

コミットは、エージェントが行ってよい（ユーザーの許可: 2026-10-05。すべての作業ディレクトリに適用）。push は、許可リストにあるリポジトリだけエージェントが行い（下の「push」）、ほかはユーザーが行う。

- **範囲**: その作業で自分が変更・生成したファイルだけを、パスを指定して `git add` する（`git add -A` と `git add .` は使わない）。ユーザーの未コミットの変更、並行セッションの変更、内容を確認していない既存ファイル、機密の可能性があるものは、含めない。含めなかったものは、報告に書く。
- **コミットの前に確認する**: ① `git add` の直後に `git diff --cached --stat` で、意図したファイルだけか、**行数が自分の変更量と合うか**。共有された `docs/` や設定ファイルは、並行セッションやユーザーが同じファイルを編集していることがあり、パスを指定しても他人の変更が一緒にステージされる。行数が多いときは、`git diff --cached <パス>` で中身を見て、自分の変更だけに絞る（`git add -p`）か、混ざったことを報告する。② 身元が下の「コミットの身元とトレーラー」どおり。③ トークン、秘匿値、業務固有の情報が入っていない（`git diff --cached` を、`token` `secret` `password` `bearer` `webhook` で検索する。語だけでは漏れるので、URL 中の長い ID も見る）。外れたら、`git reset -q -- <パス>` でステージを戻して、コミットせずに報告する。
- **コミットを分けるとき**（例: 改行だけの変更と内容の変更）は、`git commit` にパスを指定しない。パスを指定した `git commit -- <パス>` は、index ではなく作業ツリーの現在の内容をコミットするので、ステージで分けても1コミットにまとまる。分けたい内容は index に入れ（`git add -p`、または `git hash-object -w --no-filters` と `git update-index --cacheinfo`）、`git diff --cached --stat` で確認してから、パスなしでコミットする（2026-10-07 dotfiles で発生。未 push のコミットは `git reset --soft HEAD~1` でやり直せる）。
- **メッセージ**は `[領域] 変更内容`（そのリポジトリの `AGENTS.md` に固有の規則があれば、それを優先する）。
- **コミットの身元とトレーラー**（2026-10-06 ユーザーの決定。終了処理のコミットだけでなく、作業の途中でエージェントが作るコミットのすべてに適用する）: エージェントのコミットは、人間のコミットと区別できるようにする。remote なしのローカルリポジトリでも、`git log` で「誰の行動か」と「どの時点の規則か」が分かるようにするため。
  - 身元は、コミット1回ごとの `-c` で渡す。`git config`（グローバルも `.git/config`）は書き換えない（後で人間が手動でコミットしたときまで agent 名義になるため）。作者とコミッターは、どちらも agent にする。
  - 名前は `agent`、メールは `agent@agent.local`。道具やモデルは、名前でなくトレーラーに書く。
  - トレーラーは2行を毎回付ける（`git commit --trailer "<キー: 値>"`）。`Agent: <道具> <モデルID>`（例: `Agent: claude-code claude-sonnet-5-5`）、`Kit-Rev: <ハッシュ>`（`resources/` の `git rev-parse --short HEAD`。`resources/` に未コミットの変更（未追跡ファイルとステージ済みを含む。`.gitignore` で除外されたものは含まない）があれば末尾に `-dirty`。判定: `git status --porcelain` が空でない）。
  - 例: `git -c user.name=agent -c user.email=agent@agent.local commit -m "[works] ..." --trailer "Agent: claude-code claude-sonnet-5-5" --trailer "Kit-Rev: 3daeff6"`
  - 人間の名義でコミットしたい（ユーザーが言葉で指示した）ときだけ、`git config` の身元を使う。未設定、または `example.com` を含む仮値なら、コミットせずに設定を促して止まる。
  - 過去のコミットは書き換えない（`workbase` の既存コミットは `user` 名義のまま。移行日以降が agent 名義）。
- **コミットしないもの**: 「ナレッジ化して」で `exmem/inbox/` に作ったメモ（ユーザーの指示、2026-10-05）。inbox のメモは、解釈して `knowledge/` に統合した後に削除する運用なので、未追跡のまま残す。**対象は、フックが作ったメモのファイルだけ。** 同じリポジトリのほかの変更（kit、`knowledge/`、`tags.md`、`inbox/README.md`、手順書など）は対象外で、コミットしてよい。報告では「メモはコミットしていない」と範囲を限定して書き、「変更全体がコミット対象外」と読める書き方をしない。コミットを人に頼まない（人が行うのは push だけ）。
- **しないこと**: 許可リスト外の push、`git add -f`、`--amend`、`reset --hard`、`rebase`、`--force`、`--no-verify`、他のコミットの書き換え（ステージを戻すだけの `git reset -q -- <パス>` は、してよい）。ユーザーが「コミットしないで」と言ったときも、しない。
- **push** は、呼び出し元の `AGENTS.md` の**許可リスト**にあるリポジトリだけ、エージェントが行う（2026-10-08 ユーザーの決定。試験運用。当面の対象は、PC ローカルの非公開リポジトリだけ。共有リポジトリ（`workbase`）と dotfiles は、公開範囲が決まるまで対象外）。許可リストに無いリポジトリは、報告にコマンドを書いて案内する（ユーザーに頼まれたときは、実行の直前に、remote、ブランチ、公開範囲を示して確認する）。許可リストのリポジトリでも、**毎回、次をすべて確認してから** push する。1つでも満たさなければ、push せず、理由を報告して止まる。
  1. 公開範囲が非公開（`gh repo view <owner>/<repo> --json visibility`。`gh` が使えなければ push しない）。
  2. 現在のブランチが、許可リストのブランチ（通常は `main`）。
  3. `git fetch` の後に、fast-forward で push できる（`git merge-base --is-ancestor origin/<ブランチ> HEAD`）。そうでなければ（別の端末やセッションが先に push している）、止まって報告する。マージや rebase は、ユーザーの確認なしにしない。
  4. push する範囲（`origin/<ブランチ>..HEAD`）の差分に、`token` `secret` `password` `bearer` `webhook` と、URL 中の長い ID が無い（`git diff origin/<ブランチ>..HEAD` を検索する）。
  5. `--force`、`--force-with-lease`、`--no-verify` を使わない。
  結果（push したコミットの範囲、または止まった理由）は、報告に書く。ハーネス（Claude Code）の権限設定が `git push` を許可していないときは、許可を求めず、報告にコマンドを書く。
- **使い捨ての環境での緩和**（2026-10-07 ユーザーの決定。試行）: クラウドのセッション（モバイルから使う Claude Code on the web など）は、環境が片付けられると、未 push のコミットと未追跡のファイルが消え、ユーザーは手元から push できない。この環境では、次の2点を緩和する。
  - push もエージェントが行う。セッションで最初の push の前に1回、remote、ブランチ、公開範囲を示して確認し、以後の push は報告に書くだけでよい。ブランチは、ユーザーが指定しなければ、そのリポジトリの通常の運用（`workbase` は `main`）に従う。push が失敗したら、コミットが環境の中にしか無いことを報告に書く。
  - 「ナレッジ化して」で `exmem/inbox/` に作ったメモも、コミットして push する（未追跡のままだと消えるため）。統合した後のメモの削除も、コミットする。作業の引継ぎ（現在の状態と次にやること）は、`exmem/contexts/<名>/context.md` に書く（`exmem/AGENTS.md`）。
  - 身元とトレーラー、範囲、コミット前の確認は、上と同じ。
- **報告**に、コミットのハッシュと内容、含めなかったファイルを書く。

## 書き方の共通ルール

- 日付、バージョン、OS を明記する。確認していないことは「仮説」「未確認」と書く。確認した事実には、根拠（実行したコマンド、見たファイル）を1語添える。
- 長い Markdown（`docs/log.md` など）の書き換えは、Edit ツールで行う。スクリプトで全文を読み書きすると、1か所のミスで文書全体を失う（2026-10-06 に、二重と空の事故があった）。やむを得ずスクリプトで書くときは、書き込みの直前に、内容が空でないことと行数を確認し、書く前に `git` でコミット済み（または退避済み）であることを確かめる。
- 機密（トークン、秘匿値）は書かない。
- リスクや制約が生まれる変更は、事前にユーザーへ確認する。
