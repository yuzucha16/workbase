# docs/ の運用規則

作業ディレクトリの経緯・決定・次にやることを、そのディレクトリの `docs/` に残す。`docs/` は各作業ディレクトリの側に置き、exmem には置かない（exmem は知識・経験・ルールの置き場で、作業ログは置かない。`docs/` は将来、日報・仕様書・手順書などの文書の入力にもなる）。ナレッジは exmem の担当で、ここには書かない（再利用できる知識は「ナレッジ化して」で渡す。`knowledge-hook.md`）。

## ファイル

| ファイル | 役割 |
|---|---|
| `docs/log.md` | 現在の状態と次にやること。作業を再開するときの入口 |
| `docs/decisions.md` | 判断の根拠（Why）、却下案、Gotchas、実機で確認した事実 |
| `README.md`（あれば） | 構成と使い方（How）の正本 |

`README.md` と `docs/` で同じ表を重複させない。

小さく一過性のディレクトリには、専用の `docs/` を置かない。親の作業ディレクトリの `docs/` に含める（小さな作業のために `docs/` 一式を持つのは適正でない）。

## 読む順番

1. `docs/log.md`
2. `README.md`（あれば）
3. `docs/decisions.md`

## 更新のタイミング

- 作業の終わりの処理（更新、棚卸し、ナレッジ化、コミット）は、「終了処理して」フック（`closing-hook.md`）が順序を固定して行う。
- 作業の終わりに、`log.md` の Next Actions を更新し、Log に日付つきで追記する。
- 判断（決めたこと・根拠・却下案）、遭遇した詰まり、実機で確認した事実は、その場で `decisions.md` に書く。
- 「ナレッジ化して」の前に `docs/` が未更新なら、先に更新する。

## log.md の書式

```markdown
# 作業ログ（log）

<このディレクトリの現在状態と次にやること。判断の根拠は docs/decisions.md。>

## Next Actions
## Open Questions
## Log

### YYYY-MM-DD

- <1項目で完結する記述>
```

- Log は日付の降順。新しい日付の見出しを上に足す。
- **1項目は単体で読めるようにする**: 何を・なぜ・結果（確認したか）を書く。判断を伴うなら `decisions.md` の項目名を添える。コミットや関連ファイルがあれば添える。日報・週報・仕様書などの入力に使うため、「あれ」「さっきの」のような会話依存の表現を避ける。
- Next Actions は、終わったら消す。経緯は Log に残る。
- Open Questions は、決まったら Log に移して消す。

## decisions.md の書式

```markdown
# 判断の記録（decisions）

## Principles
## Decisions
### 【汎用】<決めたこと>（YYYY-MM-DD）
- 決めたこと / 根拠 / 却下案 / 確認済み（日付と根拠）
- 行き先: <状態>
## Gotchas
```

- Decisions は、決めたこと・根拠・却下案をそろえる。根拠や却下案が無いものは Facts として書く（見出し `## Facts` を足してよい）。
- **決定として書くのは、ユーザーが明示または承認したものだけ。** AI の提案は「提案」と書き、承認を確認できるまで決定にしない。理由: 提案が決定として残ると、以後の判断が、承認されていない前提に乗る。
- 撤回した決定は消さず、「撤回済み」と理由・日付を残す。
- Gotchas は、実際に遭遇した詰まりと解決方法だけ。方針は Principles へ。
- 各項目に、ラベルと行き先を付ける（次の節）。

## decisions.md の項目の行き先

`docs/` で生まれた知識とルールが、どこにも行き場がなく溜まる（滞留する）のを防ぐ。`docs/` は共有しないので、知識は exmem へ、全作業ディレクトリに効く規約は kit へ、「一般化して」渡す。コピーはしない（コピーすると、固有情報が共有側に出て、同じ内容の正本が複数になる）。

**項目**: Principles・Facts・Gotchas は最上位の箇条書き1つ、Decisions は `###` の節1つ。

**ラベル**: 項目の頭に、【汎用】（他の作業でも成り立つ）か【この件】（この作業に固有）を付ける（`knowledge-hook.md` と同じ定義）。Gotchas は、3行セット（状況・原因・解決）を崩さないよう、入れ子の4行目に `  - 【汎用】行き先: …` と書く。

**行き先**: 項目の中に `行き先: <状態>` を1つ書く（Decisions は項目の末尾の行 `- 行き先: …`、Principles と Facts は項目の末尾）。状態は次の6つ。

| 状態 | 意味 | 書き方 |
|---|---|---|
| `未仕分け` | まだ判断していない | `行き先: 未仕分け` |
| `転記待ち` | 一般化した内容を、まだ運んでいない | `行き先: 転記待ち（→ <先>）` |
| `転記済` | 運んだ（到達を確認した） | `行き先: 転記済（YYYY-MM-DD → <先>）` |
| `local` | 固有。この `docs/` に残す（行き場あり） | `行き先: local（<理由>）` |
| `滞留` | 一般化が難しく、保留 | `行き先: 滞留（<理由>）` |
| `破棄` | 不要 | `行き先: 破棄（<理由>）` |

- `<先>` は `exmem/<ファイル>`、`kit/<ファイル>`、別のソースの `<リポジトリ>/docs/decisions.md` など。
- 行き先が複数ある項目（例: exmem には済み、kit には未）は、未完の方の状態にする。
- `転記済` の日付は、到達を確認した日。確認は、転記先に、根拠と却下案が欠けなく写っているかまで見る（見出しの一致だけで済ませない）。
- `転記済` にした項目は、汎用の本文を元から外し、見出し・日付・行き先だけにする（正本を1つにする）。固有の文脈は残してよい。
- `滞留` は、破棄でも失敗でもなく保留。一般化が難しい項目こそ価値が高いことがあるので、理由を必須にして、棚卸しのたびに「固有情報を剥がすと、何が言えるか」を問う。
- 一般化とは、固有情報（会社・パス・その PC の事情）を剥がして、別のソースでも成り立つ形に書き直すこと。剥がすと意味が失われるものは、`local` か `滞留` にする。

**棚卸し**: 作業の終わりに `docs/` を更新するとき、`pwsh -NoProfile -File <kit>/tools/check-docs.ps1`（`pwsh` が無い環境では手で確認）で、行き先の欠落・不正な状態・書式を点検する。`未仕分け` `転記待ち` `滞留` の件数を報告に書く。`転記待ち` の上限は20件（超えると FAIL。人が手で運ぶ量の上限）。

`転記待ち（→ exmem/inbox/<メモ>）` の項目は、棚卸しのとき、そのメモが `exmem/inbox/` に残っているか確認する。無くなっていたら（exmem が統合した）、統合先の `knowledge/` に根拠と却下案が写っているかを見て、`転記済（日付 → exmem/knowledge/<ファイル>）` に進め、本文を外す。残っていれば、そのままにする（統合は exmem 側の運用で、`docs/` の側からは進められない）。

**運び方**はソースの種類で分ける。

- **直結ソース**（`docs/` と共有リポジトリ `workbase` が同じ PC にある。例: PC2 = 個人 PC）: エージェントが直接運べる。知識は「ナレッジ化して」で `exmem/inbox/` へ（`knowledge-hook.md` が、`未仕分け` と `転記待ち` の【汎用】項目も対象にする）。ルールの変更は、kit の改善フック（`knowledge-hook.md`）で、承認を得て行う。運んだら、元の項目の行き先を `転記待ち（→ exmem/inbox/<メモ>）` にし、exmem が `knowledge/` に統合した後、次の棚卸しで `転記済` にする（上の「棚卸し」）。
- **隔離ソース**（`docs/` を git や通信で共有側へ出せない。例: PC1 = 会社 PC）: 経路は、ユーザーの目視と手入力（画像かタイピング。事前に個人情報・機密を落とす）だけ。エージェントは、`転記待ち` の【汎用】項目を grep し、一般化した短文を画面に出す（1回10件前後、上限20件）。各件に「個人情報・機密・固有名が無い」確認欄を付ける。ユーザーが別の PC で入力して、「転記した」と申告したら、`転記済` にする。

PC1・PC2 は、ユーザーの呼び名（PC1 = 会社 PC、PC2 = 個人 PC。2026-10-06）。

## コミットと push

コミットは、エージェントが行ってよい（ユーザーの許可: 2026-10-05。すべての作業ディレクトリに適用）。push は、ユーザーが行う。

- **範囲**: その作業で自分が変更・生成したファイルだけを、パスを指定して `git add` する（`git add -A` と `git add .` は使わない）。ユーザーの未コミットの変更、並行セッションの変更、内容を確認していない既存ファイル、機密の可能性があるものは、含めない。含めなかったものは、報告に書く。
- **コミットの前に確認する**: ① `git add` の直後に `git diff --cached --stat` で、意図したファイルだけか、**行数が自分の変更量と合うか**。共有された `docs/` や設定ファイルは、並行セッションやユーザーが同じファイルを編集していることがあり、パスを指定しても他人の変更が一緒にステージされる。行数が多いときは、`git diff --cached <パス>` で中身を見て、自分の変更だけに絞る（`git add -p`）か、混ざったことを報告する。② 身元が下の「コミットの身元とトレーラー」どおり。③ トークン、秘匿値、業務固有の情報が入っていない（`git diff --cached` を、`token` `secret` `password` `bearer` `webhook` で検索する。語だけでは漏れるので、URL 中の長い ID も見る）。外れたら、`git reset -q -- <パス>` でステージを戻して、コミットせずに報告する。
- **メッセージ**は `[領域] 変更内容`（そのリポジトリの `AGENTS.md` に固有の規則があれば、それを優先する）。
- **コミットの身元とトレーラー**（2026-10-06 ユーザーの決定）: エージェントのコミットは、人間のコミットと区別できるようにする。remote なしのローカルリポジトリでも、`git log` で「誰の行動か」と「どの版の規則か」が分かるようにするため。
  - 身元は、コミット1回ごとの `-c` で渡す。`git config`（グローバルも `.git/config`）は書き換えない（後で人間が手動でコミットしたときまで agent 名義になるため）。作者とコミッターは、どちらも agent にする。
  - 名前は `agent`、メールは `agent@agent.local`。道具やモデルは、名前でなくトレーラーに書く。
  - トレーラーは3行を毎回付ける（`git commit --trailer "<キー: 値>"`）。`Agent: <道具> <モデルID>`（例: `Agent: claude-code claude-sonnet-5-5`）、`Workflow-Kit: <版>`（`workflow-kit/README.md` の「版」）、`Kit-Rev: <ハッシュ>`（`resources/` の `git rev-parse --short HEAD`。`resources/` に未コミットの変更（未追跡ファイルとステージ済みを含む。`.gitignore` で除外されたものは含まない）があれば末尾に `-dirty`。判定: `git status --porcelain` が空でない）。
  - 例: `git -c user.name=agent -c user.email=agent@agent.local commit -m "[works] ..." --trailer "Agent: claude-code claude-sonnet-5-5" --trailer "Workflow-Kit: 2026-10-06.1" --trailer "Kit-Rev: 3daeff6"`
  - 人間の名義でコミットしたい（ユーザーが言葉で指示した）ときだけ、`git config` の身元を使う。未設定、または `example.com` を含む仮値なら、コミットせずに設定を促して止まる。
  - 過去のコミットは書き換えない（`workbase` の既存コミットは `user` 名義のまま。移行日以降が agent 名義）。
- **コミットしないもの**: 「ナレッジ化して」で `exmem/inbox/` に作ったメモ（ユーザーの指示、2026-10-05）。inbox のメモは、解釈して `knowledge/` に統合した後に削除する運用なので、未追跡のまま残す。**対象は、フックが作ったメモのファイルだけ。** 同じリポジトリのほかの変更（kit、`knowledge/`、`tags.md`、`inbox/README.md`、手順書など）は対象外で、コミットしてよい。報告では「メモはコミットしていない」と範囲を限定して書き、「変更全体がコミット対象外」と読める書き方をしない。コミットを人に頼まない（人が行うのは push だけ）。
- **しないこと**: push、`git add -f`、`--amend`、`reset --hard`、`rebase`、`--force`、`--no-verify`、他のコミットの書き換え（ステージを戻すだけの `git reset -q -- <パス>` は、してよい）。ユーザーが「コミットしないで」と言ったときも、しない。
- **push** は、報告にコマンドを書いて案内する。ユーザーに頼まれたときは、実行の直前に、remote、ブランチ、公開範囲を示して確認する。
- **報告**に、コミットのハッシュと内容、含めなかったファイルを書く。

## 書き方の共通ルール

- 日付、バージョン、OS を明記する。確認していないことは「仮説」「未確認」と書く。確認した事実には、根拠（実行したコマンド、見たファイル）を1語添える。
- 長い Markdown（`docs/log.md` など）の書き換えは、Edit ツールで行う。スクリプトで全文を読み書きすると、1か所のミスで文書全体を失う（2026-10-06 に、二重と空の事故があった）。やむを得ずスクリプトで書くときは、書き込みの直前に、内容が空でないことと行数を確認し、書く前に `git` でコミット済み（または退避済み）であることを確かめる。
- 機密（トークン、秘匿値）は書かない。
- リスクや制約が生まれる変更は、事前にユーザーへ確認する。
