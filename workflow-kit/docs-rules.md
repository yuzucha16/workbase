# docs/ の運用規則

作業ディレクトリの経緯・決定・次にやることを、そのディレクトリの `docs/` に残す。`docs/` は各作業ディレクトリの側に置き、exmem には置かない（exmem は知識・経験・ルールの置き場で、作業ログは置かない。`docs/` は将来、日報・仕様書・手順書などの文書の入力にもなる）。ナレッジは exmem の担当で、ここには書かない（再利用できる知識は「ナレッジ化して」で渡す。`stock-hook.md`）。

## ファイル

| ファイル | 役割 |
|---|---|
| `docs/log.md` | 現在の状態と次にやること。作業を再開するときの入口（短く保つ。4KB 目安。上書きで更新する） |
| `docs/log-history.md` | 経緯（日付つきの Log）と、過去の Next Actions の全文。開始時に読まない。必要なとき検索する |
| `docs/decisions.md` | 判断の根拠（Why）、却下案、Gotchas、実機で確認した事実 |
| `README.md`（あれば） | 構成と使い方（How）の正本 |

`README.md` と `docs/` で同じ表を重複させない。

小さく一過性のディレクトリには、専用の `docs/` を置かない。親の作業ディレクトリの `docs/` に含める（小さな作業のために `docs/` 一式を持つのは適正でない）。

## 読む順番

1. 窓口（`README.md`、トピックは `*-start-here.md`。あれば）
2. `docs/log.md`（開始時に読むのはここまで。「期日」の節があれば、今日以前または3日以内の項目を、最初の返答で知らせて判断を求める）
3. `docs/decisions.md` と `docs/log-history.md` は開始時に読まない。何かを決める・変える前に `decisions.md` を検索して、既存の決定と矛盾しないか確かめる。経緯が要るときは `log-history.md` を検索する

### 上の階層で起動して「<名前> の続き」と言われたら

起動する単位（cwd）は、リポジトリのトップだけにする。下位の単位（リポジトリ直下のディレクトリ、トピック、Project、Area）は、cwd を増やさず、この規則で扱う。その単位の窓口 → `docs/log.md` の順で読む（`AGENTS.md` があればそれも読む）。その単位が、このセッションで作業した単位になる（`wrap` の書き込み先）。実行できるフックと、領域をまたぐ書き込みの型は、`hooks.md` の「領域とフックの権限」。単位に `docs/` が無いときは、親のリポジトリの `docs/` に書く。

## 更新のタイミング

- 作業の終わりの処理（更新、昇格の案、コミット）は、「終了処理して」フック（`wrap-hook.md`）が順序を固定して行う。
- 作業の終わりに、`log.md` の現在状態（Next Actions、Open Questions）を更新し、`log-history.md` の `## Log` の先頭に日付つきで追記する。
- 判断（決めたこと・根拠・却下案）、遭遇した詰まり、実機で確認した事実は、その場で `decisions.md` に書く。
- 「ナレッジ化して」の前に `docs/` が未更新なら、先に更新する。

## log.md の書式

```markdown
# 作業ログ（log）

<このディレクトリの現在状態と次にやること。経緯は docs/log-history.md、判断の根拠は docs/decisions.md。>

## 期日（日付つきの項目があるときだけ）
## Next Actions
## Open Questions
```

`log-history.md` の書式: `# 作業ログの経緯（log-history）`、`## Log`、日付の見出し `### YYYY-MM-DD`、1項目で完結する記述。過去の Next Actions の全文も、ここに残す。

- Log は日付の降順。新しい日付の見出しを上に足す。
- **1項目は単体で読めるようにする**: 何を・なぜ・結果（確認したか）を書く。判断を伴うなら `decisions.md` の項目名を添える。コミットや関連ファイルがあれば添える。日報・週報・仕様書などの入力に使うため、「あれ」「さっきの」のような会話依存の表現を避ける。
- Next Actions は、終わったら `log.md` から消す。経緯は `log-history.md` の Log に残る。
- Open Questions は、決まったら `log-history.md` の Log に移して `log.md` から消す。
- **期日の節**（2026-10-16 ユーザーの決定）: 日付で浮上する項目の置き場。表は `期日 | 種別 | 内容 | 担当`。種別は、**単発**（判断すれば消える）と、**定例**（周期で戻ってくる。例: 週1の `review`）。定例は、実行したら次回の期日に書き換え、消さない。Next Actions と Open Questions には、終わりのある項目だけを置く。周期のある項目は置かない（置くと「0 になる」判定が成り立たない）。
- `log.md` が 4KB を超えたら、古い状態を `log-history.md` へ移して縮める。

## decisions.md の書式

```markdown
# 判断の記録（decisions）

## Principles
## Decisions
### 【汎用】<決めたこと>（YYYY-MM-DD）
- 決めたこと / 根拠 / 却下案 / 確認済み（日付と根拠）
- → <名前>（知識にしたとき。次の節）
## Gotchas
```

- Decisions は、決めたこと・根拠・却下案をそろえる。根拠や却下案が無いものは Facts として書く（見出し `## Facts` を足してよい）。
- **決定として書くのは、ユーザーが明示または承認したものだけ。** AI の提案は「提案」と書き、承認を確認できるまで決定にしない。理由: 提案が決定として残ると、以後の判断が、承認されていない前提に乗る。
- 撤回した決定は消さず、「撤回済み」と理由・日付を残す。
- 撤回・取り消しの理由は、「確認できた事実」と「推測」を分けて書く。同じ撤回を複数の場所に記録するときは、理由の正本を1か所に決め、ほかはそこを指す（理由を各所に書き直さない）。理由: cwd 前提の変更の取り消し（2026-10-05）は、理由が2か所で食い違い、誰も当時の理由を言えなくなった（2026-10-17 の振り返り）。
- 決定を覆したときは、「覆した決定」の行に、型（A〜E。不明なら「不明」）と欠けていた入力を1行で付ける（型は `approval-screening.md`）。仮決めは、見出しに `【仮 〜YYYY-MM-DD】` を付ける（同じ）。
- Gotchas は、実際に遭遇した詰まりと解決方法だけ。方針は Principles へ。
- 各項目に、ラベル（【汎用】【案件】【この件】のどれか）を付ける。知識にしたら `→ <名前>` を足す（次の節）。【案件】は AI 作業部屋の Project だけで使う（Area の他の Project にも効く項目。`room` が回収のときに Area の `ai/docs/inbox.md` へ転記する。2026-10-14 ユーザーの決定。部屋を使わない作業ディレクトリでは、【汎用】か【この件】だけ）。

## decisions.md の項目を知識にしたとき

`docs/` で生まれた知識とルールが、どこにも行き場がなく溜まるのを防ぐ。`docs/` は共有しないので、知識は exmem へ、全作業ディレクトリに効く規約は kit へ、一般化して渡す（コピーはしない。固有情報が共有側に出て、正本が複数になるため）。

- 項目の頭に、【汎用】（他の作業でも成り立つ）、【案件】（同じ Area の他の Project にも効く。部屋の Project だけ）、【この件】（この作業に固有）のどれかを付ける（【汎用】と【この件】は `stock-hook.md` と同じ定義）。【案件】は知識にしない（`→` は付けない。Area の `inbox.md` への転記が行き先）。
- 知識（exmem）や規約（kit）にしたら、その項目の末尾に `→ <名前>`（例: `→ inbox/2026-10-08-hook-naming`、`→ kit/hooks.md`）を1行足す。作業側から共有側への参照だけにする（共有側から作業側へは張らない）。**`→` のある【汎用】の項目は運んだもの、無い【汎用】は未**とみなす。状態の欄・日付・本文ハッシュは持たない。メモが統合されて消えた後も、`→` は消さない（統合先は exmem の git の履歴で追える）。
- 一般化とは、固有情報（会社・パス・その PC の事情）を剥がして、別のソースでも成り立つ形に書き直すこと。剥がすと意味が失われるものは、【この件】のままにする。
- 運んだ項目の本文は、外さなくてよい（根拠はこの `docs/` に残る）。長いときだけ、見出しと `→` の行に畳む。
- 2026-10-08 より前に書かれた `行き先:` の行は、履歴としてそのまま残す。新しい項目には書かない。
- `→` の無い【汎用】の項目の件数は、`wrap` の報告と `review` で見る（棚卸しのスクリプトは持たない）。

**運び方**はソースの種類で分ける。

- **直結ソース**（`docs/` と共有リポジトリ `workbase` が同じ PC にある）: 「ナレッジ化して」で、`→` の無い【汎用】の項目も対象にして、`exmem/inbox/` へ運ぶ（`stock-hook.md`）。ルールの変更は、kit の改善の流れ（`hook-common.md`）で、承認を得て行う。
- **隔離ソース**（`docs/` を git や通信で共有側へ出せない。例: 会社 PC）: エージェントは、`→` の無い【汎用】の項目を grep し、一般化した短文を画面に出す（1回10件前後）。各件に「個人情報・機密・固有名が無い」確認欄を付ける。ユーザーが別の PC で入力して、「転記した」と申告したら、`→` を足す。
## コミットと push

コミットは、エージェントが行ってよい（ユーザーの許可: 2026-10-05。すべての作業ディレクトリに適用）。push は、許可リストにあるリポジトリだけエージェントが行い（下の「push」）、ほかはユーザーが行う。

- **範囲**: その作業で自分が変更・生成したファイルだけを、パスを指定して `git add` する（パスなしの `git add -A` と `git add .` は使わない。範囲が決まらず、他人の変更を巻き込むため。パスを指定した `git add -A <パス>` は、削除と rename のステージに使ってよい。2026-10-15 ユーザーの決定）。ユーザーの未コミットの変更、並行セッションの変更、内容を確認していない既存ファイル、機密の可能性があるものは、含めない。含めなかったものは、報告に書く。
- **コミットの前に確認する**: ① `git add` の直後に `git diff --cached --stat` で、意図したファイルだけか、**行数が自分の変更量と合うか**。共有された `docs/` や設定ファイルは、並行セッションやユーザーが同じファイルを編集していることがあり、パスを指定しても他人の変更が一緒にステージされる。行数が多いときは、`git diff --cached <パス>` で中身を見て、自分の変更だけに絞る（`git add -p`）か、混ざったことを報告する。② 身元が下の「コミットの身元とトレーラー」どおり。③ トークン、秘匿値、業務固有の情報が入っていない（`git diff --cached` を、`token` `secret` `password` `bearer` `webhook` で検索する。語だけでは漏れるので、URL 中の長い ID も見る）。外れたら、`git reset -q -- <パス>` でステージを戻して、コミットせずに報告する。
- **コミットを分けるとき**（例: 改行だけの変更と内容の変更）は、`git commit` にパスを指定しない。パスを指定した `git commit -- <パス>` は、index ではなく作業ツリーの現在の内容をコミットするので、ステージで分けても1コミットにまとまる。分けたい内容は index に入れ（`git add -p`、または `git hash-object -w --no-filters` と `git update-index --cacheinfo`）、`git diff --cached --stat` で確認してから、パスなしでコミットする（2026-10-07 dotfiles で発生。未 push のコミットは `git reset --soft HEAD~1` でやり直せる）。
- **メッセージ**は `[領域] 変更内容`（そのリポジトリの `AGENTS.md` に固有の規則があれば、それを優先する）。
- **コミットの身元とトレーラー**（2026-10-06 ユーザーの決定。終了処理のコミットだけでなく、作業の途中でエージェントが作るコミットのすべてに適用する）: エージェントのコミットは、人間のコミットと区別できるようにする。remote なしのローカルリポジトリでも、`git log` で「誰の行動か」と「どの時点の規則か」が分かるようにするため。
  - 身元は、コミット1回ごとの `-c` で渡す。`git config`（グローバルも `.git/config`）は書き換えない（後で人間が手動でコミットしたときまで agent 名義になるため）。作者とコミッターは、どちらも agent にする。
  - 名前は `agent`、メールは `agent@agent.local`。道具やモデルは、名前でなくトレーラーに書く。
  - トレーラーは2行を毎回付ける（`git commit --trailer "<キー: 値>"`）。`Agent: <道具> <モデルID>`（例: `Agent: claude-code claude-sonnet-5-5`）、`Kit-Rev: <ハッシュ>`（`resources/` の `git rev-parse --short HEAD`。`resources/` に未コミットの変更（未追跡ファイルとステージ済みを含む。`.gitignore` で除外されたものは含まない）があれば末尾に `-dirty`。判定: `git status --porcelain` が空でない）。
  - `init 更新`（`init-update.md`）の反映のコミットだけは、3行目に `Template-Rev: <ハッシュ>`（反映した雛形の版。`resources/` の短縮ハッシュ）を付ける。次回の反映の基点になる。
  - 例: `git -c user.name=agent -c user.email=agent@agent.local commit -m "[works] ..." --trailer "Agent: claude-code claude-sonnet-5-5" --trailer "Kit-Rev: 3daeff6"`
  - 人間の名義でコミットしたい（ユーザーが言葉で指示した）ときだけ、`git config` の身元を使う。未設定、または `example.com` を含む仮値なら、コミットせずに設定を促して止まる。
  - 過去のコミットは書き換えない（`workbase` の既存コミットは `user` 名義のまま。移行日以降が agent 名義）。
- **コミットしないもの**: 「ナレッジ化して」で `exmem/inbox/` に作ったメモ（ユーザーの指示、2026-10-05）。inbox のメモは、解釈して `lessons/` に統合した後に削除する運用なので、未追跡のまま残す。**対象は、フックが作ったメモのファイルだけ。** 同じリポジトリのほかの変更（kit、`lessons/`、`tags.md`、`inbox/README.md`、手順書など）は対象外で、コミットしてよい。報告では「メモはコミットしていない」と範囲を限定して書き、「変更全体がコミット対象外」と読める書き方をしない。コミットを人に頼まない（人が行うのは push だけ）。
- **しないこと**: 許可リスト外の push、`git add -f`、`--amend`、`reset --hard`、`--force`、`--no-verify`、他のコミットの書き換え、コミットを消す・書き換える `rebase`（`-i`、`drop`、`squash`、`reword`、`edit`。ユーザーの承認が要る）（ステージを戻すだけの `git reset -q -- <パス>` は、してよい）。ユーザーが「コミットしないで」と言ったときも、しない。
- **未追跡のファイルの削除**（2026-10-18 ユーザーの決定。全フックに適用）: コミットや push のために、未追跡のファイルを削除することになる場合（`git clean`、`rm`、ブランチの切り替えや `rebase`・`stash` で消える場合を含む）は、先にユーザーに確認する。ファイルの一覧と、消えると困るかを示して、承認を待つ。承認が無ければ消さず、未追跡のまま残して報告する。フック自身が works の外の一時ディレクトリに作った作業用ファイルを消すことは、対象外。
- **`rebase` の許可**（2026-10-18 ユーザーの決定）: 複数端末の分岐による時系列のずれの修正と、その衝突の解消に限り、承認なしで行ってよい。対象は未 push のローカルのコミットを `origin/<ブランチ>` の上に載せることだけ。条件: ① 実行前に、双方のコミット日時と他端末由来かを示す（`exmem/lessons/git-rebase-chronology.md`）。② 衝突は、双方の内容を残して解く。③ マーカー（`<<<<<<<` など）が残っていないことを確かめてから `--continue` する。④ 終わったら、結果（`git log --oneline`）を報告する。コミットを消す・内容や情報を書き換える操作は、これまでどおりユーザーの承認が要る。
- **push** は、呼び出し元の `AGENTS.md` の**許可リスト**にあるリポジトリだけ、エージェントが行う（2026-10-08 ユーザーの決定。試験運用。2026-10-16 に、公開リポジトリ（`workbase`、dotfiles）も許可リストに載せてよいと、ユーザーが決めた。公開のまま、エージェントが push する）。許可リストに無いリポジトリは、報告にコマンドを書いて案内する（ユーザーに頼まれたときは、実行の直前に、remote、ブランチ、公開範囲を示して確認する）。許可リストのリポジトリでも、**毎回、次をすべて確認してから** push する。1つでも満たさなければ、push せず、理由を報告して止まる。
  1. 公開範囲を確認し、報告に書く（`gh repo view <owner>/<repo> --json visibility`。`gh` が使えない環境では、GitHub の API（MCP など）で確かめてよい。どちらでも確かめられなければ push しない）。**公開（PUBLIC）なら、条件 4 の検索を広げる**。push は世界に公開されるので、あとで消しても、キャッシュや履歴に残りうる。
  2. 現在のブランチが、許可リストのブランチ（通常は `main`）。クラウドの環境で作業ブランチ（例: `claude/...`）が指定されているときは、作業ブランチのまま `git push origin HEAD:<許可リストのブランチ>` で push してよい（2026-10-17 ユーザーの決定。指定ブランチへの push は要らない）。条件 3 と 4 は `origin/<許可リストのブランチ>` に対して確かめる。環境のローカルの `main` は古いことがあるので、checkout しない。
  3. `git fetch` の後に、fast-forward で push できる（`git merge-base --is-ancestor origin/<ブランチ> HEAD`）。そうでなければ（別の端末やセッションが先に push している）、止まって報告する。マージは、ユーザーの確認なしにしない。rebase は、上の「`rebase` の許可」の範囲でしてよい。
  4. push する範囲（`origin/<ブランチ>..HEAD`）の差分に、`token` `secret` `password` `bearer` `webhook` と、URL 中の長い ID が無い（`git diff origin/<ブランチ>..HEAD` を検索する）。公開リポジトリでは、さらに、メールアドレス、Windows のユーザー名を含む絶対パス、会社・顧客・個人を特定する名前が無いことを確かめる（見つけたら止まり、ユーザーに確認する）。
  5. `--force`、`--force-with-lease`、`--no-verify` を使わない。
  結果（push したコミットの範囲、または止まった理由）は、報告に書く。ハーネス（Claude Code）の権限設定が `git push` を許可していないときは、許可を求めず、報告にコマンドを書く。
- **使い捨ての環境での緩和**（2026-10-07 ユーザーの決定。試行）: クラウドのセッション（モバイルから使う Claude Code on the web など）は、環境が片付けられると、未 push のコミットと未追跡のファイルが消え、ユーザーは手元から push できない。この環境では、次の2点を緩和する。
  - push もエージェントが行う。セッションで最初の push の前に1回、remote、ブランチ、公開範囲を示して確認し、以後の push は報告に書くだけでよい。ブランチは、ユーザーが指定しなければ、そのリポジトリの通常の運用（`workbase` は `main`）に従う。push が失敗したら、コミットが環境の中にしか無いことを報告に書く。
  - 「ナレッジ化して」で `exmem/inbox/` に作ったメモも、コミットして push する（未追跡のままだと消えるため）。統合した後のメモの削除も、コミットする。作業の引継ぎ（現在の状態と次にやること）は、該当する `exmem/lessons/` のノートの `Open Questions` / `Next Actions` に書く（`exmem/AGENTS.md`。`contexts/` は 2026-10-10 に廃止）。
  - 身元とトレーラー、範囲、コミット前の確認は、上と同じ。
- **報告**に、コミットのハッシュと内容、含めなかったファイルを書く。

## 書き方の共通ルール

- 日付、バージョン、OS を明記する。確認していないことは「仮説」「未確認」と書く。確認した事実には、根拠（実行したコマンド、見たファイル）を1語添える。
- 長い Markdown（`docs/log.md` など）の書き換えは、Edit ツールで行う。スクリプトで全文を読み書きすると、1か所のミスで文書全体を失う（2026-10-06 に、二重と空の事故があった）。やむを得ずスクリプトで書くときは、書き込みの直前に、内容が空でないことと行数を確認し、書く前に `git` でコミット済み（または退避済み）であることを確かめる。
- 階層化するときは、情報も階層化する。上段（リポジトリ直下の README など、最初に読むもの）は表引きにして、順序、要点、入口だけを書く。詳細（引数、入力、出力、失敗時の挙動、観点）は下段（近くの README など）に置き、上段から指す。詳細は捨てずに、原文のまま下段へ移す。上段と下段に同じ表を重複させない。
- リスクや制約が生まれる変更は、事前にユーザーへ確認する。

## 読み方の共通ルール

- 大きいファイル（目安 10KB 超）は、見出しの一覧を先に見て、必要な節だけを読む。理由: 会話の履歴は毎ターン再送されるので、一度読んだ量が、その後のターンにも載り続ける。
- ログ、一覧、コマンドの出力は、件数、`head`、検索で絞ってから読む。
- スクリプトに読ませるときは、表の全行でなく、要約と件数を返させる（例: 点検スクリプトは FAIL の行と件数だけ）。
