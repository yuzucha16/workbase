# 「workflowを導入して」フック

作業ディレクトリに、workflow-kit の共通機能を導入するためのフック。ユーザーが「workflowを導入して」と言ったときだけ実行する（自発的には導入しない）。

導入項目は増やせる。workflow に新しい機能を足すときは、「導入項目の一覧」に行を足す（手順は下の「導入項目を足すとき」）。

出力のブレを減らすため、入力・手順・自己点検・報告の型を固定してある。迷ったら、このファイルと `examples/setup-example.md`（見本）に合わせる。

## 導入項目の一覧

| # | 項目 | 生成物 | 必須 | 規則の正本 |
|---|---|---|---|---|
| 1 | 共通ルールの参照 | `AGENTS.md`、`CLAUDE.md` | 必須 | `templates/AGENTS.md` |
| 2 | 作業ログと判断ログ | `docs/log.md`、`docs/decisions.md` | 必須 | `docs-rules.md` |
| 3 | 「ナレッジ化して」 | なし（`AGENTS.md` の共通ルールに参照を入れる） | 必須 | `knowledge-hook.md` |
| 4 | 履歴からの復元 | `docs/` の Log と判断記録の補完 | 任意 | 下の「履歴からの復元」 |

### 導入項目を足すとき

1. 上の表に行を足す（生成物、必須か任意か、規則の正本）。
2. 「手順」の生成の節に、その項目の作り方を足す。
3. 「自己点検」に、その項目の確認を足す。
4. 見本（`examples/setup-example.md`）を合わせる。
5. `improvements.md` に1行残す。

## 場所と書き込みの制約

- 書き込み先は、対象ディレクトリの中の `AGENTS.md`、`CLAUDE.md`、`docs/` だけ。`exmem` やその他は触らない。
- **既存のファイルは、上書きしない。** 既存があれば、差分の案を示して承認を得る。承認の前に変更しない。
- コミット・push はしない（ユーザーが行う）。
- 対象が `notes` の中にあり、`.gitignore` の既定でローカル専用になる場合は、その旨を報告に書く（確認: `git check-ignore -v <パス>`）。ローカル専用の `docs/` は、他のPCに届かない。
- このフックが呼べるのは、`setup-hook.md` を参照している `AGENTS.md` の配下（`notes/` の中）と、ユーザーがこのファイルのパスを指示したとき。それ以外の場所からの入口は、Claude 用スキル（未作成。TODO）。

## 入力

次の4項目。会話に材料があれば、質問せずに埋めて、報告で確認する。足りない項目だけ、1回に1問ずつ質問する。

1. 対象ディレクトリ（絶対パス）
2. 目的（1〜2行）
3. 読む順番の、固有の項目（`README.md` など。無ければ「なし」）
4. 固有ルール（編集の注意、コミットの規則など。無ければ「なし」）

## 手順

1. **プランモードなら先に抜ける**（`knowledge-hook.md` の手順 1 と同じ）。
2. **対象を確認する。** `AGENTS.md`、`CLAUDE.md`、`docs/` の有無、`.git` の有無、`.gitignore` による追跡状況を調べる。`docs/` がローカル専用（`.gitignore` で除外される）と分かったときは、共有するかをユーザーに質問する。既定は、ローカル専用のままにする。`.gitignore` を変更するのは、リスクや制約が生まれる変更なので、ユーザーの承認を得てから行う。
3. **入力を受け取る。**
4. **生成する。**
   - `AGENTS.md`: `templates/AGENTS.md` を埋める。「共通ルール」の節（パス、2項目、読めない場合の一文）は、雛形のまま変えない。ただし、このディレクトリが導入の入口を兼ねる（`setup-hook.md` を参照する側。例: `notes/`）ときは、3項目目に `setup-hook.md` を足す。既存があれば、追加する節（共通ルール、読む順番）の差分案を示して承認を待つ。既存の `AGENTS.md` がそれ自体で規則を持つときは、「読む順番」の2番目を「この `AGENTS.md` の各節」とする。
   - `CLAUDE.md`: `@AGENTS.md` の1行。既存があれば、`@AGENTS.md` が入っているかを確認し、無ければ差分案を示す。
   - `docs/log.md`、`docs/decisions.md`: `templates/` から作り、冒頭の説明に目的を入れる。既存があれば触らない。
5. **任意: 履歴から復元する**（ユーザーが望むときだけ。下の節）。
6. **「自己点検」を通す**（下の節）。
7. **報告する**（下の「報告の型」）。

## 履歴からの復元（任意）

- 一覧: `git log --format='%h %ad %s' --date=short -- <パス>`。変更範囲: `git show --stat <ハッシュ> -- <パス>`。設定値の変化: `git show <ハッシュ> -- <ファイル>`。
- Log は日付の降順で、項目ごとにコミットのハッシュを添える。
- 理由が書かれているもの（コミットメッセージ、ファイルのコメント、既存のナレッジ）だけを、出典つきで書く。書かれていない理由は、推測で補わず「不明」と書く。
- 根拠と却下案が履歴にある項目だけを Decisions にする。無いものは Facts に事実として書く。
- 冒頭に、復元元と範囲、残っていないもの（履歴の作り直しなど）を書く。別のリポジトリから移ったものは、移管元の履歴も調べる。

## 自己点検

報告の前に、次をすべて確認する。1つでも外れたら直す。

- [ ] 書き込み先が、対象ディレクトリの中だけ
- [ ] 既存のファイルを上書きしていない（差分案を示して、承認を待っている）
- [ ] `AGENTS.md` の「共通ルール」の節が、雛形どおり（パス、2項目、読めない場合の一文）。導入の入口を兼ねるときは、3項目目に `setup-hook.md` がある
- [ ] 「読む順番」の1番目が `docs/log.md`
- [ ] `CLAUDE.md` が `@AGENTS.md` を含む
- [ ] `docs/log.md` の見出しが Next Actions / Open Questions / Log、`docs/decisions.md` の見出しが Principles / Decisions / Gotchas
- [ ] 雛形のプレースホルダ（`<` `>`）が残っていない
- [ ] 目的が1〜2行
- [ ] 共有したくない値が無い
- [ ] 追跡状況（共有かローカル専用か）を報告に書いた
- [ ] 復元した場合は、出典・範囲・「不明」の明記がある

## 報告の型

次の順で報告する。

1. **対象**: ディレクトリのパス。
2. **変更したファイル**: 新規に作ったファイルと、差分案を示した既存ファイル（承認待ち）。
3. **追跡状況**: 共有（Git 管理）かローカル専用か。
4. **承認が必要なこと**: 既存ファイルの差分案、`docs/` を共有するか（ローカル専用だったとき）など。
5. **改善案**: 下の「このフックの改善」に従う。

## このフックの改善

改善の流れは、`knowledge-hook.md` の「このフックの改善」と同じ（1〜3点を `場所 / 問題 / 案` で提案、承認後に kit を直し、`improvements.md` に残し、モバイル用プロンプトと見本を合わせる必要があれば合わせる）。実行後に、次を確認して報告する。

- 入力の型・雛形・自己点検で、曖昧だった点、迷った点、足りなかった項目。
- 導入項目の一覧に、足すべき機能。

**承認なしに、このディレクトリを書き換えない。**
