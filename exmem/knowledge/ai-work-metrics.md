# AI 活用の指標を会話履歴から測る

## Purpose

AI 活用のスキルと、AI との作業手順（workflow）の効果を、自己改善のために数値化する。何を測り、どこから取り、どう読むかをまとめる。質問・提案の指標は [[para-operations]]。会話履歴（jsonl）の保存場所は [[claude-code-storage]]。

## Principles

- 自走時間は、壁時計ではなく、ターン（実プロンプトから次の実プロンプトの直前まで）の長さで測る。壁時計には `--resume` の離席や放置が混ざり、AI が自走した時間にならない。
- 自走時間を単独の目標にしない。品質（修正の件数、撤回、目標の達成）と対にし、作業の種類で分けて比べる。監督を減らして品質が落ちても、自走時間は良く見える。
- 時間の分布は、最小と平均でなく、中央値と上位 10% 点で見る。最小は1行の質問で決まり、平均は外れ値（離席）に弱い。
- 人の評価は、観測できる行動と件数だけにし、各行に根拠（発言の要旨）を残す。AI の印象評価（段階評価）は使わない。AI の評価はお世辞に寄る。
- 「無駄」は、判定でなく合図として出し、中身を見て決める。ツールエラーや放置は、探索や中断の正当な結果でもある。
- AI が直された件数は、起因（AI の欠陥、ユーザーの指示不足、ユーザーの批判的レビューの成果）を分けて数える。同じ「修正」が、AI の質の低さにも、ユーザーのスキルにもなり、混ぜると読めない。
- n が小さいうちは、総合スコアを作らない。重みの根拠が無く、1件で大きく動く。

## Decisions

すべて 2026-10-06。

- **スレッド（1会話）の指標は、会話履歴から自動で抽出し、判断が要る項目だけを AI が終了時に1行足す**。根拠: 履歴に、時刻、実プロンプトとツール結果の区別、ツール数、トークンがあり、全52本を約8秒で処理できた。ユーザーの記録の手間が要らない。却下案: AI が毎回すべてを推定して記録する（精度が落ち、過去分を取り戻せない）、ユーザーが手で記録する（続かない）。
- **ターンの長さは30分で打ち切り、打ち切った件数を別に数える**。根拠: 離席や許可待ちの放置が、数万秒のターンとして混ざる。打ち切った件数は、放置の合図になる。却下案: 打ち切らない（外れ値で指標が壊れる）、外れ値を捨てる（放置の情報が消える）。
- **指標の用途は、ユーザー本人の自己改善だけにする**。根拠: ユーザーの指示（第三者への評価に使わない。忖度は邪魔になる）。却下案: 第三者に見せる評価も想定する（AI が人を採点する形式に、慎重さが要るため）。
- **補正の記録に、起因の列（`ai` `user` `review`）を足す**。根拠: ユーザーの承認。AI の欠陥と、ユーザーの批判的レビューの成果が、同じ「修正」に混ざるため。却下案: 修正の件数だけを見る。
- **用語を分ける: スレッド = Claude Code の1会話（jsonl 1本）、セッション = 開始インタビューから終了処理までの作業手順の単位**。1スレッドに複数セッション、複数スレッドで1セッションがありうるので、セッションの記録に会話 ID を書いて紐づける。根拠: ユーザーの確認（この対応でよい）。却下案: 未検討。
- **指標の構成は、規模・分割、自走、品質、リテラシー、無駄の合図の5群にする**。規模・分割: Area あたりの Project 数、Project のリードタイム・完了条件の達成・見直し日の超過、Project あたりのスレッド数、スレッドあたりのセッション数とその逆。自走: ターン長の中央値と上位 10% 点、ターンあたりのツール数、最大トークン。品質: 修正、漏れ、撤回、起因、セッションの達成度。リテラシー: 最初の依頼の完備度（0〜4）、批判的レビューの件数、仕組み化の件数。無駄の合図: セッションに紐づかない会話、放置（3日）、ツールエラー率（20% 以上）、打ち切ったターン（閾値は暫定で、実測で見直す）。根拠: ユーザーの承認。却下案: Project 数だけを規模の指標にする（時点の値で、効果に直結しない）、総合スコア（n が小さく、重みの根拠が無い）、概念の理解の測定（会話から推定しにくく、当面は対象外）。
- **開始の形を、`bare`（「作業を始めて」だけ）と `briefed`（最初の依頼に、ゴール・完了条件・制約・やらないことを添える）に分け、背景なし → 背景ありの順に試す**。根拠: ユーザーの承認。背景を最初に渡すと、開始インタビューの効果が隠れ、完備度は開始の形の結果になる。混ぜると、効果と指示の質を分けて読めない。却下案: 毎回背景を渡す、毎回渡さない（どちらも片方の指標が測れなくなる）。

## Facts

- Claude Code の会話履歴（jsonl）の1応答は、複数の行に分かれ、同じ `message.id` と同じ `usage` が各行に繰り返される。1ファイルで 601 行が 170 応答だった。`message.id` で一意化しないと、トークンを約 3.5 倍に過大計上する（確認: 2026-10-06、根拠: `message.id` の一意数の集計）。
- ユーザーの実プロンプトと、ツール結果は、どちらも `type` が `user`。ツール結果には `toolUseResult` がある。376 件中 359 件がツール結果だった（確認: 2026-10-06、根拠: 最大の jsonl の集計）。
- 履歴には、時刻（`timestamp`）、ツール呼び出し、トークン数（`usage`）がある。1会話の壁時計は、最大で約5日（`--resume` の離席）だった（確認: 2026-10-06、根拠: 全52本の集計）。
- ターンの長さの中央値は、会話ごとに 20〜140 秒だった（確認: 2026-10-06、根拠: 全52本の試作の集計）。
- 履歴に、コンテキストの圧縮（compact）の記録は見当たらなかった（確認: 2026-10-06、根拠: `isCompactSummary` と `compact_boundary` の検索。ヒットは検索語を含む当該会話の1件だけ）。
- Vault のディレクトリ名を変えて履歴をコピーすると、同じ会話 ID が旧キーと新キーの両方のディレクトリに残る。会話 ID で重複を除く必要がある（確認: 2026-10-06、根拠: 抽出で 52 本が 50 会話になった。[[claude-code-storage]]）。
- Claude Code の履歴のディレクトリ名は、作業ディレクトリのパスの英数字以外を `-` に置き換えたもの（例: `C:\vault\works` は `C--vault-works`）。作業ディレクトリから、その作業の履歴を絞れる（確認: 2026-10-06、根拠: 作業ディレクトリのキーで履歴を選び、期待どおりの会話が選ばれた）。
- 抽出と集計のスクリプトは、作業ディレクトリの `docs/metrics/`（`extract-threads.ps1`、`summarize.ps1`）にある（確認: 2026-10-06、根拠: ディレクトリの一覧）。

## Gotchas

- **PowerShell の `Export-Csv` で書いた CSV を、LF 統一のリポジトリでコミットしようとした**: `Export-Csv` は Windows で CRLF を書き、`git add` が置換の警告を出す。書いた後に、全体を読み直して `` `r`n `` を `` `n `` に置換して書き戻す（BOM なしの UTF-8）。

- **終了時に、今の会話を「最新の更新ファイル」で選ぶと、並行する別の会話を選んだ**: 並行して動いている別のトライアルの会話が、より新しく更新されていた（実測で再現）。原因: 最新の更新を選ぶ方式は、並行セッションを区別できない。解決: 作業ディレクトリのキーの履歴の中から選び、前後 30 分以内に別の会話も更新されていたら、警告を出す。

## Open Questions

- 履歴の自動削除の有無と保持期間が分からない。抽出が追いつかないと、古い会話の行が作れない。抽出を、どの頻度で回すのがよいか。
- 最初の依頼の完備度（ゴール・完了条件・制約・やらないこと、0〜4）の数え方が、人によってぶれないか。
- 提案（AI の提案。未承認）: コンテキスト量を、compact の回数でなく、1回の入力の最大トークン数で代用する。

## Next Actions

- 終了のたびに抽出と1行の記録を回し、完備度の数え方、打ち切りの30分、無駄の合図の閾値（ツールエラー率20%、放置3日）を、実測で見直す（2026-10-06 時点）。
- 数回回して安定したら、終了処理の手順（kit の `closing-hook.md`）への昇格を、承認を得て判断する。
