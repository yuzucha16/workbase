# PARA の運用と、AI の質問・提案の指標

## Purpose

PARA の `projects/` と `areas/` の役割・判断基準・構造・フック（開始・終了）と、AI がユーザーに聞く質問と、AI の提案の効果を指標で測って改善する仕組みをまとめる。最初の Project を、開始から close まで回した実測を含む。Vault の構造は [[obsidian-vault]]、会話履歴からの指標は [[ai-work-metrics]]。

## Principles

- Project は、完了条件のある取り組み（終われば `archives/` へ移す）。Area は、終わりのない責任領域（維持する基準を持つ）。分類は、「完了条件を1文で書けるか」で決める。書けなければ Area。「終わらせることを目指すか、維持することが目的か」が、PARA の本来の区別だから。
- 完了条件を達成したら、見直し日を待たずに Project を閉じる。AI は、達成を確認した時点で close を提案する。見直し日まで残すと、完了済みの Project が一覧に居座り、進行中の上限（Project 3 件）を食う。
- 質問と提案の効果は、回答率・採用率・適合率・冗長率・覆り率と、漏れ（聞かれなかった前提が後から出た件数）で測る。適合率は聞いた質問のズレを測るが、漏れは聞かなかった質問の欠落を測り、どちらも改善の根拠になる。
- AI の提案の承認率が高いとき、承認率は判別力が低い。修正されたか（`fix`）と、後で覆ったか（`reversed`）を、承認の確認のたびに記録して見る。既存の改善案 66 件の採用率は約 98% で、承認が形式的か、提案が事前に絞られているかを区別できなかった。
- 答えが1つに定まる項目は質問せず、要約に宣言して、反対があるときだけ受ける。質問の前に、`docs/` と環境を確認する。事前に分かる前提を聞くと、冗長率が上がり（試行では 50%）、ユーザーの手間になる。
- 開発系の作業は、実装の前に、専門領域、設計の優先順位、コーディングルールとチェックの有無、対象環境を確認する。初回の Project で、これらが後から出た（漏れ 4 件）。AI の推奨が、ユーザーの優先順位（安全性が起動速度より上）と逆になった例もある（[[embedded-c-constraint-checks]]）。
- 質問のまとまりの最後に、「ほかに前提はありますか」の自由記述を1つ置く。選択肢の外の前提が、承認の確認の補足として、14 件中 8 件出た（効果は未測定）。

## Decisions

すべて 2026-10-06。

- **`projects/<名>/` と `areas/<名>/` と `archives/` の役割と、判断基準 8 項目を定める**。根拠: 業務には、終わりのない責任と、期限・完了条件のある成果物が混在する。前者は Area、後者は Project に分ける。基準: ① 完了条件を1文で書けるか、② 見直し日を置けるか、③ 成果物が1つに特定できるか、④ 複数セッションにまたがる Project は `docs/` を持つ、⑤ 同時進行の上限は Project 3・Area 5（暫定）、⑥ 完了・中止・見直し日を2回超えて更新が無いとき `archives/` へ、⑦ 閉じるとき再利用できる知識を exmem へ、⑧ 業務固有の内容は、そのリポジトリの中に置く。却下案: 案件の業務そのものを Project にする（終わりが無く、完了条件を書けない）。
- **ディレクトリ構造は、`areas/<領域>/` と `projects/<名>/` を並べる（フラット）。Area の `README.md` に、Project の一覧とパス付きのリンクを書く**。根拠: 移動が `projects/` から `archives/` へだけで済む。Project の `README.md` の frontmatter に `status` `area` `review` を持たせて、Bases などで一覧する。却下案: Area の中に Project を入れ子にする（閉じるときに所属が切れ、複数の Area にまたがる Project で破綻する）、Area ごとに `docs/` を持つ（Project が少ない間は空の `docs/` が増える）。
- **フックを、Project の寿命と、セッションの寿命の2層で連鎖させる: open → [開始インタビュー → 作業 → 終了処理]×N → close。開始インタビューは、育成・改善方式（最初は手動で聞き、実測で形式化）で作る**。根拠: セッションの開始側にだけフックが無く、ゴールや前提を、ユーザーが毎回手で書いていた。ユーザーの方針: 制度を徐々に上げる。作業の種類（文書作成、開発）のカテゴライズと、抽象化・継承による定型化を、2〜3回の実測の後に設計する。却下案: 最初から全項目を固定した手順書にする（実測が無く、聞く項目の漏れが多くなる）。
- **質問・承認・改善案を、1件1行のイベントログ（CSV）で記録する。種類は、聞き取り・承認の確認・改善案・漏れ。記録は AI が、回答を受けた同じターンに行う**。根拠: 質問の効果を、全体・Area・Project・セッションの単位で集計して、AI が質問と提案を改善する入力にするため。承認の確認の多くは、質問でなく、AI の提案への承認のため、種類を分ける。却下案: 質問ごとに別ファイル（集計が難しい）、Project ごとの別の CSV（Area と全体の集計に結合が要る）。
- **新しいセッションの呼び出しは、言葉「作業を始めて」を決め、`AGENTS.md` から開始インタビューの手順書を参照する**。根拠: 手順書を、新しいセッションが自動で見つける仕組みが無かった。却下案: 手順書を読むよう、ユーザーが毎回プロンプトで指示する。

## Facts

- 既存の改善案 66 件（改善の受け皿の表）の採用率は約 98%（回答 63 件中 62 件）で、却下は撤回の 1 件だけだった（確認: 2026-10-06、根拠: 表の状態列を機械的に取り込んで集計）。
- 最初の Project の開始インタビュー（聞き取り 4 件）の結果: 回答率 100%、採用率 100%、適合率 75%、冗長率 50%。ズレは「やらないこと」の選択肢に、リポジトリの変更の許可を混ぜたことが原因で、「触ってよい範囲」を独立させた（確認: 2026-10-06、根拠: 記録したイベントの集計）。
- 同じ Project の承認の確認 14 件は、修正 5、補足 8、適合率 29%。漏れは 4 件（専門領域、コーディングルールと制約、設計の優先順位、ポインタ操作の規則）で、すべて開発系の前提だった（確認: 2026-10-06、根拠: 記録したイベントの集計）。
- Project を `archives/` へ移すとき、ディレクトリごとの `git mv` が `Permission denied` で失敗した。`git ls-files` を回して、ファイル単位で `git mv` すると、リネームとして履歴が保たれた。移したあとに、未追跡のビルド成果物だけが旧ディレクトリに残った（確認: 2026-10-06、根拠: 25 ファイルの移動と `git status`）。原因は未特定（使用中ディレクトリの rename 拒否と同種の可能性。[[obsidian-vault]] の Gotchas）。
- Area の一覧のリンクは、`README.md` が複数あるので、ファイル名だけでは解決できず、パス付きの wikilink（`[[archives/<名>/README|<名>]]`）にする（確認: 2026-10-06、根拠: 新旧の Area の一覧）。
- 同日のうちに、開始（open）、開始インタビュー、作業、close を一巡できた。close の時点では、採用済みで維持されている行の `reversed` を 0 に確定した（確認: 2026-10-06、根拠: 25 行を更新）。
- 手順書（`session-start-interview.md`、`project-open.md`、`project-close.md`）は作業ディレクトリの `docs/drafts/` にあり、`AGENTS.md` が「作業を始めて」で参照している。イベントログと集計のスクリプトは `docs/metrics/` にある（確認: 2026-10-06、根拠: ディレクトリの一覧と `AGENTS.md` の記述）。

## Gotchas

- **承認済みの改善案が、新しいセッションで、手順書を見つけられない状態だった**: 手順書が `docs/drafts/` にあるだけで、`AGENTS.md` から参照されていなかった。呼び出しの言葉を決めて、`AGENTS.md` に1行足した。

## Open Questions

- 「ほかに前提はありますか」の自由記述で、補足と漏れが減るか（2回目の Project で測る）。
- 作業の種類（文書作成、開発）ごとの、質問項目の定型（共通と差分）の設計。
- 上限（Project 3 件、Area 5 件）と、`archives/` へ移す契機の見直し。
- 手順書を、kit に昇格するか、他の環境（会社 PC など）へ投入するか（安定してから判断する）。

## Next Actions
