# AIエージェントのモデルとハーネス

## Purpose

Claude（claude.ai / Claude Code）、GPT（ChatGPT / Codex）、Microsoft 365 Copilotなどの違いを「モデル」と「ハーネス」に分けて理解する。最終的な関心は、AIの自走期間を一問一答（秒オーダー）から長くすること。実装は [[ai-handson-framework]] で行い、この文書は座学（概念）をまとめる。

## Principles

- モデル=Linuxのカーネル、ハーネス=ミドルウェア、プロダクト=ディストロ、として捉える。チャット型とエージェント型の違いを「ハーネスの違い」として吸収できる。
  - 比喩のずれ: ハーネスとモデルは完全に直交しない（ハーネスはモデルの癖に合わせて調整され、モデルもハーネス上で訓練される）。1社が複数のハーネスを持つ。
- ハーネス=「実行環境とインタフェース」。
- 確実に守らせたいことは権限・フックで強制し、方針と文脈は指示ファイルに書く。指示ファイルに「するな」と書いても守られるとは限らない。
- 自走が長くなるほど人が確認できなくなるため、**検証 → 状態の外部化 → 権限**の順で足す。1周で足す要素は1〜2個にして、効果を切り分ける。
- 一発完成を目指さない。失敗した箇所に対応する要素から足す。
- 権限を緩めるときは、失敗時の回収手段（チェックポイント、git）を対で置く。実装の例は [[claude-code-permissions]]（読み取りと取返し可の書き込みはallow、取返し不可は確認、壊してよい環境だけ緩める）。
- AI界隈の新しい用語は、既存の工学・管理技法との対応を探して理解する（後述）。完全に新規の技術概念として受け取らない。

## ハーネスの構成要素

中心はエージェントループ（問い合わせ → ツール実行 → 結果返却の繰り返し）。周辺に6要素がある。

| 要素 | 定義の形 | 備考 |
|---|---|---|
| ツール層 | MCP等の接続 | モデルが読んで解釈する（お願い） |
| コンテキスト管理 | md / skills（自然言語） | モデルが読んで解釈する（お願い） |
| 権限とサンドボックス | 設定ファイル + スクリプト | ハーネスが強制する |
| 制御フック | 設定ファイル + スクリプト | ハーネスが強制する |
| 状態と永続化 | ハーネス機能（履歴再開、チェックポイント、worktree）+ 指示ファイルの運用ルール | 組み合わせ |
| 接点（UI）と検証 | 起動方法と他要素の組み合わせ | |

### コンテキストウィンドウ

- 単位はトークン（バイトではない）。日本語は英語より多く消費する傾向がある。
- 指示、ツール定義、履歴、ツール出力、モデルの出力が同じ枠を共有する。ツール出力（ログ、巨大ファイル）が最も枠を消費しやすい。
- 毎ターン全履歴を再送するため、水位が高いまま回すほどコストと遅延が増える。プロンプトキャッシュの読み取りは安い（Opus 5.5で入力 $4 に対しキャッシュ読み取り $0.20 / Mtok、2026-09-30 時点・メモ記載）。
- 水位は自然には下がらない。回復手段は圧縮、新規セッション/クリア、サブエージェントへの隔離のみ。圧縮で落ちた情報は戻らない。
- 管理手段は6つ: 常駐、遅延読み込み、自分で探索、圧縮、隔離、外部化。

### 永続指示（CLAUDE.md / AGENTS.md）

- セッション開始時に自動で載り常駐する。階層（ユーザー全体、プロジェクト、サブディレクトリ）で効く範囲を分けられる。
- 書く基準は「書かないと間違える、かつコードから読み取れない」もの。書かないものは、読めば分かること、長い手順書、頻繁に変わる状態、秘密情報。
- 強制力はない。失敗から育てる運用が基本。
- exmemでは `AGENTS.md` に一本化している（[[ai-development-workflow]] D6）。

## モデル軸（2026-09-30 時点のスナップショット）

メモがWeb検索で確認した内容。モデル名・提供範囲は週単位で変わる。

- モデルはティア（Haiku / Sonnet / Opus等）、世代、推論の深さ（effort）の3軸で整理できる。
- Claude Code: Opus 5.5（9/22）、Sonnet 5.5（9/28）。いずれも1Mコンテキスト。上位にFable 5.1。Claudeモデルのみ。
- Codex: GPT-6 Astra（9/3〜順次）、GPT-6 Sol/Luna（9/22〜、有料プラン向け）、GPT-5.6系など。プランや展開状況で異なる。
- Microsoft 365 Copilot: マルチモデル。Claude Opus 5.5とGPT-6 Sol（9/22〜）がWord/Excel/PowerPoint/Chat/Cowork/Studioに展開。Fable 5.1とGPT-6 AstraはCowork/Copilot Studio限定。既定はAuto。ライセンスと地域で差がある。
- 未確認: Claude Codeの既定モデル。ソースにより「Opus 5.5」「Sonnet 5.5（2.1.284）」と食い違う。なお、このPCのZedは `claude-acp` に `default_config_options.model: "sonnet"` を設定している（2026-10-02 に `settings.json` で確認、[[zed-dotfiles]]）。

## 既存の設計方法論との対応

会話内の概念整理であり、網羅的な学術検証ではない。Prompt / Context / Harnessは重なるため、一対一ではなく「主な責務」での対応。

| AI側の概念 | 既存概念の対応 |
|---|---|
| Prompt Engineering | 要求仕様、インタフェース仕様、Design by Contract、事前条件・事後条件 |
| Context Engineering | ドメインモデル、リポジトリ、イベント、情報隠蔽、依存関係管理、構成管理 |
| Harness Engineering | ランタイム、開発基盤、テスト、CI/CD、ガードレール、オブザーバビリティ、業務プロセス設計 |
| Loop Engineering | インタフェース設計・コネクタ設計（Agent → Interface → Tool/Connector → 外部システム → 結果・イベント → Agentへ戻る循環） |
| Agent orchestration | 分散システム、ワークフロー設計、WBS、役割分担、組織設計 |
| Evaluation | テスト、QA、品質評価、フィードバック制御 |

- Context Engineeringは「AIに何を知った状態で仕事をさせるか」を、情報の配置・境界・参照方法として設計する問題。
- 対象が人間なら組織設計、ソフトウェアモジュールならアーキテクチャ設計、AI Agentなら両者にまたがる設計問題になる。

## Gotchas

### ハーネス情報が見つかりにくい

- 原因（AIの推測）: モデルは番号とベンチマークで比較できるが、ハーネスには標準の体系がない。ベンチマークはモデルとの合成結果になり、各社はモデル名で売る。
- 解決: 6要素に分解して、要素ごとに調べる。

### コンテキストウィンドウの宣言値と実効値は別

- 1Mのうち自由に使える分は、指示・ツール定義・履歴が占めた残り。「入っている」ことと「効いている」ことも別。

### 圧縮で決定事項や制約が失われうる

- 解決: 進捗と決定事項をファイルに書き出し、再開時に読み直す。

### コンテキストは攻撃面になる

- Webやファイルの内容が入力になるため、読んだ内容に影響されても被害が限定されるよう権限を絞る（[[ai-handson-framework]] のプロンプトインジェクションも参照）。

### 既存理論との対応を過信しない

- すべてを既存のソフトウェア工学で説明できると断定するのも不適切。確率的な振る舞い、評価設計、長期コンテキスト管理、自律的な行動ループにはAI特有の課題がある。出力の非決定性や自然言語仕様の曖昧さが、従来のモジュールとの差。

## 仮説・未確認

- ハーネスの歴史の年表（2022〜2026）と解釈（「足場から構造へ」「モデルが強くなるほど足場は薄くなり、権限・コンテキスト・検証が構造として残る」）は、一般知識とAIの見立て。個別の出来事は検索で確認していない。
- 設定ファイルの名前と書式（settings.json、config.toml、承認モードの名称、`claude -p`、`codex exec` など）は一般知識に基づく。使用バージョンの公式ドキュメントで要確認。

## Open Questions

- 自分の現状プロンプトのトークン量は実際どの程度か。
- 権限モデルの深掘りをどのタイミングで行うか（後回しにしている）。
- 「完了条件と検証手順」をどう定義するか（テスト、点検項目）。
- 人間組織・ソフトウェアモジュール・AI Agentを横断する汎用的な設計原理は何か。「責務」「情報」「権限」「相互作用」「フィードバック」「評価」の軸で、既存理論で説明できる範囲とAI固有の課題はどこで分かれるか。
- Loop Engineeringを、API契約、イベント駆動、状態管理、冪等性、リトライ、トランザクション境界、オブザーバビリティなどでどこまで体系化できるか。
- Evaluationを、従来のテスト工学と確率的システムの評価の両面からどう整理するか。
