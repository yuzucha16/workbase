# 作業ログとナレッジ化フックの共通機能（workflow-kit）

## Purpose

作業ディレクトリごとに必要になる「`docs/`（作業ログと判断ログ）」と、「ナレッジ化して」（再利用できる知識を exmem の inbox へ渡すフック）を、特定のリポジトリの記述から切り出し、どの作業ディレクトリからも参照できる共通機能にする。置き場は `notes` の `resources/workflow-kit/`。手順そのものの正本は kit のファイルで、ここには設計の根拠を残す。出力のブレ対策は [[ai-output-consistency]]。exmem と他リポジトリの関係は [[ai-development-workflow]]。

## Principles

- **ナレッジと作業ログを分ける。** ナレッジは育てて共有する知、作業ログは作業ディレクトリが持つ記録。寿命と読み手が違う。ナレッジは次の作業で再利用され、作業ログは日報・週報・仕様書などの文書の入力になる。
- **共通の仕組みは、コピーではなくパス参照で配る。** 改善が1か所に集まり、各ディレクトリのコピーが乖離しない。
- **各ディレクトリの `AGENTS.md` は薄く保ち、固有情報（目的、読む順番、固有ルール）だけを書く。** 共通部を直しても、全ディレクトリを直さずに済む。
- **共通機能への参照は、`@` ではなく平文のパスで書く。** `AGENTS.md` はどのエージェントも読むが、`@` の取り込みは Claude 専用。
- **共通機能は、使うたびに直す前提で作る。** 最初から完全を目指さず、小さく始める。使ってみないと、曖昧さや不足は見つからない。
- **改善の受け皿は、共通機能の中に1か所だけ持つ。** 各ディレクトリに散ると、同じ改善が重複し、乖離する。却下した提案も、理由つきで残す（蒸し返しを防げる）。
- **改善は、AIが提案し、人間が承認する。承認なしに共通機能を書き換えない。** 変更の影響が、参照する全ディレクトリに及ぶ。
- **改善の確認は、実行の直後に、観点を固定して行う**（曖昧だった点、欠けていた情報、使いにくかった点）。記憶が新しいうちのほうが気づけ、観点が揺れると提案の質も揺れる。提案は1回あたり最大3点、「場所 / 問題 / 案」の型で書く。
- **承認後の反映は、共通機能の1か所だけにする。** 呼び出し元には、コピーを作らず、1行の記録だけ残す。
- **共通機能が読めないときは、記憶で代用せず止まる。** 版の違う手順で動くと、出力が揺れる。
- **履歴から復元できるのは「何を・いつ」であり、「なぜ」は書かれている場合に限る。** 書かれていない理由は、推測で補わず「不明」と書く。推測が事実として記録に残ると、後で根拠として引用される。復元した記録には、復元元と範囲（どのコマンドの結果か、何が残っていないか）を明記する。

## Decisions

### 共通機能を `notes` の `resources/workflow-kit/` に置く（2026-10-04）

- 根拠: `resources/` は共有（Git 管理）で他のPCに届く。ナレッジ（`exmem`）と、仕組みの部品を分けられる。
- 却下案: `exmem` 内に置く（ナレッジと仕組みが混ざる）、各ディレクトリにコピーする（乖離する）。

### 参照は平文のパスを基本にし、Claude 用スキルは「kit を読むだけ」の薄いポインタにする方針（2026-10-04。スキルは未作成）

- 根拠: 手順の実体を1か所に置け、他のエージェントでも読める。
- 却下案: `@` の取り込みだけにする（Claude 以外で読めない）、手順をスキルに写す（kit と二重になる）。

### `docs/` は各作業ディレクトリ側に置き、`exmem` には作業ログを置かない（2026-10-04）

- 決めたこと: `contexts/` は「`notes` から見えない場所の作業を引き継ぐコンテキスト」に位置づける。作業ディレクトリが無い作業を `contexts/` に記録する、という当初の案（AI が承認前に追加した）は取り消した。
- 根拠: `exmem` は知識・経験・ルールの置き場。`docs/` は将来、日報・仕様書・手順書などの文書の入力にするので、`exmem` には置けない。`contexts/` は、モバイルや他環境での壁打ちの内容を引き継ぐ受け皿として、別の役割がある。
- 却下案: 作業ディレクトリが無い作業の記録を `contexts/` に置く（`contexts/` の役割が引継ぎから作業ログへ広がる）、`contexts/` を全廃する（引継ぎの受け皿が無くなる）。

### `exmem` への書き込みは、`inbox/` の新規ファイルだけを維持する（2026-10-04）

- 根拠: `knowledge/` への統合時に、実物との照合とタグの正規化を行うため。
- 却下案: `knowledge/` へ直接書く（照合と正規化を飛ばす）。

### `notes/` を作業ディレクトリとし、`docs/` を `notes/docs/` に置く（2026-10-04）

- 決めたこと: `.obsidian/` は `notes/` の一部として扱い、専用の `docs/` は置かない。直前の「`.obsidian/docs/` に暫定で置く」を取り消した。
- 根拠: `.obsidian/` は小さく一過性のディレクトリで、専用の `docs/` を置くのは適正でない。作業ログを `exmem` に置かない方針は維持する（[[app-config-placement]]）。
- 却下案: `.obsidian/docs/` に置く、記録を `exmem/contexts/` に置く（作業ログを `exmem` に置かない方針に反する）。

### 導入手順を「workflowを導入して」の導入フックにする。試験導入先は `notes/`（2026-10-04）

- 根拠: 「ナレッジ化して」と同じ構成（手順・入力の型・自己点検・報告の型・改善フック）にそろえると、出力のブレを抑えられ、`docs/` 以外の追加機能にも対応しやすい。
- 却下案: 手順書だけにする（埋め方が揃わない）、導入スクリプトにする（固有ルールを埋められず、保守が増える）。

### ファイル形式の見出しは、該当が無くても省略せず「なし」と書く（2026-10-04）

- 根拠: 統合のときに、見出しの有無を迷わずに済む。
- 却下案: 該当が無い見出しを省略する（旧モバイル用プロンプトの方式）。

### 改善の受け皿は `improvements.md` 1つ。確認は「ナレッジ化して」の実行後の手順に組み込み、承認制にする（2026-10-04）

- 根拠: 1か所で、日付・発生元・提案・状態を1行ずつ並べて見られる。フックを使った直後が、不足に最も気づきやすい。共通機能の変更は、全ディレクトリの出力に影響する。
- 却下案: 各ディレクトリの `docs/log.md` にだけ残す（散る）、外部の課題管理ツール（小さく始める方針に合わない）、定期レビューだけにする（記憶が薄れる）、AI が提案と同時に直す（承認なしの変更で出力が揺れる）。

### 校正の3原則を、共通機能の README に常設する（2026-10-04。ユーザーの指示）

- 根拠: 以後、どのエージェントがどのディレクトリで使っても、同じ考えで改善が進む（原則の内容は [[ai-output-consistency]]）。
- 却下案: 会話の記憶に任せる（次の会話に引き継がれない）。

### 履歴からの復元では、根拠が履歴に残っている項目だけを Decisions にし、移管元の履歴も調べる（2026-10-04）

- 根拠: Decisions は根拠と却下案が必須という書式なので、推測を混ぜずに済む。対象のディレクトリが別のリポジトリから移ってきた場合、移管前の履歴は元のリポジトリにある。
- 却下案: 理由を推測で補って Decisions に書く（推測が根拠として残る）、現在のリポジトリの履歴だけを調べる（移管前の変更が分からない）。

## Facts

- 復元の手順（2026-10-04、実際に実行）: 一覧は `git log --format='%h %ad %s' --date=short -- <パス>`、変更範囲は `git show --stat <ハッシュ> -- <パス>`、設定値の変化は `git show <ハッシュ> -- <ファイル>` の差分。差分から正確に分かるのは、ファイルの追加・削除と設定値の変化。多くのコミットメッセージは、変更内容だけで理由が書かれていない（11コミットで確認）。理由の手掛かりは、`.gitattributes` や CSS のコメント、既存ナレッジの Proposals など。
- 履歴を作り直した（単一コミットにした）リポジトリでは、それより前の履歴が残っていない（移管元で `git log --all -- <パス>` が初期コミットと移管コミットしか返さなかった）。
- 実物（2026-10-04）: `resources/workflow-kit/` に `AGENTS.md`、`README.md`、`docs-rules.md`、`knowledge-hook.md`、`setup-hook.md`、`improvements.md`、`examples/`、`templates/` がある。`notes/AGENTS.md` が共通ルールの参照先と読む時機を持ち、`notes/docs/` に `log.md` と `decisions.md` がある（`notes/docs/` はローカル専用）。`improvements.md` には採用済みの提案が大半で、「提案」の状態が3件ある（Claude 用スキル、`contexts/` を消化する手段、実際のメモでの校正と kit の版の記録）。
- `notes` では `resources/` だけが Git 共有で、`projects/` `areas/` `archives/` はローカル専用。そこに置いた `docs/` はそのPC内に留まる。
- Windows からは `C:\vault\notes\resources\workflow-kit\` 以下を読める。WSL の `/mnt/c/vault/notes/...` で読めるかは未確認（仮説）。作業ディレクトリの外のファイルを `@` で取り込むと、初回に承認が要る可能性がある（仮説）。
- 今後、`docs/` の作業ログを日報・週報・仕様書の入力にし、ナレッジのマージ・見直しも行う予定（未実施）。改善の受け皿は、その見直しにも使える見込み（仮説）。

## Gotchas

- **ファイル形式が2か所に書かれ、見出しの扱いが食い違った**: モバイル用プロンプトと dotfiles の手順で、見出しを省略するか「なし」と書くかが違った。共通機能を正本にし、モバイル用プロンプトを写しとして合わせた。変更の順番は「kit → モバイル用プロンプト（`exmem/inbox/README.md`）→ 見本」。
- **改善を呼び出し元の `AGENTS.md` に直接書き換える運用だと、他のディレクトリへ伝わらない**: 手順の実体が各ディレクトリの `AGENTS.md` の中にあったため。手順の実体を共通機能に集め、呼び出し元は薄い参照だけにした。
- **Claude Code の `Write` で既存ファイルの上書きが失敗した**: そのファイルを、その会話で先に読んでいなかったため。先に `Read` してから上書きする。
- **追跡の有無が切り替わったファイルの理由を履歴から探したが、コミットメッセージに一言（端末ごとのキャッシュ）しか無かった**: 理由は「不明」と明記し、Open Questions に残した。

## Open Questions

- 実際の inbox メモ数件で手順を校正すると、出力の揺れは減るか。メモに使った kit の版を残すか（例: frontmatter に `kit: YYYY-MM-DD`）。exmem の frontmatter 規則との整合は要確認。
- ネイティブ Linux で、`notes` がどこにあるか。参照パスをどう書くか。Claude 用スキルを作る場合、WSL とのパスの違いをどう吸収するか。
- `docs/log.md` の1項目の書式（何を・なぜ・結果）で、日報・週報・仕様書の入力として足りるか。ナレッジの見直し・マージの契機をどう仕込むか。
- `notes/docs/` は、他のPCに共有するか（`.gitignore` の既定ではローカル専用）。
- `contexts/`（`notes` から見えない場所の引継ぎコンテキスト）を消化する手段。モバイル用プロンプトは作業ログを拾わないため、現在状態の入力が無い（拾えるのは Open Questions と Next Actions だけ）。他のプロジェクトの `contexts/` をリポジトリ側へ寄せるかも、ここに関わる。
- 却下の理由は1行で足りるか。`improvements.md` が長くなったときの整理のルール（採用済みを別ファイルへ移すなど）。受け皿を誰が・どのくらいの間隔でレビューするか。改善の効果をどう測るか。
- 履歴を作り直したあとの期間の記録の補い方。復元の信頼度を書式で標準化するか（例: 「出典: コミットメッセージ」「出典: 差分」「不明」）。復元の手順を共通機能の手順として整備するか。
