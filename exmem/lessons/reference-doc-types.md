# 人が見る文書の3種類の作り方

## Purpose

exmem の用途は2つ。(1) AI が今後の参考にするもの（`exmem/lessons/`）。(2) ee さんが手順や仕組みを思い出すためのもの（`guides/`）。(2) の文書を、読み手の問いで3種類に分け、それぞれの作り方（ノウハウ）をここに置く。(2) の文書そのものは `guides/` に置き、ここには作り方だけを書く。

## Principles

- 文書の種類は、読む人の最初の問いで決める。理由: 内容でなく問いで分けると、迷ったときに決められる。

| 種類 | 読む人の問い | 順序 | 例 |
|---|---|---|---|
| 手順書 | どの順で何をやるんだっけ | あり | dotfiles の `windows/claude/README.md` |
| 理解ガイド | なぜそうなる？ どう動いている？ | 説明の流れ | `guides/explain/ssl-inspection.md`。調査の成果物（`brief 調査`。`checked` つき）も、この種類 |
| クイックリファレンス | あのコマンド・設定は何だっけ | なし（引く） | `guides/quickref/apt.md` |

- 判定の順: 順序があって実行するなら手順書。自分で説明できることが目的なら理解ガイド。どちらでもなく単発の引きものならクイックリファレンス。
- 手順書の正がスクリプトにあるなら、手順書はスクリプトの隣（作業リポジトリ）に置く。汎用の理解ガイドとクイックリファレンスは workbase に置く。理由: 正のある場所に置くと、片方が古くなるのを防げる。
- 3種類に共通: 冒頭に目的と範囲を書く。確認していないことは「未」「要確認」と書く。固有情報（社名、ユーザー名、秘密）は書かない。AI 用の根拠の細部（確認の日付と根拠）は `lessons/` に任せ、人用の文書には結論だけ書く。

### 手順書の型（見本: dotfiles `windows/claude/README.md`）

1. 冒頭: 何のためか、範囲、正の場所
2. 早見表（やりたいこと → コマンド）
3. 仕組み（ファイルの役割の表）
4. 初回の手順（番号つき）
5. 判断の分かれ目（選択肢の表）
6. 他の PC・運用（入れ替え、戻し方）
7. うまくいかないとき（症状 → 確認すること）

### 理解ガイドの型（見本: `ssl-inspection.md`）

1. 冒頭: 目的（自分で説明できるところまで）、前提、確認状況
2. 状況と解決のダイジェスト（状況 → 原因 → 解決）
3. 基礎知識（用語、仕組み、表）。末尾に「自分で説明するときの一言」
4. チェックリスト（症状 → 原因 → 対処の表）
5. 補足（比較表、経緯、一覧）
6. 要確認事項

### クイックリファレンスの型（見本: `apt.md` の書き直し案 `apt-quickref-draft.md`）

1. 冒頭1行: 何のコマンド集か
2. 場面ごとの節。節の中は `やりたいこと | コマンド | 注意` の表
3. 引数は `<name>` で示す。1行で収まらない説明は書かない（理解ガイドへリンクする）
4. よく忘れる点は、表の「注意」欄か節末に1行
5. 出典（`migrated_from` など）は frontmatter に残す

### 読者の違う1つの情報を、分けるか1ファイルにするか（2026-10-21 追記）

- 1つの情報を読者の違う複数の人に読ませるときは、分ける基準を「読む問いが違い、かつ中身も違うか」にする。同じ事実の表示違いは分けない。理由: 分けると同期がずれる。
- 手順書のように、読む問い（順序・実行）が違う文書は、別の型として分ける。理由: 同じ事実の表示違いではなく、中身も違う。
- 同じ内容を二重に持つなら、正を1つに決め、もう一方はそこから導く。ずれたら正を信じる。理由: 二重に持つと同期がずれる。

## Decisions

- **会議録は、1ファイルに2層（冒頭の数行は人向け、本文は AI 向け）で持つ**（2026-10-21）
  - 根拠: ユーザーの決定。同じ事実の表示違いで、ファイル分割は最小にしたい。横断の一覧は、frontmatter の項目で絞った表示（Bases）で見る。
  - 却下案: 2ファイル（同期がずれる）、正本1つと見る側を都度生成（今は採らない）、完全に同じ1系統（人の読みやすさを落とす）。
- **ToDo の正は本文の表にし、frontmatter の件数と期日は表から数えた派生にする**（2026-10-21）
  - 根拠: ユーザーの承認。人が編集するのは表のほうが自然で、件数は数えれば出る。ずれたら表を信じる。
  - 却下案: frontmatter を正にする（人が編集しにくい）。
- **人が見るものは `guides/` に置き、作り方のノウハウは `exmem/lessons/` に置く**（2026-10-09 の方針。名前は 2026-10-10 に確定）
  - 根拠: ユーザーの方針。`knowledge/` は AI 用の名前として広すぎ、中身（判断・原則・落とし穴）に合う `lessons/` にした。`cheatsheets/` は手順書や理解ガイドには狭いので `guides/` にした。
  - 却下案: 人用を種類別にトップへ並べる、トップを `for-ai/` `for-human/` にする、名前を変えず役割だけ再定義する（ユーザーが案 1 を選択）。
- **文書の種類を、読む人の最初の問いで決める（手順書・理解ガイド・クイックリファレンス）**（2026-10-10）
  - 根拠: ユーザーが「問いで決める案は良い」と承認した。内容でなく問いで分けると、迷ったときに決められる。
  - 却下案: 未検討（承認の経緯: 提案をそのまま承認）。
- **クイックリファレンスは「やりたいこと | コマンド | 注意」の表を、場面ごとの節に並べる形にする**（2026-10-10）
  - 根拠: ユーザーが表の形を承認した（「ok」）。`apt.md` を試作して書き直した。
  - 却下案: 従来の `**説明**` + コードブロック（navi 由来）。単発の引きものを表で探せない。

## Facts

- Bases の1行は1ファイルで、本文中の箇条書きを1件ずつ並べる一覧は作れない（仮説）。補足: 横断の ToDo 一覧は、frontmatter に件数と期日を持たせた会議録単位の一覧から始める。

## Open Questions

- 会議録の冒頭の行数の上限（仮に10行）は、実例で測って決める。
- 会議録の型の用語（冒頭の数行は人向け、本文は AI 向け）が、理解ガイドの6見出しの型と食い違わないか。
- `quickref/` の `git.md` `docker.md` `shell.md` の説明は、元の英語のまま。日本語にするか、場面ごとの節に分け直すか（`git.md` は38行が1つの表）。`markdown.md`（記法の見本）と `ssh.md`（メモ）は、表にならないので書き直していない（2026-10-10 時点）。
- `guides/` に、`exmem/exmem-index.md`に当たる入口（やりたいこと・場面から引く索引）が無い。
- `tags.md` と frontmatter の規約（`created` `updated` `status` など）を `guides/` にも適用するか。今は `type` `title` `tags` だけ。
- 旧名は `cheatsheets/`（`env/` を含む）と `knowledge/`。履歴の中の旧名は読み替える。

## Next Actions

- 会議録の型を実例1件で通し、冒頭に収まった決定・ToDo の数と、人が直した箇所の数を測る（2026-10-21 時点）。
