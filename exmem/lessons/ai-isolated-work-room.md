# AI に見せる領域を分ける: 作業部屋（専用 WSL）方式

## Purpose

顧客データなど AI に見せたくない領域と、AI に作業させる領域を、設定の禁止リストでなく**物理的な分離**で分ける設計の判断と原則。実装は `workflow-kit/room/`、使い方は `guides/howto/ai-room-setup.md`、理由と経緯は `guides/explain/ai-room-why.md`。

## Principles

- 「全部見える・一部隠す」（禁止リスト）でなく、「何も見えない・渡したものだけ見える」（許可リスト）にする。理由: 禁止リストは、漏れ（`grep -r`、スクリプトの中、別のツール）を防げない。
- 境界は OS 層（別の WSL ディストリビューション、`automount` と `interop` を無効、AI は一般ユーザー）に置く。AI の権限設定（deny）は、works 側の安全網にとどめ、境界の保証としない。理由: 権限設定は AI のツール経由しか止められない。
- AI に渡すものは、マスクしたコピーにする。原本・対応表・復元済みの成果物は、AI から見えない場所（`_noai/`）に置き、git で追跡しない。
- 副作用のある手順（マウント、マスク、復元、移動、コミット）はスクリプトが行い、AI には実行させない。AI は判断（聞き取り、確認、下書き）を、決まったファイルに書いて渡す。2つの層の接点は、ファイルの受け渡しだけ。
- 外へ出すのは下書きだけにして、人の確認を通す。公開されうる共有知（workbase）へ、対応表の語を含むものを入れない。
- 境界（顧客・機密度）は、部屋の単位（Area）と一致させる。
- wsl.exe に渡す `sh -c` のスクリプトでは、スクリプト内で代入した変数を使わない。複数行のスクリプトは標準入力（`sh -s`）で渡す。理由: wsl.exe は引数を部屋側の外側のシェルでもう一度解釈するので、スクリプト内の変数が空に展開される。
- WSL を差し替える（モックする）単体テストが通っても、wsl.exe 経由の実行は実機で確かめる。理由: 引数の解釈や展開の挙動はモックで再現できず、今回も実機で初めて露見した。
- 自動で書き換える設定ファイルは、目印で囲んだ範囲だけを入れ替え、ほかの内容を変えない。理由: 利用者が同じファイルに書いた内容を消さず、繰り返し実行しても重複しない。
- 作成のたびに増減するもの（WSL のディストリビューション）が、追跡している設定ファイルへ自動で書き足されるなら、自動生成を止めて、必要なものだけ固定する。理由: 作成のたびに設定ファイルに差分が出て、追跡の意味が薄れる。
- 作業ディレクトリの外を読む許可の確認は、「常に許可」で済ませない。理由: 同じ `~` に認証情報（`~/.claude/.credentials.json`）があり、許可が必要以上に広がる。
- 部屋の AI に届ける上位の約束は、部屋の外のファイルを読ませず、読み取り専用の写しを `ai/ctx/` に置く。理由: 部屋は、渡したものだけが見える許可リスト方式で、Area のファイルは見えない。
- 写しは追跡せず、セッションごとに作り直して終了時に消す。理由: 正本が二重になって古くなるのを防ぐ。
- マスクの検証は、実データでなく、架空のダミーで先に行う。ダミーには、ピボットテーブル、コメント、定義名、文書プロパティ、語を含むシート名、書式が途中で変わる文字列を入れる。理由: 実データを使わずに、実機の Excel で開けるかまで確かめられる。
- マスクは xlsx のすべての部品（共有文字列、シート名、定義名、コメント、文書プロパティ、ピボットのキャッシュ）に一貫して掛ける。理由: 一部だけだと、語が残るか、ピボットのキャッシュと表示が食い違う。
- 手で組んだ xlsx は、マスクの前に原本を Excel で開いて有効かを確かめる。理由: 警告が出たときに、原本の不備かマスクの不具合かを切り分けられる。
- 往復（マスクして復元）では、表記ゆれが正規化される前提で設計する。理由: 復元は対応表の正式名に戻すので、元の表記や、同じ種類にまとめた別の形（メールアドレスなど）は戻らない。
- 辞書にも列指定にもない語（人名など）は、マスクされずに残る前提で運用する。理由: 検出は、対応表と列指定が頼りである。
- AI に渡す写し（部屋に置く README の写しなど）の元には、隠したい語を書かない。語の置き場は、写されない側（追跡せず、AI に見せない領域）にする。理由: 写しは AI が最初に読むので、元に書いた語がそのまま見える。
- 作業の種類（設計、文書、調査など）と、データの扱い（マスクしない、マスクだけ、マスクして復元）は、別の軸にする。理由: 掛け算で型が増えると、使わない組み合わせの仕様と文書まで要る。
- 使い方が固まっていない機能は、仕様を足す前に運用（コピーなど）で試し、困ってから仕様にする。仕様を省いたときは、文書も作らない。理由: 仕様と文書の両方が先に増えると、使われなかったときに直す箇所が増える。
- 仕様外の組み合わせは、禁止にせず警告にする。理由: 使う人の試行を止めず、仕様外だと分かるようにするだけで足りる。
- 分離した部屋では、Windows 側の CA bundle を「指定する」方式を取れない（`/mnt/c` が見えない）。勤務先のルート証明書は、人が指定した少数の証明書だけを、root が部屋のシステムストアへ入れる。理由: 信頼先を最小にでき、`ai` ユーザーは読めても書き換えられない。
- Windows のストア全体を入れない。理由: 数百枚が AI から見える領域に入り、信頼先が不必要に広がる。
- 部屋へ入る `wsl.exe` には、Windows の `WSLENV` を渡さない。理由: `/p` 付きのパスが `/mnt/c` の無い部屋で変換できず、壊れた `SSL_CERT_FILE` などが残って curl が失敗する。環境変数の漏れは、分離の面でも望ましくない。
- 新しい PC では、障害を1つずつ踏む前に、関所を順に確かめる（Facts の「関所の一覧」）。理由: TLS 検査のある PC では、証明書、環境変数の漏れ、Node、環境変数の引き継ぎ、資格情報の5つを順に踏み、検査のない PC では1つも出なかった。

## Decisions

- **Area ごとにディストロ、Project ごとにマウント（`ai/` だけを `/mnt/room/<Project>`）**（2026-10-12）
  - 根拠: ライフサイクルが分かりやすく、ログインと導入が Area の数で済む。ユーザーが決定。
  - 却下案: Project ごとのディストロ（数が増えて管理が重い）。
- **すべての projects / areas の AI 作業を、部屋の 1 パターンに揃える**（2026-10-12）
  - 根拠: ユーザーの「できれば1パターンに揃えたい。管理に自信がない」。
- **共有知（workbase）は、起動のたびに写しを `~/shared` に読み取り専用で送る（方式 A）。基準コミットを記録する**（2026-10-13）
  - 根拠: ユーザーが方式 A を選択。分離前と同じ環境になる。
  - 却下案: `resources/` を 2 つ目のマウントにする（B）、部屋の中で clone（C。認証情報が要る）。
- **共有知への戻しは下書きだけ（`ai/out/stock/`）。基準コミットと観測日を持たせ、基準が古ければ印を付け、`integrate` が 3 点で照らす**（2026-10-13）
  - 根拠: git の rebase にならい、検出は機械的に回収時、解決は意味の判断として統合時。ユーザーが方向に合意。
- **部屋の中の Claude Code への案内は、`room start` が毎回、部屋の `~/.claude/CLAUDE.md` に目印つきで置く**（2026-10-14）
  - 根拠: 選択肢（毎回書く方式と、作成手順に手で1回書く方式）を示し、ユーザーが毎回書く方式を選んだ。作成手順に頼らないので、既存の部屋にも効く。
  - 却下案: 部屋の作成手順に、1回だけ手で書く（忘れた部屋で案内が出ない）。
- **Windows Terminal の WSL 動的プロファイル（`Microsoft.WSL`）を無効にして、`Ubuntu-24.04` だけ固定し、部屋へは PowerShell の関数 `room-sh <Area>` で入る**（2026-10-14）
  - 根拠: ユーザーが「対話シェルの起動が楽であればよい」「毎回差分が出るのは困る」と述べ、提案を承認した。部屋が増えても設定を変えずに済む。
  - 却下案: 部屋ごとに固定プロファイルを足す（部屋を作るたびに設定が変わる）。現状維持（作成のたびに差分が出る）。
- **部屋の AI が `~/shared` を読むときの許可の確認には、当面、毎回手動で答える**（2026-10-14）
  - 根拠: ユーザーが「当面は手動で確認します。意識づけ」と決めた。
  - 却下案: 設定ファイルに `~/shared` だけの読み取り許可を足す（提案の段階。設定のキーの形が未確認）。

- **Project を跨ぐ約束は Area の README に書き、`room start` が Area の README を `ai/ctx/area-README.md` に読み取り専用で写す**（2026-10-15）
  - 根拠: 既存のパス（`ai/ctx/`）を使え、`room` の変更が小さい。`ai/ctx/` は追跡されず、`start` の終了ごとに消えるので蓄積しない。Area は境界の単位なので、写る Project 名は同じ Area のものだけになる。ユーザーが承認した。
  - 却下案: Project の README に写す（Area 側と二重になり、古くなる）。Project の `ai/docs/decisions.md` に持つ（Area に1つのルールを、複数の Project が重複して持つ）。

- **復元は、人が変えた `_noai/final/` を上書きせず止める（`--force` で上書き）**（2026-10-16）
  - 根拠: 人が `final/` で仕上げ（ピボットの更新など）をする設計で、無条件の上書きはそれを消す。前回の書き出しのハッシュ（`_noai/map/final-manifest.json`）と比べ、AI だけの変更では止まらない。ユーザーが最小案を承認した。
  - 却下案（今は採らない）: 正本の宣言、`raw/` → `mask` → `ai/in/` の戻り方の約束。実 Project の1巡で足りないと分かってから決める。
- **勤務先のルート証明書は、`init --ca-cert <PEM、5枚まで>` で、人が指定したときだけ、root が `/usr/local/share/ca-certificates/` へ入れる**（2026-10-19）
  - 根拠: ユーザーが承認した。入れる前に SHA-256 を表示し、秘密鍵の混入と枚数の超過は、部屋を触る前に止める。
  - 却下案: Windows のストア丸ごと（信頼先が広がる）、環境変数でツールごとに指す（漏れが出て、`ai` が書き換えられる場所に置く）。
- **Node.js は、apt でなく、公式の tarball をチェックサム確認つきで `/usr/local` へ入れる**（2026-10-19）
  - 根拠: ユーザーが依頼した。Zed の Agent が Node 22 以上を要り、Ubuntu 24.04 の apt は 18。
  - 却下案: NodeSource（取得したスクリプトを root で実行する）、apt の版のまま（足りない）。
- **マスクの一致は広く拾い（部分一致、大小文字と全半角を区別しない）、全ての語を長い語優先の1回の走査で置換する**（2026-10-13）
  - 根拠: 漏れのほうが余分なマスクより重く、余分は復元で戻る。順に置換すると、置換後のプレースホルダーの文字を別の語が拾う。仕様は `workflow-kit/room/mask-spec.md`。

## Facts

- Area の README の大きさは 1.3〜2.2 KB だった（確認: 2026-10-15、根拠: works の `areas/*/README.md` のファイルサイズを測った）。
- `ai/ctx/` は `.gitignore` の `**/ai/ctx/` で追跡されず、`room start` の終了時に削除される（確認: 2026-10-15、根拠: `room.py` と `.gitignore` の雛形を読んだ）。
- `room start` が Area の README を `ai/ctx/area-README.md` に写し、読み取り専用になる。単体テスト2件が通る（確認: 2026-10-15、根拠: `room` の単体テストを実行）。統合時にも `room.py` の `_snapshot(area_readme, ctx_dir / "area-README.md")` と `room/README.md` の `start` の記述を確認した（2026-10-15）。
- 部屋の AI が、開始時に `ai/ctx/area-README.md` を実際に読めるか（仮説）。実際の WSL では確かめていない。
- 実機（WSL）で、専用ディストリビューション、`/mnt/c` が空、`ai/` だけのマウント、Claude Code と Zed（WSL リモート）が部屋の中で動くことを確認した（確認: 2026-10-12、根拠: 実機検証 S1〜S6）。
- マスクは csv と xlsx（zip 内の XML を置換）。
- Windows のネイティブでは Claude Code のサンドボックスが使えない。部屋の中（Linux）では、物理分離があるので重ねる意味が薄い。
- `wsl.exe -d <名> -- sh -c 'd="$HOME/shared"; echo "[$d]"'` は、`$d` が空の `[]` を出し、`$HOME` は展開された。変数を `\$` でエスケープすると、内側で展開された（確認: 2026-10-14、根拠: 実機の部屋で実行した出力）。
- 変数を使わず `"$HOME/shared"` を直接書いたスクリプトで、作成、tar の展開、`chmod -R a-w`、書き込みの拒否（`Permission denied`）まで動いた（確認: 2026-10-14、根拠: 実機の部屋で一時ディレクトリに対して実行）。
- 部屋の `~/.claude/CLAUDE.md` の案内に従って、部屋の AI が `~/shared/ROOM.md`、`hooks.md`、`wrap-hook.md` を順に読んだ（確認: 2026-10-14、根拠: ユーザーが貼った Claude Code の Read の表示）。
- 作業ディレクトリの外を読むと、「Allow this read outside the working directories?」の確認が毎回出た（確認: 2026-10-14、根拠: ユーザーが貼ったダイアログ）。
- `--no-launch` で待機している間、別の `wsl.exe` セッションからは、`/mnt/room/<Project>` が空で、`/proc/mounts` にもマウントが無かった。root でも同じだった（確認: 2026-10-14、根拠: 実機で `grep /proc/mounts` と `ls` を実行）。drvfs のマウントが、マウントしたセッションの中だけに見える可能性がある（仮説）。
- 部屋のディストリビューションを作ると、Windows Terminal の `settings.json` に `"source": "Microsoft.WSL"` のプロファイルが自動で書き足された。`disabledProfileSources` に旧方式の `Windows.Terminal.Wsl` が既にあっても防げず、`Microsoft.WSL` を足す必要があった。足したあと、Terminal を開き直しても差分は出なかった（確認: 2026-10-14、根拠: dotfiles の `git diff` と、ユーザーの開き直しての確認）。
- `wsl -l -q` の出力は UTF-16 で、そのまま読むと文字の間に NUL が入る（確認: 2026-10-14、根拠: 実機の出力が1文字ずつ空白で区切られて表示された）。
- 手で組んだ xlsx（ピボットテーブルとそのキャッシュ、コメント、定義名、文書プロパティ、語を含むシート名）をマスクすると、マスク後のブックが警告なしで開いた（確認: 2026-10-14、根拠: ユーザーの報告「ai/in のファイルまで正常に開いてマスクできていました」）。
- 復元したブックは、Excel で警告なしに開き、ピボットの「すべて更新」が通った（確認: 2026-10-14、根拠: ユーザーの報告）。
- 通常の文字と太字をまたぐ語（「アクメ」を通常、「商事」を太字にしたセル）は、1つの書式にまとめて置換された。マスクの出力に、まとめた件数の注意が1件出た（確認: 2026-10-14、根拠: `room mask` の出力と、`sharedStrings.xml` の内容）。
- マスク後のブックの全部品を文字列検索すると、対応表の語は残っていなかった。シート名は `SHEET_001`、定義名は `NAME_001` になり、ピボットのキャッシュの項目も共有文字列と同じ置換になった（確認: 2026-10-14、根拠: 展開した xlsx の全部品の検索と、`workbook.xml` の内容）。
- cp932 の csv は、マスク後に `utf-8-sig` になった。全角・半角カナ・英字の表記ゆれも置換され、復元で正式名に戻った。復元した csv は、Excel で文字化けなく開いた（確認: 2026-10-14、根拠: マスク後の csv の内容と、ユーザーの報告）。
- 同じ種類にメールアドレスと社名を入れると、マスク後は同じ番号のプレースホルダーが2回並んだ（確認: 2026-10-14、根拠: マスク後の文字列）。復元では、2つとも正式名に戻る設計である（仮説）。
- 辞書にも列指定にもない人名は、マスク後も残った（確認: 2026-10-14、根拠: マスク後の csv の内容）。
- 読み手が本人だけの要約・抽出は、プレースホルダーのままでも読めるので、復元が要らない。復元を自動で行う仕組みだと、`ai/out/` に未知の形式のファイルがあるだけで止まる（確認: 2026-10-19、根拠: `maskkit.py` の `restore_files` を読んだ。実機は未）。
- pptx のマスクでは、`docProps/thumbnail.*`（先頭スライドの縮小画像）に語が写るので削除する。画像と埋め込みブックは、語を検査できない part として警告に出す（確認: 2026-10-19、根拠: 合成データの単体テスト。実機の PowerPoint は未）。
- pptx では、1つの語が複数の run（書式の違い）にまたがる段落がある。先頭の run に置換後の文字を置き、残りの run から語の分を消すと、書式を残したまま漏れなく置換できる（確認: 2026-10-19、根拠: 合成データの単体テスト）。
- 対応表の番号は、`mask.toml` の語の並び順で振られる。同じ並びでコピーして使えば、Project をまたいでも同じ番号になる（仮説）。
- TLS 検査のある PC（PC1）では、部屋の中の `curl https://…` が終了コード 60 で失敗し、部屋から見える証明書の発行元が勤務先名だった。検査のない PC（PC2）では、同じ手順がそのまま通った（確認: 2026-10-19、根拠: ユーザーの実機の報告）。

## Gotchas

- 状況: 個人のグローバル ignore の `out/` が、`ai/out/` の新しい成果物を無視した
  - 原因: リポジトリの `.gitignore` より、グローバルの ignore が効いた
  - 解決: works の `.gitignore` に `!**/ai/out/` を足して打ち消す
- 状況: Zed を部屋ではなくローカルのフォルダで開くと、エージェントが Windows 側で動き、works 全体が見える
  - 原因: Zed のエージェントは、開いたフォルダのある側で動く
  - 解決: Zed は WSL リモート接続でだけ使う
- 状況: 部屋へ共有知の写しを送る処理が `mkdir: cannot create directory ''` で止まった
  - 原因: wsl.exe が `sh -c` の引数を外側のシェルで解釈し直し、スクリプト内で代入した `$d` が空に展開された
  - 解決: 変数を使わず、`$HOME` を含むパスを直接書いた
- 状況: 日本語の Windows で、`python -I` から `⟦` を print すると `UnicodeEncodeError` になった
  - 原因: `-I`（隔離モード）は環境変数 `PYTHONIOENCODING` を無視し、標準出力が cp932 のままだった
  - 解決: `-X utf8` を付けた
- 状況: 「同じ内容なら同じバイト列」を確かめる tar.gz の単体テストが、間欠的に落ちた
  - 原因: gzip ヘッダーの時刻が、2回の生成の間に秒をまたぐと変わる
  - 解決: 未修正（確認: 2026-10-14、根拠: `room.py` の `tarfile.open(..., mode="w:gz")` に mtime の指定が無い）。`GzipFile` に `mtime=0` を渡す案がある（仮説）
- 状況: Area 共通のマスク語を、Area の README に書く案を出した
  - 原因: Area の README は、部屋を起動するたびに `ai/ctx/area-README.md` として写され、部屋の AI が開始時に読む
  - 解決: 共通のマスク語は `areas/<Area>/_noai/` に置き、README には置き場所だけを書く。確認の途中で取り下げた
- 状況: 部屋に入るたびに「failed to translate」が出る
  - 原因: Windows の `WSLENV` の `/p` 付きのパスが、`/mnt/c` の無い部屋で変換できない
  - 解決: `WSLENV` を外して `wsl.exe` を起動する（`room shell` を足した。実機の確認は未了）
- 状況: 部屋の curl が証明書エラー（60）になる
  - 原因: TLS 検査のプロキシのルート証明書が部屋に無い。`WSLENV` 経由の壊れた `SSL_CERT_FILE` も重なる
  - 解決: `--ca-cert` で勤務先のルート証明書を入れた。通った
