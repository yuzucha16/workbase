# AI に見せる領域を分ける: 作業部屋（専用 WSL）方式

## Purpose

顧客データなど AI に見せたくない領域と、AI に作業させる領域を、設定の禁止リストでなく**物理的な分離**で分ける設計の判断と原則。実装は `workflow-kit/room/`、使い方は `guides/howto/ai-room-setup.md`、理由と経緯は `guides/explain/ai-room-why.md`。

## Principles

- 「全部見える・一部隠す」（禁止リスト）でなく、「何も見えない・渡したものだけ見える」（許可リスト）にする。理由: 禁止リストは、漏れ（`grep -r`、スクリプトの中、別のツール）を防げない。
- 境界は OS 層（別の WSL ディストリビューション、`automount` と `interop` を無効、AI は一般ユーザー）に置く。AI の権限設定（deny）は、works 側の安全網にとどめ、境界の保証としない。理由: 権限設定は AI のツール経由しか止められない。
- AI に渡すものは、マスクしたコピーにする。原本・対応表・復元済みの成果物は、AI から見えない場所（`_noai/`）に置き、git で追跡しない。
- 副作用のある手順（マウント、マスク、復元、移動、コミット）はスクリプトが行い、AI には実行させない。AI は判断（聞き取り、確認、下書き）を、決まったファイルに書いて渡す。2つの層の接点は、ファイルの受け渡しだけ。
- 外へ出すのは下書きだけにして、人の確認を通す。公開されうる共有知（workbase）へ、対応表の語を含むものを入れない。
- 境界（顧客・機密度）は、部屋の単位（Area）と一致させる。
- wsl.exe に渡す `sh -c` のスクリプトでは、スクリプト内で代入した変数を使わない（外側で定義済みの `$HOME` は展開されるので使える）。変数を代入するスクリプトや複数行のスクリプトは標準入力（`sh -s`）で渡す。理由: wsl.exe は引数を部屋側の外側のシェルでもう一度解釈するので、スクリプト内で代入した変数が先に展開されて空になる。
- 秘密や任意の文字列を部屋へ渡すときは、引用つきのヒアドキュメント（`<<'EOF'`）で標準入力に載せる。理由: コマンドラインに残らず、`$` やバッククォートも展開されない。
- 失敗の再現と修正の検証は、実際のコードと同じ呼び出し経路で行う。理由: 手で打った同等のコマンドは、引用と展開の層が実コードと違い、失敗を再現できないことがある（`aws-key` の `touch` は、手で打つと通り、原因が見えなかった）。
- 失敗の報告と手元の出力が食い違うときは、出力から「問題なし」と結論せず、報告者がどの経路で実行したかを確かめる。理由: 食い違いは、経路の違いを示していることが多い。
- WSL を差し替える（モックする）単体テストが通っても、wsl.exe 経由の実行は実機で確かめる。理由: 引数の解釈や展開の挙動はモックで再現できず、今回も実機で初めて露見した。
- 自動で書き換える設定ファイルは、目印で囲んだ範囲だけを入れ替え、ほかの内容を変えない。理由: 利用者が同じファイルに書いた内容を消さず、繰り返し実行しても重複しない。
- 作成のたびに増減するもの（WSL のディストリビューション）が、追跡している設定ファイルへ自動で書き足されるなら、自動生成を止めて、必要なものだけ固定する。理由: 作成のたびに設定ファイルに差分が出て、追跡の意味が薄れる。
- 作業ディレクトリの外を読む許可の確認は、「常に許可」で済ませない。理由: 同じ `~` に認証情報（`~/.claude/.credentials.json`）があり、許可が必要以上に広がる。
- 部屋の AI に届ける上位の約束は、部屋の外のファイルを読ませず、読み取り専用の写しを `ai/ctx/` に置く。理由: 部屋は、渡したものだけが見える許可リスト方式で、Area のファイルは見えない。
- 写しは追跡せず、セッションごとに作り直して終了時に消す。理由: 正本が二重になって古くなるのを防ぐ。
- マスクの検証は、実データでなく、架空のダミーで先に行う。ダミーには、ピボットテーブル、コメント、定義名、文書プロパティ、語を含むシート名、書式が途中で変わる文字列を入れる。理由: 実データを使わずに、実機の Excel で開けるかまで確かめられる。
- マスクは xlsx のすべての部品（共有文字列、シート名、定義名、コメント、文書プロパティ、ピボットのキャッシュ）に一貫して掛ける。理由: 一部だけだと、語が残るか、ピボットのキャッシュと表示が食い違う。
- 手で組んだ xlsx は、マスクの前に原本を Excel で開いて有効かを確かめる。理由: 警告が出たときに、原本の不備かマスクの不具合かを切り分けられる。
- 往復（マスクして復元）では、表記ゆれが正規化される前提で設計する。理由: 復元は対応表の正式名に戻すので、元の表記や、同じ種類にまとめた別の形（メールアドレスなど）は戻らない。
- 辞書にも列指定にもない語（人名など）は、マスクされずに残る前提で運用する。理由: 検出は、対応表と列指定が頼りである。
- AI に渡す写し（部屋に置く README の写しなど）の元には、隠したい語を書かない。語の置き場は、写されない側（追跡せず、AI に見せない領域）にする。理由: 写しは AI が最初に読むので、元に書いた語がそのまま見える。
- 作業の種類（設計、文書、調査など）と、データの扱い（マスクしない、マスクだけ、マスクして復元）は、別の軸にする。理由: 掛け算で型が増えると、使わない組み合わせの仕様と文書まで要る。
- 使い方が固まっていない機能は、仕様を足す前に運用（コピーなど）で試し、困ってから仕様にする。仕様を省いたときは、文書も作らない。理由: 仕様と文書の両方が先に増えると、使われなかったときに直す箇所が増える。
- 仕様外の組み合わせは、禁止にせず警告にする。理由: 使う人の試行を止めず、仕様外だと分かるようにするだけで足りる。
- 分離した部屋では、Windows 側の CA bundle を「指定する」方式を取れない（`/mnt/c` が見えない）。勤務先のルート証明書は、人が指定した少数の証明書だけを、root が部屋のシステムストアへ入れる。理由: 信頼先を最小にでき、`ai` ユーザーは読めても書き換えられない。
- Windows のストア全体を入れない。理由: 数百枚が AI から見える領域に入り、信頼先が不必要に広がる。
- 部屋へ入る `wsl.exe` には、Windows の `WSLENV` を渡さない。理由: `/p` 付きのパスが `/mnt/c` の無い部屋で変換できず、壊れた `SSL_CERT_FILE` などが残って curl が失敗する。環境変数の漏れは、分離の面でも望ましくない。
- 新しい PC では、障害を1つずつ踏む前に、関所を順に確かめる（Facts の「関所の一覧」）。理由: TLS 検査のある PC では、証明書、環境変数の漏れ、Node、環境変数の引き継ぎ、資格情報の5つを順に踏み、検査のない PC では1つも出なかった。

## Decisions

- **Area ごとにディストロ、Project ごとにマウント（`ai/` だけを `/mnt/room/<Project>`）**（2026-10-12）
  - 根拠: ライフサイクルが分かりやすく、ログインと導入が Area の数で済む。ユーザーが決定。
  - 却下案: Project ごとのディストロ（数が増えて管理が重い）。
- **すべての projects / areas の AI 作業を、部屋の 1 パターンに揃える**（2026-10-12）
  - 根拠: ユーザーの「できれば1パターンに揃えたい。管理に自信がない」。
- **共有知（workbase）は、起動のたびに写しを `~/shared` に読み取り専用で送る（方式 A）。基準コミットを記録する**（2026-10-13）
  - 根拠: ユーザーが方式 A を選択。分離前と同じ環境になる。
  - 却下案: `resources/` を 2 つ目のマウントにする（B）、部屋の中で clone（C。認証情報が要る）。
- **共有知への戻しは下書きだけ（`ai/out/stock/`）。基準コミットと観測日を持たせ、基準が古ければ印を付け、`integrate` が 3 点で照らす**（2026-10-13）
  - 根拠: git の rebase にならい、検出は機械的に回収時、解決は意味の判断として統合時。ユーザーが方向に合意。
- **部屋の中の Claude Code への案内は、`room start` が毎回、部屋の `~/.claude/CLAUDE.md` に目印つきで置く**（2026-10-14）
  - 根拠: 選択肢（毎回書く方式と、作成手順に手で1回書く方式）を示し、ユーザーが毎回書く方式を選んだ。作成手順に頼らないので、既存の部屋にも効く。
  - 却下案: 部屋の作成手順に、1回だけ手で書く（忘れた部屋で案内が出ない）。
- **Windows Terminal の WSL 動的プロファイル（`Microsoft.WSL`）を無効にして、`Ubuntu-24.04` だけ固定し、部屋へは PowerShell の関数 `room-sh <Area>` で入る**（2026-10-14）
  - 根拠: ユーザーが「対話シェルの起動が楽であればよい」「毎回差分が出るのは困る」と述べ、提案を承認した。部屋が増えても設定を変えずに済む。
  - 却下案: 部屋ごとに固定プロファイルを足す（部屋を作るたびに設定が変わる）。現状維持（作成のたびに差分が出る）。
- **部屋の AI が `~/shared` を読むときの許可の確認には、当面、毎回手動で答える**（2026-10-14）
  - 根拠: ユーザーが「当面は手動で確認します。意識づけ」と決めた。
  - 却下案: 設定ファイルに `~/shared` だけの読み取り許可を足す（提案の段階。設定のキーの形が未確認）。

- **Project を跨ぐ約束は Area の README に書き、`room start` が Area の README を `ai/ctx/area-README.md` に読み取り専用で写す**（2026-10-15）
  - 根拠: 既存のパス（`ai/ctx/`）を使え、`room` の変更が小さい。`ai/ctx/` は追跡されず、`start` の終了ごとに消えるので蓄積しない。Area は境界の単位なので、写る Project 名は同じ Area のものだけになる。ユーザーが承認した。
  - 却下案: Project の README に写す（Area 側と二重になり、古くなる）。Project の `ai/docs/decisions.md` に持つ（Area に1つのルールを、複数の Project が重複して持つ）。

- **復元は、人が変えた `_noai/final/` を上書きせず止める（`--force` で上書き）**（2026-10-16）
  - 根拠: 人が `final/` で仕上げ（ピボットの更新など）をする設計で、無条件の上書きはそれを消す。前回の書き出しのハッシュ（`_noai/map/final-manifest.json`）と比べ、AI だけの変更では止まらない。ユーザーが最小案を承認した。
  - 却下案（今は採らない）: 正本の宣言、`raw/` → `mask` → `ai/in/` の戻り方の約束。実 Project の1巡で足りないと分かってから決める。
- **勤務先のルート証明書は、`init --ca-cert <PEM、5枚まで>` で、人が指定したときだけ、root が `/usr/local/share/ca-certificates/` へ入れる**（2026-10-19）
  - 根拠: ユーザーが承認した。入れる前に SHA-256 を表示し、秘密鍵の混入と枚数の超過は、部屋を触る前に止める。
  - 却下案: Windows のストア丸ごと（信頼先が広がる）、環境変数でツールごとに指す（漏れが出て、`ai` が書き換えられる場所に置く）。
- **Node.js は、apt でなく、公式の tarball をチェックサム確認つきで `/usr/local` へ入れる**（2026-10-19）
  - 根拠: ユーザーが依頼した。Zed の Agent が Node 22 以上を要り、Ubuntu 24.04 の apt は 18。
  - 却下案: NodeSource（取得したスクリプトを root で実行する）、apt の版のまま（足りない）。
- **マスクの一致は広く拾い（部分一致、大小文字と全半角を区別しない）、全ての語を長い語優先の1回の走査で置換する**（2026-10-13）
  - 根拠: 漏れのほうが余分なマスクより重く、余分は復元で戻る。順に置換すると、置換後のプレースホルダーの文字を別の語が拾う。仕様は `workflow-kit/room/mask-spec.md`。

## Facts

- Area の README の大きさは 1.3〜2.2 KB だった（確認: 2026-10-15、根拠: works の `areas/*/README.md` のファイルサイズを測った）。
- `ai/ctx/` は `.gitignore` の `**/ai/ctx/` で追跡されず、`room start` の終了時に削除される（確認: 2026-10-15、根拠: `room.py` と `.gitignore` の雛形を読んだ）。
- `room start` が Area の README を `ai/ctx/area-README.md` に写し、読み取り専用になる。単体テスト2件が通る（確認: 2026-10-15、根拠: `room` の単体テストを実行）。統合時にも `room.py` の `_snapshot(area_readme, ctx_dir / "area-README.md")` と `room/README.md` の `start` の記述を確認した（2026-10-15）。
- 部屋の AI が、開始時に `ai/ctx/area-README.md` を実際に読めるか（仮説）。実際の WSL では確かめていない。
- 実機（WSL）で、専用ディストリビューション、`/mnt/c` が空、`ai/` だけのマウント、Claude Code と Zed（WSL リモート）が部屋の中で動くことを確認した（確認: 2026-10-12、根拠: 実機検証 S1〜S6）。
- マスクは csv と xlsx（zip 内の XML を置換）。
- Windows のネイティブでは Claude Code のサンドボックスが使えない。部屋の中（Linux）では、物理分離があるので重ねる意味が薄い。
- `wsl.exe -d <名> -- sh -c 'd="$HOME/shared"; echo "[$d]"'` は、`$d` が空の `[]` を出し、`$HOME` は展開された。変数を `\$` でエスケープすると、内側で展開された（確認: 2026-10-14、根拠: 実機の部屋で実行した出力）。
- 引数経路（`wsl.exe -d <部屋> -- sh -c <複数行のスクリプト>`）で、スクリプト内の `f="$HOME/.aws/credentials"` を `echo "f=[$f]"` で読むと `f=[]` になり、`touch "$f"` に当たる行は `cannot create : Directory nonexistent` で失敗する。`$HOME` は `/home/ai` に正しく展開され、スクリプト内で代入した変数だけが空になる。`\$v` と書くとリテラルが渡る（確認: 2026-10-20、根拠: 実コードと同じ関数を呼ぶ読み取り専用のプローブを、別の部屋で実行）。
- 標準入力（`sh -s`）で渡し、本文を引用つきのヒアドキュメントに埋める形に直した `aws-key` は、権限 600、所有者が一般ユーザーで書け、本文の `$HOME` とバッククォートがそのまま入る（確認: 2026-10-20、根拠: 実機の部屋で、`HOME` を一時ディレクトリに差し替えて実行）。ユーザーも別の PC で動作を確認した（確認: 2026-10-20、根拠: ユーザーの発言）。
- 同じ引数経路を使う共有知の送付（`push_shared`）は、代入した変数を使わない書き方で、この不具合は無い（確認: 2026-10-20、根拠: スクリプトを読んだ）。
- WSL を差し替える単体テストは、この不具合を検出しなかった。差し替えは、渡されたスクリプトを記録するだけで、展開の層を通らない（確認: 2026-10-20、根拠: テストの差し替えクラスを読んだ）。
- 手で直接実行した `touch` が通った理由は、引数の渡り方（PowerShell 側の引用）の違いだと考えられる（仮説。直接実行の出力は終了コード 0 で、エラー文は無かった）。
- 変数を使わず `"$HOME/shared"` を直接書いたスクリプトで、作成、tar の展開、`chmod -R a-w`、書き込みの拒否（`Permission denied`）まで動いた（確認: 2026-10-14、根拠: 実機の部屋で一時ディレクトリに対して実行）。
- 部屋の `~/.claude/CLAUDE.md` の案内に従って、部屋の AI が `~/shared/ROOM.md`、`hooks.md`、`wrap-hook.md` を順に読んだ（確認: 2026-10-14、根拠: ユーザーが貼った Claude Code の Read の表示）。
- 作業ディレクトリの外を読むと、「Allow this read outside the working directories?」の確認が毎回出た（確認: 2026-10-14、根拠: ユーザーが貼ったダイアログ）。
- `--no-launch` で待機している間、別の `wsl.exe` セッションからは、`/mnt/room/<Project>` が空で、`/proc/mounts` にもマウントが無かった。root でも同じだった（確認: 2026-10-14、根拠: 実機で `grep /proc/mounts` と `ls` を実行）。drvfs のマウントが、マウントしたセッションの中だけに見える可能性がある（仮説）。
- 部屋のディストリビューションを作ると、Windows Terminal の `settings.json` に `"source": "Microsoft.WSL"` のプロファイルが自動で書き足された。`disabledProfileSources` に旧方式の `Windows.Terminal.Wsl` が既にあっても防げず、`Microsoft.WSL` を足す必要があった。足したあと、Terminal を開き直しても差分は出なかった（確認: 2026-10-14、根拠: dotfiles の `git diff` と、ユーザーの開き直しての確認）。
- `wsl -l -q` の出力は UTF-16 で、そのまま読むと文字の間に NUL が入る（確認: 2026-10-14、根拠: 実機の出力が1文字ずつ空白で区切られて表示された）。
- 手で組んだ xlsx（ピボットテーブルとそのキャッシュ、コメント、定義名、文書プロパティ、語を含むシート名）をマスクすると、マスク後のブックが警告なしで開いた（確認: 2026-10-14、根拠: ユーザーの報告「ai/in のファイルまで正常に開いてマスクできていました」）。

## Gotchas

- 状況: 個人のグローバル ignore の `out/` が、`ai/out/` の新しい成果物を無視した
  - 原因: リポジトリの `.gitignore` より、グローバルの ignore が効いた
  - 解決: works の `.gitignore` に `!**/ai/out/` を足して打ち消す
- 状況: Zed を部屋ではなくローカルのフォルダで開くと、エージェントが Windows 側で動き、works 全体が見える
  - 原因: Zed のエージェントは、開いたフォルダのある側で動く
  - 解決: Zed は WSL リモート接続でだけ使う
- 状況: 部屋へ共有知の写しを送る処理が `mkdir: cannot create directory ''` で止まった
  - 原因: wsl.exe が `sh -c` の引数を外側のシェルで解釈し直し、スクリプト内で代入した `$d` が空に展開された
  - 解決: 変数を使わず、`$HOME` を含むパスを直接書いた
- 状況: `aws-key`（部屋へ秘密を書き込むコマンド）が、部屋の `~/.aws/credentials` への `touch` で失敗した（2026-10-14 の上の項目と同じ原因の再発。10-14 の規則は別の関数のコメントと `lessons/` にあり、新しい関数を書く時点では読まれず、10-14 に続いて 10-19 にも再発した）
  - 原因: スクリプトを `sh -c` の引数で渡したため、スクリプト内の変数（`$f` `$x` `$t`）が外側のシェルで空に展開され、`touch ""` になった
  - 解決: スクリプトと本文を標準入力（`sh -s`）で渡し、本文は引用つきのヒアドキュメントにした（`room.py` の `cmd_aws_key` の呼び出し部分。確認: 2026-10-20、根拠: `room.py` のコメントと呼び出しを読んだ）
- 状況: 上の失敗の切り分けで、同等のコマンドを手で打って出力を見た。終了コード 0 で、エラーが無かった
  - 原因: 手で打つ経路は、実コードの経路と引用・展開の層が違う。出力を「失敗しない」と読み、失敗を再現できなかった
  - 解決: 実コードと同じ関数を呼ぶ、書き込みのないプローブで再現した
- 状況: 日本語の Windows で、`python -I` から `⟦` を print すると `UnicodeEncodeError` になった
  - 原因: `-I`（隔離モード）は環境変数 `PYTHONIOENCODING` を無視し、標準出力が cp932 のままだった
  - 解決: `-X utf8` を付けた
- 状況: 「同じ内容なら同じバイト列」を確かめる tar.gz の単体テストが、間欠的に落ちた
  - 原因: gzip ヘッダーの時刻が、2回の生成の間に秒をまたぐと変わる
  - 解決: 未修正（確認: 2026-10-14、根拠: `room.py` の `tarfile.open(..., mode="w:gz")` に mtime の指定が無い）。`GzipFile` に `mtime=0` を渡す案がある（仮説）
- 状況: Area 共通のマスク語を、Area の README に書く案を出した
  - 原因: Area の README は、部屋を起動するたびに `ai/ctx/area-README.md` として写され、部屋の AI が開始時に読む
  - 解決: 共通のマスク語は `areas/<Area>/_noai/` に置き、README には置き場所だけを書く。確認の途中で取り下げた
- 状況: 部屋に入るたびに「failed to translate」が出る
  - 原因: Windows の `WSLENV` の `/p` 付きのパスが、`/mnt/c` の無い部屋で変換できない
  - 解決: `WSLENV` を外して `wsl.exe` を起動する（`room shell` を足した。実機の確認は未了）
- 状況: 部屋の curl が証明書エラー（60）になる
  - 原因: TLS 検査のプロキシのルート証明書が部屋に無い。`WSLENV` 経由の壊れた `SSL_CERT_FILE` も重なる
  - 解決: `--ca-cert` で勤務先のルート証明書を入れた。通った

## 並行 start・データの置き場・変換の道具・実行の設計（2026-10-21 追記）

### Principles（並行）

- 排他の確認は「環境全体に何かあるか」でなく「自分の対象だけ」を見る。理由: 並行を許すと他者の資源が残っているのは正常で、全体を見る確認は、先に終わった側を誤って失敗にする。
- 共有ファイルの更新は、横で完成させてから置き換える（rename）。削除してから作り直さない。理由: 動いている他の利用者が、無い瞬間や途中の状態を読む。
- 後始末の対象は、状態だけでなく年齢でも絞る（作って1分以上たった空の資源だけ消す）。理由: 他の利用者が作った直後で、まだ使い始めていない資源を消す競合を避ける。
- 排他の「止まる」という検知を外すときは、代わりに通知で補う（同時に動いている相手を毎回表示する）。理由: これまで止まることで気づけた残骸が、静かに残るようになる。
- 他のプロセスも書くファイルは、記録済みなら書かず、書くときは置き換えにする。理由: 書き込みの回数と、壊れた状態を見せる時間を減らせる。
- 並行の安全は、コードだけで担保できない。運用の約束（開始のタイミングをそろえる、足すときは動いているセッションを止める）を文書に書いて組み合わせる。理由: 利用者自身（AI）が書くファイルの競合は、置き換えでは緩和にとどまる。
- 作業単位（Project）の粒度は、成果物の数でなく、入力・境界・終了時期が同じかで決める。理由: 入力と境界は AI に見せる範囲を決め、終了時期は完了を宣言する単位を決める。
- 3つ（入力・境界・終了時期）が揃わないときは、無理にまとめず、分けたまま並行して使えるようにする。理由: まとめると、無関係な入力が AI に見えるか、完了を別々に宣言できなくなる。

### Principles（実名の境界とデータの置き場）

- 実名を AI に見せない境界を持つ系では、処理を置く場所を「実名を読むか」で決める。実名を読む処理（取り出し、マスク、復元）は人が実行するコマンドにし、実名の無い処理（統合、要約）は部屋の AI にやらせる。理由: 実名を読む処理を AI 側に1つでも置くと、境界の意味が失われる。
- AI から見える場所（来歴の記録、ファイル名、ログ）に、実名を含みうる情報を書かない。名前は AI から見えない側の対応表に置き、見える側にはハッシュ由来の名前を渡す。理由: マスクは本文にしか効かず、ファイル名とメタデータは別の経路で漏れる。
- 生成物を、人が編集しうる場所へ書き戻すときは、前回書いたもののハッシュを持ち、現在の内容がそれと違えば止める（強制は明示のオプション）。理由: 黙って上書きすると、人の編集が消える。
- 設定が実際に効くのが「拒否」と「ガード」だけなら、その設定は消し、処理を対象の有無（状態）で決める。理由: 設定と状態が食い違う場合（設定は「しない」なのに対象がある）のガードが要り続け、組み合わせの分だけ仕様とテストが増える。
- 状態で決めるときの判定は、入力の有無でなく、過去にその処理をした証跡の有無で見る。理由: 出力ディレクトリに何かあるだけで復元を走らせると、処理の対象外のもの（コードなど）まで巻き込み、「復元できない形式」で止まる。
- 秘匿のクラスが同じデータは、役割別に散らさず、1つの親に寄せる。追跡の除外と閲覧の拒否は、その親の名前に結びつける。理由: 新しい置き場を親の下に作るだけで同じ守りが効き、親の外に作ったものが、気付かず保護から外れるのを防げる。
- データの区分は、役割（入力、出力、再利用する知識）で名付け、昇格の向き（入力 → 出力 → 知識）で関係づける。別の層で使っている語（入力と出力を指す短い名）は避ける。理由: 同じ名前が秘匿の度合いの違うものを指すと、実名ありのものとなしのものが混ざる。
- 「窓口が複数ある」と感じたら、入力元と処理の窓口を分けて描き、窓口は処理の入口で数える。理由: 似たファイルが複数の場所にあるだけで、窓口が複数に見える。

### Principles（部屋の道具と実行）

- 部屋の道具は、root が版を固定して入れ、AI には入れさせない。理由: 取得元と版を AI が選ぶと部屋の中身が実行ごとに変わり、AI が書き換えることもできてしまう。
- Linux の道具で完結する変換は、部屋の中で完結させ、Windows が要る範囲を狭く保つ。理由: 人の操作が残るほど、忘れて未実行になりやすい。
- 日本語の PDF や画像を作る部屋では、フォントの優先を明示する。理由: CJK のフォントは日本語・簡体字・繁体字・韓国語を同居させ、既定では簡体字が選ばれて漢字が中国式の字形になる。
- 大きな取得物は、版と SHA-256 を固定し、必要な部分だけを置き、入っていれば取り直さない。理由: 部屋の再実行のたびに数百 MB を取り直さずに済み、取得物の差し替えも検出できる。
- 人が実行する処理を AI に任せる設計では、依頼と実行の記録を、書く側で分ける。依頼は AI が書き、実行の記録は AI が書けない側だけが書く。理由: AI が「実行済み」を偽れず、実行後のスクリプトの書き換えをハッシュで検出できる。
- 実行しなかったことへの気づきは、人が思い出すことに頼らず、次に必ず使う操作に置く（作業の開始時の表示、作業を閉じるときの停止）。理由: 操作を覚えていなくても検出できる。限界: 次にその操作を使うまで分からない。
- 人が承認して実行する範囲は、1件ずつ、名前で指定し、全文を見せてから実行し、承認なしの自動実行を作らない。理由: 全体実行は成果物が変わりうる。関門が人の目だけになるので、範囲を狭めて見る量を減らす。
- AI が書いたコードを実データに対して実行する設計は、環境の保証（AI は実データを見ず、Windows に触れない）からの後退として、条件を言葉で固定する（実行前の静的検査、入力のコピーに実行、書き出しとログは AI に見えない側）。理由: 条件を固定しないと、保証が崩れる範囲が静かに広がる。
- 構造が複雑になったら、最小の版（道具を入れるだけ）を先に実装し、価値の判定で次の版に上げる。理由: 設計の議論を重ねるほど、使いこなせなくなる。今回の例は1つだけで、型にするには早いかもしれない。
- 隔離環境の Windows 向けスクリプトの作り方と検査は [[shell-script-testing-wsl]] の「Windows で実行するスクリプトを、隔離した Linux の環境で作って検査する」。AI が読める場所へ自動で出すログはマスクを通らない（その節の Principles）。

### Decisions（並行・粒度）

- **並行を、明示するフラグでなく既定の動作にした**（2026-10-21）
  - 根拠: ユーザーが今後は並行を基本の使い方にする。1つだけのときも動作は変わらない。
  - 却下案: 並行を明示するフラグ（毎回付ける手間が増え、ユーザーが既定にすると決めた）。
- **Project は成果物ごとに分けたまま、同じ境界の中で並行して開く**（2026-10-21）
  - 根拠: 成果物ごとに入力と終了時期が揃わない（ユーザーの説明）。
  - 却下案: 1つの Project にまとめ、`ai/out/<成果物>/` で分ける（入力と終了時期が揃わず、完了も Project 単位でしか宣言できない）。

### Decisions（実名入りの知識）

- **統合は、Area を読める AI でなく、部屋の作業にする**（2026-10-21）
  - 根拠: 部屋の目的は実名を AI に見せないこと。作業ディレクトリの AI が Area の実名入りの知識を読んで統合すると、境界に反する。マスクした写しを部屋で統合し、人が実名に戻す。
  - 却下案: 作業ディレクトリの AI が Area を直接読んで統合する（実名を AI が読む。ツールの deny はシェル経由を止めない）、統合用のフックの権限を広げる（上と同じ問題）。
- **知識を3層で扱う: 事実（実名、Area）、部屋用の写し（渡すときに作るマスク済み）、一般化した教訓（共有リポジトリ）**（2026-10-21）
  - 根拠: ユーザーの決定。固有の事実は、仮名にしても共有リポジトリに出さない（案件の内容や日付から再識別できる）。共有に出すのは、一般化したものだけ。
  - 却下案: 最初から仮名で書く（人が読みにくい。書くときの漏れの検査が人の規律になる）、仮名版を常に生成物として持つ（今は採らない。負担が出たら見直す）。
- **マスクは渡すときに行う。渡す分は条件で絞って人が確認する（仮案）**（2026-10-21）
  - 根拠: ユーザーの決定。Area 内は実名で書けるようにする。確認の手間が大きくなる懸念があり、仮案とした。
  - 却下案: Area の知識をマスク済みの写しで常に持つ（二重管理で同期がずれる）、AI が Area を直接読む（境界に反する）。
- **人が変えた Area のファイルがあれば、書き戻しは警告でなく停止にする**（2026-10-21）
  - 根拠: ユーザーの決定。人の編集を黙って消さない。
  - 却下案: 警告して上書きし、直前の版を退避する（最初の実装。止めるほうを選んだ）。上の 2026-10-16 の「復元は、人が変えた `_noai/final/` を上書きせず止める」を、Area への書き出しに広げたもの。

### Decisions（変換の道具・実行）

- **部屋の変換の道具は、部屋を作る `init` で root が入れる**（2026-10-20）
  - 根拠: 証明書や Node.js と同じ扱いになり、AI が書き換えられず、同じ Area の部屋で版がそろう。
  - 却下案: AI がホームに入れる（取得元と版を AI が選ぶ）、入れない（HTML 化は Python、実行は人が毎回操作を覚える）。
- **mermaid の画像化は部屋で完結させる。Chromium は Playwright 版を使う**（2026-10-20）
  - 根拠: 作る側が最後まで持つ、というユーザーの方針。Ubuntu 26.04 の apt の chromium は使えなかった。
  - 却下案: 画像化だけ Windows で人が実行する（人の操作が残る）。
- **等幅フォント PlemolJP の取得は、使い捨ての部屋での試験が安定するまで `init` から外す**（2026-10-20）
  - 根拠: zip が約 220 MB で、試験のたびに待つ。手順は残してあり、コメントを外せば戻せる。
  - 却下案: 入れたまま試験する（毎回の待ち時間が長い）。
- **`room run` の版を3つに分ける: v1 = 道具だけを入れる、v2 = 実行を1件指定で行う `room run`（実データに使わない）、v3 = v2 に実データへの実行を足す。v1 に価値がなければ v2 に上げる**（2026-10-20）
  - 根拠: 変換と mermaid の画像化は部屋の中で完結でき、Windows が要る範囲は VBA の確認とピボットの作成に狭まる見込み。複雑になるのでユーザーが「もっと絞って」と指示した。
  - 却下案: 最初から v3 まで作る（構造が複雑になり、使いこなせない）。
- **`room run` のスコープは、1回に1件、Project 内の成果物を名前で指定する。全体実行と Area 単位の実行は作らない**（2026-10-20）
  - 根拠: 全体実行は成果物が変わりうる。
  - 却下案: Project 全体の一括実行、Area 単位の実行（成果物が変わる）。
- **スクリプトは `ai/work/run/`（使い捨てのスクリプトの置き場）、成果物は `ai/out/<成果物名>/dist/`（実データ由来は `_noai/final/<成果物名>/dist/`）に置く**（2026-10-20）
  - 根拠: 使い捨てのスクリプトは `ai/work/`、成果物は `ai/out/<成果物名>/` に一式、という既存の置き場の規則に合う。`dist/` は全 type 共通の派生物置き場で、1成果物1フォルダを保てる。
  - 却下案: 予約名のディレクトリ `ai/out/run/`（成果物が2か所に分かれる）、type ごとの構造に従う（AI が毎回判断し、上書きの事故が起きうる）。
- **v3（実データへの実行）は、静的検査・入力のコピーに実行・書き出しは AI に見えない側・ログも同じ、の条件で許す**（2026-10-20）
  - 根拠: 条件つきなら、保証の後退を許容できるとユーザーが判断した。
  - 却下案: v3 を作らず、実データは人が手で操作する（実データの Excel 処理を AI に任せられない）。

### Gotchas（2026-10-21 追記分）

- 状況: 掃除コマンドが「作って1分以上」で絞っていることの単体テストが失敗した
  - 原因: 実行したスクリプトの文字列を `-empty` で絞ったところ、git の `--allow-empty` を含む別のスクリプトにも当たった
  - 解決: コマンドの先頭（`find /mnt/room`）で絞るように直した
- 状況: 取り出したファイルの来歴を、元の Area のパスで記録しようとした
  - 原因: 来歴の記録は、部屋の AI から読める場所にある。Area のファイル名（日付とスラッグ）は顧客名を含みうる
  - 解決: 来歴には名前を書かず、元の名前は部屋に渡らない対応表の側に置いた。部屋に渡るファイル名も、日付と元のパスのハッシュにした
- 状況: 復元の実行条件に「対応表がある」を足した後、対応表を作らずに出力だけ置いていた既存テストが、問題を返さず0件で通り、検証が空振りした
  - 原因: テストが前提（マスク済み）を省いていた
  - 解決: テスト側で、マスクして対応表を作ってから復元するようにした
- 状況: 置き場を親ディレクトリの下へ移したら、テストの準備処理（親を作らずに子を作る）が失敗した
  - 原因: 子の作成が親の存在を前提にしていた
  - 解決: 準備処理を、親ごと作る呼び方に直した
- 状況: Ubuntu 26.04 の部屋で、apt で chromium を入れようとした
  - 原因: apt の chromium が snap への移行パッケージで、部屋では snap を使えない
  - 解決: Playwright の Chromium を、root が `/opt` に入れた
- 状況: `chrome --headless --dump-dom 'data:text/html,<p>日本語</p>'` の出力が文字化けした
  - 原因: `data:` URL に文字コードの指定が無く、Latin-1 として読まれた（Chromium の不具合ではない）
  - 解決: `data:text/html;charset=utf-8,…` と指定した
- 状況: Chromium の実行で `dbus ... Failed to call method` の ERROR 行が出た
  - 原因: 部屋に dbus が無い
  - 解決: 無害な警告なので無視した
- 状況: 叩き台で、スクリプトの置き場を `ai/out/win/` にした
  - 原因: Project の置き場の規則（`ai/work/` は使い捨てのスクリプト）を確かめずに決めた
  - 解決: ユーザーの指摘で `ai/work/run/` に直した
