# WSL でシェルスクリプトを試験する

## Purpose

WSL とネイティブ Linux で分岐するシェルスクリプト（dotfiles の `30_link.sh`、`50_repos.sh` など）を、ネイティブ Linux の実機が無くても、実環境を壊さずに試験する方法。項目の頭の【汎用】は他のスクリプトにも使える内容、【この件】は dotfiles の Linux 対応（2026-10-05）に固有の内容。手順書側は [[pc-setup-manuals]]。

注: 以下の Facts は 2026-10-05 の作業時の確認で、2026-10-06 の統合時には dotfiles の実物が見つからず再確認していない。

## Principles

- 【汎用】環境の判定（WSL かネイティブか）は1つの関数にまとめ、差し替え用の環境変数（例: `/proc/version` の場所を指す変数）を用意する。理由: ネイティブ Linux の実機が無くても、WSL 上で両方の分岐を試験できる。
- 【汎用】試験は、一時ディレクトリ（`mktemp -d`）、偽の HOME、スクリプトの上書き用の指定（`--dst` や環境変数）に閉じ込め、実環境の `~` を変更しない。理由: 試験の失敗が普段使いの設定を壊さないようにする。
- 【汎用】外部コマンドと通信は偽物に差し替える。コマンド（例: `ghq`）は PATH の先頭に置いた偽の実行ファイルで、clone 元はローカルの bare リポジトリにする。理由: ネットワークや本物の副作用に依存せず、再現できる。
- 【汎用】リンクや clone を扱うスクリプトは、「新規作成」「再実行（冪等）」「dry-run は何も作らない」「元に戻す（unlink）」「実体が既にあれば止まって変更しない」「リンク切れの置き換え」「元が無ければ skip」を最低限の観点にする。理由: リンク配置の事故（上書き、消し過ぎ）の主な入口がこの7つ。
- 【汎用】差し替えた試験に加えて、本物の環境で動く確認を1項目は入れる。理由: 差し替えが本物と食い違うと、試験が通っても実機で動かない。

## Facts

- 【汎用】構文は `bash -n` で、`.profile` は `/bin/sh -n` で確認できる。Ubuntu 24.04 の `/bin/sh` は dash なので、POSIX の範囲で書けているかも分かる（確認: 2026-10-05、根拠: `readlink -f /bin/sh` が dash を指した）。
- 【汎用】Windows から WSL のスクリプトは `wsl -e bash /mnt/c/<パス>/test.sh` で実行できる。スクリプトは LF で書く（確認: 2026-10-05、根拠: 実行した。CRLF で失敗するかは未実施で、仮説。改行の規則は [[git-line-endings]]）。
- 【汎用】`stow` は展開先の指定（`-t`）で偽の HOME に展開できる。展開から `unlink` までの往復も試験できる（確認: 2026-10-05、根拠: `30_link.sh` の `link` → `unlink` を偽の HOME で通した）。
- 【汎用】`git clone --bare <ローカルのリポジトリ>` で、試験用のリモートを作れる。`/mnt/c` 上のリポジトリでも所有者の警告（dubious ownership）は出なかった（確認: 2026-10-05、根拠: 実行した。WSL2 Ubuntu 24.04）。
- 【汎用】結果を PASS / FAIL で数える小さな `check` 関数（条件式を `eval` して判定）と、失敗数を終了コードにする末尾で、1ファイルの試験スクリプトにできる（確認: 2026-10-05、根拠: 35項目を1つのスクリプトで実行した）。
- 【汎用】WSL の `~/.profile` などが stow で dotfiles リポジトリへの symlink になっていると、リポジトリ内の編集は、試験の前から実環境に効く（新しいログインシェルから）。初期化ファイルを直すときは、先に構文を確認する（確認: 2026-10-05、根拠: `ls -l ~/.profile` が dotfiles への symlink だった）。
- 【汎用】存在しないファイルを `source` すると、`set -e` の非対話の bash スクリプトは終了する（仮説: bash の仕様から。試験では偽の HOME に空の `.profile` を最初から置いたので、実際には遭遇していない）。
- 【この件】試験は35項目で、観点は次のとおり: 構文4、`.profile` の `NOTES_DIR` の分岐4（WSL / ネイティブ / 明示 / export）、`notes_dir` 4、clone 4、`.obsidian` のリンク9、`30_link.sh` の通し5、`50_repos.sh` 5。すべて合格し、実環境の `~` は変更していない（確認: 2026-10-05、根拠: 試験スクリプトの出力が `failures=0`）。
- 【この件】試験のために、`is_wsl()` と `home/.profile` に、環境変数 `PROC_VERSION_FILE`（`/proc/version` の差し替え）を足した。未設定なら本番の挙動は変わらない（確認: 2026-10-05、根拠: 実機の WSL で、未設定のまま `notes_dir` が WSL の値になった）。
- 【この件】ネイティブ Linux の実機は未確認。ネイティブの分岐は、差し替えで再現しただけ（仮説: 実機でも同じ結果になる）。

## Gotchas

- **PowerShell ツール経由で、シェルの断片（`rm -- "$x"`）や `rmdir /s /q`、`robocopy /E` を含むコマンドが拒否された**（2026-10-05 に複数回）。コマンド文字列中の `rm` や `/s` `/E` を、削除コマンドとその引数と誤認する安全チェックが働いた。スクリプトの本文はファイル書き込みのツールで直接書き、削除はパスを固定して `Remove-Item -LiteralPath` で、コマンドを分けて行う。

## Open Questions

- 試験スクリプトは、試験後に削除して保存していない。再利用できる形（例: dotfiles の `tests/`）にするか。AI の提案（未承認）は、35項目の観点がリンク配置スクリプトの変更のたびに使えるため置くこと。
- 差し替え用の環境変数（`PROC_VERSION_FILE`）を、本番のコード（`is_wsl` と `.profile`）に残すか、試験用の包みスクリプトで差し替えるか。
- ネイティブ Linux の実機で、`30_link.sh -n` → `link` → `unlink`、`50_repos.sh` を通して確認する（未実施）。

## Windows のバッチスクリプトの試験（2026-10-06 追記）

Scoop でアプリを入れる Windows のバッチ（dotfiles の `20_apps.bat`）を、ネットワークにも実環境の scoop にも触れずに試験する方法。WSL 側の `tests/linux/` と対称にした。【汎用】は他のバッチにも使える内容、【この件】は dotfiles の `tests/windows/test_20_apps.ps1`（2026-10-06）に固有の内容。導入の中身は [[scoop-app-management]]。

### Principles（バッチ）

- 【汎用】数十 MiB を超える導入（ダウンロードを伴うインストール）は、試験では実行せず dry-run にする。外部コマンドを、引数を記録するだけの偽物に差し替える。通信とストレージの負荷を避け、再実行しても同じ結果になる。
- 【汎用】スクリプトが外部実行ファイルを完全パスで呼ぶときは、差し替え用の環境変数（未設定なら本来の完全パス）を1つ用意する。完全パスの呼び出しは PATH の先頭に偽物を置いても差し替わらない。
- 【汎用】ホームを指す環境変数（`USERPROFILE`）を一時ディレクトリに差し替え、実環境の scoop や設定に触れない。Linux の「偽の HOME」と同じ。
- 【汎用】バッチ内に埋め込んだ PowerShell の1行は、呼び出し記録の文字列照合だけでなく、取り出して実際に実行し、コマンドレットを偽物に差し替えて分岐を試験する。文字列が合っていても、分岐の条件が正しいかは実行しないと分からない。

### Decisions（バッチ）

- **導入そのものは実行せず dry-run とし、数十 MiB を超える導入は試験に含めない**（2026-10-06）
  - 根拠: ユーザーの制約。通信とストレージの負荷になる。
  - 却下案: 使い捨て環境で実際に導入する（負荷が大きい。実際の導入は、新しいアカウントか VM での確認に回す）。
- **試験を `tests/windows/test_20_apps.ps1` として保存する**（2026-10-06）
  - 根拠: ユーザーの依頼で、`tests/linux/` と対称にする。スクリプトを変えるたびに再実行できる。
  - 却下案: 試験のたびに使い捨てる（再利用できない。WSL 側も同じ理由で保存に改めた）。

### Facts（バッチ）

- 【汎用】偽の `scoop.cmd`（引数をログに追記するだけ）と、偽の `powershell.exe` の代わりの `.cmd`（引数を記録し、成功時は偽の `scoop.cmd` を作る）で、「scoop が無く導入成功」「導入失敗」「scoop が既にある」の3場面を試験できる（確認: 2026-10-06、根拠: 12項目が合格）。
- 【汎用】バッチの末尾の `pause` は、標準入力を `< nul` にすると EOF で抜けるので、試験が止まらない（確認: 2026-10-06、根拠: `cmd /c "<bat> < nul"` の試験が完了した）。
- 【汎用】PowerShell の関数は、同名のコマンドレットより優先される。`function Set-ExecutionPolicy { ... }` で偽物に差し替えた状態で、取り出した1行を実行できる（確認: 2026-10-06、根拠: 分岐6項目が合格し、実機の CurrentUser ポリシーは試験の前後で RemoteSigned のまま）。
- 【汎用】`powershell.exe -ExecutionPolicy <値>`（Process スコープ）で、実効ポリシーを作れる。レジストリは書かないので、実機の設定を変えずに試験できる（確認: 2026-10-06、根拠: 同上）。
- 【この件】試験は18項目: バッチの3場面12項目と、埋め込み PowerShell の6項目（`Restricted` `AllSigned` は設定して導入、`RemoteSigned` `Unrestricted` `Bypass` は設定せず導入、設定失敗は警告して続行）。すべて合格した（確認: 2026-10-06、根拠: メモに記録された出力 `failures=0`）。
- 【この件】`tests/windows/test_20_apps.ps1` と `tests/linux/test_scripts.sh` が dotfiles にある。`20_apps.bat` に `PS_EXE`（未設定なら `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`）が足されている（確認: 2026-10-06、根拠: ファイルの存在）。Linux 側の試験の保存（`tests/linux/`）も、上の WSL 節の Open Questions（置き場）の答えになっている。
- 【この件】実機の新しい Windows アカウントでの導入は未確認（仮説: 実機でも試験と同じ分岐になる）。

### Gotchas（バッチ）

- **偽の `powershell` を `.cmd` で作り、バッチから `"%PS_EXE%" ...` と呼んだら、バッチがそこで終わり、後続の `scoop install` に進まなかった**: バッチから別の `.cmd` を `call` なしで呼ぶと、制御が戻らない（本物の `.exe` では起きない）。呼び出しを `call "%PS_EXE%" ...` にした。`.exe` に `call` を付けても挙動は変わらない。

### Open Questions（バッチ）

- 差し替え用の `PS_EXE` を本番のバッチに残すか、試験用の包みスクリプトで差し替えるか（未決。WSL 側の `PROC_VERSION_FILE` と同じ論点）。AI は本番に残す現状を採った（AI の判断。未承認）。
- 実機（新しい Windows アカウント）で、導入が通るかは未確認。本物の導入を1回は確認する必要がある。
- 試験の対象は `20_apps.bat` だけ。ほかの `.bat`（`30_link.bat` など）への展開は未定。

## Windows バッチ（.bat）の落とし穴と、入力を伴う試験（2026-10-06 追記）

セットアップ用の `.bat`（対話入力、色付き表示、ログ保存）を作って試験したときの、cmd 固有の挙動。上の節と同じ会話の続き。

### Principles（落とし穴）

- `.bat` は、コメントを含めて全体を ASCII にし、バイト値が127を超える文字が無いことを自動試験で検査する。日本語（UTF-8）のコメントは、コードページ932のコンソールで行末のバイトが次の行と混ざり、意図しないコマンドとして実行される。
- 対話の再入力ループ（空入力・不正入力なら聞き直す）には、試行回数の上限を付ける。標準入力が閉じている（EOF）と、`set /p`（cmd）も `read`（bash）も空を返し続け、ループが終わらない。
- 入力待ちや再入力ループを持つスクリプトの試験は、入力をファイルのリダイレクトで渡し、実行にタイムアウトの番人（`Start-Job` と `Wait-Job -Timeout`）を付ける。ハングすると呼び出し側のタイムアウトまで待たされ、子プロセスが残る。
- 対話の入力を要する `.bat` は、`call :MAIN >> log` のような出力のリダイレクトで包まない。プロンプトがログに入り、画面に出ない（仮説）。
- **暫定の正は、上の1つ目（コメントと表示を含めて全体を ASCII にする）。cp932 の `.bat` は作らず、cp932 の試験もしない**（2026-10-20 のユーザーの決定。下の Decisions）。日本語を表示したいときも、表示を英語にする。

#### 【草稿・優先度低】日本語を表示する `.bat` を cp932 で書く場合（2026-10-19 のメモ。暫定では使わない）

別環境の1件の経験だけが根拠で、この環境では再確認していない。ASCII の方針を変えるときの材料として残す。

- 日本語を表示する `.bat` は、UTF-8 に `chcp 65001` を足さず、cp932・CRLF で保存する。理由: UTF-8 の日本語を含む行を、cmd が途中で切って別のコマンドとして実行することがある。
- cp932 の `.bat` を作るときは、書き出し後にバイト列を確認する（BOM が無いこと、CRLF であること）。理由: ツールは UTF-8 と LF で書くことがあり、そのまま使うと崩れる。

### Decisions（落とし穴）

- **日本語の質問文（y/N の確認など）を持つ `.bat` を、cp932・CRLF で書き直した**（2026-10-19）
  - 根拠: UTF-8 に `chcp 65001` を付けた版は、実機で行が崩れた。cp932 に直した版は、ユーザーが「いいね」と受け入れた。
  - 却下案: UTF-8 に `chcp 65001`（日本語の `echo` の途中で行が切れ、後半が別のコマンドとして実行された）。
- **`.bat` は、暫定で全体 ASCII を正とする。cp932 の `.bat` は作らず、cp932 の試験もしない。cp932 の内容は草稿とし、優先度は低い**（2026-10-20）
  - 根拠: 2026-10-06 の ASCII ルール（dotfiles の README と `docs/decisions.md`）は、日本語コメントの文字化けへの対策だった。2026-10-19 の件は、works で `.bat` を作った AI がルールに届かず、`chcp 65001` を選んで崩れたもの（経緯の確認: 2026-10-20、根拠: dotfiles と workbase の git 履歴）。ユーザーが「暫定で ASCII を正にして、cp932 の試験はやらない。cp932 の lesson は草稿として、優先度が低いと書く」と指示した。
  - 却下案: 「日本語の表示が要るときだけ cp932・CRLF の例外にし、検査の試験は例外を別扱いにする」（同日の先の決定。試験で見分ける方法が未定で、dotfiles の変更が要るため、同日にユーザーが暫定で取り下げた）。
  - 影響: dotfiles の README、`docs/decisions.md`、`tests/windows/test_20_apps.ps1` は、全体 ASCII のままでよく、変更しない。

### Facts（落とし穴。確認: 2026-10-06）

- `set /p` は、標準入力がパイプだと、2つ目以降の入力を取りこぼす。ファイルのリダイレクト（`< in.txt`）なら全部読める。実際のコンソールでは問題ない（根拠: `set /p` を2回呼ぶ最小のバッチに `one` と `two` を渡し、パイプでは `[one][]`、ファイルでは `[one][two]`）。
- `cmd /c "コマンド & echo %errorlevel%"` の `%errorlevel%` は、行の解析時に展開されるので、古い値になる。判定は `&&` と `||` で書く（根拠: `reg query` の存在判定で、あるときもないときも `0` と表示され、`&& echo present || echo missing` では正しく出た）。
- ANSI の色は、ESC 文字を `for /F "delims=" %%E in ('echo prompt $E^| cmd') do set "ESC=%%E"` で取得すれば、ソースを ASCII のまま出せる。出力に ESC（27）と `[38;5;208m`（256色の208、オレンジ）と、リセットの `[0m` が入る（根拠: 出力のバイト列）。実際にオレンジに見えるかは未確認（仮説）。
- `endlocal & exit /b %RC%` は、`setlocal` の中の `RC` を、環境を戻したあとに終了コードとして返せる（根拠: 成功時 0、失敗時 1 が期待どおり）。
- GitHub の Raw が返す LF だけの `.bat` では、ラベル（`goto :X`、`call :X`）が壊れることがある（仮説）。未検証。ラベルを使わない書き方にすれば避けられる。（2026-10-10 に、生成ツールで作った LF の `.bat` でラベルが見つからない事例が出た。下の「生成した .bat の改行とラベル」。Raw 経由では未検証のまま。）
- `scripts/windows/*.bat` の全体が ASCII であることを、`tests/windows/test_20_apps.ps1` が検査している。`10_env.bat`、`20_apps.bat`、`40_wsl_enable.bat` の日本語コメントを英語にして、全8本が合格した（根拠: 試験の出力）。
- （2026-10-19 の別の件。下の4点は、別環境のメモを写真から書き写したもので、この環境では再確認していない。）UTF-8 の `.bat` に `chcp 65001` を付けて日本語の `echo` を並べたところ、「…is not recognized as an internal or external command」が出て、後続の入力待ちの表示も崩れた（確認: 2026-10-19、根拠: ユーザーが貼った実機の出力）。
- 括弧と読点を含む行（`(既定)` など）が崩れた行だった。括弧が原因かは切り分けていない（仮説）。

## 生成した .bat の改行とラベル、セットアップ用 .bat のログ（2026-10-10 追記）

ファイル作成ツールで新しい `.bat` を作ったところ、`call :LABEL` が失敗した件と、セットアップ用 `.bat`（インストーラ、環境変数の設定）の実行後に状態が分かるログの出し方。上の節と同じ系統（dotfiles の `scripts/windows/`）。

### Principles（改行とラベル）

- 生成ツールで作った `.bat` は、作った直後に改行を CRLF にそろえる。理由: ツールは LF で書くことがあり、`.gitattributes` の `eol=crlf` は `git add` や checkout の時にしか効かないので、作業ツリーの新規ファイルは LF のまま残る（[[git-line-endings]]）。
- ラベル（`call :X`、`goto :X`）を使う `.bat` は、作った直後に、ラベルへ飛ぶ経路を実際に実行して確認する。理由: 構文の確認では見つからず、`The system cannot find the batch label specified` は実行した時にだけ出る。
- 試験から偽のコマンドを `.cmd` で差し込むときは、`.bat` 側の呼び出しに `call` を付ける。理由: `.cmd` を `call` なしで呼ぶと、呼び出し先の終了後に元の `.bat` へ戻らず、後続の処理が実行されない（上の「バッチ」の Gotchas と同じ）。

### Principles（ログの出し方）

- セットアップ用の `.bat` は、成功・SKIP・エラーのどの経路でも、最後に `pause` で止める。理由: 終わった時点でウィンドウが閉じると、何が行われたか分からなくなる。
- 終了経路を `pause` の1か所に集める。`endlocal & exit /b N` を途中で何か所も書かず、`set "RC=N"` のあと `goto :END` で飛び、`:END` で `pause` してから `endlocal & exit /b %RC%` で終える。理由: 経路ごとに `pause` を書くと、経路を足したときに書き忘れる。
- 何かを設定しない（SKIP する）ときは、`[SKIP]` に「何を設定しなかったか」と「理由」と「どうすれば設定されるか」を書く。例: `[SKIP] <ファイル> not found. SSL bundle not set. Put the CA bundle there and run this script again.`。理由: 理由が無い SKIP は、失敗と見分けがつかない。
- SKIP は、ユーザーが `n` と答えた場合も含め、設定しない理由が何であっても出す（`answered n` と理由に書く）。理由: 設定されなかった事実を、ログだけで確認できるようにする。
- 環境変数を `setx` などで設定したら、設定した変数名と値を、最後にまとめて表示する。設定しなかった変数は `[not set]` と表示する。理由: 後から何が設定されたか把握できる。`setx` は現在のセッションに反映されないので、表示は「新しいターミナルで有効」と添える。
- 環境変数の値の表示は、スクリプト内の専用変数（例 `SHOW_X`）に、実際に設定したときだけ値を入れて行う。`%X%` を直接見ない。理由: 以前から環境に同名の変数があると、設定していないのに設定したように見える。

### Facts（改行とログ）

- 生成ツールで作った LF の `26_uv.bat` は、`call :ASKYN` で `The system cannot find the batch label specified - ASKYN` になった。CRLF に変換すると解消した（確認: 2026-10-10、根拠: 試験スクリプトの実行結果と、変換後の再実行）。
- 同時に作った 2 本（`25_awscli.bat`、`27_volta.bat`）は LF のままでも `:ASKYN` が見つかったかは、確認していない。ラベルの位置（ファイル内のオフセット）に依存する可能性がある（仮説）。
- `.gitattributes` が `*.bat text eol=crlf` でも、`git ls-files --eol` の `w/` 列は作業ツリーの実際の改行を示し、新規ファイルは `w/lf` になる（仮説）。補足: 2026-10-11 の実物では、`scripts/windows/23_claude.bat` が `i/lf w/lf attr/text eol=crlf`、`25_awscli.bat` `26_uv.bat` `27_volta.bat` は `i/lf w/crlf` だった（作業ツリーが LF のままのファイルが実在する）。
- `if defined X echo ...` を括弧のブロックにせず1行で書くと、値に `)` を含むパス（`Program Files (x86)` など）でもブロックが壊れない。`echo` の中で `(` `)` を文字として出すときは `^(` `^)` とエスケープする（確認: 2026-10-10、根拠: 3本の `.bat` を偽のコマンドで実行する試験が全件 PASS）。
- 同じ指示（最後に pause する）を、別の `.bat` を作るたびに再度受けた。先に作った2本は後から pause を足していたが、新しく作った3本には入っていなかった（確認: 2026-10-10、根拠: ユーザーの発言「前にも言った」）。
- 実物（2026-10-11 に照合）: `25_awscli.bat` `26_uv.bat` `27_volta.bat` は、`pause`、`[SKIP]` 3 か所、環境変数の表示（`[ENV]` か `not set`）を持つ。`23_claude.bat` は `pause` が無く、`[SKIP]` が 1 か所で、ラベル（`:ASK` `:SKIP` `:INSTALL`）を持つのに作業ツリーが LF のため、上の予防の対象になる。`10_env.bat` は `pause` と `[SKIP]` が 1 か所ずつで、環境変数のまとめ表示（`[ENV]` `not set`）は見当たらない。

### Gotchas（改行とログ）

- **生成ツールで `.bat` を新規作成し、ラベルを `call` したら失敗した**: ファイルが LF だけで、`cmd` がラベルを見つけられなかった。作業ツリーのファイルを CRLF に変換した（`(?<!\r)\n` を `\r\n` に置換）。
- **試験で偽の `setx.cmd`、`uv.cmd` などを PATH の先頭に置き、`.bat` から呼んだら、最初の呼び出しの後で `.bat` が終了した**: `call` なしで `.cmd` を呼んだため。外部コマンドの呼び出しに `call` を付けた（実物の `.exe` に付けても害はない）。

### Open Questions（改行とログ）

- ラベルが見つからなくなる条件（ファイルの大きさ、ラベルの位置）は特定していない。GitHub の Raw から取得した LF の `.bat` で起きるかは、未検証のまま（上の「バッチ」の Facts の仮説に対し、生成ツールの LF のファイルで起きた事例が出たので、仮説の根拠は増えた）。
- 新規の `.bat` を作るときの雛形（終了経路の集約、pause、`[ENV]` 表示）を、規則や雛形のファイルに昇格するか。

## Windows で実行するスクリプトを、隔離した Linux の環境で作って検査する（2026-10-21 追記）

Windows を呼べない隔離した WSL（AI 作業部屋。[[ai-isolated-work-room]]）で AI が bat・ps1 を作ると、構文や文字コードの誤りが Windows で初めて見つかり、デバッグが多かった。実行できない前提で、構成と検査をどうするかを決めた。

### Principles（ps1・bat の構成と検査）

- 人が複数のスクリプトを1回で実行したいだけなら、束ねる役も個別の処理と同じ言語（ps1）で書き、bat は起動用の定型だけにする。理由: bat 固有の失敗（文字コード、LF でラベルが見つからない、`call` 忘れ）は、bat にロジックを書くから起き、ロジックを持たなければ出ない。
- 隔離環境で実行できる処理は、その環境で実行して確かめる。Windows 依存の操作（Excel の VBA・COM、レジストリ、インストール）だけを薄い層に切り出し、判定・変換・検証はその外に置く。理由: 外側は環境内の実行でテストでき、人が Windows で試す範囲が狭まる。
- 実行できない層にも、構文解析・静的解析・差し替えテストはできるよう、処理系（Linux 版の pwsh 7）と解析・テストの道具を、版を固定して隔離環境に入れる。理由: 「Windows で初めて気づく」誤りの大半（構文、未定義の変数、引用符）を、人が実行する前に取れる。
- AI が読める場所へ自動で出すログは、マスクを通らない。出力先と、出すかどうかを、最初に決める（既定では出さず、人が付けたときだけ出す）。理由: 一度出ると、実データの語、ユーザー名、パスが AI に渡る。
- 人の手数は、人が打つ1コマンドにする。実行の前提（Excel を閉じる、入力の有無）は束ねる側が確認し、満たされなければ何をすればよいかを表示して止まる。理由: 手順を人が覚えていると、忘れて未実行になる。

### Decisions（ps1・bat）

- **起動用 bat は、3行の型（`@echo off` は省略可、`pwsh -NoProfile -File "%~dp0<名前>.ps1"`、`pause`）だけ許す。束ねる役は ps1 にする**（2026-10-21）
  - 根拠: bat は、ps1 を束ねて1回で実行する人の手間を省く入口にすぎず、bat 自体に価値は無い（ユーザーの決定）。
  - 却下案: bat にロジックを書く（文字コードとラベルの失敗が出る）、AI が Windows で実行する承認つきの仕組み（用途に対して過剰で、結果を AI に戻す経路も無い）。
- **隔離環境の静的検査は、Linux 版 pwsh 7 を版固定で入れる案にする（PSScriptAnalyzer と Pester を含む。pwsh は 7 に固定）**（2026-10-21）
  - 根拠: ps1 の誤りの大半は構文・変数・引用符で、Parser と PSScriptAnalyzer で取れる。Python では PowerShell の構文を解析できない（ユーザーの承認）。
  - 却下案: Python だけで検査する（BOM・改行などの規約の一部しか見られない）。
- **束ねる ps1 のログ出力は、機能として残し、既定では出さない（`-Log` のときだけ）**（2026-10-21）
  - 根拠: ログを AI が読める領域に自動で出すと、マスクを通らない（ユーザーの指摘で、失念していたと訂正）。
  - 却下案: 常に AI の作業領域へ出す（初案）、成果物の隣へ出す（配布物に混ざる）。

### Facts（ps1・bat）

- PowerShell の公式リリースの `hashes.sha256` は UTF-16 LE で配られる。UTF-8 として読むと文字の間に空白が入り、検索に当たらない。Unicode でデコードすると `linux-x64.tar.gz` の行が取れた（確認: 2026-10-21、根拠: v7.6.7 の `hashes.sha256` を取得してデコードを比べた）。
- 公式の Linux 版 tarball の SHA-256 は、取得したファイルの `Get-FileHash` と、`hashes.sha256` の値が一致した（確認: 2026-10-21、根拠: v7.6.7 の x64 を取得して照合した）。
- Linux 版 pwsh は、tarball を展開するだけで動く。ICU に頼らないよう `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` を指定した包みから、Ubuntu 26.04 の部屋で `pwsh --version` が 7.6.7 と出た（確認: 2026-10-21、根拠: 部屋の一般ユーザーで実行した）。この指定では、日付や数値の書式など、文化に依存する動作が Windows と違いうる（仮説）。
- PSScriptAnalyzer と Pester 5 は、pwsh 7.6.7 に同梱されていない。Windows 側の Modules にも無く、Windows PowerShell 5.1 側には Pester 3.4.0 だけがあった（確認: 2026-10-21、根拠: `Get-Module -ListAvailable`）。
- PSScriptAnalyzer 1.25.0 は Linux 版 pwsh で、`Invoke-Expression`、未使用の変数、未使用の引数を Warning として検出した。Pester 5.9.1 は `Mock` を含むテストが通った（確認: 2026-10-21、根拠: 一時ディレクトリでの実行）。
- `Find-PSResource -Version '5.*'` は5系に絞らず、6系も返した。5系に絞るには `'[5.0.0,5.99.99]'` と書く（確認: 2026-10-21、根拠: 実行の出力）。
- `Start-Transcript` の先頭には、Windows のユーザー名とマシン名が入る（確認: 2026-10-21、根拠: 出力されたログのヘッダー）。
- 未処理のエラーの表示は、`finally` で `Stop-Transcript` した後になるので、ログに入らない。ログに残したいエラーは、`catch` の中で書く（仮説）。補足: 初めから `catch` で書く型にしたので、入らない状況は再現していない。
- 上の案は、部屋を作る `init` の手順として実装されている: pwsh 7（公式 tarball、チェックサム確認つき）、PSScriptAnalyzer と Pester（版を固定、`-Scope AllUsers`）、`DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1` の包み（確認: 2026-10-21、根拠: `room.py` の `PWSH_INSTALL` と単体テストを読んだ）。

### Gotchas（ps1・bat）

- 状況: 工程を順に呼ぶ束ねる ps1 で、`Set-StrictMode -Version Latest` の下、`$LASTEXITCODE` で成否を見た
  - 原因: 外部コマンドをまだ呼んでいない状態の `$LASTEXITCODE` は未設定で、読むと「has not been set」のエラーで止まる
  - 解決: 呼ぶ前に `$global:LASTEXITCODE = 0` を入れ、`-ne 0` で判定した
- 状況: 一時の `HOME` で `Install-PSResource` を実行した
  - 原因: `HOME` 配下の `.local/share` が無く、リポジトリの設定を読めなかった。また、`-TrustRepository` が無いと、対話の確認で止まる
  - 解決: `.local/share` と `.config` を先に作り、`-TrustRepository` を付けた
- 状況: 検査スクリプトで、指摘を1件ずつ数えたうえで、「指摘が無い」というまとめの行も数えた
  - 原因: まとめの行の既定の重大度が FAIL で、Warning だけでも FAIL が1件増えた
  - 解決: まとめの行は、指摘が0件のときだけ PASS として数えた

### Open Questions（ps1・bat）

- 実行先の Windows に Python（または uv）があるか。あれば、Windows 依存の薄い層も Python にできる。
- TLS 検査のあるネットワークで、GitHub と PSGallery からの取得が通るか。
- 隔離環境の AI が、案内に従って束ねる ps1 と3行の bat を作り、検査を使うか。

## Windows の 8.3 短縮名で `relative_to` が失敗するのを避ける（2026-10-21 追記）

同じコミットで、ある PC ではテストが通り、別の PC では `relative_to` の `ValueError` で落ちた原因と、外部コマンドに依存するテストの扱い。

### Principles（パスとテスト）

- パスの包含判定（`relative_to`）や比較は、両側を同じ方法で正規化（`resolve()`）してから行う。理由: 一方が8.3短縮名、他方が長い名前だと、同じ場所でも文字列が一致せず失敗する。
- 環境ごとに結果が違うテスト失敗は、仮説を立てる前に、失敗した PC のトレースバックを取る。理由: 通る環境では再現せず、原因はパスや外部コマンドなど環境側にあることが多い。
- `PATH` 上の外部コマンド（`openssl` など）に依存するテストは、`skipUnless(shutil.which(...))` で、無い環境ではスキップにする。理由: 環境の都合による失敗が、コードの退行と見分けられなくなる。

### Decisions（パスとテスト）

- **表示用の相対パスは、両側を `resolve()` してから `relative_to` する**（2026-10-21）
  - 根拠: ユーザーが原因の修正を依頼し、テストが通る形になった。
  - 却下案: テスト側の一時ディレクトリだけを `resolve()` する（本体コードが同じ状況で落ちる）。
- **`openssl` が無い環境では CA 証明書のテストをスキップにする**（2026-10-21）
  - 根拠: ユーザーが「skip にしてほしい」と指示した。
  - 却下案: テストで証明書を Python だけで作る（作り直しが大きく、今回は求められていない）。

### Facts（パスとテスト）

- `tempfile` の一時ディレクトリは、ユーザー名が長い PC では8.3短縮名（`~1` を含む形）で返り、`Path.resolve()` は長い名前に展開する（確認: 2026-10-21、根拠: 失敗した PC のトレースバックで、片方が短縮名、もう片方が長い名前だった）。
- 修正後、失敗した PC でスキップを含む全テストが通った（確認: 2026-10-21、根拠: ユーザーの報告）。
- 修正前に、ユーザー名が短い PC では同じテストが通っていた（確認: 2026-10-21、根拠: ユーザーの報告と、別の PC での実行）。
- 実物にも反映されている: `room.py` の相対パスの表示は `Path(ctx.vault).resolve()` を使い、`test_room.py` の CA 証明書のテストは `skipUnless(shutil.which("openssl"), …)` が付いている（確認: 2026-10-21、根拠: `room.py` と `test_room.py` を検索した）。

### Gotchas（パスとテスト）

- 状況: `ctx.vault`（短縮名）と、そこから別の経路で作ったパス（長い名前）に `relative_to` を使った
  - 原因: 同じ場所を指しているのに、文字列の接頭辞が一致しない
  - 解決: 両側に `resolve()` をかけてから `relative_to` した
