# スレッド（セッション）を切り替える作法

## Purpose

長くなったスレッドや、話題が変わったスレッドから、新しいスレッドへ作業を移すときのやり方。トークンの消費を抑えながら、決定を落とさずに続けるための手順を残す。

## Principles

- 話題が変わったとき、スレッドが長くなったとき、利用上限が近いときに切る。理由: 履歴は毎ターン読まれ、間が TTL を超えると全体が書き直される。水位は自然には下がらず、長い会話ほど1ターンごとの入力が増える（[[ai-harness-concepts]]）。
- 状態は会話でなくファイルとリポジトリに置き、依頼文は参照で渡す。理由: 新しいスレッドが履歴を読み直さずに、必要なファイルだけで続けられる。
- 切る前に、コミットと push を済ませる。理由: 新しいスレッドはリポジトリを読んで始めるので、未コミットの内容は見えない。
- 履歴の貼り付けと、全文の要約を渡さない。理由: 依頼文に履歴を載せると、新しいスレッドの先頭が重くなり、切った意味が薄れる。
- 続けるか切るかは、「間（キャッシュが生きているか）」と「会話の長さ」の2軸で決める。理由: キャッシュが生きている間は再送される履歴の読みが約1/20の単価で済み、切れると全履歴の書き直しが割高になる。
- 金額の差が小さいときは、金額だけを理由にせず、遅延と長い会話での取りこぼしも理由に数える。理由: 数十円の差では、切るコスト（状態の読み直し）に見合わないと感じやすく、基準が守られない。
- 数値の目安は、実測の前は暫定として置き、重い会話の事例で見直す。理由: AI はセッションの中でキャッシュの命中率もトークン数も正確には測れない。
- 短い会話は、間があいても続けてよい。理由: 切っても新しい会話の最初に読み直す量が変わらず、状態を失うだけになる。
- 続けるか切るかの「間」の基準は、固定の5分にせず、使っているキャッシュの保持時間（TTL）にそろえる。理由: Claude Code の主な会話の TTL は、Claude のサブスクの利用枠内なら1時間、API キー・追加クレジット・クラウド事業者経由なら5分で、環境で変わる（2026-10-18 の実測メモから。下の Open Questions に、Decisions の見直しを残した）。
- 文脈に積んだものの費用は、書き込み1回と、残りのターン数分の読み出しで決まる。理由: Sonnet 5.5 では、5分の書き込みが読み出しの25倍、1時間の書き込みが40倍の単価で、積んだものが25〜40ターン残ると、読み出しの合計が書き込みを超える。
- 間が TTL を超えたら、会話の大きさ H が新しい会話の土台 B を上回る分だけ、切るほうが安い。理由: 続けると会話の全体を書き直し、切ると土台だけを書くので、差は (H − B) に書き込み単価を掛けた額になる。
- TTL 内で切るかどうかは、残りのターン数で決める。切ったときの土台の書き込みを、続けた場合の追加の読み出しで取り戻すまでのターン数は、(書き込み単価 ÷ 読み出し単価) × B ÷ (H − B)。理由: 土台が2万トークンで会話が10万なら、5分TTL で約6ターン、1時間TTL で約10ターン続けるなら、切るほうが安い。
- バッチ化や自動化は、それだけでは費用を下げない。変わるのは間隔だけ。理由: 先頭が同じことは対話でも同じで、独立した作業を別の会話に分けても、続けた場合とほぼ同じ費用だった。

## Decisions

- **切り替えの作法を、次の手順にする**（2026-10-10）
  - 根拠: ユーザーが提案を承認した（「OK。お作法をここで進めて」）。
  - 却下案: 未検討（承認の経緯: 提案をそのまま承認）。

1. 未完の作業を片づけ、コミットして push する（作業ディレクトリが使い捨ての環境のときは特に）。
2. 決定は、該当する `exmem/lessons/` のノートの Decisions に、未決は Open Questions に、次にやることは Next Actions に書く。
3. 新しいスレッドへの依頼文を、3行で書く（下の型）。切り替え元のスレッドが下書きを出し、ユーザーがコピーして貼る。
4. ユーザーが、プロジェクトのチャット（スレッドの外）に依頼として貼る。これで新しいスレッドが立つ。
5. 新しいスレッドは、依頼文の「先に読むファイル」と `exmem/exmem-index.md` の索引から該当ノートだけを読んで始める（全件は読まない）。

依頼文の型:

```text
<やること（1文）>。
済んでいること: <コミットやノート名で。例: main の <ハッシュ>、lessons/<ノート>.md の Decisions>。
先に読むファイル: <パスを2〜3個>。<コミットや承認の扱い>。
```

- **依頼文の下書きは、`wrap` の報告で毎回出す。`wrap` の後は会話を切り、`--resume` で続けない**（2026-10-15）
  - 根拠: ユーザーが、トークン節約の対応案（`wrap` に依頼文の下書きを足す）を選んだ。kit の `wrap-hook.md` の報告の型「次の会話への依頼文」と、`start-hook.md` の契機に反映した。
  - 却下案: 切り替え元のスレッドが、頼まれたときだけ下書きを出す（切るきっかけが、人の判断だけになる）。

- **窓口と `docs/log.md` がある単位（トピック、Project など）の続きは、依頼を「<名前> の続き」の1行にする**（2026-10-16）
  - 根拠: topic-workflow の Q6（状態は窓口と `log.md` だけに置く）の取り込み。`wrap-hook.md` の「次の会話への依頼文」を1行に直した。上の3行の型は、単位の外の作業に使う。
  - 却下案: 毎回3行を出す（済んでいることと読むファイルが `log.md` の写しになる）。

- **依頼文の下書きは `wrap` だけでなく、全フックの報告の最後の共通の項目「次にやること」にした。続けるか切るかを理由つきで推奨する**（2026-10-17）
  - 根拠: ユーザーの指示（次に何をするのかが分からなくなる。トークン節約のため、キャッシュが効くなら同じセッションで続けたい。固定の「<単位> の続き」だけなら不要）。キャッシュが効いている間は再送される履歴の単価が安く、切れると割高になる。続ける条件は、同じ単位・同じ話題・会話が短い・直前の応答から間がない。切る条件は、話題が変わった・会話が長い・間があいた・利用上限が近い。間があいた古い会話の `--resume` はしない。
  - 却下案: 固定の「<単位> の続き」の1行を、`wrap` だけが無条件に出す（次の一手と続けるか切るかの判断が無く、迷う）。

- **切り替えの数値の目安（暫定）: 間は5分、会話の長さは約10万トークン、短い会話は約2万トークン**（2026-10-17）
  - 根拠: 単価は Sonnet 5.5 で、入力 $2、キャッシュ読み $0.10（約1/20）、5分キャッシュ書き込み $2.50（/100万トークン。Anthropic 公式の価格表、2026-10-17 に確認）、1 USD = 158円。会話が10万トークンのとき、間があいて続けると全履歴の書き直しが約40円、切って新しく始めれば（約2万トークンと仮定）約8円で、差は約32円。以後、毎ターンの読みの差が約1.3円ずつ。20ターンで合計約57円。5万トークンなら合計約21円。金額は小さく、主な理由は遅延と、長い会話での取りこぼし（計測していない）。5分は標準のキャッシュ保持時間。
  - 却下案: 数値を決めず、AI の感覚に任せる（推奨がぶれる）。キャッシュ保持時間が1時間の環境の扱いは未検証で、当面は5分で推奨する（長めに続けてしまう方向の誤りは小さい）。
  - 見直し: `review` の入力 5（重い会話）で、10万トークンを超えた会話が実際にあったか、切るべきだった区切りがあったかを見て、数値を直す。
  - 2026-10-18 の更新: 「間は5分」は下の決定で TTL 基準に置き換えた（10万・2万の数値は変えない）。

- **続ける・切るの「間」を、固定の5分でなく TTL（サブスク1時間、API キー5分）にする。切る式は、TTL 切れ後は H − B、TTL 内は残りターン数**（2026-10-18）
  - 根拠: ユーザーの承認（`review 消化` での Open Questions の整理。「1,2を先にお願いします」）。Facts の実測（5分TTL で6分あけると1回約20〜22円増、1時間TTL なら増えない）と、公式 docs の TTL の記述。式は Principles の2つ（間が TTL を超えたら H − B、TTL 内は (書き込み単価 ÷ 読み出し単価) × B ÷ (H − B) ターン）。kit の `hook-common.md` の「次にやること」と `token-matrix.md` の「切る」の定義を直した。
  - 却下案: 5分固定のまま（サブスクでは、1時間以内の間でも切ってしまう）。
  - 未検証: ローカルの既定の TTL（下の Open Questions）。

## Facts

- スレッドを新しく作れるのは、プロジェクトのチャットの側で、スレッドの中のエージェントは作れない（確認: 2026-10-10、根拠: 今回のスレッドで使えるツールに、スレッドを作るものが無かった）。
- 利用上限で止まったスレッドは、ユーザーが「再開」と書くと続きから進められた（確認: 2026-10-10、根拠: 同日のスレッドで実際にそうなった）。
- キャッシュの保持時間は環境で違う。標準は5分で、1時間のものもある（確認: 2026-10-17、根拠: 同じセッションの実行環境の説明に、1時間と書かれていた）。
- 切るほうが安いのは主に遅延と取りこぼしの面で、長い会話で何が落ちるかは計測していない（仮説）。
- Claude Code の主な会話の TTL は、サブスクの利用枠内なら1時間、API キー・追加クレジット・クラウド事業者経由なら5分。`promptCacheTtl` か環境変数 `CLAUDE_CODE_PROMPT_CACHE_TTL` で `5m` / `1h` を選べる（確認: 2026-10-17、根拠: Claude Code 公式 docs の prompt caching のページ。サブスクのクラウドセッションの記録で、書き込みが 1時間側の項目に入っていることも見た）。
- 同じ読み取りだけの3ステップを、条件を変えて実行した。会話をつないで続けて実行は $0.121、別の会話で3回は $0.130、6分あけて1時間TTL は $0.276、6分あけて5分TTL は $0.387（Sonnet 5.5。1回ずつ。クライアント側の概算）（確認: 2026-10-17、根拠: `claude -p --output-format json` の `total_cost_usd` を4条件で実行して比べた）。
- 5分TTL で6分あけると、間のたびに会話の大半（5.8万〜6.7万トークン）を書き直し、1回あたり約20〜22円（1ドル158円）増えた（確認: 2026-10-17、根拠: 同じ実行の `usage` の書き込みと読み出し）。
- 1時間TTL の最初の書き込みの割増（約$0.13）は、間が1回空けば取り戻せる（仮説）。補足: 1回ずつの実行で、他の条件が先に温めた共通の先頭を1時間側が読めなかった影響も混ざる。
- 長い会話の記録の費用は、書き込みが半分以上を占めた。Sonnet 5.5 の部分は書き込み69%、読み出し16%、出力15%。Opus 5.5 の部分は書き込み55%、読み出し33%、出力12%（定価での推定。メインの会話のみ）（確認: 2026-10-17、根拠: 会話の記録の `usage` を `message.id` で重複を除いて集計）。
- `claude -p --output-format json` の結果には、`usage.cache_read_input_tokens`、`usage.cache_creation_input_tokens`、`usage.cache_creation` の `ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens`、`total_cost_usd` が入る。`--resume` で続けると、`total_cost_usd` は前の実行を含む合計で、`usage` はステップごとの値（確認: 2026-10-17、根拠: 実行の出力）。
- 対話中の `/usage` に、`Prompt cache (main)` の行（ヒット率、ミスの回数、直前のミスの原因）が出る（仮説）。補足: 公式 docs の記述で、実機では未確認。
- 同じディレクトリの別の `claude -p` の実行は、起動時の git status が同じなら先頭を共有する（確認: 2026-10-17、根拠: Claude Code 公式 docs。実験でも、別の条件の1ステップ目が約6.7万トークンを読んだ）。

## Gotchas

- **`claude -p` を `--resume` でつなぐ実験を、Claude Code のクラウドセッションの中から動かした**: 環境変数 `CLAUDE_CODE_SESSION_ID` などが残り、`claude -p` が返す session_id がどれも親と同じになった。`env -u CLAUDE_CODE_SESSION_ID -u CLAUDE_CODE_CHILD_SESSION -u CLAUDE_CODE_REMOTE_SESSION_ID` を付けて実行した。
- **条件ごとに別の作業コピーで並行実行したが、1ステップ目の読み出し量が条件で違った**: ツール定義などの共通の先頭が、他の条件や事前の確認で温まっていた。TTL が違う条件は、その分を読めなかったと推測する（仮説）。条件ごとに `--append-system-prompt` の目印を変えて減らしたが、完全には防げなかった。

## Open Questions

- 提案: 数値の目安（約10万トークン、約2万トークン）が実測に合うか。AI はキャッシュの命中率を測れないので、`review` の入力 5（重い会話）で確かめる。
- サブスクの利用枠で、キャッシュの書き込みと読み出しがどう数えられるか。
- ローカルの Claude Code で、サブスクの既定の TTL が1時間か（クラウドでは1時間の書き込みを確認）。

## Next Actions

- 重い会話の事例（10万トークンを超えた会話）で、切るべき区切りがあったかを見て、数値を直す（2026-10-17 時点）。
- 実機で同じ実験を、本物のフック列で3回以上繰り返す（2026-10-18 時点）。
- 作業の終わりに `/usage` のヒット率を見て、期限切れで書き直した量を確かめる（2026-10-18 時点）。
- `effort` を変えた同じ作業の費用と品質を比べる（2026-10-18 時点）。
