# アプリの設定ディレクトリを置くリポジトリの判断基準

## Purpose

アプリの設定ディレクトリを、データのリポジトリ（例: Vault のトップ `works`。2026-10-06 まで `notes`）に置くか、設定ファイル用のリポジトリ（dotfiles）に置くかを決める基準。最初の適用例は Obsidian の `.obsidian/`。Zed や Notepad++ など他のアプリの設定にも使える形にする。

## Principles

- **設定の置き場は、その設定が何と連動して変わるかで決める。** 連動先が Vault の中身（ノート規約、プロパティ型、検索除外）なら Vault 側、環境全体（テーマ・フォントを複数アプリでそろえるなど）なら dotfiles 側。連動するものと同じリポジトリにあれば、変更が1つのコミットで済む。
- **アプリが固定の場所を読む設定は、実体をその場所に置く。** リンクで別のリポジトリに逃がさない。リンクは、clone 順、リンク前の起動による衝突、コミット先の分離といった運用の負担を足す。
- **設定ファイルの管理を2つのリポジトリで相互に参照させない。** セットアップの順序が循環し、片方だけの環境で動かなくなる。リポジトリ全体では、次の2項になる。
- **リポジトリを切る線は、「PC に置かれる・実行されるもの」か「人か AI が読んで判断・作業するもの」か。** 前者は dotfiles、後者は workbase（共有リポジトリ）。迷ったら「PC を作り直すときに要るか」で決め、要るなら dotfiles に置く（2026-10-12 方針）。
- **依存は dotfiles → workbase の一方向だけにする。** dotfiles が workbase について知るのは、clone の URL と置き場所、スキルが読む kit のパスだけ。workbase は dotfiles を、名前とリンクでしか呼ばず、スクリプトの中身や挙動を書かない。理由は3つ: 立ち上げの順番（dotfiles が先に clone され、そこから workbase が置かれる）、AI の境界（AI がノートのついでに直したものが、次の PC セットアップでそのまま実行されない）、規約（「PC ごとのデータを入れない」とぶつからない）。dotfiles を workbase に取り込まず、別リポジトリのまま保つ。dotfiles の挙動を書いた手順書は dotfiles の `docs/setup/` に置く（2026-10-16 に移した）。
- **`AGENTS.md` と `docs/` は、リポジトリのルートか、独立して判断を積む単位にだけ置く。** 小さなサブディレクトリごとには置かない。AI が読む前提資料が作業単位ごとに増え、管理コストだけが膨らむ（[[workflow-kit]]）。
- **AI に置き場の影響を説明させるときは、作業場（Claude を開くディレクトリ）がどこになるかを前提に整理させる。** 置き場を変えると作業場も変わるので、粒度への影響は作業場を基準にしないと誤る（Gotchas）。

## 判断基準の6項目

① アプリが読む場所の制約、② 設定の連動先、③ リポジトリ間の依存の向き、④ 全環境への到達性、⑤ 履歴の軽さ、⑥ `AGENTS.md` と `docs/` を置く粒度。⑥は、どちらのリポジトリでもルートで作業すれば差が出ない（ユーザーの指摘）。④は、全PCに dotfiles も clone するので、今は決め手にならない（ユーザーの発言）。

## アプリが自動で書き換えるファイルを追跡するかの判断基準（5項目）

置き場とは別に、「アプリが自動で書き換えるファイル」（例: Obsidian のコミュニティプラグイン `colored-tags` の `data.json`）を Git で追跡するかどうかを決める基準。

### Principles（追跡）

- **「アプリが自動で書き換えるファイルは追跡しない」と一律に決めず、次の5項目で決める。** ① 再現したい設定か（見た目や動作が、他の端末でも同じになる必要があるか）、② 共有ノートから決まる内容か（端末ごとの内容に依存しないか）、③ 差分が作業の意図と対応するか（無関係な差分が出続けないか）、④ 共有して問題ない内容か（機密やローカル専用ノートの内容を含まないか）、⑤ 外したとき再生成できるか。①〜④がすべて「はい」なら追跡する。一律に外すと、見た目の再現に要る設定まで外れる（実際に `data.json` で判断に迷った）。
- **端末ごとの状態（例: Obsidian の `workspace.json`）は、①と②が「いいえ」なので追跡しない。** 端末ごとに内容が違い、共有する意味がない。
- **⑤の「再生成できる」は、外す理由にしない。** 再生成できても、内容が変わる（例: 色の割り当てが変わる）なら、追跡して固定する価値がある。再生成できるかではなく、再生成した結果が同じかが、再現の条件になる。
- **追跡の判断材料は、実データを検索して確かめ、検索の精度の限界を数値に添える。** 概数を事実として扱うと、後で食い違う。
- **追跡するかの判断は、一度で固定せず、「再現したい設定の量」と「複数PCで衝突するコスト」を比べて決め直す。** 設定の価値はタグ数などの規模で下がり、衝突のコストは使うPCの数で上がる。
- **要素に連番や出現順で値を振る台帳は、複数PCで独立に増えると番号が衝突するので、共有に向かない。** 同じ番号が別の要素に割り当たり、値が食い違うだけでなく、毎回マージ衝突の原因になる。
- **追跡を外す判断は、期限を決めた試用にする。** 外した結果の不便は使ってみないと分からず、`.gitignore` の行を消して `git add` すれば戻せる。

### Decisions（追跡）

- **（2026-10-15 に試用で変更。下の決定を参照）`colored-tags` の `data.json` は追跡する**（2026-10-04。既存の決定を5項目で確認して維持）
  - 根拠: ① 色の割り当てを全端末で同じにしたい。② 78タグのうち74件は共有ノートの本文に出てくる（部分一致の検索で、概数）。③ 新しいタグが増えたときだけ末尾に追記される（当日6件）。④ タグ名だけで、機密はない。⑤ 再生成はできるが、色は発見順の連番なので、clone ごとに変わりうる（仮説）。
  - 却下案: 追跡しない（clone 後に色が変わる）、CSS スニペットで色を固定する（タグが増えて必要になったら移る）。
- **`colored-tags` の `data.json` を `.gitignore` に入れて追跡から外す。1週間の試用にする**（2026-10-15。上の 2026-10-04 の決定を、試用の間は置き換える）
  - 根拠: ユーザーが「タグが100個近く、色を固定しても覚えられず、固定する価値が下がっている」と判断した。台帳（`knownTags`）の更新で、複数PCの diff が頻発していた。5項目では、①（再現したい設定か）の価値が下がり、③（差分が作業の意図と対応するか）が、規模の拡大（78件から約100件）と複数PCで崩れた。
  - 却下案: `tagColors` で色を明示（`knownTags` の diff は残る）、git の clean フィルタで `knownTags` を除く（仕組みが増える）、一方のPCだけでタグを足す運用（運用の負担）。
- **（上の外す決定により、試用の間は不要）運用として、新しいタグを使い始めたコミットに、`data.json` の追記分を含める**（2026-10-04。`notes/docs/decisions.md` に記録済み）。メモの時点では「AI の提案で、ユーザーは追記分を単独のコミットで追跡した」と書かれていたが、その後に決定として記録された（作業ログとの照合で確認）。

### Facts（追跡）

- `data.json` の構成: `palette`（`selected: adaptive-soft`、`mixColors: true`、`transition: true`）、`knownTags`（タグ名から連番への対応。階層タグは親ごとに別の連番）、`_version`。`knownTags` は78件（2026-10-04 に実物で確認）。
- 新しいタグを使い始めると、`knownTags` の末尾に追記される。当日、`tool/notepadpp`、`tool/scoop`、`tool/winget`、`accessibility`、`tool/windows-terminal`、`tool/gh` の6件が追記された（`git diff`）。追記分は `646f44b` でコミットされている（2026-10-04 に `git log` で確認）。
- 78タグのうち、共有ノートの本文に出てくるのは74件。出てこない4件は `dashboard`、`report`、`monthly`、`weekly`（追跡対象の `resources/` の `.md` の部分一致検索。短いタグは過大に一致するので74件は多めの数。日本語名の6ファイルは検索できなかった）。`auto_ota` や `your_project` のような固有名のタグも、共有側の `_archive/` のノートに出てくる。ローカル専用ノートから漏れたものではない（`git grep`）。
- 色の割り当てが、タグを見つけた順の連番で決まることは、既存のナレッジの記述による（仮説: 実際の割り当て処理は未確認）。2026-10-15 時点でも、プラグインのソースは確認しておらず、2PCで同じ番号が別のタグに付く衝突も観測していない（仮説）。
- 2026-10-15 の時点で、`data.json` はほぼ `knownTags`（タグ名からパレット番号への対応）で、`palette.seed: 0`、`selected: adaptive-soft` のとき、色は番号から決まる。`tagColors` は空だった（確認: 2026-10-15、根拠: `data.json` の全文と `git diff`）。
- 追跡を外すコミットを pull したとき、`data.json` に未コミットの変更があるPCでは、modify/delete の衝突になる（確認: 2026-10-15、根拠: `git rebase` が `deleted in <commit> and modified in HEAD` で止まった）。`git rm --cached <パス>` で削除側を採用し、`git rebase --continue` で解消でき、ファイルは作業ツリーに残った（確認: 2026-10-15、根拠: 解消後に `Test-Path` が True）。

### Gotchas（追跡）

- **追跡を外すコミットを、`data.json` が別のPCで更新された origin に rebase したら、衝突した**: 片方が削除、もう片方が変更なので、modify/delete の衝突になる。同じコミットが触った `docs/log.md` でも、テキストの衝突が出た。`data.json` は `git rm --cached` で削除側を採用し、`docs/log.md` は両方の追記を残して `git rebase --continue` した。他のPCでは、pull の前に `data.json` の未コミット変更を退避するか `git restore` する。

- **追跡対象のノートを検索したとき、日本語名の6ファイルが読めなかった**: `git ls-files` が非 ASCII のパスを引用符つきの8進エスケープで出力したため（仮説）。結果を概数とし、「検索できなかったファイルがある」と注記した。回避策は `core.quotepath=false` か `-z`（仮説。未実施）。

## Decisions

### `.obsidian` を dotfiles へ戻す（2026-10-05。2026-10-04 の決定「`notes` に置き続ける」を撤回）

- 決めたこと（ユーザー）: `.obsidian` の実体を dotfiles に置き、Vault のトップ（`NOTES_DIR`）の `.obsidian` へジャンクションで張る。
- 撤回の理由: Vault のトップを、PC ごとのローカルなリポジトリ（PC1 は remote なし）にして、共有の部分を別リポジトリ `workbase`（`resources/` に clone）に分けた。トップは PC 間で共有されないので、`.obsidian` をトップに置くと、設定が PC ごとに別管理になる。dotfiles は全 PC に clone するので、設定を共有できる（判断基準の ③ 依存の向きと ④ 全 PC への到達性が、前提から変わった）。
- 経緯: 提案の時点で、2026-10-04 の決定を示せていなかった。ユーザーに、10-04 の決定と根拠を示した上で、改めて確認して決めた。
- 引き受ける負担（下の撤回済みの決定の根拠と同じもの）: ジャンクション越しの運用。リンクの前に Obsidian を開くと、実ディレクトリが先にできて `30_link.bat` が止まる。設定の変更が dotfiles のコミットになる（`[obsidian]` の接頭辞は dotfiles 側で使う）。`workspace*.json` の除外が dotfiles の `.gitignore` に要る。
- 却下案: トップのリポジトリで管理する（PC 間で共有されない）。

### （撤回済み 2026-10-05）`.obsidian` は `notes` に置き続け、dotfiles には戻さない（2026-10-04）

- 根拠: Obsidian は Vault 直下の `.obsidian` を読む（dotfiles に置くとジャンクションが必須）。設定の中身は Vault と連動する。dotfiles → `notes` の片方向の依存を保てる。プラグインで dotfiles の履歴が重くなるのを避けられる。Zed とテーマ・フォントをそろえる意図は無い（ユーザーの発言）。
- 却下案: dotfiles に戻して `notes/.obsidian` へリンクする（上の負担が増え、得られるのは Zed との統一だけで、その意図が無い）。

### Obsidian の設定を変える作業は、`notes` のルートで Claude を開いて行う（2026-10-04）

- 根拠: `.obsidian/` 専用の `AGENTS.md` と `docs/` を作らずに済む。
- 却下案: `.obsidian/` 単体を作業単位にする（専用の `AGENTS.md` と `docs/` が要る。`.obsidian/docs/log.md` は `git log -- .obsidian` の再掲で、履歴から復元して作れた。その後、`notes/docs/` に置く形に変わった）。

## Facts

`.obsidian` を dotfiles に置いて `notes/.obsidian` へリンクした場合の、確認できている影響（既存のリンクスクリプトの仕様と `links.map` から。2026-10-04）:

- `notes` と dotfiles の clone 順が循環する（dotfiles の `links.map` が `..\notes` を参照するため）。
- リンクの前に Obsidian が実ディレクトリの `.obsidian` を作ると、リンクスクリプトが「実体がある」として止まる。手で退避して再実行する。
- 設定の変更が dotfiles のコミットに入り、`notes` 側の `[obsidian]` コミットが使えなくなる。
- `workspace.json` の除外が、両リポジトリで要る。

同じ構成の、確認していない影響（仮説）:

- 改行コードの規則が、`notes` の `.gitattributes`（LF 統一）ではなく dotfiles 側になる。
- `notes` のルートで Claude を開くと、実体は作業ディレクトリの外になり、編集の確認が増える。
- ripgrep などはシンボリックリンクを既定でたどらないので、中身が検索に出ない。
- シンボリックリンクの作成には開発者モードか管理者権限が要る（ジャンクションは不要）。
- ファイル単位のリンクは、Obsidian の保存で実ファイルに置き換わる。
- Obsidian のコアプラグイン `sync` や、WSL（`/mnt/c`）からのリンクの見え方は不明。
- Obsidian の「設定フォルダを上書き」機能で `.obsidian` を別の場所に置けるか（端末ごとの設定のはずで、採用しても脆い）。

実物（2026-10-04）: `.obsidian/` は `notes` で追跡されている（2026-10-05 以降は、dotfiles が実体を持つ）。

## Gotchas

- **AI が「置き場を変えても解決しない」と答えた**: `.obsidian` を dotfiles に置いた場合の `AGENTS.md` と `docs/` の粒度への影響を整理させたとき。置き場を変えると作業場が dotfiles のルートに変わり、既存の `AGENTS.md` で足りることを見落とした（作業場を前提にしないまま一般化した）。ユーザーの指摘で「置き場では差が出ない。コストが生じるのは `.obsidian/` 単体で Claude を開く運用のときだけ」に直した。
