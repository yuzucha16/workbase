# AI で作る小さなツールの成果物構成・文書・テストの型

## Purpose

他環境で、AI に小さな業務ツールを作らせて保守させるために整備した成果物の構成・文書・テストの型を、言語に依存しない形で取り込み、AI 作業部屋（`ai/` と `_noai/` に分ける設計。[[ai-isolated-work-room]]）の構造と合流させる。型の出どころは他環境1か所の実績で、この環境での再現は未検証。言語固有の知識は [[excel-vba-ai-development]] に分けた。

## Principles

- 編集するのは正本だけにし、派生物（変換後のソース、HTML、README の HTML、見本のブック）はスクリプトで生成する。手で直さない。理由: 二重管理は必ずずれ、手で直した派生物は次の生成で消える。
- 仕様書に書く関数名・定数名・シート名・セル番地は、ソースと同じ識別子にする。食い違ったらソースが正で、文書を直す。理由: AI が文書だけを見て、正しい箇所を直せる。
- 異常（見出しの不一致、重複、読み取り専用など）を見つけたら、何も書かずに中止するか、「要チェック」にして人に渡す。理由: 業務データを壊す損害は、手作業の手間より大きい。
- 列・行の位置、シート名、ファイル名、しきい値は先頭の定数に集め、一覧を機能仕様書に載せる。理由: レイアウト変更の依頼が、定数の変更だけで済む。
- 色・文言・書式は成果物の間で統一し、決めたら1か所に書く。理由: 利用者が成果物ごとに迷わない。
- AI の環境で動かせない確認は「範囲外（実環境で確認する）」と明記し、確認済みと書かない。理由: 確認していないことを確認済みと書くと、通信による手戻りが起きる。
- 実環境で実行した結果を AI に渡すときは、実データの語を伏せる。理由: エラーメッセージやダイアログの全文に、マスク前の実データが混ざりうる。

## Decisions

- **検証を2層に分ける: 部屋の中で完結する検証は AI が実行し、実環境が要る検証は人が Windows で実行する**（2026-10-14）
  - 根拠: 部屋は `interop` と C: の自動マウントを無効にするので、中の AI は Excel など Windows のアプリを動かせない。判断は AI、副作用や実環境での実行は人という既存の分担に合う。
  - 却下案: 部屋の `interop` を有効にして Excel を起動する（Excel 経由で C: 全体に届き、境界が破れる）。
- **実環境の結果を AI に渡すときは、人が実データの語を伏せてから渡す（規約）**（2026-10-14）
  - 根拠: 手数が増えず、今すぐ運用できる。デバッグで `ai` と `_noai` の往復が増えることは認識したうえでの選択。
  - 却下案: 人が置いた結果を `room` がマスクして `ai/in/` へ入れる受け取り口を作る（確実だが実装が要る。Next Actions に残す）。
- **成果物は `ai/out/<成果物名>/` に一式（README、src、docs、tests、tools、派生物）で置く**（2026-10-14）
  - 根拠: 1成果物を1フォルダで自己完結させると配布の単位になり、`room` の復元（`ai/out/` の置換）がそのまま掛かる。`ai/docs/` は作業記録（log と decisions）だけにし、仕様書は成果物の `docs/` に置いて階層で区別する。受け取った参考資料は `ai/in/`、中間成果物は `ai/work/`、元データは `_noai/raw/` に置く。
  - 却下案: `ai/work/` を正本、`ai/out/` を派生物にする（原則とは合うが、コピーの工程が増えて手数が重い）。
- **他環境の作業固有の仕組みと、業務由来の数値・例は取り込まない**（2026-10-14）
  - 根拠: 最終工程の打刻とブロック解除、版の識別子の打刻、ブックへの打刻、プロジェクト名や作業番号、進捗の段階分け、色の RGB 値、Vault 固有のコミット規則は、他環境の作業固有。業務由来の数値と例は、exmem に業務の文脈を書かない決定（2026-10-08）に当たる。ユーザーが指示した。
  - 却下案: 一般化して残す（作業固有で、一般化しても使い回せない）。業務語だけ一般語に置き換えて数値は残す（数値から実績を特定できる）。
- **HTML など派生物の生成は、実装の詳細を書かず、原則だけ残す。決定の記録（log / decisions）の運用は、`workflow-kit/docs-rules.md` へのリンクだけにする**（2026-10-14）
  - 根拠: 生成の実装（変換ツール、図の描画方法）は他環境の道具立てに依存する。記録の運用は `docs-rules.md` が正本で、写すと古くなる。
  - 却下案: 生成の手順を短く残す（他環境の実装に寄りすぎる）。記録の運用の要点を写す（正本が二重になる）。

- **決定の項目のラベルは、【汎用】【案件】【この件】の3種類にそろえる**（2026-10-14）
  - 根拠: `room-context.md` と `room.py` が【案件】を使っており、`docs-rules.md` だけが2種類で食い違っていた。ユーザーが「3種類にする」と決めた。`docs-rules.md` に【案件】を足した（部屋の Project だけで使い、知識にしない）。
  - 却下案: 2種類にそろえて【案件】を廃止する（`room` の Area への転記の仕組みを作り直すことになる）。

## Facts

他環境の文書をユーザーが画像で提示したもの（確認: 2026-10-14）。この環境では未再現。

- 他環境では、1成果物を1フォルダにまとめ、README、`src/`（正本と派生物）、`docs/`（正本の文書）、`html/`（生成物）、`tests/`、`tools/`（変換・検査・生成）で構成した。作業をまたぐ約束は親フォルダの共通ルール1枚に、成果物固有の約束は成果物の README に置いた。
- 文書は、要求仕様書（何を満たすか、ID 付き）→ 機能仕様書（どう実現するか、識別子はソースと一致）→ 運用マニュアル（使い方と困ったときの対応）の3点セットと README で構成した。README は要約と案内に徹し、同じ表を docs と重複させない。
- README の章立ては、状況（実環境での確認の有無を含む表）、実行環境、ファイル構成（何が正本で何が生成物か、再生成のコマンド）、変更後の標準手順、導入、使い方、設定、注意の順だった。
- 書き方の規約: 要求に ID を振り（変更のたびに既存の最後の番号の次から。欠番や振り直しをしない）、1 ID を検証できる1文にする。「〜する」で言い切り、数値・文言まで具体的に書く。中止の条件を列挙し、未確認や仮説を明記する。図は1章に全体図を入れ、入力・本体・出力の3区分で説明する。用語表で同じ概念に別の語を使わない。
- 運用マニュアルに、AI への変更依頼のひな形を持たせた。構成は、背景 → 入力 → 守ること → コードの書き方 → 出力の形式 → 注意 → 変更依頼。記入欄は、変更の種類、したいこと、期待する動作、現在の動作、変えてはいけないこと、確認方法の希望の6項目。不具合のときは、再現手順、エラー全文（番号と工程名つき）、結果の全文、ログ、期待値と実際の値を足す。
- テストは、実環境で動かす自動テストと合成データ（実データ、個人名、金額を使わない）で構成した。終了コードは全件合格で 0、不合格ありで 1。出力は `PASS` / `FAIL` と最後の件数で、所要は1分未満を目安にした。
- テストの区分の型: 準備、正常系（対象外の列・行と入力ファイルが不変であること、設定の復元を含む）、ログ、別モード、中止（どれも「何も書かれていない」ことを確認）。テストの README の末尾に「範囲外（実環境で確認する）」を書き、成果物の README の状況表の「実環境での確認」と対応させた。
- 立ち上げでは、曖昧な点を先に質問して答えを決定の記録に「ユーザー回答」として残し、依頼文の誤記は解釈の根拠を備考に残した。テストはソースと並行して育て、文書は要求 → 機能 → 運用 → README の順に、ソースを見て識別子を合わせて書いた。報告には「実環境で未確認の点」と「利用者にお願いする確認」を書いた。
- 完了の条件: ソースの検査が通る、自動テストが全件合格（件数を記録）、文書が最新で識別子がソースと一致、派生物を再生成済み、ログを更新、状況表に実環境での確認の有無を正直に書く、コミットは範囲を指定して含めなかったファイルを報告する。
- AI との協働の約束: 実行できない範囲は出力前に読み直し、実行できる範囲は数値で報告する。仕様と食い違う変更が要るときは、実装前に理由と代案を示す。提案と決定を区別する。同日の仕様変更は全層（要求、機能、運用、README、テスト、派生物）に反映する。長い Markdown は全文を読み書きせず、差分で直す。
- 他環境の振り返りでは、最初から同じ章立てで作ると2つ目以降の立ち上げが速く、自動テストが先にあると仕様変更を同日に全層へ反映できた。結果の表示を「要チェックだけを短く」と「全件のログ」の二層にすると、確認の負担が小さかった。
- 部屋（`ai/` と `_noai/`）の中で、この型がそのまま機能するか（仮説）。

## Gotchas

- 状況: 依頼文の記述が、実データの見出しと食い違っていた（期間の番号の誤記）
  - 原因: 依頼文の誤記
  - 解決: 実データの見出しを根拠に解釈し、解釈の根拠を備考に残して、利用者に確認する

## Open Questions

- 提案: 往復を減らすため、AI のフェーズで完結させる仕組みを作る（実環境に依存する層を薄くする、部屋で再現できる合成データのテストを厚くする、実環境の確認が要る変更をまとめて1回で渡す）（AI の提案。未承認）。
- HTML など派生物の生成（図の描画にブラウザを使う）を、部屋の中で動かせるか。動かせないなら、人が Windows で行う工程にする。
