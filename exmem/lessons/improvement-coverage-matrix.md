# 改善のやり方3: 観点を絞り込み、星取り表から修正・削除・追加の案を出して実施項目を決める

## Purpose

すでに仕組み（規約、手順書、スクリプト）がある対象を改善するとき、思いついた案から手を付けずに、「観点のランキングと絞り込み → 星取り表 → 修正・削除・追加の対応案 → 優先度つきのリスト → 影響範囲とリスクによる実施項目の確定」の流れで進める。この流れを「改善のやり方3」として残す。
数値で改善幅を比べる改善は [[improvement-quantified-options]]（改善のやり方1）、想定と実際のズレから直す改善は [[improvement-expectation-gap]]（改善のやり方2）。

## Principles

- 改善の観点を先に挙げ、影響度と支配度でランキングし、上位に絞り込んでから進める。理由: 観点を絞るほど、1セッション・1トークンあたりの改善度が高くなる。全観点を一度に扱うと、表も案も薄く広がる。
- 対応案を出す前に、星取り表を作る。行は既存のルール・仕組み、列は絞り込んだ観点。理由: どの観点がすでに押さえられていて、どこが空いているかが見えてから案を出すと、効いている仕組みを重ねて作らずに済む。
- 星取り表には、記号（◎ 直接効く、○ 効く、△ 部分的）に加えて、効き方（スクリプトが強制する、手順書の手順にある、常駐の規約にある、知識のノートにあるだけ）を書く。理由: 同じ ◎ でも、知識にあるだけのものは、探したときにしか効かない。空いているところは「◎ が無い列」だけでなく「◎ が知識にしかない列」にもある。
- 対応案は、修正・削除・追加の3つの観点に分けて出す。理由: 追加に偏りやすい。修正（項目を増やさずに直す）と削除（畳む）を先に考えると、規模を増やさずに改善できる。
- 各案に、影響範囲（何ファイル・どの層に及ぶか、既存の利用先を手で直す必要があるか）とリスクを付け、そこから実施項目を確定する。理由: 効果だけで選ぶと、雛形や常駐の規約のように、変えると既存の全体に及ぶものを軽く扱ってしまう。
- 優先度は、改善度を、影響範囲とリスクで割った大きさで付ける。影響が小さく項目を増やさない修正は、先に着手してよい。規模の凍結（足すなら畳む）があるときは、追加を削除と対にして出す。

## 用語

このノートでの使い方（AI が言葉にし、ユーザーが意図と合っていると確認した。確認: 2026-10-15、根拠: ユーザーの発言）。

- **影響度**: その観点を改善したときに、効果がどれだけ大きいか。
- **支配度**: その観点が、ほかの観点の前提になったり、全体の結果を左右したりする度合い。例: 状態の外部化は、会話を切ることの前提になる。
- **影響範囲**: 対応案が及ぶ範囲。小（ノートかスクリプトだけ）、中（手順書1〜2ファイル。pull するだけで全体に反映される）、大（雛形や常駐の規約。既存の利用先を手で直す必要がある）。

## 手順

1. **観点を挙げてランキングする**: 改善したい観点を列挙し、影響度と支配度で順位を付ける。
2. **絞り込む**: 上位の観点だけを残す。1回の改善で扱う観点は、2〜4個を目安にする。
3. **星取り表を作る**: 行に既存のルール・仕組み（場所つき）、列に絞り込んだ観点を置き、記号と効き方を付ける。列ごとに ◎ の数と、そのうち強制・手順・常駐で効くものの数を数え、空いているところを書き出す。
4. **対応案を出す**: 修正・削除・追加の3つに分けて、対象、対応策、効く観点、影響範囲、リスクを並べる。削除しても効果が無いもの（すでに読まれていないもの）は、そう書いて外す。
5. **優先度を付けてリストアップする**: 改善度と、影響範囲・リスクから順位を付ける。追加は削除と対にする案を添える。
6. **実施項目を確定する**: ユーザーが、影響範囲とリスクを見て、どれを実施するかを決める。

## Decisions

- **既存の仕組みの改善は、修正・削除・追加の観点で対応案を出し、影響範囲とリスクから実施項目を確定する**（2026-10-15）
  - 根拠: ユーザーの依頼（「改善作業は、修正・削除・追加の観点で対応案を出す。その影響範囲とリスクから実施項目を確定させる」）。
  - 却下案: 未検討（ユーザーの依頼をそのまま採った）。
- **対応案の前に星取り表を作り、星取り表の前に観点を影響度と支配度でランキングして絞り込む**（2026-10-15）
  - 根拠: ユーザーの依頼（「事前に星取り表を作成する必要がある。星取り表は事前に影響度や支配度をランキング形式にする」「絞り込みでセッション・トークン当たりの改善度を高くする」）。
  - 却下案: 未検討（同上）。
- **対応案は、優先度を付けてリストアップする**（2026-10-15）
  - 根拠: ユーザーの依頼（「その上で優先度をつけて対応案をリストアップする」）。
  - 却下案: 未検討（同上）。

## Facts

実例: workbase のトークン消費を抑える改善（確認: 2026-10-08〜15、根拠: トークン節約の検討で作った3つの表。ランキング、星取り表、対応案の一覧）。

- 手順「観点を挙げてランキングする」: トークンを抑える観点を12個挙げ、効果の大きい順に並べた。上位は、①会話を短く切る、②ツール出力を絞る、③毎回読むものに字数の予算を置く、④状態をファイルに外部化する。④は①を安く行うための前提（支配度が高い）。
- 手順「絞り込む」: まず上位4点に絞り、星取り表のあと、さらに「切る」と「絞る」の2点に絞った（ユーザーの指定）。
- 手順「星取り表を作る」: workbase の既存のルール・仕組み22件を行にした。◎ の数は、切る 1、絞る 2、予算 6、外部化 5。◎ のうち強制・手順・常駐で効くものは、切る 0、絞る 2、予算 6、外部化 4。予算と外部化は厚く押さえられていて、切るの ◎ は知識のノート（[[session-handoff]]）だけだった。
- 手順「対応案を出す」: 切ると絞るについて、修正7件、削除3件、追加5件を出し、影響範囲を付けた。例:
  - 修正（中）: `wrap` の報告に「ここで切り、次は新しい会話で `start`」を1文足す。
  - 修正（大）: 雛形の workspace `AGENTS.md` の読む順番を、開始時に `decisions.md` を読まない形に直す（既存のワークスペースも手で直す）。
  - 削除（中）: `wrap` の停止中の自動採用の節（約1.6k字で、本体の約4割）を畳む。
  - 追加（中）: `wrap` で、次の会話への3行の依頼文を下書きとして出す。
  - 効果の無い削除: 凍結済みの `improvements.md` は読まれていないので、消してもトークンは減らない。
- 手順「優先度を付けてリストアップする」: 項目を増やさない小さな修正（スクリプトの出力を絞る、ノートの未決を決定に移す）を先頭に置いた。追加は削除と対にした（`wrap` の依頼文の下書き ↔ 自動採用の節を畳む、読み方の3行 ↔ 大きいノートの過去の節を畳む）。
- 手順「実施項目を確定する」: ユーザーが、修正は影響が小と中の6件、削除は3件すべて、追加は3件（`wrap` の依頼文の下書き、読み方の共通ルール、`review` の重い会話）を選んだ。追加の残り2件（切る目安の数値、ノートの字数の目安）は見送った。影響が大の修正（雛形の読む順番。既存のワークスペースを手で直す）は、修正前後の星取り表を比べた後に、追加で実施を選んだ（確認: 2026-10-15、根拠: ユーザーの発言）。
