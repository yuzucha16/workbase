# 作業ログとナレッジ化フックの共通機能（workflow-kit）

> **更新（2026-10-08）**: 転記の 6 状態・本文ハッシュ・台帳 `integrated.md`・`review` の B（転記の一括確定）・`check-docs.ps1` は、同日のうちに畳んだ。判断記録の項目を知識にしたときは、`→ <名前>` のリンクを 1 行足すだけにした（規則の正本は `workflow-kit/docs-rules.md` の「decisions.md の項目を知識にしたとき」）。下の該当する Principles / Decisions / Facts は、設計の経緯の履歴として残す。畳んだ理由は、第三者レビュー（L3・L5）の指摘と実測（台帳の仕組みで確定した件数 0、手作業の一括確定 42 件）。

## Purpose

作業ディレクトリごとに必要になる「`docs/`（作業ログと判断ログ）」と、「ナレッジ化して」（再利用できる知識を exmem の inbox へ渡すフック）を、特定のリポジトリの記述から切り出し、どの作業ディレクトリからも参照できる共通機能にする。置き場は `works` の `resources/workflow-kit/`（`resources/` は共有の `workbase`）。手順そのものの正本は kit のファイルで、ここには設計の根拠を残す。出力のブレ対策は [[ai-output-consistency]]。exmem と他リポジトリの関係は [[ai-development-workflow]]。

## Principles

- **ナレッジと作業ログを分ける。** ナレッジは育てて共有する知、作業ログは作業ディレクトリが持つ記録。寿命と読み手が違う。ナレッジは次の作業で再利用され、作業ログは日報・週報・仕様書などの文書の入力になる。
- **共通の仕組みは、コピーではなくパス参照で配る。** 改善が1か所に集まり、各ディレクトリのコピーが乖離しない。
- **各ディレクトリの `AGENTS.md` は薄く保ち、固有情報（目的、読む順番、固有ルール）だけを書く。** 共通部を直しても、全ディレクトリを直さずに済む。
- **共通機能への参照は、`@` ではなく平文のパスで書く。** `AGENTS.md` はどのエージェントも読むが、`@` の取り込みは Claude 専用。
- **共通機能は、使うたびに直す前提で作る。** 最初から完全を目指さず、小さく始める。使ってみないと、曖昧さや不足は見つからない。
- **改善の受け皿は、共通機能の中に1か所だけ持つ。** 各ディレクトリに散ると、同じ改善が重複し、乖離する。却下した提案も、理由つきで残す（蒸し返しを防げる）。
- **改善は、AIが提案し、人間が承認する。承認なしに共通機能を書き換えない。** 変更の影響が、参照する全ディレクトリに及ぶ。
- **改善の確認は、実行の直後に、観点を固定して行う**（曖昧だった点、欠けていた情報、使いにくかった点）。記憶が新しいうちのほうが気づけ、観点が揺れると提案の質も揺れる。提案は1回あたり最大3点、「場所 / 問題 / 案」の型で書く。
- **承認後の反映は、共通機能の1か所だけにする。** 呼び出し元には、コピーを作らず、1行の記録だけ残す。
- **共通機能が読めないときは、記憶で代用せず止まる。** 版の違う手順で動くと、出力が揺れる。
- **履歴から復元できるのは「何を・いつ」であり、「なぜ」は書かれている場合に限る。** 書かれていない理由は、推測で補わず「不明」と書く。推測が事実として記録に残ると、後で根拠として引用される。復元した記録には、復元元と範囲（どのコマンドの結果か、何が残っていないか）を明記する。

- **コミットの権限の委譲は、取り返しの可否で分ける。** ローカルで戻せる操作（コミット）は許可し、外向きで戻せない操作（push、GitHub 側のリポジトリ作成）は委譲せず、コマンドを案内する。[[claude-code-permissions]] の方針（取返し可は allow、不可は確認）と一致し、誤りの影響が閉じる。
- **コミットを許可するときは、範囲と事前の確認と禁止事項を、共通ルールに書く。** 範囲: 自分が変更・生成したファイルだけを、パス指定で追加する。確認: 意図したファイルだけか、`user.email` が仮値でないか、機密が混ざっていないか。禁止: `--amend`、`reset --hard`、`rebase`、`--force`、`--no-verify`、`git add -f`、push。機密や、確認していない既存ファイルを巻き込まないため。
- **自動で生成するフックは、既定値で動けるようにしつつ、報告に「使った条件」（既定値か指定か、変え方）を必ず書く。** 決め打ちで作ったことが、後から分かる。
- **手順書は、呼び出し元と参照先の関係を前提にして設計する。** 共通ルールを置いたリポジトリ（`workbase`）の中から呼び、その外の場所を対象にする。別の場所から呼ぶ設計にすると、入口（`AGENTS.md`）が無い場所が出る。
- **AI が実行する手順書は、一時ディレクトリで3回以上試験してから使う**（空の状態、既存の中身がある状態、中止すべき条件）。試験で、手順書に未定義の部品（remote なしのときの `pre-push` の中身）が見つかった。

## Decisions

### 導入フックにワークスペース（Vault のトップ）の生成を足し、「workflowを導入して」だけで、初回コミットまで行う（2026-10-05。版 2026-10-05.7 時点）

- 決めたこと: 既定値は、対象 `$HOME\works`（決定時は `C:\vault\notes`。2026-10-06 に `C:\vault\works` へ rename し、同日に `$HOME\works` へ移した）、業務用、remote なし、初回コミットする。報告に「条件」を出す。
- 根拠: 入口を1つにして、覚える言葉を増やさない。呼び出し元は `workbase` の中。
- 却下案: 別の言葉（「ワークスペースを作って」）を足す（入口が増える）。

### コミットの権限を、すべての作業ディレクトリで、エージェントに移す。push と GitHub 側の作成は委譲しない（2026-10-05）

- 根拠: コミットはローカルで戻せる。push は外向きで、既存のコミットとの衝突の判断も要る。GitHub 側の作成は、公開範囲を間違えると取り返しが難しい。
- 却下案: 委譲しない（従来）、push も委譲する（外向き。毎回の確認が要る）。

### ワークスペースの初回コミットは、フックが生成したファイルだけにする（2026-10-05）

- 根拠: `areas/` などの既存の中身に、業務の情報が含まれる可能性がある。
- 却下案: PARA の中身も含める（機密の混入に気づかないリスク）。

### 項目 5 の既定の対象を「Claude を開いたディレクトリ」にする案を取り消し、固定パスに戻す（2026-10-05）

- 根拠: 呼び出し元が `workbase` の中という前提を見落としていた。cwd 方式にすると、新しい PC のトップに `AGENTS.md` が無く、手順書に行き着けない。
- 却下案: cwd を対象にする（実装・試験・コミットした後に取り消した。`git revert` で戻し、理由を記録した）。

### 「ナレッジ化して」で inbox に作ったメモは、コミットしない（2026-10-05）

- 根拠: inbox のメモは、統合した後に削除する運用で、統合後は不要になる。
- 却下案: inbox のメモもコミットする（削除のコミットと対になり、履歴にメモの出入りが残る）。

### 「ナレッジ化して」に、範囲を限定された実行の扱いと、【汎用】【この件】のラベルを足す（2026-10-05）

- 決めたこと: 範囲を限定された実行は、その範囲だけを対象にし、曖昧なら1問確認し、次の実行は前回の範囲を除く。
- 根拠: 「前回の実行以降」だけでは、範囲を限定した前回より前の内容が漏れる。汎用と固有を1ファイルで分けるとき、作業ログに寄らない約束が要る。
- 却下案: 汎用と固有を別ファイルにする（統合先が同じ話題では、「分けた各ファイルの Principles と Decisions が3項目に満たない」規則と衝突しやすい）。

### 共通機能を `notes` の `resources/workflow-kit/` に置く（2026-10-04）

- 根拠: `resources/` は共有（Git 管理）で他のPCに届く。ナレッジ（`exmem`）と、仕組みの部品を分けられる。
- 却下案: `exmem` 内に置く（ナレッジと仕組みが混ざる）、各ディレクトリにコピーする（乖離する）。

### 参照は平文のパスを基本にし、Claude 用スキルは「kit を読むだけ」の薄いポインタにする方針（2026-10-04。スキルは未作成）

- 根拠: 手順の実体を1か所に置け、他のエージェントでも読める。
- 却下案: `@` の取り込みだけにする（Claude 以外で読めない）、手順をスキルに写す（kit と二重になる）。

### `docs/` は各作業ディレクトリ側に置き、`exmem` には作業ログを置かない（2026-10-04）

- 決めたこと: `contexts/` は「`notes`（現 `works`）から見えない場所の作業を引き継ぐコンテキスト」に位置づける。作業ディレクトリが無い作業を `contexts/` に記録する、という当初の案（AI が承認前に追加した）は取り消した。
- 根拠: `exmem` は知識・経験・ルールの置き場。`docs/` は将来、日報・仕様書・手順書などの文書の入力にするので、`exmem` には置けない。`contexts/` は、モバイルや他環境での壁打ちの内容を引き継ぐ受け皿として、別の役割がある。
- 却下案: 作業ディレクトリが無い作業の記録を `contexts/` に置く（`contexts/` の役割が引継ぎから作業ログへ広がる）、`contexts/` を全廃する（引継ぎの受け皿が無くなる）。

### `exmem` への書き込みは、`inbox/` の新規ファイルだけを維持する（2026-10-04）

- 根拠: `knowledge/` への統合時に、実物との照合とタグの正規化を行うため。
- 却下案: `knowledge/` へ直接書く（照合と正規化を飛ばす）。

### `notes/` を作業ディレクトリとし、`docs/` を `notes/docs/` に置く（2026-10-04）

- 決めたこと: `.obsidian/` は `notes/` の一部として扱い、専用の `docs/` は置かない。直前の「`.obsidian/docs/` に暫定で置く」を取り消した。
- 根拠: `.obsidian/` は小さく一過性のディレクトリで、専用の `docs/` を置くのは適正でない。作業ログを `exmem` に置かない方針は維持する（[[app-config-placement]]）。
- 却下案: `.obsidian/docs/` に置く、記録を `exmem/contexts/` に置く（作業ログを `exmem` に置かない方針に反する）。

### 導入手順を「workflowを導入して」の導入フックにする。試験導入先は `notes/`（2026-10-04）

- 根拠: 「ナレッジ化して」と同じ構成（手順・入力の型・自己点検・報告の型・改善フック）にそろえると、出力のブレを抑えられ、`docs/` 以外の追加機能にも対応しやすい。
- 却下案: 手順書だけにする（埋め方が揃わない）、導入スクリプトにする（固有ルールを埋められず、保守が増える）。

### `notes/docs/` はローカル専用のままにする（2026-10-04。ユーザーの承認）

- 根拠: 作業ログに、会社固有の情報が入る可能性がある。`notes` リポジトリが公開か非公開かは未確認（[[obsidian-vault]]）。`.gitignore` のホワイトリスト（`/*`）の既定でローカル専用になり、変更しなくてよい（2026-10-05 以降: `docs/` は、PC ローカルな Vault のトップのリポジトリで追跡し、共有の `workbase` には載らない。ホワイトリストは無くなった）。
- 却下案: `.gitignore` に `!/docs/` を足して共有する（会社固有の情報が共有側に出るリスク）。
- 影響: `docs/` は他のPCに届かない。日報などの入力にするのは、そのPCの中になる。導入フックは、`docs/` がローカル専用と分かったとき、共有するかをユーザーに質問する（既定はローカル専用）。

### メモに、作った時点の kit の版を残す（2026-10-04。ユーザーの承認）

- 決めたこと: kit の `README.md` に「版」（`YYYY-MM-DD.N`）を置き、inbox のメモの frontmatter に `kit: <版>` を書く。統合のとき `knowledge/` には写さない（`exmem/AGENTS.md` に任意項目として明記）。
- 根拠: 版ごとの出力を比べて、手順の改善が出力の揺れを減らしたかを確かめられる。
- 却下案: 版を残さない（どの版の手順で作ったメモか分からない）。

### ファイル形式の見出しは、該当が無くても省略せず「なし」と書く（2026-10-04）

- 根拠: 統合のときに、見出しの有無を迷わずに済む。
- 却下案: 該当が無い見出しを省略する（旧モバイル用プロンプトの方式）。

### 改善の受け皿は `improvements.md` 1つ。確認は「ナレッジ化して」の実行後の手順に組み込み、承認制にする（2026-10-04）

- 根拠: 1か所で、日付・発生元・提案・状態を1行ずつ並べて見られる。フックを使った直後が、不足に最も気づきやすい。共通機能の変更は、全ディレクトリの出力に影響する。
- 却下案: 各ディレクトリの `docs/log.md` にだけ残す（散る）、外部の課題管理ツール（小さく始める方針に合わない）、定期レビューだけにする（記憶が薄れる）、AI が提案と同時に直す（承認なしの変更で出力が揺れる）。

### 校正の3原則を、共通機能の README に常設する（2026-10-04。ユーザーの指示）

- 根拠: 以後、どのエージェントがどのディレクトリで使っても、同じ考えで改善が進む（原則の内容は [[ai-output-consistency]]）。
- 却下案: 会話の記憶に任せる（次の会話に引き継がれない）。

### 履歴からの復元では、根拠が履歴に残っている項目だけを Decisions にし、移管元の履歴も調べる（2026-10-04）

- 根拠: Decisions は根拠と却下案が必須という書式なので、推測を混ぜずに済む。対象のディレクトリが別のリポジトリから移ってきた場合、移管前の履歴は元のリポジトリにある。
- 却下案: 理由を推測で補って Decisions に書く（推測が根拠として残る）、現在のリポジトリの履歴だけを調べる（移管前の変更が分からない）。

### エージェントのコミットは、身元 `agent <agent@agent.local>` とトレーラー3行で区別する（2026-10-06。ユーザーの決定。kit 版 `2026-10-06.1`）

- 決めたこと: 身元は `git config` に書かず、コミット1回ごとの `-c user.name=agent -c user.email=agent@agent.local` で渡し、作者とコミッターの両方に使う。トレーラーは毎回3行: `Agent: <道具> <モデルID>`、`Workflow-Kit: <版>`、`Kit-Rev: <`resources/` の短縮ハッシュ>`（未コミットの変更・未追跡・ステージ済みがあれば末尾に `-dirty`。判定は `git status --porcelain` が空でないこと）。正本は kit の `docs-rules.md`。
- 根拠: remote なしのローカルでは `git log` が唯一の履歴で、誰の行動か・どの規則かを追えるようにする。人間の `git config` が仮値で初回コミットが止まったので、人間の設定に依存させない。`git config` に書くと人間の手動コミットまで agent 名義になる。作者名は道具に依存させず（Claude / Codex / Copilot が同じ規則）、道具とモデルはトレーラーへ。版は意味、ハッシュは再現性を担うので両方要る。
- 却下案: 人間の `git config` に頼る（仮値で止まる）、`.git/config` に agent を設定する（手動コミットも agent 名義）、作者 agent・コミッター人間（人間側が仮値のため見送り）、メールを `.invalid` にする（ユーザーが `.local` を選んだ）、トレーラーを1行に絞る（意味か再現性が失われる）、過去のコミットの作者を書き換える（履歴の改変）、エージェントが人間の `git config` を設定する（人間の設定を勝手に変える）。
- 付随: 導入フックの報告で、ユーザー自身の `git config`（`user.name` `user.email`）の設定を促す（無くても導入は止まらない）。

## Facts

- 復元の手順（2026-10-04、実際に実行）: 一覧は `git log --format='%h %ad %s' --date=short -- <パス>`、変更範囲は `git show --stat <ハッシュ> -- <パス>`、設定値の変化は `git show <ハッシュ> -- <ファイル>` の差分。差分から正確に分かるのは、ファイルの追加・削除と設定値の変化。多くのコミットメッセージは、変更内容だけで理由が書かれていない（11コミットで確認）。理由の手掛かりは、`.gitattributes` や CSS のコメント、既存ナレッジの Proposals など。
- 履歴を作り直した（単一コミットにした）リポジトリでは、それより前の履歴が残っていない（移管元で `git log --all -- <パス>` が初期コミットと移管コミットしか返さなかった）。
- 実物（2026-10-04）: `resources/workflow-kit/` に `AGENTS.md`、`README.md`、`docs-rules.md`、`knowledge-hook.md`、`setup-hook.md`、`improvements.md`、`examples/`、`templates/` がある（2026-10-06 に再確認: `tools/` に `check-inbox.ps1`、`find-knowledge.ps1`、`check-docs.ps1` が加わった。`docs-rules.md` に「decisions.md の項目の行き先」の節がある）。`notes/AGENTS.md` が共通ルールの参照先と読む時機を持ち、`notes/docs/` に `log.md` と `decisions.md` がある（`notes/docs/` はローカル専用）。`improvements.md` には採用済みの提案が大半で、「提案」の状態が3件ある（Claude 用スキル、`contexts/` を消化する手段、実際のメモでの校正。kit の版の記録は採用済み）。

## Gotchas

- **remote なしの方針で `pre-push` を置く手順を書いたが、試験するまで、中身が定義されていなかった**: 手順に雛形が無かった。`pre-push` を雛形にして、誤って remote を足した push が止まることを試験した。
- **見本に「生成物は9ファイル」と書いたが、実際は10ファイルだった**: ディレクトリ（`docs/`）を1つと数えたが、実際は2ファイルだった。試験の出力（`git show --stat`）から数え直して、見本を直した。
- **ファイル形式が2か所に書かれ、見出しの扱いが食い違った**: モバイル用プロンプトと dotfiles の手順で、見出しを省略するか「なし」と書くかが違った。共通機能を正本にし、モバイル用プロンプトを写しとして合わせた。変更の順番は「kit → モバイル用プロンプト（`exmem/inbox/README.md`）→ 見本」。
- **改善を呼び出し元の `AGENTS.md` に直接書き換える運用だと、他のディレクトリへ伝わらない**: 手順の実体が各ディレクトリの `AGENTS.md` の中にあったため。手順の実体を共通機能に集め、呼び出し元は薄い参照だけにした。
- **Claude Code の `Write` で既存ファイルの上書きが失敗した**: そのファイルを、その会話で先に読んでいなかったため。先に `Read` してから上書きする。
- **追跡の有無が切り替わったファイルの理由を履歴から探したが、コミットメッセージに一言（端末ごとのキャッシュ）しか無かった**: 理由は「不明」と明記し、Open Questions に残した。

- **PowerShell で `git log --format=%(trailers:...)` を引用符なしで書くと構文エラーになった**: `%(` が PowerShell の構文として解釈され、コマンド全体が実行されなかった。書式を変数に入れ、`"--format=$fmt"` で渡した。
- **PowerShell から `[IO.File]::ReadAllText("相対パス")` を呼ぶと、存在しないパスを指した**: .NET の相対パスは、PowerShell の現在位置ではなくプロセスの作業ディレクトリで解決される。`Join-Path` で絶対パスにする。
- **初回コミットが、人間の `git config user.email` の仮値（`example.com`）で止まった**: 確認項目が「仮値でないこと」だったため。確認を「身元が規則どおり」に差し替え、agent の身元を `-c` で渡した。

## メモの点検スクリプト（check-inbox / find-knowledge。2026-10-06 追記）

「ナレッジ化して」で AI が書く inbox のメモを機械的に点検する `workflow-kit/tools/check-inbox.ps1` と、既存知識を検索する `find-knowledge.ps1` の、設計の考え方と育て方。点検の項目と書式の正本は kit の `stock-hook.md` と、各スクリプトの冒頭。2026-10-15 に、この節の Decisions・Facts・Open Questions・Next Actions を畳んだ（kit の正本と重なるか、置き換わった記録のため。全文は畳む前のコミット `33e9fe3` の、このファイルにある）。

### Principles（点検）

- AI の出力の自己点検は、機械で確認できる項目（書式、数、形、禁止語）をスクリプトにし、意味の判断（重複、承認、根拠の真偽）は手で確認する。書式の揺れと見落としが減り、人と AI は意味の判断に集中できる。
- 書式は、正確な一致で縛り、スクリプトを緩めて揺れを許さない（例: 仮説は `（仮説）` の完全一致）。揺れを許すと機械判定が曖昧になる。
- FAIL は規則違反、WARN は目安や、後から正常になり得る不一致（作成後に版が上がるなど）に使い、終了コードは FAIL の数にする。WARN で止めると、正常な運用まで止まる。
- 許容リストを持つ検出は、境界の悪い例まで試験する。例示用ドメインの許容で、最初の版の `\b` が `example.com.evil.jp` を通した。
- 点検の誤検知は、メモを書き換えて避けず、スクリプトを直す。回避の書き換えは読みやすさを下げ、同じ誤検知が繰り返される。
- スクリプトは手順書（仕様）の写しなので、手順を変えたら、スクリプトも合わせるかを確認する。

### Gotchas（点検）

- **Gotchas の見出しの下に「なし」と補足を同じ行に書いたら、3行セットの検査が FAIL（状況0、原因0、解決0）になった**: 見出しの下が `なし` と完全一致のときだけ「該当なし」とみなされる。見出しの直後を「なし」だけにし、補足は別の見出しに書く（専用のメッセージは .12 で追加）。
- **Facts に `（仮説: …）` と書いたら FAIL になった**: `（仮説）` の完全一致を見る。補足は括弧の外の別の文にする。
- **ファイル名が6語、`sources` の末尾に日付を足したメモが FAIL になった**: 語数はハイフン区切りで2〜5語、`sources` は `<AI名> conversation "<テーマ>"` の定形だけ、と手順書から読み取れなかった。手順書に明記した。
- **メモ間の重複検出で、インラインコードを `` `([^`\n]{8,})` `` のように長さを指定した正規表現で取り出したら、候補が事前の測定より1件少なかった**: 8文字未満のコード片を飛ばすと、閉じのバッククォートが次の開きとして扱われ、対応がずれた。すべてのコード片を取り出してから長さで絞り、回帰試験と対照試験を足した。

## `docs/` の知識とルールを共有側へ運ぶ設計（decisions.md の行き先。2026-10-06 追記）

`docs/`（共有しない作業ログ）に溜まる、再利用できる知識とルールを、共有側（exmem と workflow-kit）へ取りこぼさず届ける仕組みの、設計の考え方。当時の6状態の仕組み（`行き先:` の状態、`check-docs.ps1`）は 2026-10-08 に畳まれ、「→ 知識名」のリンクの有無だけになった（[[accretion-without-pruning]]）。今の規則の正本は kit の `docs-rules.md` の「decisions.md の項目を知識にしたとき」。2026-10-15 に、この節の Decisions・Facts・Open Questions・Next Actions を畳んだ（kit の正本と重なるか、置き換わった記録のため。全文は畳む前のコミット `33e9fe3` の、このファイルにある）。

### Principles（行き先）

- データの流れは、「各データの行き先が一意に決まっているか」で設計する。どこにも行き場のない状態（滞留）を作らない。経路があっても、通らなかったデータは存在すら分からず、取りこぼしに気づけない。
- 共有できないソースから共有側へ移すときは、コピーでなく一般化（固有情報を剥がした再記述）にする。コピーは固有情報を共有側に出し、同じ内容の正本を複数に増やす。
- 運び終えたら、元の側には汎用の本文を残さず、見出し・日付・行き先だけにする。正本を1つに保てる。
- 経路に人の手作業が入るときは、1回に運ぶ量の上限と、運ぶ直前の確認（個人情報・機密・固有名の有無）を設計に入れる。手作業は量が増えると、確認が形だけになる。
- 「運び終えた」の判定は、見出しやキーワードの一致だけで済ませず、根拠と却下案が転記先に欠けなく写っているかまで見る。元の本文を外した後は、欠落を取り戻せない。
- 一般化が難しい項目は、破棄でも固有（残す）でもなく、「滞留」という別の状態で保留にし、理由を残して定期的に見直す。一般化しにくい項目に、価値が高いものが含まれることがある。

### Gotchas（行き先）

- **PowerShell で、行を入れる変数 `$l` と、行のリスト `$L` を使ったら、リストが1行の文字列に置き換わり、出力が1行になった**: PowerShell の変数名は大文字と小文字を区別しない。変数名を分け、書き出す前に出力行数の下限を確認するガード（例: 100行未満なら中止）を入れた。
- **`[System.Collections.Generic.List[string]]` を `::new()` なしで代入して `Add` が失敗し、そのまま書き出すと、ファイルが型名の文字列1行に置き換わった**: `[型名]` だけでは型を指すだけで、インスタンスにならない。`::new()` にし、書き出し前に変更前のファイルを git で復元できることを確認した（壊れたときは `git restore`）。
- **Gotchas の項目の頭にラベルと行き先を付けたら、「状況・原因・解決」の3行セットの形が崩れた**: ラベルと行き先は、入れ子の4行目（`  - 【汎用】行き先: …`）に置く。

## フック名の体系（2026-10-08 追記）

AI に作業の手順を呼び出させるフックの名前を、寿命（works、Project、セッション、随時）ごとの開始と終了の対にそろえた考え方。今の名前と呼び出し表の正本は kit の `hooks.md`、体系は kit の `README.md` の「フックの体系」。2026-10-15 に、この節の Decisions・Facts・Open Questions・Next Actions を畳んだ（kit の正本と重なるか、置き換わった記録のため。全文は畳む前のコミット `33e9fe3` の、このファイルにある）。

### Principles（フック名）

- フックは、寿命の階層ごとに、開始と終了の対にする。理由: 対称で覚えやすく、抜けている側（開始だけ、終了だけ）が表から見える。
- フックの対象は、作業手順と Project の寿命にし、ツールが作る会話（スレッド）にはしない。理由: 1スレッドに複数セッション、複数スレッドで1セッションがありうるので、スレッドの開始・終了とフックが対応しない。
- 呼び出しの言葉は、短い英語を主にし、日本語の言葉は別名として当面残す。理由: 日本語の言い回しは覚える負担が大きく、微妙に揺れる。
- 名前を変えるときは、旧名のファイルに案内だけを残し、新しい名前を使ってある程度の期間が過ぎてから、参照とともに一斉に削除する。理由: 旧名の参照が複数の作業ディレクトリに散らばっていて、一度には直せない。
- 紛らわしい語（`end` は「会話を終える」と取られやすい）は避ける。理由: 終了の対象が、会話か、作業手順の区切りかで、誤解が起きる。

## 権限移譲の線引き（2026-10-08 追記）

ユーザーの承認を前提にしていた手続き（フックの改善案の承認、push、転記マークの確定）を、エージェントへ移すときの考え方。転記の台帳・本文ハッシュは 2026-10-08 に、改善案の自動採用は 2026-10-15 に畳んだ（[[accretion-without-pruning]]、[[layered-third-party-review]]）。push の許可リストは有効で、正本は kit の `docs-rules.md` の「push」。2026-10-15 に、この節の Decisions・Facts・Open Questions・Next Actions を畳んだ（kit の正本と重なるか、置き換わった記録のため。全文は畳む前のコミット `33e9fe3` の、このファイルにある）。

### Principles（権限移譲）

- 承認の形骸化は、指標（採用率、修正数、補足数）で確かめてから、承認を外す部分だけを選ぶ（一律に外さない）。理由: 素通りの承認は情報量が無いが、安全に関わる規則は、素通りでも事故の被害が大きい。
- 規則の自動採用は、範囲を限定し（専用の節の中だけ）、可逆にし（1改善 = 1コミット）、見直しの期日と戻す条件を持たせる。理由: 提案者と評価者が同じ AI なので、評価が甘くなる。
- 規則の削除率は、単独の目標にしない。削除後の再発率と、規則の総量と組で見る。理由: 過剰追加と過剰削除の往復でも、削除率は上がる。
- 発動が稀な保険の規則は、頻度では削除しない。理由: 発動しないことが、不要の証拠にならない（生存者バイアス）。
- 非同期の確定（あとでまとめて確認する方式）では、日付でなく本文のハッシュで「変更が無いこと」を確認する。理由: 1ファイルに複数の項目があると、ファイルの更新日は無関係な編集でも進み、統合日はメモの作成日の代用にならない。
- 不可逆な操作（共有側の正本を残して、元の本文を外すこと）の前に、照合は、元と転記先が手元にある時点で、人の承認つきで行う。理由: 後でAIが「怪しくなければ外す」判断をすると、手間は減らず、判定の責任が人から AI に移るだけになる。
- 設計は、独立した別モデルにレビューさせる。理由: 影響分析で見逃した重大な穴（日付比較が機能しない、名前の再利用で誤って確定する）が、11件の指摘のうち4件、高の重大度で出た。

### Gotchas（権限移譲）

- **並行セッションが同じ `decisions.md` を未コミットで編集している間に、パスを指定して `git add` とコミットをしたら、他のセッションの項目が混ざった**: パスを指定しても、作業ツリーのファイル全体がステージされる。未 push なら `git reset --soft HEAD~1` で戻し、`git show HEAD:<path>` の内容に自分の変更だけを適用して、`git hash-object -w` と `git update-index --cacheinfo` で index に入れ、パスなしでコミットした（[[git-line-endings]] の Gotchas と同じ手法。PowerShell の引数の注意は [[windows-cli-pitfalls]]）。
- PowerShell での `git update-index --cacheinfo` の引数と、1組だけの配列の渡し方は [[windows-cli-pitfalls]] の Gotchas。

## フック手順書の章立て（2026-10-08 追記）

複数のフック手順書（`*-hook.md`）の章立てを、共通部と固有部に分けて揃えたときの考え方。今の章立ての規則の正本は kit の `hook-common.md`（点検は `tools/check-hook-outline.ps1`）。一般的な進め方は [[abstract-concrete-matrix-review]]。2026-10-15 に、この節の Decisions・Facts・Open Questions・Next Actions を畳んだ（kit の正本と重なるか、置き換わった記録のため。全文は畳む前のコミット `33e9fe3` の、このファイルにある）。

### Principles（章立て）

- 複数の手順書の章立てを揃えるときは、既存の章を並べ替えず、足りない章を挿入して揃える。理由: 「上の」「下の」など位置を指す参照が、並べ替えで壊れる。
- 揃える対象は、全体で共通の章（共通部）に絞り、共通部の存在と相対順序だけを一致させる。固有の章は置き場所を自由にする。理由: 固有の章まで厳密に揃えると、該当なしの章（「なし」）が増え、文書が肥える。
- 章立ての規則は、機械で点検できる形（存在と順序）にしておく。理由: 人の目では、フックが増えるたびに崩れやすい。

## 並行作業で溜まった Next Actions の消化（2026-10-16 追記）

複数のセッションや端末で並行して作業すると、Next Actions に「すでに終わった項目」が溜まる。その消化（`review 消化`）の分け方の考え方。手順の正本は kit の `review-hook.md` の「消化モード」。

### Principles（消化）

- 項目は、まず「実機・他PC・ユーザーの判断でしか確かめられないもの」と「いま書き換えられるもの」に分ける。理由: 前者は AI が確かめられないので、ユーザーに完了かどうかを聞くしかなく、後者は承認だけで終わる。混ぜると、確認の往復が増える。
- 完了の判断は、リポジトリの状態（コミット、実ファイル、決定の記録）を見て根拠を付けて挙げる。推測だけで完了にしない。理由: 並行作業の結果は、記録に残る一方で、記述が古くなっていることが多い。
- 「いま書き換えられるもの」は、承認を得たら、書き換え・履歴への追記・コミットまでを一度に行う。理由: 項目ごとに確認を挟むと、ユーザーの答えが「やる」の一言で済むのに往復だけが増える。
- ユーザーが決めた事実（公開で確定、見送りを撤回、完了とみなす）は、その場で判断の記録（decisions）にも書く。理由: 現在状態（log）だけを書き換えると、判断の根拠が残らない。

### Decisions（消化）

- **消化の手順を、3分類（完了の可能性・すぐ終わる・それ以外）の「それ以外」をさらに2つに分けた形にする**（2026-10-16）
  - 根拠: ユーザーが、この形で一直線に作業が終わったと評価し、手順に取り込むことを承認した。`review-hook.md` の「消化モード」に反映済み。
  - 却下案: 3分類のままにする（「それ以外」の中で、ユーザーに聞く項目と、いま書き換えられる項目が混ざり、確認の往復が増える）。

### Facts（消化）

- 実際に使った分け方は、完了している可能性のあるもの（コミットが別のハッシュで取り込まれていた、すでに追跡から外れていた、など）、すぐ終わるもの（記述の削除・書き換え・末尾の空行の修正）、それ以外（実機・他PC・判断待ち）の3つ。1回目の提示で、ユーザーの答えは各項目に「完了」「やる」で返ってきた（確認: 2026-10-16、根拠: この作業のやりとり）。
- rebase を使うと、ログに書いた未 push のコミットのハッシュは、現在の履歴に存在せず（`git branch -a --contains` が空）、一覧が古くなる（確認: 2026-10-16、根拠: `git merge-base --is-ancestor` が非0、同じ題のコミットが別のハッシュで存在）。
- 公開か非公開かのような「未定」の項目は、確定したら、その選択肢で併記していた記述（クイックスタートの片方、手順書の片方）の削除まで連鎖する（確認: 2026-10-16、根拠: README と手順書2本の差分）。

- **消化の結果「完了」と判断された項目の、現在状態からの削除と履歴への追記は、1コミットにまとめる**（2026-10-17）
  - 根拠: ユーザーが AI の提案を承認した。2026-10-16 の消化でも1コミットにまとめた。
  - 却下案: 項目ごとにコミットを分ける（承認の経緯: 却下案は未検討。提案をそのまま承認）。

### Next Actions（消化）

- 消化モードを使う別のリポジトリでも、「それ以外」の2分割が確認の往復を減らすかを確かめる（2026-10-16 時点）。

## 長い取り組みを閉じるときの移管と二重管理の解消（2026-10-19 追記）

複数日にわたる取り組みのノートを、閉じるときに、どこへ何を移し、何を消すかの型。取り組みの置き場を消す前に、知識が失われず、二重管理が残らないようにする。閉じる手順の正本は `topics/AGENTS.md` の「トピックを終わらせるとき」。

### Principles（移管）

- 閉じるときは、内容の種類ごとに行き先を決める。設計と理由は理解ガイド、決定は決定の記録、仕様は実装の隣、原則は lessons、経緯は git に任せる。理由: 種類で行き先が決まれば、移し忘れと二重管理を避けられる。
- 移し終えたノートは、元を削除する。理由: 正本が 2 か所にあると、片方が古くなり、読む人が誤る。
- 移す前に、消えるファイルを指す参照を grep で洗い、先に直す。理由: ノートの名前で参照するコードや文書が、削除でリンク切れになる。
- 閉じてよいかの確認は、取り組みの状態表だけを根拠にしない。上位の経緯の最新の記録とも突き合わせる。理由: 状態表の更新が漏れていることがあり、未達と誤判断する。（2026-10-19 に `topics/AGENTS.md` の手順 0 として採用。[[session-handoff]] にも同じ事例）
- 閉じる前に、残件を上位の Next Actions に移し、確認項目の漏れを各引き継ぎから拾う。理由: 削除すると、PC で確認するはずの項目が失われる。
- 実装前の設計を移すときは、実装されていない部分に「未実装」と注記する。理由: 設計として書いた内容が、実装済みと読まれないようにする。

- **マスク仕様を、実装の隣（`workflow-kit/room/mask-spec.md`）に置く**（2026-10-18）

  - 却下案: README に統合する（README が 11KB から 17KB ほどになる）。
- **移管が済んだ分は元を削除し、二重管理を減らす**（2026-10-18）
  - 根拠: ユーザーが「不要になったらこちらの分は削除でよい。二重管理を減らす」と述べた。
  - 却下案: 経緯のログ全体を root に統合する（39KB あり、経緯は git の履歴で足りる）。

### Facts（移管）

## AI が毎回聞く選択は、優先順位の規則にして全経路へ入れる（2026-10-21 追記）

部屋の AI が、スクリプトの言語のような同じ種類の選択を毎回ユーザーに聞く問題を、規則でどう止めるか。

### Principles（既定の規則）

- ユーザーの好みが安定している選択は、毎回聞かせず、優先順位つきの既定の規則にする。聞いてよい条件は、順で決められない事情があるときだけに限る。理由: 毎回の質問はユーザーの手間になり、答えはいつも同じになる。
- 規則を足すときは、AI がその場面で実際に読む経路をすべて洗い出して、同じ内容を入れる。理由: 経路のどれかが古いまま残ると、AI はその経路の文に従い、規則を足したのに挙動が変わらない。
- 優先順位は、移植性の高いものを先にし、環境固有のものは薄い層に限る（例: Python → ps1 → bat）。各段に「使ってよい条件」を書く。理由: 順位だけでは、AI が下位を安易に選ぶ。
- 規則で決めた選択は、報告に選んだ結果と理由を1行書かせる。理由: 聞かない代わりに、ユーザーが後から異議を言える。

### Decisions（既定の規則）

- **スクリプトの言語は、Python → ps1 → bat の順で AI が決め、聞かない**（2026-10-21）
  - 根拠: ユーザーの依頼（Windows 依存を減らしたい。room の AI が毎回「Python でよいか、ps1 がよいか」と聞いていた）。
  - 却下案: 従来のまま、ユーザーに毎回確認する（毎回同じ答えになるため）。

### Facts（既定の規則）

- 部屋の AI が読む規則の経路は、少なくとも4つあった: 手順書の本体（`dev-deliverable-guide.md`。2026-10-24 に実行の方針などを `script-guide.md` へ分けた）、部屋での読み替え（`room-context.md`）、部屋へ送る案内文を生成するコード（`room.py`）、手順書の索引（`README.md`）（確認: 2026-10-21、根拠: `実行の方針` を grep して全箇所を見た）。2026-10-21 に再確認すると、4か所とも「Python → ps1 → bat」の文が入っていた（確認: 2026-10-21、根拠: `workflow-kit/` を `Python → ps1` などで検索した）。
- 生成された案内文は、既存の部屋には次の `room start` まで届かない（仮説）。補足: 案内文は起動のたびに部屋へ送られる設計だと読んだが、実機で再送は見ていない。

### Gotchas（既定の規則）

- 状況: 手順書の本文だけを直すと、部屋の AI の挙動が変わらないおそれがあった
  - 原因: 部屋の AI は、生成コード内の案内文（起動時に部屋へ置かれる）も読む。手順書とは別の場所に、同じ趣旨の文があった
  - 解決: 規則に使うキーワード（`実行の方針` など）で kit 全体を grep し、見つかった経路すべてに追記した

### Open Questions（既定の規則）

- 経路が増えるたびに grep で探す運用でよいか。正本を1か所にして、他は指すだけにできないか（案内文は短くしたい事情がある）。

### Next Actions（既定の規則）

- 規則の追加時に使う、経路の洗い出しの手順を、`hook-common.md` に足すか判断する（`hook-common.md` には今、この手順は無い。2026-10-21 時点）。
