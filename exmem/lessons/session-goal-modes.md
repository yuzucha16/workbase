# セッションの進め方: ゴールを決める工程と達成する工程の分離（start のモードの根拠）

## Purpose

セッションの進め方を、A（ゴールを決める工程）と B（ゴールを達成する工程）に分け、やり方集の型と `start` の開始インタビューを結びつける。開始インタビューがうまく機能しない原因（ゴールが先か後かの不整合）を解く。
`workflow-kit/start-hook.md` の手順「モードを決める」の根拠にあたるノート。

## Principles

- ゴールを決める工程（A）と、達成する工程（B）を分けて考える。理由: 混ざると、ゴールが先に決まる前提の質問が、ゴールが後から決まる作業で外れる。
- A の出力（ゴール、完了条件）を B の入力にする。A から B に進む点を、ゴール確定のゲートとする。理由: 何が決まった時点で作業に入るかが見える。
- B の途中でゴールが変わったら、A に戻る。戻りは問題解決2（[[problem-solving-iterative-revision]]）の差し戻しとして数え、全体4回までにする。理由: ゴールの変更を予定された反復に入れると、手戻りにならない。
- 開始時に、確定型か探索型かを1問で決める。理由: 作業の進め方が成果物によって変わる。
  - 確定型: ゴールを先に決め、決め打ちで作り、その後に改善を回す。start のインタビューの項目を聞く。
  - 探索型: 仮ゴールで走る。仮ゴールと「ゴールを変える条件」だけを聞く。
- モードの目安は、成果物の合否を事前に書けるか。書けるもの（仕様、規格、数値）は確定型、出してみないと評価が決まらないもの（設計案、文書の骨子、運用の形）は探索型（確認: 2026-10-14、根拠: ユーザーの発言。実セッションでの使用結果は未測定）。理由: 合否を書けるかどうかが、ゴールを先に決められるかどうかを決める。
- A と B は、細かく交互に起きうる。分離は概念の整理として使い、運用はモードと「戻る条件」にとどめる。理由: 交互に起きる作業で、工程を厳密に区切ると、かえって進めにくい。

## Decisions

- **セッションの進め方を、A（ゴールを決める）と B（達成する）に分ける**（2026-10-14）
  - 根拠: ユーザーの発言（「ゴールを決める工程とゴールを達成する工程が混じっている。ここは分離した方が良さそう」）。
- **開始時に確定型か探索型かを決めるモードを導入し、`start-hook.md` に反映する**（2026-10-14）
  - 根拠: AI の提案に、ユーザーが「よいです」と返答した。`start-hook.md` への反映の差分は、ユーザーが承認した（引き継ぎ文書の記録）。ユーザーは「まずはやってみます」と述べた。
- **A/B とモードは、やり方集に入れず、`start` の根拠の独立したノートにする**（2026-10-14）
  - 根拠: ユーザーの指示（「A/B,モードはstartの根拠にしてください」）。
  - 却下案: やり方集（`problem-solving-*` `improvement-*`）に入れる（ユーザーが start の根拠を選んだ）。

## Facts

- A の型は、問題解決のやり方1・2（[[problem-solving-analogy]]、[[problem-solving-iterative-revision]]）と、改善のやり方1（[[improvement-quantified-options]]）。B の型は、start の「作業の種類の差分」（開発、文書作成、調査）にあたる。欠けているのは、A から B へのゲートと、B から A へ戻る決まり（確認: 2026-10-14、根拠: start-hook.md を読んだ結果。対応はユーザーが分離を承認した）。
- 開始インタビューがうまくいかなかった場面は、進め方と実作業の順番だった。ゴールが作業中に変わる場面が多く、手戻りが起きた（確認: 2026-10-14、根拠: ユーザーの発言）。
- ユーザーは、走りながらゴールを決めることもあれば、先に決め打ってから改善を回すこともある。成果物による（確認: 2026-10-14、根拠: ユーザーの発言）。
- 変更前の start のインタビューは、ゴールを最初に確定する前提で、共通の項目（ゴール、前提・制約、対象と資料、触ってよい範囲、やらないこと、完了の判断）を聞いていた（確認: 2026-10-14、根拠: workflow-kit/start-hook.md）。

## Gotchas

- 状況: 開始インタビューでゴールを聞いたが、作業中にゴールが変わり、手戻りになった
  - 原因: ゴールが後から決まる作業で、ゴールを先に確定する前提の質問をした
  - 解決: 探索型を設け、仮ゴールで始めてゴールの変更を反復に数える（案。未検証）

## Open Questions

- モードの目安と型の判定方式は、ユーザーが「合っている」と確認した（2026-10-14）。ただし実セッションで使った結果は未測定。次回の `review` で、モードの使われ方を点検する。
- 開始の形の比較（`bare` `briefed`）に、型を指定して始める `typed` を足すか。足す場合の見方は、実測のあとに決める（再伝達 `again` と漏れ `gap` の件数は、2026-10-15 に廃止した）。
- 仮ゴールの変更を `events` に `kind=goal_change` で記録する手順は、`start-hook.md` に足した。作業側（このリポジトリの外）の `AGENTS.md` の `kind` の定義への追記は、まだ。
