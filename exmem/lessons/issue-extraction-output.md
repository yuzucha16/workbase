# 論点出しの出力の型

状態: 試用中（2 案件で試した。実作業での手戻りの減り方は未確認）。版は v4（試用後の直し、「確」「聞」、順序欄、フィードバックの手順、論点の表の「セットで決める ID」を足した）。

作業の依頼とレビューを 1 セッションでやると、決める点が作業の中で後出しになり、手戻りが起きる。作業の前に論点だけを出させ、判断（決・任・後・確・聞）を付けて決定メモにし、作業セッションへ渡す。
**使い方**: 下の「貼り付け用プロンプト」の四つのバッククォートで囲まれた部分を、新しいセッションに貼る。「フィードバック」と言えば、改善の 1 行が出る。

作業の依頼の前に、Claude に「論点だけ」を洗い出させるためのプロンプト。作業はさせない。ユーザーが懸念をうまく言葉にできなくても、書いていないことの中から論点を拾わせるのが狙い。最初の試用はエクセル集計表の案件。

## 使い方（3 段）

流れ: 論点出し → 判断を付ける → （確・聞があれば）別セッションで確かめる・人に聞く → 結果を決定メモへ戻す → 実作業。確かめることと作ることを同じセッションにしない（手戻りを防ぐため）。

1. 下の「貼り付け用プロンプト」をコピーし、【】を埋めて新しいセッションに貼る。分からない欄は空のままでよい（空欄も論点として拾わせる）。
2. 論点の表が返る。各 ID に「決 B」「任」「後」「確」「聞」を付けて返す。例: `1 決 B / 2 任 / 3 後 / 4 確 / 5 聞`。「確」「聞」があれば、決定メモに確かめ方・質問文が付いて返る。全部に付けなくてよい（無印は「任」扱い）。
3. 決定メモが返る。それを作業セッションの最初に貼る。

判断の意味:

- **決**: 今ここで ユーザーが決める。選択肢の記号か、自分の言葉で書く。
- **任**: 作業する AI に決めさせる。ただし、何に決めたかを作業の報告に書かせる。
- **後**: 今は決めない。作業は推奨案で仮置きして進め、メモに「仮」と見直す時期を残す。
- **確**: 事実を確かめてから決める（技術課題。例: 「リンクをマクロが開けるか」）。作業とは別の短いセッションで、答えを1つ出すためだけに確かめる。作らない。
- **聞**: 人に聞いてから決める（組織課題。例: 決める人、指揮系統）。Claude が送れる質問文の下書きを作る。

「確」と「聞」が0個なら、決定メモをそのまま作業セッションに貼って実作業へ進む（課題設定の工程は飛ばす）。

## 私の入力（分からない欄は空のままでよい）
- やりたいこと（1文）: 【】

## やってほしいこと
1. 入力を読み、次の観点で抜けを点検する。論点がない観点は飛ばしてよい。
   - 目的: 何のための物か。出来たと言える状態は何か
   - 使い手と場面: 誰が、何を見て、何を判断するのに使うか
   - 入力: 元データの出どころ、形、量、更新のされ方、汚れ（欠け、表記ゆれ、重複）
   - 出力: 形、粒度、見せ方、他の人や他の道具へ渡すか
   - ルール: 計算・分類の定義、例外の扱い、境界の値
   - 運用: 誰が更新・保守するか、頻度、引き継ぎ
   - 検証: 正しいことを、何で・誰が確かめるか
   - 制約とリスク: 環境、機密、期限、間違っていたときの影響
   - 変化: 後から変わりそうなもの（項目の追加、量の増加、使い手の追加）
   - 言葉: 私の入力にある曖昧な言葉（例: 「不整合」「ミス」）が、人や場面で別の意味にならないか。定義を問う論点にする
2. 論点を下の「出力の型」で表にする。論点は問いの形で書く。
3. 私への質問は表の外に出さない。入力の欠けも、選択肢で答えられる論点として表に入れる。

## 守ること
- 表に載せる論点は 12 個まで。重み「高」を先に並べる（高は 7 個まで）。他の論点の前提になる論点は、重みを一段上げる。それ以外は「その他」に名前だけ並べる。
- 各論点に、決めないまま進めると後で何が起きるかを 1 文で書く。
- 選択肢は 2〜3 個。推奨を 1 つ ★ で示すが、推奨は決定ではない。根拠が私の入力なら〔入力〕、推測なら〔推測〕と付ける。
- 私の入力に書いてある前提を疑ってよい。ただし、私の意図を推測で決めつけず、論点として出す。
- 解決策の詳細や作業の手順は書かない。

## 出力の型
### A. 入力の読み（3 行まで）
私が作りたい物を、あなたがどう読んだか。読みが割れるなら、それも論点にする。

### B. 論点の表
「セットで決める ID」は、答えが他の論点の答えを縛る論点の ID（例: 検出の範囲とキー）。無ければ「－」。判断を返す前に、片方を決めるともう片方が決まる組が分かるようにする。
| ID | 重み | 種類 | 論点（問い） | セットで決める ID | 決めないと後で困ること | 選択肢（推奨に★、根拠のタグ） |
種類は次のどれか。
- 決める: 方針の選択
- 前提: 抜けやすい前提の確認（当然だと思って書かれていないこと）
- 先の困りごと: 今は問題にならないが、後で効いてくること

### C. その他（名前だけ、1 行ずつ）

### D. 判断の返し方
最後に次の 1 行だけ添える。
「各 ID に 決〈選択肢か自由記述〉 / 任 / 後 / 確 / 聞 を付けて返してください。無印は任として扱います。」
確・聞にできる論点（事実か、人の返事で決まるもの）には、種類の欄に〔確かめられる〕〔聞ける〕の印を付けておく。

## 私が判断を返したら
作業はまだせず、次の「決定メモ」を作る。メモは、別の作業セッションの最初に貼って使う。
- 決: 決めたことに書く。
- 任: 任せたことに書く（作業する AI が決め、決めた内容を作業の報告に書く）。
- 後: 後回しに書く（推奨案で仮置きするか、触れずに進めるか。見直す時期）。
- 判断から読み取れる矛盾（決めたこと同士の食い違いを含む）や、新しく生じた論点があれば、メモの前に 3 個まで挙げる。
- 新しく生じた論点には枝番（2a、4a）を付け、元の ID の判断に従って「決／任／後」のどれかを仮に付けて載せる（私が直せるように、仮と明記する）。
- 確は「確かめること」に、聞は「聞くこと」に書く。確は、確かめる事柄・一番小さい確かめ方（使い捨てで、成果物を作らない）・結果でどの ID が決まるか・合否の見分け方を書く。聞は、誰に何を聞くか・そのまま送れる質問文の下書き・返事でどの ID が決まるかを書く。
- 確・聞の結果は、私が決定メモの「決めたこと」へ戻す。戻すまで、その ID に依存する作業は始めない（メモの「未確認」に載せる）。
- 担当や値が決まっていないもの（例: 確かめる人）は、本文に「要確認」と埋め込まず、メモの「未定」に分けて書く。

# 決定メモ: 〈やりたいこと〉
- 目的: （1 文）
- 出来たと言える状態:
  - G1: （確かめられる 1 文）
## 決めたこと
- 〈論点の ID と名前〉: 決定。理由（あれば短く）
## 任せたこと
- 〈論点の ID と名前〉: 作業する AI が決めてよい。決めた内容は作業の報告に書くこと
## 後回し
- 〈論点の ID と名前〉: 仮の置き方 ／ 見直す時期
## 先に確かめること（確）
- 〈ID と名前〉: 確かめる事柄 ／ 一番小さい確かめ方 ／ 結果で決まる ID ／ 合否の見分け方
## 確・聞の順序
- 依存（どれの結果がどれの前提か）と、並行できるもの。一番長く待つ鎖（クリティカルパス）と、詰まりやすい 1 件（ボトルネック）を、1 行ずつ示す。
## 先に聞くこと（聞）
- 〈ID と名前〉: 誰に ／ 質問文の下書き ／ 返事で決まる ID
## 未確認（結果が戻るまで着手しない）
- 〈確・聞の ID〉に依存する作業: 〈内容〉
## 確かめ方（成果物の確認）
- G1: 何で・誰が確かめるか
## 未定
- 〈担当や値が決まっていないもの〉: 誰が決めるか

## 設計の判断（素案。試用で直す）

- **入力は 6 欄、すべて任意**。ユーザー に書かせる量を最小にし、欠けは Claude が論点として拾う。言葉にしにくい不安は「なんとなく」で書ける欄を 1 つだけ置いた。
- **質問は表に吸収**。Claude からの自由記述の質問をなくし、選択肢つきの論点として出させる。ユーザーの返答は「決／任／後」の記号で済む。
- **12 個の上限**。多すぎると判断が重くなるため。数は根拠のない暫定で、試用で直す。
- **既存の型との関係**:
  - 相談の型（`exmem/lessons/consultation-pattern.md`）は、論点を会話で潰して仮決めまで進む。こちらは論点に判断を付けたところで止め、作業セッションへ渡す。相談の型の前段として使える。
  - 決定メモの「目的・出来たと言える状態（ID つき）・確かめ方」は、基準文書の Must（目的と満たすべきこと、検証項目）に寄せた。
  - 6R ブランクは欄が多く重いので取り込んでいない。大きい案件では、論点出しの後に 6R を使う順が考えられる。

## 試用で見ること

1. ユーザーが書いていない論点が出たか（出た数と、そのうち「確かに要る」と思えた数）。
2. 判断を付ける負担（かかった時間、「任」と「後」に逃げた数）。
3. 作業セッションで、論点出しで拾えなかった手戻りがあったか（あれば、どの観点で拾えたはずかを記録して観点を直す）。
- 2026-11-02 金額を計算するマクロ（確を3つ意図的に付けた）で ユーザーが試用。良かった点は、論点に順序が付いたこと。確・聞の依存が見えて、ボトルネックとクリティカルパスが間接的に分かり、作業順にもなった（ユーザーの報告）。
- 直したところ（v3）: 順序が偶然に出た面があるので、決定メモに「確・聞の順序」欄（依存、並行できるもの、クリティカルパス、ボトルネック）を足して安定させた。
- 気づき（未対応）: 「後」にした ID12（別の PC で動くか）を、AI が「SharePoint 直読みに効くので先に確かめる案」として矛盾に挙げた。後の判断を、依存から見直す点検は有効だった。1 件の「確」の本文が長い（確かめる事柄・方法・決まる ID・合否が 1 つの段落）。項目ごとの改行にすると読みやすい。
- 2026-11-02 反映（v4）: 論点出しのセッションから、依存が論点の表に出ず、判断を返した後に矛盾が出たとの指摘があった。「セットで決める ID」の欄と、「前提になる論点は重みを上げる」を足した（`topics/kit-growth/inbox.md` の行は選別済みへ移した）。
