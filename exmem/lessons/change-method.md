# 変更のやり方1: 基準文書を拠りどころに、基点つきで最小の変更を入れる

## Purpose

既存の成果物に、決めたやり方で変更を入れるときの型。解決（[[problem-solving-analogy]]）と改善（[[improvement-quantified-options]]）が「何をどう変えるか」を決めるやり方なのに対し、これは決まった変更を安全に入れるやり方。要点の表は `workflow-kit/methods.md` の「変更」。出どころは、`init 更新`（雛形の反映モード）が一撃で通った事例の振り返り。1事例からの仮説で、使いながら Must を増減する。

## Principles

- 2つのブロックに分ける。ブロックA（仕込み）は、変更できる状態にしておくこと（基準文書）。ブロックB（変更）は、変更のたびのプロセス。理由: 一撃で通った要因の大半は、変更の前に揃っていた前提だった。
- 前提チェックでブロックAの有無を見る。揃っていればBに直接進み、無ければ先にAを補う（新規は自作、既存は抽出）。
- 厳格に定義しすぎない。Must（欠けたら直す）と Want（あれば良い）に分けて小さく始め、`review` で見直す（ユーザーの条件、2026-10-16）。
- 基準文書は、成果物と分けた、AI が読めるテキストの明文化。変更の設計と検証の物差しで、人と AI の工程の境界になる（ユーザーの仮説、2026-10-16: 人と AI は工程を分割し、それぞれ得意な側を担う。その境界が基準文書）。作業の途中でできる下書き・使い捨てのスクリプト（`ai/work/` の「中間成果物」）とは別物で、語を分けた。業務の成果物（AI が中身を見られない）では、変更の設計と検証を基準文書の上で行う。
- 基準文書の冒頭に**正の向き**を宣言する。新規と繰り返す成果物は基準文書が正（成果物は生成物。[[office-ai-workspace]] の決定）、既存から抽出した写しは成果物が正（基点で古さを見る）。理由: 他環境の型は「ソースが正」で、向きが逆になるため。

## Decisions

- **Must は、基準文書が3つ、変更が6つ**（2026-10-16、ユーザーの承認）
  - 基準文書: 正の向き・基点、目的と満たすべきこと（ID つき、1 ID = 検証できる1文）、検証項目（誰が・どこで確認するか）。Want: 構造と依存、規則、不変条件。
  - 変更: 前提チェック、影響範囲の列挙、基点の確定、最小実装、検証、記録。Want: 案の比較と選択（案が2つ以上のときだけ）、点検（指す先まで）、利用側への反映、小さな変更の縮め方。
  - 根拠: ガッチリ定義すると身動きが取れなくなる（ユーザー）。却下案: 全項目を Must にする。
  - 見直しの条件: 3回の `review` の後（`hook-matrix.md` の「review の点検」7）。案の比較は、`init 更新` が通った要因の一つだが、小さな変更では1案で足りるため Want にした。
- **3文書（要求仕様・機能仕様・運用マニュアル）は、基準文書の出どころとして使う**（2026-10-16、ユーザーの承認）
  - 対応: 要求仕様 → 目的と満たすべきこと・検証項目、機能仕様 → 構造と依存・規則、運用マニュアルの変更依頼ひな形 → 不変条件・検証項目、変更の入力。3文書そのものは [[ai-tool-deliverable-structure]] に残す。
  - 取り込まないもの: 自動テスト、VBA 固有（[[excel-vba-ai-development]]）、図・用語表・版の厳格な管理。
- **`areas/` `projects/` での適用**（2026-10-16、ユーザーの承認。語は「基準文書」に決定）
  - 置き場: 成果物と同じフォルダ（`ai/out/<成果物名>/`）。`dev` の Project は `docs/` の3文書が基準文書を兼ねる。部屋を使わない Project は Project 直下の `<成果物名>/`。
  - 機密: マスク後の語か一般化した形だけで書く（対応表の番号は版をまたいで安定する）。抽出の基点は `ai/in/` の manifest に記録された原本のハッシュ。人が照合した結果も、マスク後の語で書く。実名を見て直す内容は `_noai/` に置き、AI に渡さない。
  - Project をまたぐ渡し方: 前の Project の基準文書を、人が次の Project の `ai/in/` に置き、`room start --adopt` で入力として記録する（`room` の変更なし）。Area の README の一覧に、成果物ごとの最新の Project を1行書く。
  - 却下・先送り: 雛形ファイルは置かない（Must が3項目で短く、試験運用中。最初の業務の利用後に決める）。`restore` が基準文書の写しを `_noai/final/` にも作る点、`ai/out/` の語の検査は、`room` の変更になるので先送り。

## Facts

- `init 更新` が一撃で通った要因（見立て。事後の解釈、2026-10-16）: 追加先と手順の型が既にあった／正本が1か所で写しを作らない／既存原則（上書きしない・差分案・承認）の具体化だった／先に案を比べて選んでから実装した／実在する旧版と新版の雛形で検証できた／制約が文書になっていた。
- 反例: 検証の対象を「雛形のファイル」に限り、雛形が指す先（README）まで見なかったため、抜けが後から出た。点検は指す先まで含める（Want の「点検」）。
- 変更依頼のひな形の6項目（他環境の運用マニュアル。未再現）: 変更の種類、したいこと、期待する動作、現在の動作、変えてはいけないこと、確認方法の希望。

## Open Questions

- 先送りの観点: 変更の伝播（利用側への反映をいつ Must にするか）、小さな変更の縮め方、廃止（畳む・消す）に同じ型を使うか。
- 新規作成のためのフックかモード（ブロックAを新規作成の型にする）。
- 基準文書を置く場所が、最初の業務の利用で合うか（Area に置く案は、繰り返す成果物が3つ以上になったら検討）。
- Must の増減（3回の `review` の後に決める）。
