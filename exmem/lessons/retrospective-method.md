# 振り返りのやり方1: 済んだ進め方・成果物を、評価軸を先に決めて、良い点と悪い点の両面で評価する

## Purpose

済んだ**業務の進め方・成果物**を、良い点と悪い点の両方から評価し、再現と補正の施策にするときの型。呼び出しは `start 改善`（`methods.md` の「改善」の改善4）。呼び名は「振り返って」。`wrap`（その日の終了）や `review`（週1の kit の見直し）とは別物。重なる部分（撤回の回数を数える）は、`wrap` や `review` が入力に使える。要点の表は `workflow-kit/methods.md` の「改善」。

出どころは、2026-10-17 の「ee の思考の癖の分析」（[[user-thinking-habits]]）。スレッド18本から、癖・悪影響・補正策を出した手順を型にした。ただし対象を**個人でなく進め方・成果物**にし、悪い点に寄った分析の偏りを防ぐため、**良い点も出し、評価軸を先に決める**（ee の指定）。**1事例（と、その後の3回の品質チェック）からの仮説**で、使いながら Must を増減する。記録は [[retrospective-method-record]]。作り方は [[method-creation]]。

## Principles

- 要点は**範囲の宣言と、両面**。何を見て何を見ていないかを先に宣言し、同じ評価軸で良い点と悪い点を並べる。
- 自己申告は当てにならない。悪い点は、AI が一次記録から数える（品質チェック3回目: 手戻り14件に対し、遠回りの自己申告は なし4・少し1・未回答1）。
- 軸は材料を見る前に決める。後から決めると、目立った出来事に軸が引きずられる。
- 人の注意不足で終わらせず、悪い点は仕組みの欠け（どの手順・文書・分担か）に帰す。
- 厳格に定義しすぎない。Must と Want に分けて小さく始め、`review` で見直す。

## Decisions

- **区分は「改善」、呼び出しは `start 改善`**（2026-10-17、ee の決定）。理由: 区分と `start` のモードを揃える（人間が覚えきれなくなるため）。新しい区分も新しい `start` のモードも作らず、`start-hook.md` は増やさない。
- **良い点・悪い点は各最大3個**（ee の仮の値、2026-10-17）。評価軸は3〜5個（AI の案）。品質チェックでは、軸の選び方が回でぶれた。
- **品質チェックの題材は A（workbase の 10-06〜10-17）**。業務の対象（題材 B）は未実行。
- **Must は、仕込みが4、プロセスが7**（AI の案を、ee が3回の品質チェックの後に承認して main に反映）。

## ブロック A: 事前の仕込み

### Must（4）

1. **対象と期間の宣言。** 進め方（手順、分担、手戻り）か、成果物（出来、版、レビュー指摘）か、両方か。期間または件数。**期間を決めたら、材料の最古の日付（`git log --reverse` など）を先に確かめ、記録の無い期間は「見えない範囲」に書く。** 時刻は UTC に揃えて順序を扱う（別環境の記録が混ざるため）。
2. **材料の範囲と、見えない範囲。** 読む一次記録（`docs/log` と `decisions`、コミット、成果物の版、レビューや差し戻しの記録、発言の原文）を列挙し、見られないもの（別の PC、別のスレッド、口頭）を明記する。
3. **用途と読者。** 結果を何に使うか（次の進め方の改善、手順書への反映、成果物の再現）と、誰が読むか（既定は依頼した本人）。用途で、深さと置き場が変わる。

4. **評価軸の設計。** 材料を見る前に、軸を3〜5個選び、各軸の「良いの条件」「悪いの条件」を同じ粒度で書く（「評価軸の設計」）。

### Want

- 軸の候補は 「評価軸の設計」に既定を置く。業務の対象では、依頼に合わせて差し替える。
- 前回の振り返りがあれば、その施策が効いたかを最初に確かめる。
- 業務の対象では、置き場と機密の扱い（「業務の対象のときの扱い」）を先に決める。
- 件数の数え方（何を1件とするか）と、母数。

## ブロック B: 振り返りのプロセス

### Must（7）

1. **事実を一次記録から集める。** 件数と引用（日付、場所）つき。「うまくいった」「悪かった」の印象は、事実の後に書く。
2. **悪い点は AI が材料から数える。** 手戻り、撤回した決定、差し戻し、再依頼、中断。自己申告だけにしない。理由: 自己申告の遠回りは毎回「なし」だった（[[user-thinking-habits]] の癖5）。
3. **良い点を、要因まで掘る。** 「何が効いたか」を、次も再現できる形（前提、型、順序）で書く。理由: 成功は要因が分かって初めて型になる（[[change-method]]、[[research-method]] の出どころ）。
4. **悪い点は、原因を仕組みに帰す。** 人の注意不足で終わらせず、「どの手順・文書・分担に欠けがあったか」まで書く。影響（誰に・どれだけ）を添える。
5. **両面を同じ評価軸で並べる。** 軸ごとに、良い点・悪い点・根拠を1行ずつ。片方が無い軸は、「探したが無かった」と書く（無いことの確認）。報告する良い点・悪い点は各最大3個（影響の大きい順。仮の値）。
6. **事実・解釈・推測を分け、限界を書く。** 母数、見えない範囲、解釈の弱い箇所。元の分析の「この分析の限界」を型にする。
7. **次の行動に落として記録する。** 良い点は再現の施策（型にする、手順書に入れる）、悪い点は補正の施策（どの手順書・誰が・いつ見直すか）。承認待ちと明記し、承認後に反映する。施策が大きければ、改善のやり方（[[improvement-coverage-matrix]] など）へ渡す。

### Want

- 施策の優先度（影響度と支配度。改善のやり方3）。
- 前回の施策の効果の確認（実測と自己採点を区別する）。
- 悪い点の裏返し（その悪い点が、別の場面では良い点だった例）を1つ探す。
- 振り返り自体の手戻りを記録し、次回に回す。

## 出力の章立てのひな形（章は固定。調査1・調査2に倣う）

倣った点: 調査1は「章ごとに含めるものを添える」、調査2は「章を固定し、各手順を同じ型にする」。振り返りでは、**章を固定し、評価軸ごとの節を同じ型（良い・悪い・根拠・施策）にする**。省く・足すのは仕込みで決め、省いたら理由を章 9 に書く。

個数の上限（ee の仮の値、2026-10-17）: **良い点は最大3個、悪い点も最大3個**（影響の大きい順に選ぶ）。選ばなかったものは章 3 の事実の一覧に残し、章 9 に「選ばなかった件数」を書く。仮の値なので、品質チェックで増減を見る。

| 章 | 見出し | 含めるもの |
|---|---|---|
| 冒頭 | 版の行 | 作成日、対象、期間、読者、用途、状態（叩き台 / 承認済み） |
| 0 | サマリ | 読み手が最初に見る章（調査1の「3行で表すと」に相当）。(a) 3行: 良い点の核、悪い点の核、最優先の施策。両面を各1行以上。(b) 良い点3個・悪い点3個の見出しだけの対の表（軸、一言、章 5.n / 6.n への参照）。(c) 施策の件数と、承認が要るもの。(d) 範囲と限界の一言（見えない範囲、母数）。全体で画面1枚に収める（(a)(c)(d) の文の合計が400字以内。表を除く）。本文の結論だけを書き、本文に無いことは書かない |
| 1 | 範囲の宣言 | 対象（進め方 / 成果物 / 両方）、期間・件数、読んだ一次記録の表（記録、件数、取得日）、**見えない範囲**（別 PC、別スレッド、口頭） |
| 2 | 評価軸の設計 | 下の「評価軸の設計」を表で。軸ごとに 名前 / 何を見るか / 良いの条件 / 悪いの条件 / 数え方 / 選んだ理由。軸は3〜5個、省いた候補とその理由 |
| 3 | 事実の一覧 | 軸ごとの、日付・出来事・出典の表。数え方の定義（何を1件とするか）、母数。手戻り・撤回・差し戻し・再依頼・中断の件数は AI が材料から数える（自己申告で代えない） |
| 4 | 軸×両面の比較表 | 行=評価軸、列=良い点 / 悪い点 / 根拠（出典）の1枚。全軸を両面探索し、片方が無い軸は「探したが無かった」。最後の列に、章 5・6 で選んだ点の印 |
| 5 | 良い点（最大3個） | 各節 `5.n` を同じ型で: 軸 → 何が良かったか → **要因**（前提・型・順序）→ 再現条件 → 出典。要因不明は「要因不明」 |
| 6 | 悪い点（最大3個） | 各節 `6.n` を同じ型で: 軸 → 何が起きたか → 件数 → **仕組みの欠け**（どの手順・文書・分担か）→ 影響（誰に・どれだけ）→ 出典。人の注意不足で終えない |
| 7 | 事実・解釈・推測の区別 | 解釈の弱い箇所、推測【推測】とその根拠、1事例からの飛躍。母数の小ささ |
| 8 | 施策（承認待ち） | 表: # / 種別（再現 / 補正）/ 内容 / 反映先 / 優先度（影響度×支配度）/ 状態（承認待ち）。大きいものは「改善へ渡す」。前回の施策があれば、効いたかを先頭に（実測と自己採点を区別） |
| 9 | 確認できていない点・限界 | 見えない範囲の影響、省いた軸と理由、選ばなかった良い点・悪い点の件数、軸の偏りの有無、既定として置いたもの |
| 10 | 出典 | 一次記録（コミット、`docs/`、成果物の版、レビュー記録）と二次（要約、他者の評価）を分けた表 |
| 末尾 | 遠回り・次の一手 | この振り返り自体の手戻り（次回に回す）。次の振り返りの時期 |

### 数え方と選び方の定義（迷いを減らす。品質チェック1回目で足した）

- **事実の「1件」**: 一次記録の1つの出来事（1コミット、1つの記録項、1つの訂正）。軸ごとの数え方は章 2 に書き、迷ったら小さい単位で数える。
- **良い点・悪い点の「1個」**: 同じ要因（良）または同じ仕組みの欠け（悪）に帰る事実のまとめ。根拠の件数を併記する。
- **手戻りに数えないもの**: 計画された改善（品質チェックでの直し、段階的な仕上げ）は手戻りに入れず、別掲する。数えるのは、記録が「誤り」「食い違い」「取り消し」「作り直し」と明記したもの。判断に迷う件は、数えた側・数えなかった側の両方を章 3 に残す。（品質チェック2回目で足した）
- **前回の振り返りが無い**ときは、章 8 に「前回なし」と書く。
- **軸を決める時機**: 軸は材料の中身（出来事）を読む前に決める。ただし期間の確認（最古の日付、件数）のための一覧の確認（`git log` の日付など）は先に行ってよい。（3回目で足した）
- **字数・サイズの単位**: 文字数を既定とし、バイトは併記する。基準が別の単位なら、基準に合わせる。
- **サマリの字数**は、数えられる環境なら実測する。数えられなければ目測と明記する。
- **根拠が確認できないとき**（例: 参照先が別のリポジトリか書き直された履歴か区別できない）は、区別せず数えて【推測】と書き、章 7 に残す。
- **「影響の大きい順」の尺度**（軸をまたいで同じ順で比べる）: ① 再発するか（同じ原因が続く / 再現できる要因が明確）② 影響を受けた成果物・手順の数 ③ ee の手数。①が同じなら②、②が同じなら③。
- **優先度（施策）**: 高 = 影響が大きく（上の ①②）、手順書・文書の変更で防げる / 再現できる。中 = どちらか一方。低 = 影響が小さく、または人の判断が要る。
- **基準文書が無い成果物**: 既存の近い基準（重さの基準、品質チェックの記録など）を代用基準として章 2 か章 3 に宣言して照らす。基準が無いこと自体も悪い点の候補に数える（上の定義の「1個」に含めてよい）。
- **記録中の「ユーザー」**は、読者（依頼した本人）と読む。状態の語は、施策が承認前なら「叩き台」。
- 読んだ範囲が部分的なファイルは、章 1 の表に読んだ範囲を書く。

### 評価軸の設計（偏りを防ぐ。仕込み A の Must 4 と章 2）

- **軸は材料を見る前に決める。** 材料を読んでから軸を作ると、目立った出来事に軸が引きずられる（元の分析で、悪い点に寄った原因の1つ）。
- 軸の候補（既定。依頼で差し替える）: ① 手戻り・やり直し ② 判断の速さと質 ③ 分担（人と AI の境界、基準文書の有無）④ 再現性（次も同じにできるか）⑤ 成果物の出来（基準文書の検証項目に照らす）⑥ 記録の残り方。この中から3〜5個を選び、選ばなかった軸と理由を章 2 に書く。
- **各軸に「良いの条件」と「悪いの条件」を、同じ粒度で先に書く。** 片方だけ書けない軸は、測れない軸として外すか、限界に書く。
- **全軸を両面で探す。** 良い点・悪い点の上位3個は、探した結果から選ぶ。軸ごとの探索の件数を章 4 に残す。
- **偏りの確認**: 選んだ3+3個が1つの軸に集中したら、章 9 に書く（軸の設計の見直しか、実際に偏っているかを区別する）。
- 軸の追加は材料を読んだ後でもよいが、「後から足した」と章 2 に明記する。

## 業務の対象のときの扱い（`areas/` `projects/` の進め方・成果物）

- 業務の中身（顧客、案件、固有名、数値）は workbase に置かない。振り返りの結果は、**一般化した型**（仕組みの欠け、再現できる要因）だけを workbase に持ってくる。
- 置き場: 業務の振り返りは作業側の `docs/`（非公開）。部屋の Project では `ai/out/<成果物名>/retrospective.md`（マスク後の語で書く）。公開してよいもの（kit の運用など）は `topics/kit-growth/records/`。
- 成果物の出来を見るときは、基準文書（[[change-method]]）の検証項目に照らす。基準文書が無い成果物は、「基準が無い」こと自体を悪い点として数える。
- AI が成果物の中身を見られないときは、人が見た結果を、マスク後の語で記録として渡す。

## Gotchas

- 期間の宣言と、実際の材料の範囲が違うことがある（品質チェックでは、期間 10-06〜10-17 に対し git は 10-16 以降）。仕込みで最古の日付を先に確かめ、無い期間は「見えない範囲」にする。
- 参照先（ハッシュなど）が、別のリポジトリのものか、書き直された履歴のものか区別できないことがある。区別せず数えて【推測】と書く。
- 「ユーザー」「手戻り」「1件」「1個」は、定義が無いと実行者ごとに割れる。定義を章 2 と章 3 に書く。

## Open Questions

- 業務の対象（題材 B）での実行。AI から材料が見えないとき、人が渡す記録の型。
- 評価軸の選び方の指針（実行ごとに「分担」「判断」が出入りした）。
- 各最大3個が、少なすぎ・多すぎにならないか。
- 前回の施策が効いたかを確かめる手順（今回は前回が無く、未検証）。
- 手戻りの数え方（記録が「誤り」などと明記したものだけ）が、AI の見落としを生まないか。
