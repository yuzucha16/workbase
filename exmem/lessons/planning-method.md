# 計画のやり方: 6R で要求を整理し、憲章・成果物 WBS・マイルストーンで目的とゴールを共有する

## Purpose

ユーザーと AI が、作業の前に目的とゴールを共有する型。手段の目的化を防ぐ（憲章の役目）。`methods.md` の「計画」の区分（計画1）の背景と注意点。手順と欄の定義は `workflow-kit/start-plan.md`、呼び出しは `start 計画`。作り方は [[method-creation]] に従った。試験運用で、**Must だけ守る**。

## Principles

- 流れは 6R（要求の整理）→ 憲章（定義）→ 成果物 WBS → マイルストーン。6R で止めてよい（小さな再開では6Rだけ）。
- 単位は PARA の Project 1つ。期限付き。期間の上限は4週（ユーザーの決定）。長い Project の分割は未決。
- 成果物（名詞）で分解する。親は子の足し算で、モレもダブりも無い（100%ルール）。
- 資料から言えることと推測を区別する（〔資料〕〔推測〕）。知らないことは推測で埋めず、聞く。
- 毎回出る迷い（予算、体制、稼働日、バッファ）は、欄にせず既定値にする（[[method-creation]] の 17）。
- 実務の題材の中身は workbase に入れない。AI が `ai/work/` で下書きし、ユーザーが承認したものを人が Project の `ai/in/` に置く。
- WBS の第2層は、工程（要件・設計・検証）でなく、成果物の種類（利用者が受け取るものの塊）で分ける。工程はマイルストーンが持つ。理由: 名詞で書いても工程で分けると、各工程の中間記録が葉になり、実ファイルとずれる。
- 中間の記録は、後工程か利用者が入力として読むなら葉にする。読み手のいない本当の中間物（テスト、作業用スクリプト、途中のメモ）だけを、親の葉の説明に含める。判定は「後で誰かがこのファイルを読むか」。理由: 中間の記録を全部落とすと、後工程の入力が WBS から抜ける。
- 計画の問題意識は、依頼に含まれる手段でなく、論点で書く。理由: 手段のまま設計すると、ほかの選択肢が見えなくなる（例: 「2系統にしたい」は手段で、論点は「読者の違う1つの情報の管理」だった。[[reference-doc-types]]）。
- 6R のスコープの下に、変更先のファイルの洗い出しを置く（触るファイルと根拠。参照を検索して足す）。理由: ファイル構成を想像して葉を作ると、実行で構成が決まったときに合わなくなる。

## Decisions

- **マイルストーンの上限3つは「日付を持つ節目」にだけ数える**(ユーザーの決定、2026-10-21)。AI だけで進む区間は、日付でなくゲート(順序と承認点)で置き、数えない。束ねたときは理由を計画に1行残す。
- **小さな題材の規模は、変更先のファイル数で測り、葉の数をそれに合わせる**（ユーザーの決定、2026-10-21）。トークン・コスト可視化の試行は、葉13に対して実際のファイルが4つだった。却下案: なし（欄の削除はしていない。許可の形で足した）。
- **題材の計画の置き場**(ユーザーの仮決め 〜2026-10-28、2026-10-21): workbase の題材は `topics/<名前>/records/`、works の題材は Area 配下。`kit-growth/records/` は測ったことだけ。
- **stock-modes の所見6件を `start-plan.md` に反映した**(ユーザーの承認、2026-10-21): 変更先の洗い出し、裏づけの方法と時期、前提の表の書式、出典、完了時期のバッファ、見る単位は測る道具だけ。

- **試験運用で `workflow-kit/` に取り込んだ**（2026-10-20 にユーザーが 3 層で正式化、2026-10-20 に実装）。見直しの条件と戻し方: PC1 での品質チェック3回の結果で見直す。使われなければ、`start-plan.md` と `methods.md` の区分を削除して戻す（履歴は git）。
- **6R は 3 層に乗せない**（ユーザーの決定、2026-10-19）。
- 後続の課題ログは未作成。

## Facts

- 出どころは書籍の図表のキャプチャと、4題材（すべてリポジトリ自身の改善）+ 1題材（トークン・コスト可視化。kit 以外）の試行。**本の欄名は図表の読み取りで、本文は未読**。図表は写さず、欄の名前と自分たちの言葉の要約だけを書く。
- 試行で迷いが重なった点（4題材）: 測り方の指標が元の要求に無い（3/3）、戦略にあたる上位が未確認（4/4）、リーダー兼任が仮（4/4）、課題ログの置き先が揺れた（4/4）、日付が推測（4/4）。
- 節目に上限3つを置くと、早く終わる直しを遅い節目に束ねる歪みが出た。2週・4週の上限は使っていない。
- 3題材（ツール開発、手順書の変更、会議録の知識化）の計画で、WBS の葉は実際のファイル数より多かった（確認: 2026-10-21、根拠: 各題材の WBS と成果物のファイルの突き合わせ）。
- 品質チェック1回目の題材は1週間で、2週・4週の上限は検証できなかった（確認: 2026-10-21、根拠: 計画の期間が 10-21〜10-28）。
- トークン・コスト可視化の試行（kit 以外、1週間、見本なし）: 実行は1セッションで終わり、日数の見積もりは桁で外れた。憲章の体制の欄と WBS の葉の多くが実態と合わなかった。6R の「裏づけ（未確認。最初に確かめる）」の欄がいちばん役に立った。
- 測ったこと: `topics/kit-growth/records/planning-method-record.md`。試行の出力: 題材ごとのトピックの `records/`（`usage-viz` `stock-modes` `private-knowledge` は 2026-10-21 に閉じて削除、履歴は git）。

## Gotchas

- 状況: 最初の版で、6R の欄名が文書から読めず仮置きにし、予算・バッファ・体制を欄に入れた
  - 原因: 欄名が記録に無く、既定値と欄の区別も決まっていなかった
  - 解決: 欄名を記録に追記し、既定値は欄にしない骨子に直した

## Open Questions

- 2週・4週の上限(5・9)を使っていない。日付の並びが題材によらず同じで、見本の写しの疑いがある。品質チェック1回目(`private-knowledge`)は1週間の題材で、検証できなかった。2週間の題材で確かめる。
- WBS の葉と実際のファイル数がずれる原因の仮説: 第2層が工程で分かれている、葉に中間の記録(定義書、確認メモ)が入る、変更先を先に洗い出さない。「変更先の洗い出し」は 2026-10-21 に入れた。残り2点は 2026-10-21 に反映した(第2層は成果物の種類で分ける。中間の記録は、後工程または利用者が読むなら葉、読み手のいない本当の中間物だけ親に含める。ユーザーの決定)。効果は次の題材で測る。
- 試行の実行後のフィードバック（用語の定義、対象外の見直し条件、出力の置き場、承認が要る変更先、WBS の変更の記録、動作確認の欄。省く候補は1人の題材の体制、状況、日数の予算）は、2026-10-20 にユーザーの指示で `start-plan.md` に反映した（足す候補は欄に足し、省く候補は「省いてよい」「まとめてよい」の許可にした。欄の削除はしていない）。反映後の効果は品質チェックで見る。
- 振り返り（改善4）への入力にするか（直下 `docs/log.md` の Open Questions。保留 〜2026-11-11）。
