# 調査のやり方1: 問いを構造化し、読者を決めて、一次情報から事実と所感を分けてまとめる

## Purpose

「ある主題を調べて、読者が使える形の Markdown にまとめる」ときの型。解決（[[problem-solving-analogy]]）・改善（[[improvement-quantified-options]]）・変更（[[change-method]]）の延長で、調べて知るやり方。要点の表は `workflow-kit/methods.md` の「調査」、呼び出しは `start 調査`（`start-hook.md` の「引数つきモード」）。出どころは、Claude スキルの調査（2026-10-16）が、ユーザーの言う「ほぼ完璧」の出来になった事例の振り返り。1事例からの仮説で、使いながら Must を増減する。

## Principles

- 2つのブロックに分ける。**調査のやり方 = 事前の仕込み（ブロックA）+ 調査プロセス（ブロックB）**。変更のやり方（[[change-method]]）と同じ構造。理由: 出来の大半は、調べ始める前に揃っていた前提（問い・読者・品質条件）で決まっていた。
- **構造化と想定読者が要点**（ユーザー、2026-10-16）。問いを章立てに1対1で対応させ、読者を先に決める。
- 想定読者の既定は依頼した本人。読者が変わるとき（他の人・組織に渡す）は、業務の `research` type（`open-hook.md`）として扱う。読者が変わると、章立ての深さ、専門用語、機密の扱いが変わる。
- 事実・推測・第三者の意見を、見た目で分ける（「筆者の見立て」「【推測】」）。一次情報と二次情報を、出典の並びで分ける。読者の流儀（仮説の無条件の肯定を避ける。[[user-manual]]）を、想定読者の一部として持つ。
- 厳格に定義しすぎない。Must（欠けたら直す）と Want（あれば良い）に分けて小さく始め、`review` で見直す（[[change-method]] と同じ条件）。

## Decisions

- **Must は、仕込みが3つ、調査プロセスが6つ**（2026-10-16。ユーザーの依頼を受けた AI の案。ユーザーが品質チェックの後に承認して main に反映）
  - 仕込み: 構造化した問い（章立てと1対1）、想定読者、品質条件（一次情報を優先、出典に日付と URL（日付が無い資料は取得日）、推測と未確認を明記）。Want: 具体例の要否と条件（指標・対象の種類・件数）を最初に決める、類似ワードの候補（依頼者が挙げるもの）、結論の用途、出力先と形式。
  - プロセス: 題材に一次情報があるかの確認、問いごとに調べて出典を付ける（事実を述べる各問いに一次の出典を1件以上。無ければ「一次情報なし」と書く。筆者の見立ての部分は対象外）、事実と所感の分離、一次と二次の分離、確認できなかった点を末尾に書く、成果物の配置と記録。Want: 変わる値の取得日と手段、範囲を絞った基準の明記、章を足すときの番号と参照の点検。
  - 見直しの条件: 3回の `review` の後（`hook-matrix.md` の「review の点検」7）。
- **確定版の置き場は `guides/explain/<主題>.md`**（2026-10-16、ユーザーが選択。比較した候補: `research/` の新設、`exmem/lessons/`、`topics/`、repo に置かない）
  - 場面ごと: 作業中の下書きはプロジェクトの `notes/<主題>/日付-名前.md`（今のまま）。確定・公開してよい・読者が本人 → `guides/explain/<主題>.md`。業務・読者が他の人・機密を含む → 部屋の `ai/out/report.md`（`research` type。repo に入れない）。
  - 確定版の frontmatter は `type: explain`、`title`、`tags`、`checked`（調査日）。1主題1ファイルで、再調査は上書き（版は git）。ファイル名は kebab-case で、`exmem/lessons/` と重ならない名前。索引 `guides-index.md` に足す。
  - 案（ユーザー未確認）: `checked` から6か月を過ぎたら、`review` で再調査か削除を1件挙げる。AI への蒸留（`exmem/lessons/`）は、判断・原則・落とし穴が出たときだけ。
  - 根拠: 新しいディレクトリが要らず、既存の索引と規則に載る。新設は足す経路と畳む経路の非対称を悪化させる（[[accretion-without-pruning]]）。調査が3件以上たまったら、新設を見直す。
- **仕込みとプロセスの境目**（2026-10-16）。ユーザーの整理は「推測1と2が仕込み、3以降がプロセス」。AI の案は、4（読者の流儀が記憶にあった）を**想定読者**として仕込みに移す。3（題材に一次情報が揃っていた）は題材の性質で、仕込みでは変えられないため、プロセスの冒頭の確認にする。5（改善点が段階的に足された）はプロセス。
  - 仕込み: 1 依頼の型（問いと章立て）、2 品質条件の指示、4 想定読者の流儀。プロセス: 3 一次情報の有無の確認、5 段階的に足す。
  - 却下案: 読者を調査プロセスの中で決める。理由: 読者が決まらないと章立ての深さが決まらない。

## Facts

- 問いのひな形（主題を `<主題>` に置き換えて使う。ユーザーの入力そのまま。順番は入力どおり）:
  1. `<主題>` が生まれた経緯
  2. `<主題>` が解決したかった問題
  3. `<主題>` が与えた影響
  4. `<主題>` の現在の役割
  5. `<主題>` を3行で表すと？
  6. `<主題>` の今後の展望
  7. `<主題>` のリスクと懸念点
  8. `<主題>` の具体例
  9. `<主題>` の類似ワードと関連ワード
- 出力の章立てのひな形（同じ事例の最終形。**問いの順と違う**: 3行要約は冒頭に、具体例は現在の役割の直後に置いた）。章は問いに1対1で対応し（例外: 0 の3行は問い5。8 の使い方は、題材が道具・手法のときに足す章）、全部採用が既定で、省く・足すのは仕込みで決める。各章に含めるものを添える（品質のぶれを抑えるため。2026-10-16 の1回目の比較で足した）:
  0. 3行で表すと: 何であるか、どう動くか、使う上の注意の3行
  1. 生まれた経緯: 日付・出来事・出典の表。発表だけでなく、他社の採用、標準化、批判や調査の公開など第三者の動きも入れる（二次は二次と明記）
  2. 解決したかった問題: 公式が述べた課題。数値（費用、時間、量）があれば添える
  3. 与えた影響: 事実（標準化、採用、製品への取り込み）と、第三者の評価（肯定と懸念の両方を、各1件以上探す。見つからなければ「見つからなかった」と書き、「集めていない」とは書かない。意見と明記）を分ける
  4. 現在の役割: 位置づけと、製品・場面ごとの違い（表）。公式資料どうしの食い違いは、寄せずに書く
  5. 具体例: 条件（指標、対象の種類、件数。例: GitHub の星の数、スキルを主体とするリポジトリ、上位5）は仕込みで決めて宣言し、それに従う。定番・著名なもの、人気の上位5（指標、取得日、取得手段つき）、ジャンル別の代表例（5ジャンル以上。ジャンルは題材で決める）。候補は、複数の検索（トピック、名前、説明。第三者のランキングは、使えるときだけ足す）の和集合から集め、対象の種類（スキルを主体とするもの。アプリ、エージェント本体、単なる目録は除く）だけ残して、指標の順に5件とする（トピックの検索だけだと、自己申告のため取りこぼし、種類の違うものが上位に混ざる）。指標は一次の手段（検索 API、GitHub 連携のツール、`gh` の REST）で取り、作れなければ第三者のランキングで補って「第三者・取得日」と明記する。WebFetch で API を取るのは最後の手段で、「要約経由」と注記する。5件に満たないときは、理由を書く。ジャンル別は、同じ候補から、ジャンルごとに指標が高いものを選ぶ（候補の外は見ていない、という限界を書く）。選び方の基準と、除いたものを書く。中身を読んでいないものは、そう書く
  6. 今後の展望: 公式が述べたことと、筆者の見立て【推測】（根拠つき）を分ける
  7. リスクと懸念点: 安全面・運用面・標準化（普及）面の3観点で、項目を立てる。公式の警告（一次）と実態の調査（第三者）を分ける
  8. 使い方（題材が道具・手法のときだけ。短く）: 作り方、置き場、呼ばれ方
  9. 類似ワードと関連ワード: 「同じものの別名」と「似て非なるもの」の2表。周辺の機能は網羅する（公式に比較ページがあれば、その表を軸にする）。各行に、何か・いつ働くか・主題との違い
  - 末尾: 確認できなかった点・注意、出典。出典は一次と二次の2つの見出しに分け、本文は番号で参照する（番号は一次・二次を通した連番で、欠番を作らない）
- 事例の良かった点（ユーザーの評価、2026-10-16）: 冒頭の3行、経緯の表、箇条書き、「筆者の見立て」で事実と所感を分けた、出典がある、一次と二次を分けた。改善点は具体例の不足（後から足した）。
- 事例の背景（AI の推測。内部は確認できない）: 依頼が章立てになる5項目だった／一次情報優先・日付と URL・未確認の明記の条件が付いていた／題材に公式の一次情報が揃っていた／読者の流儀が記憶にあった／改善点が段階的に出た。

## Gotchas

- 具体例は、依頼に無いと最初の版から抜ける。さらに、「具体例」とだけ書くと、公式の例だけで終わる（人気の上位や、ジャンル別が出ない）。章立てのひな形に、含めるものを書く。
- 章を後から足すと、章番号と本文中の参照（「第7章」など）がずれる。足すたびに番号と参照を点検する。
- 変わる値（GitHub の星の数など）は、取得日と手段を書く。トピックの検索は自己申告のタグに頼るので、取りこぼす。上位の中に、対象の種類でないもの（ツール本体、規則集）が混ざる。除いた基準を、本文に書く。
- 一次と二次の線引き: 一次は主題の提供元（公式の発表、ドキュメント、仕様、リポジトリ、API の原データ）、二次はそれ以外（報道、解説、調査勤務先、ランキング）。要約を通して取った一次の資料は、一次に置いて「要約経由」と注記する。日付の無い資料は、取得日を書く。
- 数値が食い違うとき（ページの要約と API）は、API の値を正とし、要約の値は注記する。
- 打ち切り: 各章に含めるものを満たし、新しい一次情報が出なくなったら止める。満たせない章は「確認できなかった点」に書く。分量の目安は置かない。
- 環境によって使える手段が違う。`gh` の検索 API や GraphQL が使えないことがある（2026-10-16 の比較で、別の会話は人気順の表を作れなかった）。使える手段（GitHub 連携のツール、リポジトリ単位の REST）を順に試し、全部だめなら理由と代替を書く。
- WebFetch は小さなモデルの要約を返すので、原文の引用の確認にならない。引用や数値を原文で確かめられなければ、「確認できなかった点」に書く。
- 第三者のランキングや紹介記事の数値は、一次（API や公式ページ）で取り直せるなら、取り直す。取り直せなければ「第三者による」と書く。
- 一次情報同士の記述が食い違うことがある（例: 製品ごとのドキュメントで共有範囲の説明が違う）。どちらかに寄せず、食い違いを書く。

## Open Questions

- 読者が変わる業務の調査（`research` type）の章立てと、機密の扱い。最初の業務の利用の後に決める。
- 調べた値が古くなったときの更新（再実行の型）。今は取得日を書くだけ。
- 調査が3件以上たまったときの `research/` 新設の要否。長い成果物（約29KB）を、`guides/explain/` にそのまま置くか、分けるか。
- 引用の扱い（長さ、著作権）。今は短い引用と要約だけ。
