# 相談の型（論点の一覧 → 叩き台 → 質問 → 仮決めの締め）

## 冒頭
トピックや Project で、方針・設計・取り決めを相談するときの進め方。型を使わない相談は、議論がブレやすかった（ユーザー、2026-10-29）。確認状況: 数回の実例で試行中（仮）。呼び名（合言葉）は持たず、この `triggers:` で起動する。

## Principles

### 型（ユーザーの決定、2026-10-21）
1. 現状の事実を調べて、論点を一覧にする。
2. 一覧を叩き台にして、論点を潰していく。
3. 確認したい事実や前提があれば、ユーザーに聞く。
- 締め: 論点を解消して仮決めし、変更範囲の確定と事実関係との整合確認をして、`review 消化` の 3 段に乗せる。

### AI が足したケア（叩き台。ユーザー未確認）
1. 事実は一次情報（コード、決定、手順書）で確かめ、「確認済み」と「〔推測〕」を分け、出どころを添える。
2. 論点は表にし、読みの選択肢と、推奨の叩き台（理由つき。決定ではないと明記）を並べる。
3. 質問は 1 回に 2〜3 問まで。選択式で、ユーザーしか知らないことに絞る。
4. 前に出した叩き台が事実と食い違ったら、先に訂正する。ユーザーが「事実が壊れているかも」と言った箇所は、実際に確認して記録する。
5. 回答のたびに、ユーザーの発言を原文で根拠にして `docs/decisions.md` に仮決めを記録し、`log.md` を直す。取り下げた案は消さず、取り消し線で残す。
6. 変更範囲は表（場所・内容・変えないもの）にして、確認済みの事実と未確認（実機など）を分ける。
7. 既存の取り決めとぶつかるときは、どこまでが見直しかを示す。仕組みの変更は `review 消化` の後に実装し、それまで着手しない。
8. 公開リポジトリなので、実名・機密を書かない。main への push は毎回、条件（公開範囲、fast-forward、機密語の検索）を確かめる（`push-rules.md` を読むのは push の直前）。
9. 軽い相談（論点が 1〜2 個、仕組みの変更を含まない）は、表と締めを省き、事実・叩き台・質問だけにしてよい（ユーザー了承、2026-10-21）。

### 読み込みの費用（測定、2026-10-29）
型の有無で、事実集めの量はほぼ同じ。差は、記録と push のために読む文書の分（規則書、`decisions.md`、`log.md`）だった。読んだ文書は後の応答が毎回読み直すので、早く読むほど高くつく。
- 型の本文は、このノートの 1 回で済ませる（`decisions.md` を検索して探さない）。
- 規則書（`commit-push-rules.md`、`push-rules.md`）は、会話の早い所でなく、コミット・push の直前に読む（採用: 2026-10-30 ユーザー）。

## Decisions
- 2026-10-21: トピックで相談するときの型として仮決め（ユーザー）。
- 2026-10-28: 5 回目の判断で「残す」（トリガー方式、仮のまま）。
- 2026-10-29: 型の有無で読み込み量に差が小さいと測れた。ユーザー「トークン的に差がないのであれば今後も使いたい」。継続（仮）。本文を `decisions.md` からこのノートへ移した。格上げ（`methods.md` と `review 消化` の 3 段）は未決。
- 2026-10-29: 合言葉と `triggers:` の相談（NA 10）で型を使った。型は `triggers:` 起動のまま（呼ぶタイミングを人が決めたい手順ではないため。`decisions.md` の同日の項）。
- 2026-10-30: 規則書をコミット・push の直前に読む案を採用（ユーザー「採用して書き込んでください」）。効果は次の相談の型の会話で `decompose_session.py --steps --upto N` を使い、規則書を読んだ応答の番号で確かめる。
- 決定の根拠と経緯の正本: `docs/decisions.md`（【汎用】【仮】トピックで相談するときの型）。
