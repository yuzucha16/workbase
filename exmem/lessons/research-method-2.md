# 調査のやり方2: 手順を調べ、前提と骨格を固定して、実行できる手順書にまとめる

## Purpose

技術的なインストールや導入、何かしらのルール・仕組み（OS、サービス、規程）に沿ってやることを、調べて「そのまま実行できる手順書」にまとめるときの型。調査のやり方1（[[research-method]]）は主題を調べて**説明**するのに対し、調査2は調べた結果を**実行できる手順**にする。呼び出しは `brief 調査`（`brief-hook.md` の「引数つきモード」）で、やり方を選ぶ1問で調査1と分かれる。要点の表は `workflow-kit/methods.md` の「調査」。

出どころは、SSH 鍵の導入の手順書（2026-10-17）。ユーザーが3回の指摘（使わない道具を除く、クイックスタートと章立て、チェックリストと参考ページ、打つ場所を1か所にする）で仮決めした版を基準にして、要因を型にした。**1事例からの仮説**で、使いながら Must を増減する。品質チェックの記録は [[research-method-2-record]]。作り方は [[method-creation]]。

## Principles

- 調査1と同じく、**A 事前の仕込み + B 調査と作成のプロセス**の2ブロック。要点は「前提の確定」「従うルール・仕組みの一次情報での確認」「骨格の固定」（ユーザーの定義、2026-10-17: 「手順を調べること。特に技術的なインストールや、ルール・仕組みに沿うこと」）。
- 手順書の出来の大半は、書き始める前に、前提（使う道具・使わない道具・動く環境）と骨格（章立て、各手順の型）が決まっているかで決まる。直しは、前提の食い違い（使わない道具が本編に入る）と、構造の弱さに集中した。
- 一次情報（公式のマニュアル・文書）で確認していないコマンドは、「未確認」と書く。試せる環境があれば試す。試すと、手順の落とし穴が見つかる（品質チェック3回目）。
- 厳格に定義しすぎない。Must（欠けたら直す）と Want（あれば良い）に分けて小さく始め、`review` で見直す。

## Decisions

- **Must は、仕込みが10、プロセスが9**（2026-10-17。AI の案。ユーザーが品質チェック3回の後に承認して main に反映）
  - **A 仕込み**: ① ゴール（完了の状態を3つ以内）② 環境の前提 ③ 使う道具・使わない道具（使わない道具は本編に出さない）④ コマンドを打つ場所（1か所で完結できるならそれを本編）⑤ 読者と分量 ⑥ 図の条件（描画先で描ける記法）⑦ 秘密情報はプレースホルダ ⑧ 日常の使い方と移行元 ⑨ 従うルール・仕組みと一次情報の候補 ⑩ 既定として置いたものの列挙。答えが依頼にあるものは聞かず、既定を置いて宣言する。
  - **B プロセス**: ① 既存の決定の確認 ② 手順を調べる（一次情報で、コマンド・オプション・前提・版を確認。出典の URL・版・取得日。確認できなければ「未確認」。選択肢があるときは一次情報の推奨を優先し、理由を1行）③ 骨格（下の章立て）④ 各手順を型どおりに（番号つき見出し → 目的 → コマンド → 確認）⑤ 図 ⑥ 確認できていない点 ⑦ 管理（バックアップ・失効・紛失・棚卸し。ゴールと衝突するときは、衝突を明記して案を2つまで）⑧ チェックリストと参考ページ（トラブル対応は各手順の「確認」の失敗を網羅）⑨ 配置と記録。
  - **Want**: 関連する既存の決定の反映（字面と読み解きを分ける）、試せる環境での実行、文字数の確認（5〜10分 = 本文約3,000〜6,000字）、付録（別の場所で打つ手順があるときだけ）、順序の理由。
  - 見直しの条件: 3回の `review` の後（`hook-matrix.md` の「review の点検」7）。
- **`brief 調査` は1つのまま、やり方を選ぶ1問を足す**（2026-10-17）。調査1と調査2は、同じ「調べてまとめる」で、仕込みの聞き方だけが違う。新しい `start` のモードは作らない（`brief-hook.md` を肥大させないため。理由: 基準の +20% を超えている）。選ぶ基準は、成果物が「説明」か「実行できる手順」か。
- **事例が SSH 鍵の1つだけ**なので、章立てと Must が他の導入（言語の環境、サービスの設定など）に合うかは未検証。

## Facts

- 章立てのひな形（章は固定。各手順は同じ型）:

| 章 | 内容 |
|---|---|
| 冒頭 | 版の行（改訂日、読む時間、対象）、プレースホルダの断り、コマンドの打ち場所の断り |
| 0 クイックスタート | 最短の手順を表に（#、やること、コマンド） |
| 1 ゴールと全体像 | 完了の状態を3つ以内。構成図（mermaid） |
| 2 前提 | 必要な環境・権限・事前準備。既定として置いたものは章 8 に |
| 3 手順 | `3.1`〜。目的 → コマンド → 確認。順序は 作る・使う → 日常の使い方 → 移行元を外す |
| 4 管理 | バックアップ、失効、紛失、棚卸し |
| 5 関連する既存の決定 | 方針・境界が手順のどこに効くか（参照つき）。無ければ省く |
| 6 トラブル対応 | 症状と見るところ（4〜6件） |
| 7 チェックリスト | 3グループ程度の `- [ ]` |
| 8 確認できていない点・環境差 | 未確認、既定として置いたもの、参考ページの選定、読み解き |
| 9 参考ページ | 一次と二次を分けた表（3〜6件。開いたものだけを確認済みとして載せる） |
| 付録 | 別の場所で打つ手順があるときだけ（確認用の1コマンドでもよい） |

- 事例の直し（ユーザーの指摘 → 型）: 使わない道具が本編にあった → A③。クイックスタートが無かった → 章 0。章 3 以降がのっぺり → `3.n` と型。チェックリストが無かった → 章 7。参考ページが無かった → 章 9。PowerShell と WSL が混在 → A④（打つ場所を決め、1か所で完結）。
- 品質チェック3回の要約（記録は [[research-method-2-record]]）: 15観点の○が 9/15 → 15/15 → 15/15。3回目に、一次情報8ページの確認と Linux での試行が働き、基準にない落とし穴を見つけた（設定ファイル込みで古い鍵の拒否を試すと、新しい鍵で入れてしまい確認にならない）。
- 基準と成果物の置き場: プロジェクトの共有フォルダ `notes/ssh-key-setup/`（基準）と `notes/procedure-method/`（叩き台、run1〜3、比較表）。repo には入れていない。

## Gotchas

- 仕込みに「日常の使い方」と「移行元」が無いと、手順書が「作って登録して終わり」になる。使い続ける操作と、古いものを外す手順まで書く。
- ゴールと管理が衝突することがある（「1か所」と「バックアップ」）。判断基準が無いと実行者が割れる。衝突を明記して案を出す。
- 参考ページは、開いていない URL を確認済みとして載せない。公式が1種類に偏ってよい（第三者は二次と明記）。
- 確認の手順が、確認になっていないことがある（設定ファイルが効いて、期待と違う鍵で入れてしまう）。試せるなら試して、確かめる。
- 既存の決定は、字面から言えることだけを表にし、そこからの展開は「読み解き」と明記する。

## Open Questions

- 他の事例（言語の環境、サービスの設定、組織の規程に沿う手順）での適合。最初の別事例で、章立てと Must を見直す。
- 実機（今回は Windows 11 + WSL2）での検証。品質チェックは Linux までで、手順書のコマンドは実機で試していない。
- 手順書の更新（版が上がったときの再確認）。今は取得日を書くだけ。
- 確定版の置き場。調査1は `guides/explain/` に置くが、手順書は `reference-doc-types` の手順書の置き場と重なる（[[reference-doc-types]]）。最初の確定のときに決める。
