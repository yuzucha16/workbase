# 「〇〇のやり方」の作り方: 2ブロックで型にし、新しい会話で3回確かめて、手順書に取り込む

## Purpose

`methods.md` の表にあるやり方（解決・改善・変更・調査）を新しく足すときの型。変更のやり方（[[change-method]]）と調査のやり方（[[research-method]]）を作った流れの共通点を、ユーザーの整理（2026-10-16）に AI の追加を足してまとめた。ユーザーが「〇〇のやり方を作る」と言ったら、この型を宣言してから始める。2事例からの仮説で、使いながら直す。

## Principles

- **ユーザー指定（確定）**
  1. 2ブロックからなる。**A 事前の仕込み + B プロセスそのもの**。
  2. 仕込みで、プロセスの前に決められることを決める。
  3. 品質チェックを**3回**実施する。
  4. 修正を手順書に取り込む。
- **AI の追加（叩き台。ユーザーは2026-10-17 に repo に置くことを承認。個々の項目は使いながら見直す）**
  5. 出どころは1事例。うまくいった事例の要因を振り返って型にする。1事例からの仮説と明記し、Must / Want で小さく始める。3回の `review` の後に増減を決める。
  6. 基準（正）を1つ決める。品質チェックはこれと比べる。
  7. 品質チェックは、新しい会話（サブエージェントなど、この会話の文脈を持たないもの）に、手順書だけを読ませて実行させる。基準は読ませない。手順書に無いことを補わせず、迷った点を報告させる。
  8. ブレの主因は、未指定の条件（指標、対象の種類、件数、置き場）。仕込みで決めて宣言する。曖昧な語（「具体例」）は、含めるものを書く。
  9. 直しは回ごとに分ける。同時に入れたときは、効果が分けられないと記録する。実行1回では、ブレが消えたとは言えない。
  10. 基準の側にも、実行結果の良い点を取り込む。
  11. 登録の作業（下の Facts）を漏らさない。登録は、既存のやり方・モードの書き方に合わせる（Facts の「登録の作業」）。
  12. AI の案は承認待ちと明記し、品質チェックの後にユーザーが承認する。承認の後に main へ反映する。
  13. **作り始めに、1問で確かめる**（ユーザーが2026-10-17に承認）: 何を調べる・作るやり方か、`methods.md` のどの区分の何番か。理由: 「やり方のやり方で作って」を AI が「手順書のやり方」と解釈して作り始めたが、後でユーザーが「調査2 = 手順を調べること」と定義した（名前と位置づけが後出しだった。原因はモバイル操作のミスで、依頼の言い間違いだった）。
  14. **反復はモバイル・クラウドの会話で行い、迷いが減ってから PC 環境へ移す**（2026-10-19、ユーザーが「非常に良かった」と評価）。理由: PC 環境は、反映のたびに承認と登録の作業が要り、直しの単価が高い。
  15. 試行の間の元データ（決定、比較表、迷った点）は、共有フォルダの notes に貯め、PC 環境に入れるのは骨子と決定だけにする。理由: 元データは量が多く、確定するまで揺れる。
  16. 出力（成果物）と作り方のメモを、別ファイルにする。理由: 本番でも、README や AGENTS に置く作り方と、出力の Markdown は別物で、混ぜると出力の見本を使い回せない。
  17. 別の会話に「作り方のメモと見本」から複数の題材を作らせ、「迷った点」の重なりを数えて、作り方か既定値に戻す。理由: 同じ迷いが毎回出るのは、作り方の欠けのサインで、題材ごとに聞くと手数が増える。毎回出る迷い（予算、体制、稼働日など）は、既定値にして、題材ごとには聞かない（聞く数が減り、題材どうしを横に並べて比べやすくなる）。
  18. 数の上限で粒度をそろえるときは、何を数えるかを先に決める。理由: 数え方が曖昧だと、上限を守るために成果物を束ねる歪みが出る。
  19. ブレが減ったことを、再現性の根拠にしない。題材と期間を変え、見本を見せない回を足して確かめる。理由: 型の効果と、見本への寄せや既定値の効果を分けられない。
- **AI 作業部屋の Project の型を、人が回す実使用で確かめる（2026-10-25、実測の会話から）**
  20. 実測は、1回の往復を「題材の依頼 → AI の質問 → 回答 → 成果物 → 手順書との照合 → 記録と修正」で固定する。理由: 照合する相手（手順書の該当箇所）が毎回決まり、何を直したかが追える。
  21. 観察点は、実行の前に表にする（質問したか、置き場、完了条件の形、検査の種類）。理由: 結果を見てから観点を選ぶと、都合の良い所だけ拾う。
  22. 聞き返しの有無を測りたい項目は、依頼文に書かない。理由: 書いた項目は AI が聞かないので、聞き返す動作が測れない。
  23. AI が質問に付ける「推奨」は、そのまま選ばず、手順書と照合してから選ぶ。理由: 推奨は AI が読んだ範囲から作られ、手順書と食い違うことがある。
  24. 食い違いは、1回目は記録だけにし、2回以上続いたら原因を調べる。理由: 1例では手順書の欠陥か偶然か分からず、直すと過剰になる。
  25. 原因は、AI に「読んだ手順書を読んだ順に挙げ、その時点の該当記述を原文で引用して」と聞いて切り分ける。理由: 読んでいない、読んで従っていない、手順書同士が矛盾している、で対策が違う。
  26. 最初に読まれる汎用の文書（部屋に渡す案内など）が、個別の型の規則と同じ語を一般論で使うときは、適用条件を書く。理由: 汎用の文書の一般論が、後から読む個別の規則より優先されやすい。
  27. AI が自分の検査を作ったら、壊した入力で FAIL になることを確かめさせる。理由: 通った件数だけでは、検査が食い違いを検出できるか分からない。
  28. AI が実装に合わせてテストを緩めたときは、変更前後の基準と理由、要求の文言との照合を報告に書かせる。理由: 緩めた結果が、不具合の隠蔽か、要求の曖昧さかを判別できる。

## Decisions

- **試行の元ファイルはクラウドの共有フォルダに残し、PC 環境に運ぶ骨子と決定は、リポジトリの `topics/kit-growth/records/` に置く**（2026-10-19）。根拠: 共有フォルダは PC 環境から読めないため、PC 側で使う内容は、リポジトリに無いと届かない。却下案: 下書きも決定も共有フォルダだけに置く（PC 環境から見えず、移行の入力にならない）。
- **計画の題材（憲章・WBS・マイルストーン）の出力と、作り方のメモを、別ファイルにする**（2026-10-19）。根拠: ユーザーの指示。本番で README や AGENTS に置く作り方と、出力の Markdown が別になるのと同じ。却下案: 1枚のファイルに作り方と出力を混ぜる（最初の試行はそうだったが、他の題材に見本として渡しにくい）。
- **回数は基本3回**（ユーザー指定）。調査のやり方では4回やった（3回目の直しの確認のため）。ブレが残るときは追加してよい。上限は決めない。見直しの条件: 次のやり方を作ったとき、3回で足りたか。
- **1 Project で通す実測を、型の追記より先に行う**（2026-10-25）。根拠: 成果物ごとに別 Project で受け渡す前提（独立の検証者が対象を直さずに返す）が、1 Project では成り立たないため、型を測らずに書くと前提を誤る。ユーザー「実測ですね」。却下案: 先に1 Project 用の型を書く（測っていない前提で書くことになる）。
- **やり方ごとの「要点」を1〜2語で決める**（2事例から）。変更=基準文書、調査=構造化と想定読者。要点が、仕込みの Must の中心になる。
- **既存の解決・改善のやり方は、この型の前にできた。** 品質チェックは未実施。見直すときに、この型で確かめる。

- **品質チェックの手順**
  1. 基準を決める（人が磨いた成果物、または期待する出力）。
  2. 新しい会話に、手順書のパスと、インタビューの答え（ユーザーの入力に相当）を渡す。基準と、過去の成果物は読ませない。実行して、成果物と「迷った点・曖昧だった点」を返させる。
  3. 基準と比べる。観点を決め（章立て、出典、事実と所感の分離など。基準から取る）、○△× の表にする。
  4. 差ごとに、原因を手順書の欠け・曖昧さに帰して、手順書を直す。実行者が迷った点も直す。
  5. 直したら、次の会話で2〜4を繰り返す。
  6. 比較表と各回の直しを、改善記録に残す（`topics/kit-growth/records/<名前>-record.md`。書式と索引は [[kit-records-index]]）。大きい成果物は repo に入れず、置き場だけを記録に書く。実運用の振り返りも同じ記録に足す。
- **登録は、既存のやり方・モードに合わせる**（2026-10-17、調査のやり方2を足したときにユーザーが求めた）。同じ種類の `brief` のモード（例: `brief 調査`）が既にあれば、新しいモードを作らず、そのモードの中の「やり方を選ぶ1問」に足す（`brief-hook.md` は基準の +20% を超えているので、増やさない）。`methods.md` の表の列（選ぶ基準・骨子・ノート）、Must / Want の区分、ノート名（`<名前>-method`、続きは `-2`）、記録の置き場（`records/`）を、先にあるやり方に揃える。揃えられない点は、`decisions.md` に理由を書く。
- **登録の作業**（`hook-common.md` の「フックを足す・消すとき」を参照）: `methods.md` の表と、必要なら `brief` のモード（`brief-hook.md` の「引数つきモード」）、`hooks.md` の行、`hook-matrix.md` の「review の点検」7、`exmem-index.md`、このノートの事例の表、`topics/kit-growth/docs/decisions.md`。`brief-hook.md` は基準の +20% を超えないようにする（超えるなら畳む）。
- **計画のやり方の試行（モバイル・クラウド、2026-10-19、根拠: 共有フォルダの `notes/planning-method/` にある論点の記録と、4題材の出力・作り方のメモ。確認: 2026-10-19）**
  - 4題材の出力と作り方のメモで、迷った点が重なった: 測り方の指標が元の要求に無い（3/3）、戦略にあたる上位が未確認（4/4）、リーダー兼任が仮（4/4）、課題ログの置き先が揺れた（4/4）、日付が推測（4/4）。
  - 出力に載せる項目（対象外・前提・リスク・未決）が、1題材だけ他の3つと違った。
  - 節目の数に上限3つを置いたところ、早く終わる直しを遅い節目に束ねた題材があった。
  - 4題材とも1週間で、すべてリポジトリ自身の改善の題材だった。2週・4週の上限は、まだ使っていない。
  - 共有フォルダ（モバイル・クラウド）の notes は、PC 環境から見えない（根拠: ユーザーの発言）。
- **部屋の Project の型の実測（2026-10-25。根拠: 実測の会話。会話で見た範囲で、部屋の手順書の実物とは未照合）**
  - 依頼に書かなかった骨子と図の要否は、AI が最初の質問で聞いた。置き場と対象環境は、依頼に書いたので聞かれなかった（根拠: 文書だけの成果物の実測での AI の質問一覧）。
  - 3 本の実測で、置き場の取り違えが 5 回あった（`work/`、`deliverable/` 3 回、README、レビュー版の置き場）。部屋の AI に聞くと、案内文書の「人が読む最終版は `deliverable/` の下」が個別の型の規則と矛盾していて、正本の構造書は読まれていなかった（根拠: 部屋の AI の回答と、案内文書の該当行）。
  - 独立した検証の Project（対象を読み取り専用で扱う）が、作った側の不具合 3 件と、仕様の曖昧さ 2 件を見つけた（根拠: 検証の `report.md`）。
  - 単一の成果物を 3 Project（環境構築、テストだけ、文書だけ）に連鎖させる実測は、成果物の受け渡し（人が次の入力に置く）の検証も兼ねた（根拠: 3 Project の実測）。
- 事例での直しの例（調査のやり方）: 「具体例」とだけ書くと公式の例で終わった → 人気の上位5とジャンル別を書いた。人気順の取り方で結果が割れた → 指標・対象の種類・件数を仕込みで言い切った。出典番号の欠番 → 連番にした。

## Gotchas

- 実行環境の違い（道具の有無）で結果が変わる。手順書に代替を書く（調査: GitHub の検索 API が使えない環境があった）。
- 実行者は、手順書を読んで補ってしまう。「書いていないことを補わない」と明示する。
- 基準は1つの出力にすぎない。基準と違って良い出力は、基準に取り込む（上の10）。
- 比較の観点を、実行の後で足すと、基準に引きずられる。観点は基準から取り、先に決める。
- 状況: 計画のやり方の最初の試行で、位置付け・作り方・出力を1枚のファイルに書いた
  - 原因: 型が固まる前で、見本と作り方の境目が決まっていなかった
  - 解決: 出力と作り方のメモに分け、元のファイルは両方を指す入り口だけにした
- 状況: 試行の下書きを共有フォルダにだけ置いたまま、PC 環境への取り込みの話を進めようとした
  - 原因: 共有フォルダは PC 環境から読めない
  - 解決: 骨子と決定をリポジトリに書いて push した
- 状況: 部屋の AI の質問の推奨どおりに選ぶと、成果物の置き場が型と食い違った
  - 原因: 部屋に渡す案内の一般論が、型の規則と矛盾していた。型の正本は読まれていなかった
  - 解決: 案内の記述に適用条件を書き、立ち上げの手順に正本を読む指示を足した

- 変更のやり方の品質チェック。実施するか、実際の変更で代える（[[change-method]] の Next Actions）か。
- この進め方があれば、`topics/` は不要になり得るか（ユーザーの見立て。未決）。`topics/AGENTS.md` には「共有フォルダは議論の下書きの置き場で、確定したらトピックへ移す」とあり、今回は移し先をトピックにしなかったため、規則との食い違いがある。
- 提案: 上の 14〜19 の反復の進め方を、品質チェックの手順の前の段として足すか（AI の提案。未承認。14〜19 はメモの原則を写したもので、ユーザーの承認は 14 の評価のみ）。
- 提案: 実測のループの一部（題材の作成、質問への回答の照合、成果物の機械検査）を、AI がサブエージェントで回せるか（AI の提案。未承認）。部屋の読み込み条件（案内文書、マスク、実機）と同じにならず、「読んだ範囲」に起因する取り違えは再現しない可能性がある。
- 1 Project で環境構築・テスト・文書を通したとき、取り違えが再発しないか、検証が自己向けになって弱くならないか。
